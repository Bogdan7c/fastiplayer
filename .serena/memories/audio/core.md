# Audio Core / Concrete Audio

- Concrete `crates/audio` owns CPAL output, concrete `AudioClock`, Symphonia/Opus decoder integration, and adapters to neutral `audio-core` traits.
- S35 added neutral `audio-core::tempo` boundary for future tempo/timestretch adapters: `AudioTempoProcessor`, `AudioTempoProcessorFactory`, `AudioTempoProcessorHandle = Box<dyn AudioTempoProcessor + Send>`, typed PCM format/frame count/span, `AudioTempoRatio`, `AudioTempoSegment{Id}`, `AudioTempoProcessReport`, `AudioTempoOutputProgressMapping`, and `AudioTempoProcessorError`. Reports must keep decoded media input and stretched output distinct: consumed decoded media frames/duration, produced stretched output frames/duration, pending/buffered output inside the processor, processor latency, effective ratio, and segment id. `PlayerAudioOutput::write_samples` device tail is not processor latency and must stay owned by output/clock accounting.
- `AudioTempoProcessor::process_decoded_media`, `flush`, and `reset` are neutral contract methods only; S35 did not wire tempo into `player-core` audio runtime or audio clock mapping. Direct concrete `timestretch` dependencies remain forbidden in `audio-core` and `player-core` by `scripts/check-refactor-guardrails.py`.
- S36 added isolated workspace crate `audio-timestretch` as the concrete `timestretch 0.4.0` prototype/adapter gate, with crate-local `timestretch = "0.4"` and no runtime integration. It owns `timestretch::StreamProcessor` state, converts project `AudioTempoRatio` by inversion (`2.0x` playback -> `0.5` backend stretch; `0.5x` -> `2.0`), exposes caller-preallocated `process_decoded_media_into`, reports backend latency/capacity through neutral frame counts, and keeps `audio-core`/`player-core` free of concrete `timestretch`. S36 verified `process_into`, `set_stretch_ratio`, `capacities`, `latency_secs`, dynamic ratio smoothing, boundary rates `0.25x`/`4.0x`, no hot-path allocations after warmup, typed `BufferOverflow`, and real WAV sanity. For realtime profile use `QualityMode::LowLatency` plus FFT 1024 / hop 256; in `timestretch 0.4.0` the enum alone does not reduce FFT/hop, and the S36 test keeps latency <= 40 ms. Known limitation: Context7/README mention fixed-buffer `process_interleaved_into`/`flush_interleaved_into`, but published crates.io `0.4.0` source lacks them; use preallocated `process_into` for V1 unless a future backend/API decision changes this.
- `AudioClock::samples_played` is buffer/accounting state: it counts interleaved samples pulled by CPAL callback and may include a callback buffer that is not audible yet.
- `AudioClock::now()` / `PlayerAudioClock::now()` must return stable media time based on CPAL playback anchors plus `last_stable_played_samples`; seqlock write/conflict/no-anchor fallback must never return raw `samples_played` from the fresh callback end.
- Player scheduling must not compensate for audio future jumps in `player-core/tick`; the clock invariant belongs in `crates/audio`.
- Silence/underrun callbacks may extend output duration for timestamp chaining, but media clock must clamp to real filled audio samples and not advance into silence.
- Focused clock tests live in `crates/audio/src/clock.rs` and cover unfinished anchor write, generation conflict fallback, normal interpolation, reset, legacy `record_played`, and silence tail behavior.
