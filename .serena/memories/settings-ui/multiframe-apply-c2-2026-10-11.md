# C2: многокадровая транзакция настроек (UX edge cases 2, 2026-10-11)

План/отчёт: `user/ux-edge-cases-2/results/C2.md` (раздел «Архитектура реализации»). Решение владельца: вариант 1 — Apply не блокирует окно, config пишется только после реального успеха.

## Владельцы
- `settings-core::controller::pending_apply` (новый модуль, `controller/pending_apply.rs`): `SettingsController::begin_apply -> BeginApply::{Completed(ApplyReport), Pending, Busy}`, `poll_apply -> PollApply::{Idle, Pending, Completed}`, `cancel_pending_apply -> Option<ApplyReport>` (`ApplyFinalState::Cancelled`), `has_pending_apply`. Трейт `StepwiseCommittedApplier<D>: CommittedSettingsApplier<D>` (`begin/poll/cancel_apply_committed`, `CommittedApplyProgress::{Finished, Pending}`). Общий хвост `finish_apply` (rollback при сбое | persist -> finalize -> commit) и голова `prepare_apply` вынесены из `apply` и используются синхронным и stepwise путём. Синхронные `apply` / `commit_runtime_setting` при pending отказывают (`SettingsError::access_failed`) — транзакция одна. Тесты: `controller/pending_apply/tests.rs` (подключены из `settings-core/src/tests.rs` через `#[path]`, чтобы видеть fixtures).
- `app-egui/settings_runtime/stepwise_apply.rs`: `StepwiseRouteSequence` (маршруты по очереди, маршрут в полёте, счётчик применённого префикса для отката), `impl StepwiseCommittedApplier for SettingsRuntimeApplyDelegate`, `SettingsRuntime::{advance_pending_apply, begin/poll_apply_with_runtime_adapter, cancel_pending_apply, has_pending_apply, report_apply_still_running}`; `PendingSettingsApply { close_on_success, phase: Scheduled | InFlight{audio_level_before_apply} }`. Sync-путь `apply_draft_with_runtime_adapter` теперь `#[cfg(test)]`; `conclude_apply` (snapshot sync + status + latest report) в `transaction.rs`.
- `route_apply/stepwise.rs`: `RouteApplyStart::{Finished, Pending(PendingRoute)}`, `begin_committed_route_stepwise`, `finish_pending_route`. Pending бывает только у `MediaService` (пересборка источника) и `Player` (шаг `media_pipeline`; остальные шаги player route — decoder/backend до, worker/event-policy после — ждут в `PlayerMediaContinuation`). Snapshot владельца обновляется только после успеха (как в sync).
- Host (`SettingsRuntimeReconfigureHost`) получил методы с default-ами: `begin_player_runtime_settings`, `finish_player_runtime_settings`, `begin_media_service_runtime_settings`, `poll_media_rebuild`, `cancel_media_rebuild`; типы `MediaRebuildProgress`, `PlayerApplyStart`, `PlayerMediaContinuation`. Адаптер: `RebuildExecution::{Blocking, Stepwise}`; blocking остаётся только у отката (`rebuild_active_media_blocking`), `commit_runtime_setting` и sync-путей.
- `app-egui/state/settings_media_rebuild.rs` (+ `prepare.rs`, `restore.rs`): `SettingsMediaRebuildOwner` в `AppState` (поле `settings_media_rebuild`): фазы Preparing (поток `SettingsMediaPrepareJob`, `prepare_rebuild_source`) -> Installing (общий слот `begin_prepared_media_strong_with_backend_constraint` / `poll_prepared_media_strong`, чужой request не трогается) -> RestoringState (`dispatch_playback_restore` + `try_take_outcome`, блокирующий `restore_playback_after_media_reconfigure` = dispatch + `wait`). Controls снимаются при начале установки, а не при Apply. `media_open::SourcePreparationCancel` — узкая граница cooperative-отмены подготовки.

## Инварианты
- Persist/finalize только после успеха ВСЕХ маршрутов; до этого committed config/draft/generation не меняются.
- Повторный Apply/правка/Отмена во время полёта -> «занято» (окно остаётся; статус «Применяем настройки…»); закрытие окна НЕ отменяет пересборку.
- `runtime_reconfigure_boundary_activity` видит и `has_settings_media_rebuild()`; `next_sidebar_resize_deadline`/`next_user_audio_level_persist_deadline` = None, а due-flush no-op, пока транзакция в полёте.
- Токен отмены подготовки принадлежит подготовленному источнику (seek-поток progressive HTTP живёт под ним): `SettingsMediaPrepareJob` отменяет его в Drop ТОЛЬКО пока результат не выдан (`result_pending`). Иначе после успеха падало «demux seek worker has stopped» (найдено живой проверкой).
- Lifecycle: `flush_runtime_settings_for_lifecycle_boundary` первым вызывает `SettingsRuntime::cancel_pending_apply` (suspend/shutdown): подготовка отменяется, установка получает lossless cancel, завершённый префикс откатывается, persist нет. Планировщик event loop считает `settings_runtime.has_pending_apply()` фоновой работой (без отдельного wake — опрос по кадрам/таймеру).

## Известные ограничения
- Откат синхронный: если сбой случился после успешного маршрута-пересборки (или PartialFailure), blocking reinstall отката может подвесить окно.
- Play/Pause пользователя между началом установки и Installed даёт `applied_intent != desired_intent` -> PartialFailure -> откат.
- AppState-цепочка целиком проверена только вживую (нет AppState без Renderer); юнит-тесты — controller, SettingsRuntime с fake host, prepare-job, source-guardrail «нет блокирующих вызовов».
