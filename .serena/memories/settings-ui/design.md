- Core decisions: settings UI edits draft config; opening the settings surface starts draft transaction (`draft = committed`). `Apply`/`OK` performs validate -> atomic TOML persist -> runtime apply -> detailed `ApplyReport`; `Apply` keeps the surface open; `OK` closes only after full success. `Cancel`/sidebar close discards draft and rolls back live preview routes that captured a baseline.
- Config schema/version decision: additive/defaulted sections such as `[ui.settings]` and S12 `[frame_server]` do not require a schema bump by themselves; current public config schema version is 4 after video config migrations. Old configs deserialize with defaults; new additive sections are written only on explicit save/Apply when TOML is regenerated from full `AppConfig`. Startup must not rewrite user config just to materialize missing defaulted sections. Future policy: additive fields with serde defaults do not require bump; removed/renamed fields or breaking semantic changes require version bump plus migration.
- S30B/S30C/S30D Frame Server settings UI/runtime decision: `rustiplayer-config` owns persisted `[frame_server]` plus generated registry metadata, and all 12 V1 `frame_server.*` descriptors are editable/resettable committed settings in a dedicated `frame_server` section. Budget fields use the neutral `settings-core::SettingEditor::AutoFixedPositiveInteger` over `SettingValue::Text("auto" | positive integer)` instead of a fake capped slider; descriptor validation rejects `0`/non-numeric fixed text, while backend budget resolution/admission stays outside config/UI. `SettingPlacement::group_default_open=false` marks Frame Server groups collapsed by default inside the existing tab layout. `rustiplayer-settings` maps `frame_server.apply` to `AppRuntimeRoute::FrameServer`; the route payload carries the persisted frame-server snapshot plus a `PlayerRuntimeSettingsUpdate::frame_server_policy`. `app-egui/settings_runtime` applies it through `SettingsRuntimeReconfigureHost`/player worker reporting and commits the local route snapshot only after success. Before validate/persist/committed apply, S30D adds a narrow read-only `preflight_frame_server_hover_budget_change` hook at this app/settings boundary for `hover_pool_frames` and `hover_thread_count`; fixed-too-large live changes are rejected before TOML write, committed snapshot sync, player policy apply, or controller mutation, while already-loaded unchanged fixed-too-large values remain diagnostics-only and are not clamped/replaced with `auto`. `AppState::sync_committed_config_snapshot` owns app-side live effects: `hover_preview_enabled=false` clears only visual preview/materialization, network hover throttle updates without source/job invalidation when throttle-only, primary/recent slot shrink releases by owner boundary pressure order, grow changes future admission only, and live-scrub mode/max-Hz changes during active drag remain diagnostics-only via the existing deferred snapshot path. See `mem:archive/frame-server/s30d-hover-budget-diagnostics`.
- TOML save formatting decision: Settings UI save uses `AppConfig::to_pretty_toml()` and writes generated-comment pretty TOML, matching current config crate output. Existing user comments/custom formatting are not preserved. Generated comments are project-owned documentation if emitted on save.
- UI entrypoint decision (updated 2026-06-24): settings entrypoint теперь живёт в app-level custom titlebar слева, в `crates/app-egui/src/ui/titlebar_icon_area.rs`, а старый bottom-right `settings_ui::launcher_button` удалён. Icon-area рисует квадратную gear-кнопку высотой с titlebar и отдаёт neutral `TitlebarIconAreaAction::ToggleSettingsSidebar`; `window_chrome::show` возвращает `WindowChromeOutput { window_actions, titlebar_icon_actions }`; `state/ui_runtime.rs` мапит titlebar intent в прежний `SettingsUiAction::ToggleOpen`. Runtime semantics не изменились: closed -> same as Open (`open_settings()`: begin_edit + background options refresh), open -> same as Cancel (preview rollback + draft discard, `cancel_edit`). Sidebar close button (крестик) still maps to `SettingsUiAction::Cancel` unchanged. Titlebar icon-area является v1 entry surface, не core architecture dependency; future sidebar sections can add more titlebar icon actions without making the sidebar host own open-state.
- Apply report granularity decision: apply routes are owner-level (Ui, Render, Player, MediaService), but reports include affected setting ids and per-setting/per-group details where needed. Do not make every setting its own runtime route; reports must still identify which concrete settings were changed, skipped, failed, conflicted or applied through a given mechanism.
- Route atomicity decision: atomicity inside a runtime route is defined by the route owner through explicit atomic groups. Independent groups in one owner route may succeed/fail separately, but settings inside one group preserve owner invariants and report group-level success/failure. Avoid unstructured per-field best-effort and avoid forcing the whole owner route all-or-nothing when independent groups are safe.
- Status ownership decision: apply/preview/persist/report status is owned by `app-egui/settings_runtime`, not by the visual settings sidebar. Runtime stores latest relevant status/report snapshot so warnings, conflicts, partial apply details and durability warnings survive closing/reopening and can be surfaced by future UI surfaces. Visual UI reads status snapshot and emits actions only.
- Atomic save durability decision: save validates, serializes, roundtrips, writes temp in same directory, syncs temp file, atomically renames, then attempts best-effort parent-directory sync. Parent-dir sync failure after successful file sync + rename is reported/logged as durability warning, not normal save failure.
- OK/error decision: any validation error, conflict, persist error, rollback error, route error, partial apply or `PersistedRuntimeDiverged` keeps the settings surface open and shows report/status. A future advanced UI may add explicit close-anyway, but this is not default OK semantics.
- Settings-vs-controls decision: the main Settings UI/Config surface contains persistent preferences only. Current playback/runtime controls such as play/pause, current volume, selected track, shuffle/repeat for current queue, current quality, or other ephemeral media state are not duplicated as normal settings. Persistent defaults/policies must be modeled explicitly (e.g. default volume/default repeat policy). Future specialized panels may colocate live controls with settings only as a clearly separated live-controls layer with immediate semantics, not Apply/Cancel draft semantics.
- Reset decision: reset is scoped. `settings-core` must support reset field, reset group/surface, and reset whole document. UI should prefer safe local actions such as Reset section/tab for the current surface; global Reset all settings is a separate explicit action that resets the whole `AppConfig::default()` document and should require clear confirmation/status.
- Dynamic options decision: saved dynamic option values unavailable right now remain valid unavailable-current selections. UI shows the saved value as selected/unavailable, does not replace it with default, and does not treat provider absence as config validation error. User may keep it, choose an available option, or reset. Dynamic option values stored in TOML are stable ids, not display labels; providers return stable id plus display text. For audio devices, `default` is a reserved stable id for system default output; if CPAL/OS cannot provide perfect persistent device ids, document best-effort stability limits instead of using display-name identity. Provider execution/cache/refresh is owned by `app-egui/settings_runtime`; `settings-core` only defines neutral contracts/status types, and visual UI reads cached snapshots plus emits refresh actions without calling providers during egui rendering. V1 refresh policy is refresh-on-open/section-focus plus manual refresh; no platform watchers in v1, but contracts should allow future invalidation/watch events to mark cache stale and trigger runtime-owned refresh. CHANGED 2026-06-12 (open-freeze fix): provider execution is ASYNC — synchronous CPAL/ALSA enumeration on Open froze the sidebar slide-in start for 100-500ms. `SettingsUiAction::Open`/`RefreshOptions` now call `start_dynamic_options_refresh` which builds requests on the UI thread (needs draft access) and spawns a `settings-options-refresh` thread polling providers (`option_providers` map holds `Arc<dyn SettingOptionProvider>`, trait is already Send+Sync); result arrives via mpsc into `pending_options_refresh`, picked up by `poll_dynamic_options_refresh()` in `frame_prepare::prepare_ui_frame` BEFORE `ui_model()` (updates `option_cache` + invalidates model). A new refresh supersedes the pending one (old receiver dropped, stale thread result ignored). `has_pending_options_refresh()` is part of `AppShell::has_pending_background_job` (both call sites: the method and the local check in RedrawRequested) so the idle loop wakes to poll. Tests use `wait_for_options_refresh_for_test()` (recv_timeout 5s) after Open/RefreshOptions; focused test `open_starts_background_options_refresh_and_poll_applies_result` pins the non-blocking contract.
- Validation decision: hybrid validation. Metadata is source for simple field-level constraints used by UI feedback/generated accessors (ranges, vector lengths, editor types, static option ids). Cross-field and authoritative document rules remain in `AppConfig::validate()`, always the final gate before persist/apply. Tests must keep metadata ranges/options aligned with config validation constants and defaults.
- Partial apply decision: if TOML persist succeeds but runtime apply fails or partially fails, controller reports `PersistedRuntimeDiverged`; saved file keeps new draft values, UI shows "saved but not fully applied", runtime tracks last fully active settings separately from persisted settings, and this is neither full success nor automatic TOML rollback.
- Conflict/generation decision: settings runtime must support route generations and conflict detection for future multi-surface UI. Different sidebars, tabs, quick controls and toggle buttons may operate concurrently and should keep working while the settings surface is open. Each edit/preview transaction records baseline generation per affected route; Apply/Cancel must not silently overwrite a route changed elsewhere. Conflict resolution requires explicit user choice for affected routes: apply draft over newer state, refresh draft from current state, or discard local draft changes. V1 may block only conflicting routes with a clear status/report; no silent auto-merge, auto-drop, or last-writer-wins.
- Audio volume decision: `audio.volume` in config/settings UI means default volume for startup/new media, not current playback volume. Current session volume remains explicit runtime playback state controlled by existing volume UI/commands. Settings UI should label/report it as default volume.
- Media route decision: `rustiplayer-settings` stays a clean binding/routing crate and does not take concrete service/source runtime ownership. It groups media/network/youtube/direct diffs into typed routes; `app-egui/settings_runtime` applies them through owner-level service/source APIs. `AppState` owns active reconstructible source identity (`LocalFile`, `DirectMediaUrl`, `YouTubeUrl`) and direct/YouTube controlled rebuild; settings runtime commits its media snapshot only after the app/source owner reports success. Do not encode normal `DeferredTechnicalDebt` for these settings.
- Metadata/text decision: settings metadata lives next to config schema in `rustiplayer-config` via `settings-derive` attributes, with strict coverage for all fields. Metadata stays neutral: stable ids, text ids with Russian fallback, placement, editor kinds, ranges/options and route ids only; no egui/WGPU/runtime objects or concrete service ownership. UI labels/help come from text metadata fallback in v1, not TOML comments. V1 does not implement a full localization catalog; tests enforce text ids and Russian fallback text for all user-visible settings so a future catalog can replace fallback without changing setting identity.
- Live preview pacing decision: `settings-core` owns platform/render-neutral coalescing state for pending latest updates keyed by route; `app-egui/settings_runtime` owns clock, frame cadence, suspend/resume behavior and calls concrete appliers. `settings-core` must not know `Instant`, winit/egui, renderer backend, GPU/WGPU types or app event-loop details.
- Live preview rollback decision: capture renderer-neutral baseline lazily on first actual `ImmediatePreview` change for each preview route; Cancel/sidebar close rolls back only routes whose baseline exists; successful Apply promotes active preview to the new committed baseline. Do not use inverse-operation rollback or assume committed config always equals active runtime after partial apply.
- Live preview error/backpressure decision: preview apply errors do not mutate or rollback draft values. Draft represents user intent; preview is runtime feedback. Temporary route backpressure is not a field error: keep latest pending preview update queued and retry by app-owned pacing/frame cadence, optionally showing light pending status. Unsupported/fatal/timeout-like conditions become preview errors. Pending timeout is user-configurable as `ui.settings.live_preview_pending_timeout_ms` (default 1000, valid 100..=10000, 0 invalid), not hardcoded. Apply may retry via normal validate/persist/runtime path with separate committed apply reporting.
- Preview runtime settings decision: `ui.settings.live_preview_max_hz` and `ui.settings.live_preview_pending_timeout_ms` are committed-only settings. Changes affect settings runtime pacing/timeout only after Apply/OK succeeds; the currently open draft/preview transaction continues using last committed values. They are not self-previewed live controls.
- Two top-level apply modes: `ImmediatePreview` for shader/color/video presentation controls and `CommittedApply` for normal settings. Deferred-to-next-open is technical debt, not desired behavior.
- Live color/shader preview must change image during playback without pipeline rebuild or TOML writes; updates are coalesced and paced by `ui.settings.live_preview_max_hz` (default 60, valid 1..=240), not hardcoded.
- Implemented settings crates: reusable `settings-core`, proc-macro `settings-derive`, and project binding `rustiplayer-settings`; `app-egui` keeps visual settings UI separate from runtime bridge and still owns future concrete settings runtime/UI wiring.
- Required refactors captured in doc/plan: single authoritative runtime config owner at `AppShell` level, atomic save API in `rustiplayer-config`, generated settings registry/accessors, renderer-neutral live settings adapter in `render-core`-level contracts, typed player runtime config apply boundary instead of relying on `ReloadConfig`, controlled pipeline/source reconfigure without app restart, dynamic option providers.
- Renderer live settings must be backend-neutral and contain no WGPU types in `settings-core`, `rustiplayer-settings`, `render-core`, or visual UI; WGPU-specific mapping stays in WGPU crates.
