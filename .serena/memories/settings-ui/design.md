- Status: S01 config persistence slice implemented in `rustiplayer-config`: `AppConfig` now has defaulted `[ui.settings].live_preview_max_hz` (default `60`, validation `1..=240`, `0` invalid), `UiSettingsConfig` is exported, and `save_validated_atomic_at(path, &AppConfig)` is exported for validated generated-TOML atomic save. S02 `settings-core` metadata slice is implemented as a project-agnostic no-dependency crate with owned id/value metadata, descriptor/editor model, neutral dynamic option contracts, registry/accessor boundary and changed-field diff tests. S03 `settings-core` controller/transaction slice is implemented: `SettingsController<D: Clone + Default>` owns committed/draft/default documents, route generation baselines, neutral preview state, runtime divergence state, validate/persist/committed-apply/preview/rollback delegate traits, scoped reset, owner-level `ApplyReport`/route reports, preview coalescing keyed by `SettingRouteId`, conflict reports, and retry semantics for `PersistedRuntimeDiverged`. S04 `settings-derive` is implemented as a proc-macro workspace crate: `#[derive(SettingsSchema)]` plus `#[settings(require_all_fields)]`, strict field metadata through `#[setting(...)]`, `#[setting(nested)]` for nested config structs, generated neutral registry/accessors, span-aware compile errors, and trybuild coverage for missing metadata, unknown editor, read-only `schema_version`, and nested registry. S05 Config Metadata Coverage is implemented: `rustiplayer-config::AppConfig` and nested config structs derive `SettingsSchema`; all current leaf fields are covered by generated registry metadata; `schema_version` is read-only system metadata; live preview applies only to `render.hdr_to_sdr.*` and `render.color_adjustment.*`; `ui.settings.live_preview_max_hz` is committed-only; RGB fields use vector expected_len 3; static enum/string options use stable ids; defaults/reset read through `AppConfig::default()` accessors. S05 also extended `settings-core`/`settings-derive` with `SelectList`/`select_list` for ordered static option id lists such as `player.preferred_video_codec_order`, and made config validation ranges explicit constants where metadata needs authoritative bounds. S06 Renderer Live Settings Contract is implemented: `render-core` owns `RenderLiveSettings`, `RenderLiveSettingsUpdate`, `RenderLiveSettingId`, typed `ShaderParameter*`, `RenderLiveApplyReport`, `RenderLiveSettingsError`, and `RenderLiveSettingsAdapter`; `render-wgpu-video` and `render-wgpu-shell` implement the adapter through existing color/HDR setters without pipeline rebuild, with distinct no-op/unsupported/absent/fatal semantics and neutral dependency tests. S07 Player Runtime Apply Boundary is implemented in `player-core`: public contract types include `PlayerRuntimeSettingsUpdate`, `PlayerRuntimeApplyReport`, typed setting/group/outcome ids, and `PlayerRuntimeApplyError`; `PlayerCommandSender::apply_runtime_settings` / `PlayerWorker::apply_runtime_settings` use request/reply worker reporting. Safe in-place apply currently covers worker-owned `PlayerTickConfig` and default-volume policy storage without mutating current playback volume; decoder queue/channel/pool settings report `RequiresControlledRebuild` until S13a. S08 `rustiplayer-settings` binding is implemented as a clean project crate: workspace member/dependency `rustiplayer-settings`, registry entrypoint for `AppConfig`, `AppConfigValidator`, `AppConfigStore` over `save_validated_atomic_at`, `AppConfigSettingsDelegate<A>`, AppConfig -> `RenderLiveSettings` mapping, typed route plan/construction for Ui, RenderPreview, RenderCommitted, Player and MediaService, route/group reports with affected setting ids, and explicit non-success `DeferredTechnicalDebt` route result conversion. Important current-code fact: `settings-derive` strips `.apply`/`.preview` suffixes into route ids such as `render`, `video`, `network` and stores preview-vs-committed in `SettingApplyMode`; S08 split render preview/committed routes using descriptor apply mode or stable setting ids when only `RouteApplyUpdate` is available. S09 `app-egui` authoritative runtime owner implemented: `crates/app-egui/src/settings_runtime.rs` owns `SettingsController<AppConfig>`, config path, registry view, `AppConfigStore`, route appliers/status snapshots, and startup `LoadedConfig` ownership. `AppShell` now owns `SettingsRuntime` instead of `AppConfig`; `AppState` holds a private `CommittedConfigSnapshot` with controlled accessors for autoplay, local-open demux config, UI skin/telemetry and default volume. S10 visual-only settings UI implemented in `crates/app-egui/src/settings_ui/**`: modules `launcher_button`, `window`, `layout`, `field_widget`, `section_list`; it exposes descriptor/draft/status/options input models plus `SettingsUiAction` output only, includes bottom-right launcher and resizable egui window helpers, and remains intentionally not wired to `SettingsRuntime` until S11. Each future phase must still verify current code through Serena/code_index first.
- Core decisions: settings UI edits draft config; opening the settings window starts draft transaction (`draft = committed`). `Apply`/`OK` performs validate -> atomic TOML persist -> runtime apply -> detailed `ApplyReport`; `Apply` keeps window open; `OK` closes only after full success. `Cancel`/window close discards draft and rolls back live preview routes that captured a baseline.
- Config schema/version decision: adding `[ui.settings]` is additive/defaulted and does not bump `schema_version` (stays 2). Old configs deserialize with defaults; new section is written only on explicit save/Apply when TOML is regenerated from full `AppConfig`. Startup must not rewrite user config just to materialize missing defaulted sections. Future policy: additive fields with serde defaults do not require bump; removed/renamed fields or breaking semantic changes require version bump plus migration.
- TOML save formatting decision: Settings UI save uses `AppConfig::to_pretty_toml()` and writes generated-comment pretty TOML, matching current config crate output. Existing user comments/custom formatting are not preserved. Generated comments are project-owned documentation if emitted on save.
- UI entrypoint decision: bottom-right launcher button is a v1 entry surface, not a core architecture dependency and not a long-term UX commitment. Current plan does not add concrete hotkey/menu entrypoints; S10 implements only v1 launcher while keeping open action generic for future toolbar/menu/hotkey/multi-window entrypoints.
- Apply report granularity decision: apply routes are owner-level (Ui, Render, Player, MediaService), but reports include affected setting ids and per-setting/per-group details where needed. Do not make every setting its own runtime route; reports must still identify which concrete settings were changed, skipped, failed, conflicted or applied through a given mechanism.
- Route atomicity decision: atomicity inside a runtime route is defined by the route owner through explicit atomic groups. Independent groups in one owner route may succeed/fail separately, but settings inside one group preserve owner invariants and report group-level success/failure. Avoid unstructured per-field best-effort and avoid forcing the whole owner route all-or-nothing when independent groups are safe.
- Status ownership decision: apply/preview/persist/report status is owned by `app-egui/settings_runtime`, not by a visual settings window. Runtime stores latest relevant status/report snapshot so warnings, conflicts, partial apply details and durability warnings survive closing/reopening and can be surfaced by future UI surfaces. Visual UI reads status snapshot and emits actions only.
- Atomic save durability decision: save validates, serializes, roundtrips, writes temp in same directory, syncs temp file, atomically renames, then attempts best-effort parent-directory sync. Parent-dir sync failure after successful file sync + rename is reported/logged as durability warning, not normal save failure.
- OK/error decision: any validation error, conflict, persist error, rollback error, route error, partial apply or `PersistedRuntimeDiverged` keeps the settings window open and shows report/status. A future advanced UI may add explicit close-anyway, but this is not default OK semantics.
- Settings-vs-controls decision: the main Settings UI/Config surface contains persistent preferences only. Current playback/runtime controls such as play/pause, current volume, selected track, shuffle/repeat for current queue, current quality, or other ephemeral media state are not duplicated as normal settings. Persistent defaults/policies must be modeled explicitly (e.g. default volume/default repeat policy). Future specialized panels may colocate live controls with settings only as a clearly separated live-controls layer with immediate semantics, not Apply/Cancel draft semantics.
- Reset decision: reset is scoped. `settings-core` must support reset field, reset group/surface, and reset whole document. UI should prefer safe local actions such as Reset section/tab for the current surface; global Reset all settings is a separate explicit action that resets the whole `AppConfig::default()` document and should require clear confirmation/status.
- Dynamic options decision: saved dynamic option values unavailable right now remain valid unavailable-current selections. UI shows the saved value as selected/unavailable, does not replace it with default, and does not treat provider absence as config validation error. User may keep it, choose an available option, or reset. Dynamic option values stored in TOML are stable ids, not display labels; providers return stable id plus display text. For audio devices, `default` is a reserved stable id for system default output; if CPAL/OS cannot provide perfect persistent device ids, document best-effort stability limits instead of using display-name identity. Provider execution/cache/refresh is owned by `app-egui/settings_runtime`; `settings-core` only defines neutral contracts/status types, and visual UI reads cached snapshots plus emits refresh actions without calling providers during egui rendering. V1 refresh policy is refresh-on-open/section-focus plus manual refresh; no platform watchers in v1, but contracts should allow future invalidation/watch events to mark cache stale and trigger runtime-owned refresh.
- Validation decision: hybrid validation. Metadata is source for simple field-level constraints used by UI feedback/generated accessors (ranges, vector lengths, editor types, static option ids). Cross-field and authoritative document rules remain in `AppConfig::validate()`, always the final gate before persist/apply. Tests must keep metadata ranges/options aligned with config validation constants and defaults.
- Partial apply decision: if TOML persist succeeds but runtime apply fails or partially fails, controller reports `PersistedRuntimeDiverged`; saved file keeps new draft values, UI shows "saved but not fully applied", runtime tracks last fully active settings separately from persisted settings, and this is neither full success nor automatic TOML rollback.
- Conflict/generation decision: settings runtime must support route generations and conflict detection for future multi-window/multi-surface UI. Different windows, tabs, quick controls and toggle buttons may operate concurrently and should keep working while settings window is open. Each edit/preview transaction records baseline generation per affected route; Apply/Cancel must not silently overwrite a route changed elsewhere. Conflict resolution requires explicit user choice for affected routes: apply draft over newer state, refresh draft from current state, or discard local draft changes. V1 may block only conflicting routes with a clear status/report; no silent auto-merge, auto-drop, or last-writer-wins.
- Audio volume decision: `audio.volume` in config/settings UI means default volume for startup/new media, not current playback volume. Current session volume remains explicit runtime playback state controlled by existing volume UI/commands. Settings UI should label/report it as default volume.
- Media route decision: `rustiplayer-settings` stays a clean binding/routing crate and does not take concrete service/source runtime ownership. It groups media/network/youtube/direct diffs into typed routes; `app-egui/settings_runtime` applies them through owner-level service/source APIs. Do not encode normal `DeferredTechnicalDebt` for these settings.
- Metadata/text decision: settings metadata lives next to config schema in `rustiplayer-config` via `settings-derive` attributes, with strict coverage for all fields. Metadata stays neutral: stable ids, text ids with Russian fallback, placement, editor kinds, ranges/options and route ids only; no egui/WGPU/runtime objects or concrete service ownership. UI labels/help come from text metadata fallback in v1, not TOML comments. V1 does not implement a full localization catalog; tests enforce text ids and Russian fallback text for all user-visible settings so a future catalog can replace fallback without changing setting identity.
- Live preview pacing decision: `settings-core` owns platform/render-neutral coalescing state for pending latest updates keyed by route; `app-egui/settings_runtime` owns clock, frame cadence, suspend/resume behavior and calls concrete appliers. `settings-core` must not know `Instant`, winit/egui, renderer backend, GPU/WGPU types or app event-loop details.
- Live preview rollback decision: capture renderer-neutral baseline lazily on first actual `ImmediatePreview` change for each preview route; Cancel/window close rolls back only routes whose baseline exists; successful Apply promotes active preview to the new committed baseline. Do not use inverse-operation rollback or assume committed config always equals active runtime after partial apply.
- Live preview error/backpressure decision: preview apply errors do not mutate or rollback draft values. Draft represents user intent; preview is runtime feedback. Temporary route backpressure is not a field error: keep latest pending preview update queued and retry by app-owned pacing/frame cadence, optionally showing light pending status. Unsupported/fatal/timeout-like conditions become preview errors. Pending timeout is user-configurable as `ui.settings.live_preview_pending_timeout_ms` (default 1000, valid 100..=10000, 0 invalid), not hardcoded. Apply may retry via normal validate/persist/runtime path with separate committed apply reporting.
- Preview runtime settings decision: `ui.settings.live_preview_max_hz` and `ui.settings.live_preview_pending_timeout_ms` are committed-only settings. Changes affect settings runtime pacing/timeout only after Apply/OK succeeds; the currently open draft/preview transaction continues using last committed values. They are not self-previewed live controls.
- Two top-level apply modes: `ImmediatePreview` for shader/color/video presentation controls and `CommittedApply` for normal settings. Deferred-to-next-open is technical debt, not desired behavior.
- Live color/shader preview must change image during playback without pipeline rebuild or TOML writes; updates are coalesced and paced by `ui.settings.live_preview_max_hz` (default 60, valid 1..=240), not hardcoded.
- Implemented settings crates: reusable `settings-core`, proc-macro `settings-derive`, and project binding `rustiplayer-settings`; `app-egui` keeps visual settings UI separate from runtime bridge and still owns future concrete settings runtime/UI wiring.
- Required refactors captured in doc/plan: single authoritative runtime config owner at `AppShell` level, atomic save API in `rustiplayer-config`, generated settings registry/accessors, renderer-neutral live settings adapter in `render-core`-level contracts, typed player runtime config apply boundary instead of relying on `ReloadConfig`, controlled pipeline/source reconfigure without app restart, dynamic option providers.
- Renderer live settings must be backend-neutral and contain no WGPU types in `settings-core`, `rustiplayer-settings`, `render-core`, or visual UI; WGPU-specific mapping stays in WGPU crates.
