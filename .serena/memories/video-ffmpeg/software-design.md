- Session 22 fixed the MP4/avcC H.264 software-decode crash (`avcodec_send_packet` `InvalidData -1094995529`, FFmpeg "No start code is found. Error splitting the input into NAL units."). No CPU RGB conversion, no FFmpeg hwdecode, not hardcoded per file. The ffmpeg-gated extradata tests cover avcC/hvcC pass extradata, Annex B passes none, and missing/empty length-prefixed codec_private is typed-invalid.
- Session 17 implemented the AVFrame-backed HostPlanar resource table in `video-ffmpeg`. Repeated/stale release is a no-op; lookup after release returns `Missing`. The owner reads AVFrame rows through safe per-plane visible-row access, accepts real FFmpeg `linesize > visible row bytes`, rejects negative/non-positive/too-small linesize, null plane data, unsupported formats, contract mismatch, and FFI clone failures as typed fatal backend errors. - V1 software output target is explicit planar YUV 4:2:0/4:2:2/4:4:4 for 8/10/12-bit, added as concrete `VideoFramePixelLayout` variants with matching HostPlanar validation and renderer upload support. Do not use a generic "any planar YUV" layout as a shortcut.
- FFmpeg FFI layer must own padded `AVPacket` input (`AV_INPUT_BUFFER_PADDING_SIZE`), `AVFrame`/refcount lifetimes, send/receive queuing, typed error mapping, flush vs EOF drain semantics, color metadata mapping, and resource lifetime until `release_frame`.
- CPU color conversion/RGB output remains forbidden in the playback path; YUV sampling, color/HDR/tone mapping, and composition stay GPU-side.
- Architectural decision (2026-06-15): exactly one copy on decode->render path, and that copy is the final host-to-GPU upload. An intermediate CPU copy of decoded planes into owned host storage is forbidden in steady-state playback, so v1 is built on zero-copy host ownership over a refcounted `AVFrame` from the start, not as a later optimization. Consequence: the foundation `HostPlanarFrameDescriptor` single-`Arc<[u8]>` backing must be generalized to a provider-owned refcounted owner yielding per-plane `&[u8]` (owner may be our buffer OR a wrapped `AVFrame`); this is a deliberate resource-provider boundary change with focused lifetime tests, and `release_frame` is the only release point.

- Session 24 (perf) fixed 4K software decode bottleneck (15-17 fps на 4K60 при недогруженных ядрах). Профиль подтвердил: один `ffmpeg-decode` thread на ~99%, 5 из 8 ядер простаивали. Корневая причина — `CodecContext::open` (`ffi/codec_context.rs`) не выставлял threading до `avcodec_open2`, поэтому FFmpeg декодировал в один поток (`thread_count` по умолчанию = 1). Первичный фикс ставил перед `avcodec_open2` `thread_count = 0` (libavcodec выбирает по `av_cpu_count()`) и `thread_type = FF_THREAD_FRAME | FF_THREAD_SLICE`; текущая политика больше не отдаёт FFmpeg auto-sentinel `0` для project-level `Auto`, а резолвит его в явное положительное число потоков через `SoftwareDecodeThreadBudget::resolved_thread_count()` (`available_parallelism - 2`, минимум 2), чтобы оставить CPU headroom для render/upload/worker paths. `thread_type` по-прежнему `FF_THREAD_FRAME | FF_THREAD_SLICE`, а libavcodec сам маскирует его по `AVCodec.capabilities`; codec без threading остаётся однопоточным. После фикса decode раскладывается по `av:vp9:*` worker-потокам, present queue заполнена (6-8/8), `pauses_present_queue` растёт, `drops_decoder_starvation=0` — decode идёт впереди playback, держит реальный 4K60. Custom `get_format`/`FormatNegotiator` thread-safe под frame-threading (immutable read-only state); send/receive loop не блокируется на кадр после каждого packet (drain-оппортунистический), поэтому frame-threading decode delay не даёт deadlock. Threading остаётся целиком внутри `video-ffmpeg`; raw FFmpeg типы наружу не выносятся; CPU RGB conversion/hwdecode не добавлялись; не хардкод под файл.
- Session 24 follow-up: frame-threading вскрыл backpressure-gap в host-upload ресурсах. Раньше и resource table (`upload_slots_capacity`), и decoded-frame channel (`frame_tx`) спавнились из `frame_channel_frames` (=8). Resource table держит ВСЕ одновременно живущие decoded frames (в channel + в player present queue + в render lease-ах, освобождение только через `release_frame`), поэтому при быстром многопоточном decode переполнялась → fatal `host-upload resource table is full: 8/8`. Player тормозит отправку packets только по `frame_rx.len() >= decoder_ready_queue_frames` (ready-queue=8) и по `upload_slots_free == 0`, но один `send_packet` при frame-threading может слить burst кадров (или весь EOF/DPB tail ~thread_count) за одну drain-итерацию. Фикс (только в `video-ffmpeg::spawn`): и resource table, и `frame_tx` channel сайзятся из `decoder_surface_pool_frames` [ОБНОВЛЕНО Session 26: software-путь теперь сайзится из ОТДЕЛЬНОГО `software_frame_pool_frames` (public `video.sw_decoder_surface_pool_frames`, default 8), НЕ из hardware decoder_surface_pool_frames; см. `mem:video-ffmpeg/software-frame-pool-setting`] (=24, neutral output frame pool, тот же смысл что surface pool у hardware backend-а), а не из `frame_channel_frames`. Ready-queue backpressure threshold не менялся (всё ещё `decoder_ready_queue_frames`=8 над `frame_rx.len()`), так что 24 даёт burst-headroom без изменения flow-control семантики. Neutral `VideoDecoderThreadConfig` defaults НЕ трогались (VAAPI не затронут). `host_frames_ready` остаётся `frame_rx.len()`. Проверено release smoke на VP9 4K60 SDR и H.264 (по факту 4K) MP4: нет table-full/channel-full/InvalidData, queue полна, starvation=0.

## Свой `get_buffer2` — кадры в импортируемых блоках (cpu-parity 08b, 2026-10-22)
- `FfmpegCodecContextRequest::with_frame_memory(SoftwareFrameMemory::ImportableBlocks)` (ставит `RealFfmpegDecodeApi::open`; default `DecoderDefault`). Callback ставится только декодерам с `AV_CODEC_CAP_DR1` (H.264/HEVC/VP9/VP8); libdav1d (AV1) без DR1 → обычное выделение FFmpeg.
- Модули: `ffi::host_frame_memory` (чистый Rust: `HostFrameBlockLayout`, `HostFrameBlock` — обнулённый, начало на 2 МиБ (`HOST_FRAME_BLOCK_ALIGNMENT`, THP), длина кратна странице; `HostFrameBlockPool` — free list по текущей длине (потолок 64), `checked_out` по адресу, `close()` в Drop `CodecContext`), `ffi::direct_frame_buffers` (`allocate_frame_in_pool`: `avcodec_align_dimensions2` → `cache_friendly_linesizes` → `av_image_fill_plane_sizes` → один `av_buffer_create` на блок, free-callback возвращает блок в пул), `ffi::codec_context::callbacks` (`CodecCallbacks` за `AVCodecContext.opaque`: `get_format` + `get_importable_frame_buffer`, при `DirectFrameBufferFallback` — `avcodec_default_get_buffer2` + счётчик `fallbacks`). `CodecContext::receive_frame` привязывает блок к кадру (`OwnedAvFrame::attach_importable_block`, копируется в `try_clone_ref`, сбрасывается в `unref`); `AvFrameHostPlanarOwner::importable_memory` отдаёт offset-ы plane-ов.
- **Stride — нечётное кратное lcm(256, выравнивание декодера), по plane-ам отдельно** (`cache_friendly_linesizes`): первая версия (как `update_frame_pool`, общий рост ширины) дала 4096/2048 на 4K — степени двойки, строки в одних наборах кэша, декодер VP9 4K60 +30 п.п. ядра. Теперь 3840/2304 (4K), 2304/1280 (1080p). Цена (принято владельцем 22.10.2026): RSS +24…30 МиБ на 1080p60/4K60, GTT −19…27 МиБ (staging не нужен), общая память ≈ та же.
- Тесты `ffi/direct_frame_buffers/tests.rs` (фикстуры `tests/fixtures/direct-frame-buffers/generate.sh`, 176×100 VP9 IVF / H.264 и HEVC Annex B с AUD): побайтное равенство видимых plane-ов с `DecoderDefault`, кадр в одном странично-выровненном блоке со stride % 256, блоки переиспользуются, 0 fallback-ов; кадр переживает закрытие декодера; AV1 без пула.

## Два вида памяти блоков (gles2-renderer 12, 2026-10-27)

## Bounded EOF continuation (2026-07-27; corrected 2026-08-05)
- FFmpeg EOF NULL packet отправляется ровно один раз на generation. Если DPB tail превышает свободный HostPlanar pool budget, `FfmpegDecoderWorker` сохраняет pending EOF generation и самостоятельно продолжает только receive-side drain; player не обязан повторно вызывать begin-drain.
- Пока результат остаётся `Draining`, decoder owner обязан немедленно вернуться в свой EOF loop. Верхняя pool-проверка ждёт `release_notify_rx` только при реально полном pool; при уже свободных slots receive продолжается сразу. Нельзя переходить в обычный packet/control select: после container EOF новых packets может не быть, а coalesced последний release edge уже мог быть потреблён — это оставляло DASH/другие FFmpeg A/V источники в `Draining` навсегда после seek near EOF.
- После принятого `avcodec_send_packet(NULL)` receive-side `EAGAIN` считается typed `ProtocolViolation`, а не `Draining`: по libavcodec drain contract декодер должен вернуть frames и затем terminal `AVERROR_EOF`; бесконечный retry скрывал бы нарушение протокола.
- Configure/Clear/seek Flush сбрасывают pending EOF continuation вместе с old-generation pending packet. Shared state остаётся `Draining` до terminal libavcodec EOF, затем публикуется `Drained`; receive/publish fatal очищает continuation и публикует typed `Fatal`.
- Focused regressions `eof_drain_with_budget_reports_draining_when_capped`, `release_driven_eof_continuation_preserves_last_coalesced_release_edge` и `accepted_ffmpeg_eof_rejects_receive_eagain_instead_of_spinning` закрепляют multi-budget tail, single EOF send, lost-release-edge continuation и final `Drained`. Вертикальный player regression `seek_near_eof_with_video_and_audio_tail_reaches_auto_next_terminal_state` закрепляет post-seek video presentation + PCM output + `Drained` → `Ended` event, который использует playlist auto-next.
