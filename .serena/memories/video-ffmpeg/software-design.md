# Video FFmpeg Software Design

- Future FFmpeg integration is software-decode-only. Hardware video acceleration remains owned by the native backend path (`video-vaapi` currently); do not plan FFmpeg hardware decode, hardware download-to-RAM, or FFmpeg-as-primary hardware backend work from `user/ffmpeg_backend_design.md`.
- `video-ffmpeg` now exists as an isolated workspace crate with optional `ffmpeg` feature wiring to `ffmpeg-sys-next`; default workspace builds do not enable it and do not require FFmpeg headers/libs/runtime. The crate now contains the FFmpeg software decoder-thread foundation, AVFrame-backed HostPlanar resource provider, `FfmpegSoftwareVideoBackendFactory`, and `FfmpegSoftwareCapabilityProvider`. App composition now registers the FFmpeg provider beside VA-API and can execute the concrete `FfmpegHostUploadWgpu` plan by starting the FFmpeg backend factory plus `HostPlanarWgpuFrameMaterializer`; `player-core` still receives only neutral `StartedVideoBackend` handles. No separate public `ffmpeg_sw` TOML/UI option exists.
- Build wiring (2026-06-16, Session 23): `app-egui` now has `default = ["ffmpeg"]` where `ffmpeg = ["video-ffmpeg/ffmpeg"]`, so plain `cargo build -p app-egui` and `cargo build --release -p app-egui` (and `cargo build/check/test --workspace`) compile the `rustiplayer` binary WITH the FFmpeg software path in both debug and release. This intentionally changes the earlier "default builds do not require FFmpeg" invariant: building the workspace now requires FFmpeg dev libs/runtime present. Opt out with `cargo build -p app-egui --no-default-features`. The isolation boundary is unchanged: `ffmpeg`/`ffmpeg-sys-next` stay optional deps inside `video-ffmpeg` only, `app-egui` gains no direct FFmpeg dependency (just activates the forwarded feature), `player-core` still depends on no concrete FFmpeg/render crate, and refactor guardrails stay green. `video-ffmpeg`'s own default feature set is still empty (`cargo build -p video-ffmpeg` alone has no FFmpeg). Public `video.preferred_backend` remains schema v3 `auto`/`hardware`/`software`; legacy schema v2 `vaapi` loads as `hardware`.
- Implemented config migration target (2026-06-16, doc §12/S10): public `video.preferred_backend` has three platform-neutral values `auto` (hardware-first + future software fallback) / `hardware` (native hw only; VAAPI now, Windows hw later — value no longer tied to `vaapi`) / `software` (FFmpeg only). Migration maps legacy schema v2 `vaapi` -> `hardware`, bumps config schema version to 3, and consciously allows the public `software` value while never adding a separate `ffmpeg_sw` key — these are values of one backend selector. Other decided design inputs: PTS = best_effort_timestamp -> pts -> interpolation via time_base (doc §8); software backpressure uses a separate `HostUploadResourceSnapshot`, never the VAAPI-shaped `DecoderResourceSnapshot` (doc §10); FFmpeg runtime availability is a probed capability, not a hard dependency, with diagnostics distinguishing no-build/missing/too-old/probe-fail (doc §13).
- Target FFmpeg baseline in the design doc is stable 8.1.x (`8.1.1 "Hoare"` was latest stable on 2026-06-15) plus a required Context7 stable/trunk Doxygen recheck before implementation.
- Runtime availability probe is implemented in `video-ffmpeg::probe_runtime_availability()` (Session 13). `compile_time_probe()` remains compile-time-only and returns runtime status `NotRun`. Runtime probe treats FFmpeg availability as an optional capability, never opens player/session/decoder pipeline, and reports typed outcomes via `FfmpegProbeFailure`: `NoBuild`, `MissingRuntimeLibraries`, `TooOld`, `ProbeFailed`. With feature `ffmpeg`, probe uses optional `libloading`/dlopen over libavutil+libavcodec instead of direct FFmpeg symbol calls, so missing runtime libraries become a diagnostic rather than a Rust panic. Minimum runtime versions are libavcodec `62.28.0` and libavutil `60.26.0` (FFmpeg 8.1.x baseline); smoke checks call version functions plus `avcodec_find_decoder(AV_CODEC_ID_H264)` and `av_pix_fmt_desc_get(AV_PIX_FMT_YUV420P)`. Focused tests cover mapping/no-build/missing runtime/too-old/probe-failed, and `crates/video-ffmpeg/tests/ffmpeg_runtime_probe.rs` has an ignored real-runtime test run with `cargo test -p video-ffmpeg --features ffmpeg -- --ignored`.
- Target linking policy is dynamic LGPL FFmpeg through `video-ffmpeg` using `ffmpeg-sys-next`. Session 12 scaffold uses `ffmpeg-sys-next = 8.1.0`, `default-features = false`, feature `avcodec`, and crate feature `ffmpeg` as the only opt-in path.
- Session 14 implemented the thin safe RAII layer in `video-ffmpeg::ffi`: `FfmpegError`/`FfmpegFfiError` map negative `AVERROR` statuses into typed kinds while preserving diagnostics; `OwnedAvPacket` owns `AVPacket` allocation/free, copies caller payload, and guarantees `AV_INPUT_BUFFER_PADDING_SIZE` zero padding; `OwnedAvFrame` owns `AVFrame` allocation/free plus `av_frame_ref`/`av_frame_unref`, exposes safe metadata accessors, and exposes row-based plane reads that respect `linesize`; `CodecContext` finds/allocates/opens software-only decoders and its `get_format` callback chooses only adapter-accepted software pixel formats from a project-owned `SoftwarePixelFormatSet`. Default builds still compile without FFmpeg and return `FeatureDisabled` for real FFI allocation/open calls. Raw FFmpeg pointers remain private to `ffi`, with a focused guardrail test covering public non-ffi modules.
- Session 15 implemented the codec/pixel/color adapter boundary. `video-ffmpeg::codec_adapter::plan_ffmpeg_software_decode()` takes neutral `codec-core::VideoDecodeRequirement` plus renderer-selected `VideoFrameContract` and returns `FfmpegStreamAdapterPlan` with adapter-owned `FfmpegDecoderId`, exact one-format `SoftwarePixelFormatSet`, validated `SoftwareHostUpload` contract, and input color metadata plan. `codec-core` remains the neutral source of codec/profile/bit-depth/chroma/color requirements; raw `AVCodecID` mapping stays inside `ffi::codec_context` through `FfmpegDecoderId -> AVCodecID` under the `ffmpeg` feature.
- Session 15 profile/layout policy: H.264 ConstrainedBaseline/Main/High are accepted only as 8-bit 4:2:0; H.265 Main/Main10/Main12/Main422_10/Main422_12/Main444/Main444_10 are accepted, while Main444_12 and SCC profiles are typed unsupported; VP8 Version0To3 is 8-bit 4:2:0; VP9 profiles 0..3 are accepted only with their legal bit-depth/chroma families; AV1 Main/High are accepted and AV1 Professional is typed unsupported until an explicit v1 layout policy is added. The adapter checks profile/codec mismatch, unsupported profile, unsupported 12-bit 4:4:4, bit-depth mismatch, chroma mismatch, and profile/layout mismatch as distinct `FfmpegCodecAdapterError` variants.
- Session 15 pixel-format policy lives in `video-ffmpeg::ffi::pixel_format`: explicit accepted FFmpeg formats map to `VideoFramePixelLayout::{Yuv420Planar8,Yuv420Planar10Le,Yuv420Planar12Le,Yuv422Planar8,Yuv422Planar10Le,Yuv422Planar12Le,Yuv444Planar8,Yuv444Planar10Le}`. `FfmpegPixelFormatRejection` rejects unknown, hardware, RGB, paletted, bitstream-packed, float, alpha, big-endian, and otherwise unsupported software formats. `get_format` still accepts only adapter-allowlisted formats and does not use swscale/RGB conversion.
- Session 21 completed the FFmpeg color/HDR metadata path for software decode. `video-ffmpeg::ffi::frame::OwnedAvFrame::color_metadata()` now copies `AVFrame` color fields plus `AV_FRAME_DATA_MASTERING_DISPLAY_METADATA` and `AV_FRAME_DATA_CONTENT_LIGHT_LEVEL` side data into FFmpeg-free value structs. `codec_adapter::color_metadata_plan_from_ffmpeg_frame()` maps range/matrix/primaries/transfer plus mastering luminance and MaxCLL/MaxFALL into neutral `codec_core::VideoColorMetadata`/`HdrMetadata`, with inspected Present/Absent side-data status. `decoder_thread` preserves the existing origin/confidence policy by using frame metadata when present, merging missing core fields from `DecodePacket.resolved_color`, and falling back to SDR BT.709 only when neither frame nor packet/context color exists. CPU still performs no color conversion; unsupported/incomplete HDR colorimetry reaches the renderer boundary and is rejected by the existing HostPlanar HDR validation instead of being guessed.
- Session 16 implemented the first playback-facing FFmpeg decoder thread foundation in `video-ffmpeg`: `start_decoder_thread()` now returns a neutral `StartedVideoBackend`/`VideoDecoderThreadHandle` when feature `ffmpeg` is enabled, while default builds still report `FeatureDisabled` and do not require FFmpeg runtime. The thread owns FFmpeg send/receive state inside `video-ffmpeg`, opens software-only `CodecContext` from `VideoStreamDecodeConfig` through the existing codec adapter, creates padded `OwnedAvPacket`s, handles `avcodec_send_packet` EAGAIN by draining output then retrying the same packet, treats receive as 0/1/N frames until EAGAIN/EOF, separates seek `flush()` (`avcodec_flush_buffers`, clears generation/interpolation/drain state) from `begin_end_of_stream_drain(generation)` (NULL packet + tail drain), and wakes the neutral activity notifier on frame/packet/drain progress. PTS policy is `best_effort_timestamp` -> `AVFrame.pts` -> interpolation by frame duration/time_base.
- Session 22 fixed the MP4/avcC H.264 software-decode crash (`avcodec_send_packet` `InvalidData -1094995529`, FFmpeg "No start code is found. Error splitting the input into NAL units."). Root cause: `RealFfmpegDecodeApi::open` opened the codec context without ever setting `AVCodecContext.extradata`, so length-prefixed avcC/hvcC packets were parsed as Annex B. Fix keeps all FFmpeg-specific extradata handling inside `video-ffmpeg`: `FfmpegCodecContextRequest` now carries optional neutral `extradata: Vec<u8>` (`with_extradata`/`extradata()`, no raw FFmpeg types leaked); `decoder_thread::extradata_for_stream_config(config)` decides which `codec_private` to attach — required for `H264(AvccLengthPrefixed)`/`H265(HvccLengthPrefixed)` (missing/empty -> typed `FfmpegOpenDecoderError::Unsupported(VideoStreamConfigRejection::InvalidCodecPrivate)`, not silent fallback), `None` for Annex B (in-band SPS/PPS; attaching avcC would wrongly flip the decoder to length-prefixed mode), pass-through `codec_private` for other codecs when present. `CodecContext::open` sets `extradata` before `avcodec_open2` via `av_mallocz(len + AV_INPUT_BUFFER_PADDING_SIZE)` (zeroed padding required by the bitstream reader), copies the bytes, and assigns ownership to the context (freed by `avcodec_free_context`; do not free manually). No CPU RGB conversion, no FFmpeg hwdecode, not hardcoded per file. Verified by release smoke `preferred_backend = software` on H.264 MP4 (`ffmpeg-host-upload-wgpu` plan, no InvalidData/no-start-code/no DMA-BUF contract) and VP9 MKV (unchanged). Focused decoder-thread tests now live in `crates/video-ffmpeg/src/decoder_thread/tests.rs`, with shared fakes/helpers in `crates/video-ffmpeg/src/decoder_thread/test_support.rs` (both private child test modules). The ffmpeg-gated extradata tests cover avcC/hvcC pass extradata, Annex B passes none, and missing/empty length-prefixed codec_private is typed-invalid.
- Session 17 implemented the AVFrame-backed HostPlanar resource table in `video-ffmpeg`. Real receive now clones a refcounted `AVFrame` with `av_frame_ref`, converts it into a provider-owned entry keyed by `FrameResourceHandle`, builds a neutral `FrameResourceDescriptor::HostPlanar`, validates it against the selected `VideoFrameContract`, publishes `DecodedFrame` through `frame_rx`, and keeps the resource alive until renderer/provider `release_frame(handle)`. Repeated/stale release is a no-op; lookup after release returns `Missing`. The owner reads AVFrame rows through safe per-plane visible-row access, accepts real FFmpeg `linesize > visible row bytes`, rejects negative/non-positive/too-small linesize, null plane data, unsupported formats, contract mismatch, and FFI clone failures as typed fatal backend errors. EOF/DPB drain tail frames now return through the same publish path. `host_upload_resource_snapshot()` now returns `Available(HostUploadResourceSnapshot)` for FFmpeg software host-upload counters. Default builds still compile without FFmpeg and do not require FFmpeg runtime. Session 27/S06 refactor-only splits keep this ownership/lifecycle unchanged: AVFrame HostPlanar resource domain lives in private child module `crates/video-ffmpeg/src/decoder_thread/host_resources.rs`; send/receive loop, `SendReceiveCodecApi`, reports, PTS resolver, and time-base helpers live in `crates/video-ffmpeg/src/decoder_thread/send_receive.rs`; stream config/extradata helpers live in `crates/video-ffmpeg/src/decoder_thread/stream_config.rs`; frame/context color merge helpers live in `crates/video-ffmpeg/src/decoder_thread/color_metadata.rs`. `decoder_thread.rs` remains the decode/session worker boundary and uses only minimal `pub(super)` access to private children.
- `ffmpeg-sw` uses existing neutral boundaries: `FfmpegSoftwareVideoBackendFactory` returns `video-backend-api::StartedVideoBackend` over `VideoDecoderThreadHandle`; decode config/frame flow uses `VideoStreamDecodeConfig.frame_contract`, `DecodedFrame.frame_contract`, `FrameResourceDescriptor::HostPlanar`, and `VideoFrameTransferPath::SoftwareHostUpload`; `FfmpegSoftwareCapabilityProvider` declares raw `SupportedVideoOutput` entries with backend id `ffmpeg-sw`; `capability-core::CapabilityScanner` keeps raw outputs for diagnostics and only promotes renderer-intersected contracts into `SystemCapabilities.playable_video_outputs`. `app-egui` owns concrete selection/startup: `auto` prefers playable VA-API DMA-BUF before FFmpeg software, `hardware` rejects software-only streams, and `software` selects only playable `ffmpeg-sw` host-upload outputs.
- V1 software output target is explicit planar YUV 4:2:0/4:2:2/4:4:4 for 8/10/12-bit, added as concrete `VideoFramePixelLayout` variants with matching HostPlanar validation and renderer upload support. Do not use a generic "any planar YUV" layout as a shortcut.
- FFmpeg FFI layer must own padded `AVPacket` input (`AV_INPUT_BUFFER_PADDING_SIZE`), `AVFrame`/refcount lifetimes, send/receive queuing, typed error mapping, flush vs EOF drain semantics, color metadata mapping, and resource lifetime until `release_frame`.
- CPU color conversion/RGB output remains forbidden in the playback path; YUV sampling, color/HDR/tone mapping, and composition stay GPU-side.
- Architectural decision (2026-06-15): exactly one copy on decode->render path, and that copy is the final host-to-GPU upload. An intermediate CPU copy of decoded planes into owned host storage is forbidden in steady-state playback, so v1 is built on zero-copy host ownership over a refcounted `AVFrame` from the start, not as a later optimization. Consequence: the foundation `HostPlanarFrameDescriptor` single-`Arc<[u8]>` backing must be generalized to a provider-owned refcounted owner yielding per-plane `&[u8]` (owner may be our buffer OR a wrapped `AVFrame`); this is a deliberate resource-provider boundary change with focused lifetime tests, and `release_frame` is the only release point.

- Session 24 (perf) fixed 4K software decode bottleneck (15-17 fps на 4K60 при недогруженных ядрах). Профиль подтвердил: один `ffmpeg-decode` thread на ~99%, 5 из 8 ядер простаивали. Корневая причина — `CodecContext::open` (`ffi/codec_context.rs`) не выставлял threading до `avcodec_open2`, поэтому FFmpeg декодировал в один поток (`thread_count` по умолчанию = 1). Фикс: перед `avcodec_open2` ставим `thread_count = 0` (libavcodec выбирает по `av_cpu_count()`) и `thread_type = FF_THREAD_FRAME | FF_THREAD_SLICE` (libavcodec сам маскирует по `AVCodec.capabilities`, codec без threading остаётся однопоточным). После фикса decode раскладывается по `av:vp9:*` worker-потокам, present queue заполнена (6-8/8), `pauses_present_queue` растёт, `drops_decoder_starvation=0` — decode идёт впереди playback, держит реальный 4K60. Custom `get_format`/`FormatNegotiator` thread-safe под frame-threading (immutable read-only state); send/receive loop не блокируется на кадр после каждого packet (drain-оппортунистический), поэтому frame-threading decode delay не даёт deadlock. Threading остаётся целиком внутри `video-ffmpeg`; raw FFmpeg типы наружу не выносятся; CPU RGB conversion/hwdecode не добавлялись; не хардкод под файл.
- Session 24 follow-up: frame-threading вскрыл backpressure-gap в host-upload ресурсах. Раньше и resource table (`upload_slots_capacity`), и decoded-frame channel (`frame_tx`) спавнились из `frame_channel_frames` (=8). Resource table держит ВСЕ одновременно живущие decoded frames (в channel + в player present queue + в render lease-ах, освобождение только через `release_frame`), поэтому при быстром многопоточном decode переполнялась → fatal `host-upload resource table is full: 8/8`. Player тормозит отправку packets только по `frame_rx.len() >= decoder_ready_queue_frames` (ready-queue=8) и по `upload_slots_free == 0`, но один `send_packet` при frame-threading может слить burst кадров (или весь EOF/DPB tail ~thread_count) за одну drain-итерацию. Фикс (только в `video-ffmpeg::spawn`): и resource table, и `frame_tx` channel сайзятся из `decoder_surface_pool_frames` [ОБНОВЛЕНО Session 26: software-путь теперь сайзится из ОТДЕЛЬНОГО `software_frame_pool_frames` (public `video.sw_decoder_surface_pool_frames`, default 8), НЕ из hardware decoder_surface_pool_frames; см. `mem:video-ffmpeg/software-frame-pool-setting`] (=24, neutral output frame pool, тот же смысл что surface pool у hardware backend-а), а не из `frame_channel_frames`. Ready-queue backpressure threshold не менялся (всё ещё `decoder_ready_queue_frames`=8 над `frame_rx.len()`), так что 24 даёт burst-headroom без изменения flow-control семантики. Neutral `VideoDecoderThreadConfig` defaults НЕ трогались (VAAPI не затронут). `host_frames_ready` остаётся `frame_rx.len()`. Проверено release smoke на VP9 4K60 SDR и H.264 (по факту 4K) MP4: нет table-full/channel-full/InvalidData, queue полна, starvation=0.
