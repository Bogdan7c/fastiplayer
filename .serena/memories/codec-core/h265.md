# codec-core H.265

- `codec-core` has a platform-neutral HEVC/H.265 preparation module at `crates/codec-core/src/h265.rs`; it is exported from `codec-core` and wired into the codec-neutral adapter registry used by demux/player-core. `video-vaapi` consumes these helpers in the production H.265 Main/Main10 adapter path; H.265 capability advertisement is enabled only for validated Main 8-bit YUV420/NV12 and Main10 10-bit YUV420/P010 through the normal production intersection. There is still no renderer-specific HEVC change.
- Public APIs include structural `parse_hevc_decoder_configuration_record`, `HevcDecoderConfigurationRecord`, `H265Packetization::{AnnexB, HvccLengthPrefixed { nal_length_size }}`, `H265NalLengthSize`, `infer_h265_packetization`, `h265_nal_units`, `h265_access_unit_to_annex_b`, `h265_access_unit_to_annex_b_into`, `probe_h265_packet_decode_start`, SPS/header requirement helpers, and typed `H265*Error` enums.
- `hvcC` parsing checks `configurationVersion`, extracts `lengthSizeMinusOne`, profile-tier-level, level, raw chroma/bit-depth header fields, and validates all declared arrays while collecting only VPS/SPS/PPS. Missing VPS/SPS/PPS arrays are allowed for weak/incomplete `hvcC`; malformed declared lengths/zero-length NALs remain typed parse errors.
- Conversion uses caller-owned scratch `Vec<u8>`; it clears before writing, preserves capacity, leaves output empty on error, copies Annex B input as Annex B after validation, converts hvcC length-prefixed packets using explicit nal length size, and injects only caller-supplied VPS/SPS/PPS before the access unit.
- Decode-start probing treats all HEVC IRAP NAL types 16..=23 (BLA/IDR/CRA/reserved IRAP) as proven decode-start, parameter-set-only AUs as not decode-start, and malformed/incomplete packets as recoverable `H265PacketDecodeStartProbe::Uncertain`.
- Requirement refinement supports only production target Main 8-bit 4:2:0 -> NV12 and Main10 10-bit 4:2:0 -> P010. 4:2:2, 4:4:4, 12-bit, SCC, and other profiles are typed unsupported/future; incomplete `hvcC` can still yield header-level requirement when profile/chroma/bit-depth are safe. Non-VP9 bitstream refinement must merge missing fields from container metadata: H.265 `hvcC` can refine profile/bit-depth/chroma/surface without erasing MP4/Matroska color/HDR metadata, so `VideoDecodeRequirement.color` continues to feed `DecodePacket.resolved_color` and renderer HDR-to-SDR dispatch.
- Focused tests live in `h265.rs` and `adapter.rs` unit tests and cover hvcC length sizes 1/2/4, VPS/SPS/PPS extraction, incomplete hvcC, hev1-style in-band parameter sets, Annex B/HVCC conversion, injection, IRAP/keyframe probe, adapter requirement refinement, recoverable malformed packets, and unsupported variants.
- Session 3 validation after adapter/player wiring: `cargo test -p codec-core h265 --lib`, `cargo test -p symphonia-demux packet_mapper --lib`, `cargo test -p player-core h265 --lib`, targeted H.264/generic bootstrap tests, and `cargo check --workspace`. `cargo check --workspace` still emits pre-existing warnings from `cros-libva-patch`/`cros-codecs-patch`, not from HEVC wiring.
- Session 27A decomposed the former mixed `crates/codec-core/src/h265.rs`: the facade now owns hvcC/NAL packetization, Annex-B conversion and decode-start probing; `crates/codec-core/src/h265/requirements.rs` owns SPS/RBSP parsing, decoded-format policy and requirement construction; codec-local characterization tests live in `crates/codec-core/src/h265/tests.rs`. Public H.265 paths are preserved through the facade re-export.
