# Controlled renderer recreation — Session 08C (2026-07-11)

- Render/surface settings route теперь применяется live через app-owned `RendererLifecycleCoordinator` в `crates/app-egui/src/renderer_recreation.rs`. Settings/UI видит только `SettingsRuntimeReconfigureHost::recreate_renderer(previous, next)`; concrete surface/device ownership остаётся у shell `Renderer`, а `AppState` не хранит renderer/config.
- Transaction order: preflight busy/conflict -> полностью создать candidate `Renderer` -> восстановить текущий `RenderLiveSettings` -> подготовить materializer того же active provider-а -> проверить candidate capabilities и неизменность backend/materializer класса -> освободить renderer-bound visual leases/cache/override/frozen frame -> `Device::poll(PollType::Wait)` с bounded 5 s drain -> rebind submitted-release queue -> atomically install materializer/capabilities/renderer -> resume redraw/submissions.
- Resize/maximize/minimize действия текущего UI tick-а сериализуются тем же coordinator-ом. Apply при занятой boundary возвращает retryable `RuntimeBusy(RendererLifecycle)`; hidden queue и partial mutation отсутствуют.
- `render-wgpu-video::WgpuSubmissionQueueBinding` разделяется decoder provider wrapper-ом и app materializer state. Queue меняется только после old-GPU drain. Pending submitted releases имеют exactly-once CAS guards; после доказанного device lost binding переводится в lost state, force-releases pending resources один раз, а поздние callbacks не могут сделать double release. Future late releases до rebind освобождаются сразу.
- DMA-BUF и HostPlanar materializers реализуют `WgpuFrameTextureViewMaterializer::recreate_for_renderer`, клонируя neutral provider и создавая только device-owned resources нового renderer-а. Молчаливый переход DMA-BUF <-> HostPlanar запрещён; он является typed candidate preparation failure.
- Renderer recreation failure остаётся typed через `RendererRecreationApplyError{Kind}`, `RendererRecreationRollbackError{Kind}` и `SettingsApplyFailure`. На любой creation/preparation/drain/commit error вызывается restore boundary. Только конкретный failed restore возвращает combined apply+rollback failure. Committed render snapshot обновляется лишь после owner success; failed route сохраняет старый runtime snapshot для retry того же draft.
- WGPU device lost отслеживается через `Device::set_device_lost_callback`; drain различает device lost, timeout, wrong submission index и poisoned lifecycle state.
- `RenderProfile::OpenGles` остаётся нереализованным renderer backend-ом и теперь возвращает typed `UnsupportedProfile` с сохранением active Vulkan path вместо ложного success/deferred restart.
- Focused fake lifecycle tests: success, no active video, resource busy, creation failure+restore, device lost+rollback failure, active DMA-BUF lease order, HostPlanar preservation, commit failure, resize/fullscreen conflict+retry. Settings tests закрепляют commit snapshot only after success и same-draft retry. Exactly-once release guard имеет render-wgpu-video unit test.
- Проверки 08C: app-egui 234 tests; player-core 474; render-wgpu-video 92; render-wgpu-shell 12; fastiplayer-settings 15; strict targeted Clippy; `cargo +1.96.0 check --workspace --locked`; refactor guardrails; playback smoke probe-only including installed FFmpeg runtime probe.
- End-to-end persistence order всё ещё принадлежит Session 08D: settings-core пока persist-ит перед runtime apply и фиксирует `PersistedRuntimeDiverged` на failure; 08C не удаляет этот transitional contract.

## Сессия 02a gles2-renderer (2026-10-24): на месте + «одно окно — одна surface»
- Причины давнего падения Apply `[render.vulkan]` (код 139 на Wayland): кандидат создавал вторую Vulkan-surface на том же `wl_surface`, пока старый рендер жив (Mesa: `wp_fifo_manager_v1 ... second fifo surface`); новый egui-wgpu рендер получал только частичные дельты атласа (паника `renderer.rs:672`).
- `RendererLifecycleCoordinator::recreate` сначала классифицирует: `renderer_recreation/settings_change.rs::classify_renderer_settings_change` → `Unchanged` (Noop) | `PresentationOnly` (изменился только `vulkan`: `run_presentation_reconfigure` → `RenderShell::reconfigure_presentation`, без кандидата/импорта/drain) | `FullRecreation` (profile/tone_mapping/opengles). Группы сравниваются целиком: новое device-bound поле внутри `[render.vulkan]` потребует уточнить классификатор по полям.
- Полная транзакция: `check_candidate_settings` (OpenGles → UnsupportedProfile ДО detach) → `detach_presentation` → prepare → release → drain → commit → resume. Откат `restore_after_failure(.., OldRendererWindow)`: кандидат уничтожается ДО `reattach_presentation`; провал reattach → `ApplyAndRollbackFailed` + `SurfaceInvalidated`; DeviceLost — старый рендер остаётся без окна, новый ставится из previous. Трейт `RendererRecreationLifecycle` +4 метода (`check_candidate_settings`, `reconfigure_presentation`, `detach_presentation`, `reattach_presentation`). Ошибки перенастройки: `RejectedPreviousRestored`/`PresentationDetached`/`AlphaPreferenceChangeUnsupported` → `ApplyFailed(RendererRecreationApplyErrorKind::PresentationReconfigure)`; `PresentationLost` → rollback `SurfaceInvalidated` (`renderer_recreation/presentation.rs`). Маппинг `[render.vulkan]` → `SurfacePresentSettings` — `render_backend::presentation_settings(family, ..)` (поле записи каталога).
- После установки нового рендера — `AppState::request_full_ui_texture_set(RendererInstalled)` (см. `mem:gles2-renderer/render-shell-contract`, 02a).
- Fake-тесты в `renderer_recreation/tests.rs` (события Detach/Reattach/Reconfigure/CandidateDestroyed). `LiveRendererRecreation` автотестов не имеет (окно + AppState) — живая приёмка 02a (Wayland/XWayland, HW/SW).
- Известный давний дефект (бэклог `user/general_problems/general_backlog.md` п. 12): `validate_renderer_candidate_capabilities` считает план по `active_video_stream_requirement`, которое не обновляется при commit кандидата очереди (`commit_installed_video_candidate`) → полное пересоздание на VP8 после H.264 отклоняется (с откатом).

## Submitted-release backend lifetime (2026-07-27)
- Each WGPU pending submitted release retains a renderer-neutral `VideoBackendLifetimeGuard` until callback cleanup or proven-device-lost force release. Replacing/dropping the playback decoder handle therefore cannot destroy a VA-API/FFmpeg backend before its delayed provider release reaches the decoder thread.
- `video-backend-api` owns the shared decoder/opaque guard boundary; `render-wgpu-video` owns callback registration and exactly-once CAS release. No WGPU type enters backend API and no concrete decoder type enters the renderer. Focused tests prove decoder owner survives playback-handle drop and is destroyed after the final pending guard drops.
- AMD Radeon 780M release-runtime acceptance (2026-07-27) exercised HostPlanar CPU upload and repeated VA-API NV12 DMA-BUF installs in one process, then clean shutdown. `Failed to send zero-copy release to decoder thread`/disconnect were absent; all sampled `decoder_release_control_send_fail_count` and `import_failures` stayed zero. One independent pre-barrier yt-dlp candidate `PreparationFailed` preserved active DMA-BUF playback and is not a backend-lifetime failure.
