# Render Video

- `video-frame-contract` owns neutral decoded frame/transfer vocabulary: `VideoFramePixelLayout` (`Nv12`, `P010`, host-planar YUV420 8/10, reserved `Rgba8`), `VideoFrameContract`, `VideoFrameTransferPath`, `HardwareFrameHandle`, and `DmaBufImageLayout` (`SeparateLayers`, `ComposedLayers`). It is the source of truth for pixel layout and transfer-contract vocabulary and must stay free of codec/video/render/backend deps.
- `video-core` owns decoded frame runtime contracts, `DecodedFrame.frame_contract`, `FrameResourceHandle`, neutral `FrameResourceDescriptor`, Linux `DmaBufFrameDescriptor`/object/layer descriptors, owned `HostPlanarFrameDescriptor`/plane metadata, descriptor-vs-contract validation, and video diagnostics. Current production WGPU render path still consumes DMA-BUF NV12/P010 zero-copy; HostPlanar exists as a safe owned resource descriptor for future host upload, but WGPU upload is not implemented.
- `FrameResourceHandle` is the public opaque resource key. The old `FrameTextureHandle` name/alias is removed. A decoded frame carries `resource_handle`; it does not promise a WGPU texture.
- `video-backend-api` owns the playback/backend boundary: `VideoBackendFactory`, `StartedVideoBackend`, `PresentFrameResourceProvider`, `PresentFrameResourceProviderHandle`, `PresentFrameResourceProviderLookup`, and `PresentFrameResourceDescriptorLookup`.
- Provider lookup is split by intent: playback-facing lookup reports `Ready`/`Busy`/`Missing`/`Fatal` plus resource-pool lock timing without GPU handles; renderer-facing descriptor lookup returns duplicated owned neutral descriptors. `Ready` descriptor lookup gives renderer-owned duplicated fds; provider keeps owning the decoder frame/resource until release.
- `player-core` consumes only `StartedVideoBackend` and renderer-neutral provider handles. It owns render lease accounting and keeps absent resource, busy pool, missing handle, fatal error, submitted/unsubmitted release, and stale-generation behavior distinct. It must not depend on `video-vaapi`, `render-wgpu-video`, `wgpu`, `ash`, or `wgpu-types`.
- `video-vaapi` owns VA display/probe/decode thread, cros decoder, VA surfaces, DMA-BUF export, neutral descriptor registration, `FrameResourcePool`, and VA surface lifetime until renderer release. It no longer depends on `wgpu`, `wgpu-types`, `ash`, or `render-wgpu-video`, and it must not create WGPU texture views or own a WGPU import/cache.
- `video-vaapi::VaapiVideoBackendFactory` is the production backend factory for composition. It returns a neutral `StartedVideoBackend`; there is no `VaapiWgpuVideoBackendFactory`, `VideoTextureViewProvider`, or app-side `VaapiWgpuFrameMaterializer` bridge.
- `render-wgpu-video` owns WGPU/Vulkan DMA-BUF import and texture cache. `DmaBufWgpuFrameMaterializer` consumes a `PresentFrameResourceProviderHandle`, requests duplicated descriptors, imports DMA-BUF descriptors to WGPU plane views, and returns `WgpuFrameTextureViewLookup`. `HostPlanar` descriptors are classified as typed `Unsupported { reason: HostPlanarRequiresUploadMaterializer }`, not `Missing` or `Fatal`, and are rejected before DMA-BUF import/cache code. Import failure is a renderer error; there is no hidden CPU fallback or WGPU host upload in this stage.
- `render-wgpu-video::wrap_video_backend_for_wgpu_submission` wraps the backend provider so submitted releases call the inner provider only from `wgpu::Queue::on_submitted_work_done`. Unsubmitted decoder releases still go through the decoder thread directly.
- Renderer live settings boundary lives in `render-core`: `RenderLiveSettings` groups color pipeline, HDR-to-SDR and typed shader parameter values; `RenderLiveSettingsAdapter` exposes preview/commit/rollback reports/errors without WGPU types. `render-wgpu-video::WgpuVideoRenderer` and `render-wgpu-shell::Renderer` implement this adapter using existing `set_color_pipeline_settings` / `set_hdr_to_sdr_settings`; live updates must not rebuild WGPU pipelines, decoder, or session. Current WGPU adapter supports color adjustment plus Phase 10 BT.2446-C SDR BT.709 HDR-to-SDR settings and reports future shader parameters/future color pipeline modes/out-of-contract HDR settings as unsupported.
- `render-core::RenderCapabilities.supported_frame_contracts` is `Vec<VideoFrameContract>` and is the renderer support source of truth. It binds pixel layout + transfer path + hardware handle layout together, so capability code must not reconstruct support from independent format/path/layout lists. Current WGPU constructors advertise `NV12 + DMA-BUF ComposedLayers` (NV12 baseline is composed-first export, so NV12 image layout is `ComposedLayers`, not `SeparateLayers`) and P010 DMA-BUF contracts only for feature-enabled layouts (`TEXTURE_FORMAT_16BIT_NORM` -> `SeparateLayers`, `TEXTURE_FORMAT_P010` -> `ComposedLayers`); production WGPU does not advertise software host upload. The dead heuristic that guessed an output contract from `VideoDecodeRequirement` is removed: `render_core::RenderCapabilities::supports_decode_requirement` + private `dma_buf_frame_contract_from_decode_requirement` and `capability_core::SystemCapabilities::find_supported_render_capability` were deleted; renderer support comes only from provider/renderer-declared `VideoFrameContract` intersection. `capability-core` stores provider-declared `BackendCapabilities.raw_supported_outputs` and system-level `SystemCapabilities.playable_video_outputs`; serialized capability schema version is 5 for the raw/playable supported-output report shape.
- `app-egui` is only composition wiring for concrete backend/materializer/shell. `video_pipeline_selector.rs` is the pure app-owned selector: it reads committed `video.preferred_backend`, the last `SystemCapabilities.playable_video_outputs`, and decoder-thread config intent, returning a concrete `VideoPipelinePlan` or typed selection error without starting VAAPI/WGPU resources. Current runnable plan is only `VaapiDmaBufWgpu`, requiring a playable VA-API output with `HardwareZeroCopy { DmaBuf { image_layout } }`; `AppState` then starts `VaapiVideoBackendFactory`, wraps the backend for WGPU completion, creates `DmaBufWgpuFrameMaterializer`, and passes neutral backend handles to `PlayerWorker`.
- `WgpuRenderableFrame` constructors validate decoded frame metadata through `DecodedFrame.frame_contract`: NV12 and P010 paths accept only `HardwareZeroCopy { DmaBuf { image_layout } }` contracts and reject host-upload/host-planar frames before renderer dispatch. Plane/metadata mismatch remains a render boundary error. Host-planar layouts remain unsupported by current WGPU render preparation because host upload is not implemented in this stage.
- P010 support depends on WGPU device features/layout: separate R16/Rg16 plane views or composed P010 path. Both become Y plus UV plane views at renderer boundary.
- SDR path shader: `nv12_to_rgba.wgsl`; HDR path shader: `p010_bt2446c_to_sdr.wgsl`; HDR output is SDR BT.709 via BT.2446 Method C. This split did not change the color pipeline/HDR policy.
- `render-core` owns renderer-neutral `RenderViewport { x, y, width, height }` in physical pixels, including intersection/subtract helpers for UI exclusion geometry. `app-egui` computes a full video underlay viewport plus renderer-neutral exclusion rects for UI that must hide video, currently only the left settings sidebar. Top bar, bottom controls, and right telemetry remain translucent overlays above video and must not shrink or exclude the video viewport. `render-wgpu-shell` clamps/defaults the content viewport and clamps exclusions against the current surface. `render-wgpu-video` uses the content viewport size for letterbox/aspect-ratio calculations, then draws through scissor rects produced by subtracting exclusions, while keeping full-target black clear. Scissor rects reduce fragment work (excluded area is not shaded), so sidebar exclusion is a perf win, not a cost; `RenderDiagnostics.video_draw_rect_count` (render-core, filled in `render_or_clear`, shown in telemetry panel) exposes the current rect count (1 = no exclusions, 0 = no video pass).
- `render-wgpu-shell` owns WGPU instance/device/surface shell, egui composition, frame timing, submit and present. It consumes `render-wgpu-video` for rendering/features and does not own decoded video resources.
- `app-egui` Busy texture-view/materialization fallback may reuse the previous cached renderable frame as a visual placeholder when lifecycle identity is still valid (same source, same render generation, current video frame present), even if player/timeline marks the frame stale during an active seek; this visual reuse must not count as seek landing. Missing/Fatal/Error/Unsupported clear the cached renderable frame and become typed render boundary errors; silent black-frame fallback is only acceptable before a frame exists.
- Dependency guardrails: `video-frame-contract` stays free of codec/video/render/backend deps and currently depends only on `serde`; `video-core`/`video-backend-api` stay free of WGPU/VAAPI/cros deps; `player-core` stays free of WGPU/render/backend concrete deps; `render-wgpu-video` stays free of `video-vaapi`; `video-vaapi` stays free of `wgpu`, `wgpu-types`, `ash`, `render-core`, and renderer crates. `scripts/check-refactor-guardrails.py` also checks no FFmpeg/libav deps, no public `ffmpeg_sw` option, no returned `video-ffmpeg`/`video-vulkan` workspace crate, and no WGPU host-upload materializer module in this preparation stage.
- Container display orientation is a metadata contract, not a decoder/resource ownership change. `codec-core::VideoDisplayOrientation` flows through `media-core::VideoTrackMetadata.orientation`, `video-core::VideoStreamDecodeConfig.display_orientation`, `video-core::DecodedFrame.display_orientation`, and `render-core::RenderableFrame.display_orientation`. Decode surfaces stay in coded orientation; renderer applies quarter-turn orientation via UV transform.
- `render-wgpu-video` letterboxing must use `RenderableFrame::oriented_display_width()` / `oriented_display_height()` and both NV12/P010 shaders must convert display UV to source texture UV before sampling. Keep NV12 and P010 orientation math shared through `display_orientation_uv_transform` so SDR/HDR paths do not diverge.
