# Render Video

- `video-frame-contract` owns neutral decoded frame/transfer vocabulary: `VideoFramePixelLayout` (`Nv12`, `P010`, explicit host-planar YUV420 8/10/12, YUV422 8/10/12, YUV444 8/10, reserved `Rgba8`; YUV444 12-bit intentionally deferred), `FrameBitDepth` (`Eight`/`Ten`/`Twelve`), `FrameChromaSubsampling` (`Yuv420`/`Yuv422`/`Yuv444`), `VideoFrameContract`, `VideoFrameTransferPath`, `HardwareFrameHandle`, and `DmaBufImageLayout` (`SeparateLayers`, `ComposedLayers`). It is the source of truth for pixel layout and transfer-contract vocabulary and must stay free of codec/video/render/backend deps; it does not imply renderer capability or host-upload implementation.
- `video-core` owns decoded frame runtime contracts, `DecodedFrame.frame_contract`, `FrameResourceHandle`, neutral `FrameResourceDescriptor`, Linux `DmaBufFrameDescriptor`/object/layer descriptors, provider-owned `HostPlanarFrameDescriptor` plus `HostPlanarFrameOwner`/`HostPlanarOwnedBuffer`, descriptor-vs-contract validation, and video diagnostics. Host-planar backing stays private behind the owner trait; renderer-facing code should use descriptor-level visible row access instead of reading backing storage directly. Current production WGPU render paths consume DMA-BUF NV12/P010 zero-copy and renderer-owned HostPlanar YUV host-upload textures for the v1 software matrix: YUV420 8/10/12, YUV422 8/10/12, and YUV444 8/10. HostPlanar 4:4:4 12-bit remains intentionally outside v1.
- `FrameResourceHandle` is the public opaque resource key. The old `FrameTextureHandle` name/alias is removed. A decoded frame carries `resource_handle`; it does not promise a WGPU texture.
- `video-backend-api` owns the playback/backend boundary: `VideoBackendFactory`, `StartedVideoBackend`, `PresentFrameResourceProvider`, `PresentFrameResourceProviderHandle`, `PresentFrameResourceProviderLookup`, and `PresentFrameResourceDescriptorLookup`.
- Provider lookup is split by intent: playback-facing lookup reports `Ready`/`Busy`/`Missing`/`Fatal` plus resource-pool lock timing without GPU handles; renderer-facing descriptor lookup returns duplicated owned neutral descriptors. `Ready` descriptor lookup gives renderer-owned duplicated fds; provider keeps owning the decoder frame/resource until release.
- `player-core` consumes only `StartedVideoBackend` and renderer-neutral provider handles. It owns render lease accounting and keeps absent resource, busy pool, missing handle, fatal error, submitted/unsubmitted release, and stale-generation behavior distinct. It must not depend on `video-vaapi`, `render-wgpu-video`, `wgpu`, `ash`, or `wgpu-types`.
- `video-vaapi` owns VA display/probe/decode thread, cros decoder, VA surfaces, DMA-BUF export, neutral descriptor registration, `FrameResourcePool`, and VA surface lifetime until renderer release. It no longer depends on `wgpu`, `wgpu-types`, `ash`, or `render-wgpu-video`, and it must not create WGPU texture views or own a WGPU import/cache.
- `video-vaapi::VaapiVideoBackendFactory` is the production backend factory for composition. It returns a neutral `StartedVideoBackend`; there is no `VaapiWgpuVideoBackendFactory`, `VideoTextureViewProvider`, or app-side `VaapiWgpuFrameMaterializer` bridge.
- `render-wgpu-video` owns WGPU/Vulkan DMA-BUF import/cache, renderer-side HostPlanar upload materialization, and WGPU video shader dispatch. `DmaBufWgpuFrameMaterializer` consumes a `PresentFrameResourceProviderHandle`, requests duplicated descriptors, imports DMA-BUF descriptors to WGPU plane views, and returns `WgpuFrameTextureViewLookup`; `HostPlanar` descriptors are still classified as typed `Unsupported { reason: HostPlanarRequiresUploadMaterializer }` in this DMA-BUF materializer, not `Missing` or `Fatal`. `HostPlanarWgpuFrameMaterializer` is a separate renderer-side upload boundary: it accepts only `FrameResourceDescriptor::HostPlanar`, rejects DMA-BUF with typed `Unsupported { reason: DmaBufRequiresDmaBufMaterializer }`, validates descriptor-vs-contract through `video-core`, uploads row-by-row from visible plane bytes into renderer-owned WGPU textures/cache, and supports the exact v1 host-upload matrix: YUV420 8/10/12, YUV422 8/10/12, and YUV444 8/10. 8-bit host-planar layouts use `R8Unorm` Y/U/V textures; 10/12-bit layouts use `R16Uint` Y/U/V textures and keep the original low-bit-depth code values in 16-bit words. Import/upload failure is a renderer error; there is still no hidden CPU YUV conversion fallback.
- `render-wgpu-video::wrap_video_backend_for_wgpu_submission` wraps the backend provider so submitted releases call the inner provider only from `wgpu::Queue::on_submitted_work_done`. Unsubmitted decoder releases still go through the decoder thread directly.
- Renderer live settings boundary lives in `render-core`: `RenderLiveSettings` groups color pipeline, HDR-to-SDR and typed shader parameter values; `RenderLiveSettingsAdapter` exposes preview/commit/rollback reports/errors without WGPU types. `render-wgpu-video::WgpuVideoRenderer` and `render-wgpu-shell::Renderer` implement this adapter using existing `set_color_pipeline_settings` / `set_hdr_to_sdr_settings`; live updates must not rebuild WGPU pipelines, decoder, or session. Current WGPU adapter supports color adjustment plus Phase 10 BT.2446-C SDR BT.709 HDR-to-SDR settings and reports future shader parameters/future color pipeline modes/out-of-contract HDR settings as unsupported.
- `render-core::RenderCapabilities.supported_frame_contracts` is `Vec<VideoFrameContract>` and is the renderer support source of truth. It binds pixel layout + transfer path + hardware handle layout together, so capability code must not reconstruct support from independent format/path/layout lists. `RenderCapabilities::supports_video_output`/`check_video_output` first require the exact renderer-declared contract, then compare the selected contract layout's bit-depth/chroma with stream metadata; they must not force host-planar outputs back through the hardware `Nv12`/`P010` hint helper. Current WGPU constructors advertise `NV12 + DMA-BUF ComposedLayers` (NV12 baseline is composed-first export, so NV12 image layout is `ComposedLayers`, not `SeparateLayers`), P010 DMA-BUF contracts only for feature-enabled layouts (`TEXTURE_FORMAT_16BIT_NORM` -> `SeparateLayers`, `TEXTURE_FORMAT_P010` -> `ComposedLayers`), and exact software host-upload contracts for the v1 matrix: `Yuv420Planar8/10Le/12Le`, `Yuv422Planar8/10Le/12Le`, and `Yuv444Planar8/10Le`. HDR-to-SDR support is per concrete frame contract: P010 and high-bit host-planar v1 layouts (10/12-bit where present) may use the GPU BT.2446-C path; 8-bit host-planar layouts do not satisfy HDR requirements. The dead heuristic that guessed an output contract from `VideoDecodeRequirement` is removed: `render_core::RenderCapabilities::supports_decode_requirement` + private `dma_buf_frame_contract_from_decode_requirement` and `capability_core::SystemCapabilities::find_supported_render_capability` were deleted; renderer support comes only from provider/renderer-declared `VideoFrameContract` intersection. `capability-core` stores provider-declared `BackendCapabilities.raw_supported_outputs` and system-level `SystemCapabilities.playable_video_outputs`; serialized capability schema version is 5 for the raw/playable supported-output report shape. Capability diagnostics now avoid masking concrete raw-output layout/readiness errors with an alternative same-family host-upload renderer contract.
- `app-egui` is only composition wiring for concrete backend/materializer/shell. `video_pipeline_selector.rs` is the pure app-owned selector: it reads committed `video.preferred_backend`, the last `SystemCapabilities.playable_video_outputs`, and decoder-thread config intent, returning a concrete `VideoPipelinePlan` or typed selection error without starting VAAPI/WGPU resources. Current runnable plan is only `VaapiDmaBufWgpu`, requiring a playable VA-API output with `HardwareZeroCopy { DmaBuf { image_layout } }`; `AppState` then starts `VaapiVideoBackendFactory`, wraps the backend for WGPU completion, creates `DmaBufWgpuFrameMaterializer`, and passes neutral backend handles to `PlayerWorker`.
- `WgpuRenderableFrame` constructors validate decoded frame metadata through `DecodedFrame.frame_contract`: NV12 and P010 render paths accept only `HardwareZeroCopy { DmaBuf { image_layout } }` contracts; `from_decoded_host_yuv` accepts exact v1 host-planar YUV `SoftwareHostUpload` contracts and binds separate Y/U/V upload texture views, while `from_decoded_host_yuv420` remains a compatibility wrapper. Plane/metadata mismatch remains a render boundary error. `WgpuVideoRenderer` dispatches HostPlanar YUV frames to the host-planar YUV renderer: 8-bit shader samples normalized `R8Unorm` planes and reuses the SDR color pipeline; high-bit shader reads `R16Uint` planes with `textureLoad`, derives chroma texels from subsampling/texture dimensions for 420/422/444, normalizes by source bit depth, and keeps HDR/tone mapping GPU-side. CPU still must not do YUV-to-RGB conversion.
- P010 support depends on WGPU device features/layout: separate R16/Rg16 plane views or composed P010 path. Both become Y plus UV plane views at renderer boundary.
- SDR DMA-BUF shader: `nv12_to_rgba.wgsl`; HDR DMA-BUF shader: `p010_bt2446c_to_sdr.wgsl`; HostPlanar YUV shaders: `host_yuv420_8bit_to_rgba.wgsl` for normalized `R8Unorm` planes and `host_yuv420_16bit_to_sdr.wgsl` for `R16Uint` 10/12-bit planes (filenames predate 422/444 support). HDR output is SDR BT.709 via BT.2446 Method C. Keep SDR color settings and HDR-to-SDR policy shared across DMA-BUF and host-upload paths where the contracts overlap.
- `render-core` owns renderer-neutral `RenderViewport { x, y, width, height }` in physical pixels, including intersection/subtract helpers for UI exclusion geometry. `app-egui` computes a full video underlay viewport plus renderer-neutral exclusion rects for UI that must hide video, currently only the left settings sidebar. Top bar, bottom controls, and right telemetry remain translucent overlays above video and must not shrink or exclude the video viewport. `render-wgpu-shell` clamps/defaults the content viewport and clamps exclusions against the current surface. `render-wgpu-video` uses the content viewport size for letterbox/aspect-ratio calculations, then draws through scissor rects produced by subtracting exclusions, while keeping full-target black clear. Scissor rects reduce fragment work (excluded area is not shaded), so sidebar exclusion is a perf win, not a cost; `RenderDiagnostics.video_draw_rect_count` (render-core, filled in `render_or_clear`, shown in telemetry panel) exposes the current rect count (1 = no exclusions, 0 = no video pass).
- `render-wgpu-shell` owns WGPU instance/device/surface shell, egui composition, frame timing, submit and present. It consumes `render-wgpu-video` for rendering/features and does not own decoded video resources.
- `app-egui` Busy texture-view/materialization fallback may reuse the previous cached renderable frame as a visual placeholder when lifecycle identity is still valid (same source, same render generation, current video frame present), even if player/timeline marks the frame stale during an active seek; this visual reuse must not count as seek landing. Missing/Fatal/Error/Unsupported clear the cached renderable frame and become typed render boundary errors; silent black-frame fallback is only acceptable before a frame exists.
- Dependency guardrails: `video-frame-contract` stays free of codec/video/render/backend deps and currently depends only on `serde`; `video-core`/`video-backend-api` stay free of WGPU/VAAPI/cros deps; `player-core` stays free of WGPU/render/backend concrete deps; `render-wgpu-video` stays free of `video-vaapi`; `video-vaapi` stays free of `wgpu`, `wgpu-types`, `ash`, `render-core`, and renderer crates. `scripts/check-refactor-guardrails.py` also checks no FFmpeg/libav deps, no public `ffmpeg_sw` option, and no returned `video-ffmpeg`/`video-vulkan` workspace crate. HostPlanar WGPU upload/render support is allowed for the exact v1 software matrix (YUV420 8/10/12, YUV422 8/10/12, YUV444 8/10), but the FFmpeg software provider/config/selector path must stay absent until its own implementation sessions.
- Container display orientation is a metadata contract, not a decoder/resource ownership change. `codec-core::VideoDisplayOrientation` flows through `media-core::VideoTrackMetadata.orientation`, `video-core::VideoStreamDecodeConfig.display_orientation`, `video-core::DecodedFrame.display_orientation`, and `render-core::RenderableFrame.display_orientation`. Decode surfaces stay in coded orientation; renderer applies quarter-turn orientation via UV transform.
- `render-wgpu-video` letterboxing must use `RenderableFrame::oriented_display_width()` / `oriented_display_height()` and both NV12/P010 shaders must convert display UV to source texture UV before sampling. Keep NV12 and P010 orientation math shared through `display_orientation_uv_transform` so SDR/HDR paths do not diverge.
