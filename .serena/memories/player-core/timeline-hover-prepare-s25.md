# Player Core Timeline Hover Prepare S25/S28

- S25 adds `PlayerSnapshot.timeline_hover_prepare: Option<TimelineHoverPrepareSnapshot>` as a read-only, player-owned guard/context DTO for app-side hover prepare/preview lookup. It carries selected video/audio track selection, video track timebase, source/backend revision guards, next SeekLanding-compatible scrub generation, exactness policy, and since S28C `TimelineHoverPrepareInteraction` (`Ordinary`, `OneShotSeekLandingResumePending { spare_capacity_available }`, `LiveScrubActive`). `player-core` derives that interaction from `seek_runtime`/validated hover slot config so `app-egui` does not infer one-shot-vs-live from `PlaybackState::Scrubbing`; active live scrub, including pointer-down simple scrub before preview decode, suspends hover prepare/preview, while one-shot resume-pending maps to the existing spare-capacity admission path. It does not change public `PlaybackState` and does not give app ownership over playback/session internals.
- `TimelineHoverPrepareSnapshot::target_pts(position)`, `TimelineHoverPrepareSnapshot::quantize_hover_target_position(position, seekable_range)`, and `TimelineHoverPrepareSnapshot::target_bucket(target_pts)` are the shared app/player helpers for prepared working-set keys. Since the hover target quantization fix, app-egui quantizes the semantic hover position upward with `HOVER_TARGET_QUANTIZATION_STEP = 250 ms` and clamps the last cell to the seekable range end before building `TimelineHoverTarget`; visual placement remains unquantized. `target_bucket` now returns the ceil-quantized grid cell index rather than raw microseconds. S17 `prepared_seek_landing_bucket` still delegates to this helper so HoverPreview borrow and SeekLanding promotion use matching bucket semantics; the click seek/commit target remains exact, and only the bucket index is quantized while working-set timing validation stays `TargetOrAfter` against the exact requested target.
- `player-core` remains the only owner of prepared branch promotion/removal and SeekLanding commit/release semantics. App-side HoverPreview only borrows cloned `VideoFrameLease`s via `PlayerTimelineHoverPrepareHandoff::borrow_prepared_frame`; promotion still happens through `PreparedSeekLandingRuntime::promote_for_seek`.
- S28 adds a named hover-session cleanup boundary on `PlayerTimelineHoverPrepareHandoff`: `release_hover_owned_entries_for_session_end(reason)` delegates to the neutral working set and returns primary/recent release counters. `app-egui` uses this only after timeline hover leave grace ends or is cancelled by a non-timeline action/click. It must not be used for SeekLanding promotion/commit; promoted SeekLanding resources are already removed from hover storage and remain transaction-owned until player-core finishes/demotes/releases them. Since S28D/S30C, `PlayerTimelineHoverPrepareHandoff::reconfigure_hover_prepare_primary_capacity(...)`, `reconfigure_hover_prepare_primary_capacity_protecting(...)`, and `reconfigure_recent_superseded_budget(...)` delegate live shrink/grow to the neutral working set without exposing storage fields. S30C also adds `PlayerRuntimeSettingsUpdate::with_frame_server_policy(...)`; `app-egui/settings_runtime` applies `[frame_server]` changes through the player worker boundary so `PlayerSession.frame_server_config` and `PlayerWorkerConfig.frame_server_config` update in-place instead of staying at startup values.
- Hover decode wiring additions on `PlayerTimelineHoverPrepareHandoff`: `publish_hover_stream_decode_context`/`clear_hover_stream_decode_context`/`hover_stream_decode_context` share the playback-accepted `PlayerHoverStreamDecodeContext { stream_config, resolved_color }` (published by `configure_decoder_stream_for_track` in capability_selection), and `insert_hover_prepared_frame(admission, lease, actual_pts)` is the production frame-only insert boundary (admission via working set; NoOp drops the lease release-once). Details: `mem:frame-server/hover-decode-execution`.
- Current source/backend revisions are still the existing untracked S17 constants until a future real source/backend revision provider is introduced. If those guards become real counters later, update both the snapshot builder and prepared seek helper together.
