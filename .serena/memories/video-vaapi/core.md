# Video VAAPI Core

- `video-vaapi` owns VA display/probe/decode thread, cros-codecs adapters, VA surfaces, DMA-BUF export, neutral `FrameResourcePool`, and VA surface lifetime until renderer/player release. It must stay free of `wgpu`, `wgpu-types`, `ash`, `render-wgpu-video`, `render-wgpu-shell`, and `player-core` direct dependencies.
- Internal codec adapter shell lives in `crates/video-vaapi/src/codec_adapter.rs`. It is not public API. `VaapiVideoDecoder` owns backend-local queues/resource registration and delegates submit/flush/events/stream-info/reuse intent to a boxed internal `VaapiCodecAdapter`. `VaapiDecodedFrameHandle::surface_ready() -> anyhow::Result<bool>` is the backend-local non-blocking VA surface readiness boundary for future suppressed-surface reclaim; it delegates to cros-codecs `DecodedHandle::try_is_ready()` and must preserve query errors instead of treating them as ready, while raw `VASurfaceStatus` stays below the adapter boundary. Adapter reuse is adapter-owned through `can_reuse_for_config(&VideoStreamDecodeConfig)`: default is `false` for config-sensitive codecs, VP9 explicitly preserves same-codec reuse/no-op semantics, and H.264/H.265 recreate until an exact-config reuse contract exists.
- Implemented adapter paths are VP9, H.264, and H.265 Main/Main10. VP9 wraps `cros_codecs::StatelessDecoder<Vp9, VaapiBackend<InternalVaapiFrame>>` and ignores packet hints. H.264 wraps `cros_codecs::StatelessDecoder<H264, VaapiBackend<InternalVaapiFrame>>` privately, requires configured `VideoStreamDecodeConfig` with H.264 packetization plus non-empty `codec_private`, parses `avcC`, converts access units through `codec-core::h264_access_unit_to_annex_b_into`, and feeds cros one NAL at a time until the access unit is fully consumed. H.264 SPS/PPS injection is driven by codec-neutral internal `VaapiPacketDecodeHints { inject_parameter_sets }` plus adapter lifecycle: inject only for decode-start/keyframe AU or the first AU after configure/flush. H.265 wraps `cros_codecs::StatelessDecoder<H265, VaapiBackend<InternalVaapiFrame>>`, requires `VideoStreamPacketization::H265`, accepts absent/incomplete `hvcC` when packetization/profile contract is otherwise safe, stores known VPS/SPS/PPS from `hvcC` and later in-band AUs, converts through `codec-core::h265_access_unit_to_annex_b_into`, and uses the same pending-AU/backpressure/CheckEvents retry lifecycle. H.265 capability advertisement is enabled only for physically supported Main 8-bit YUV420/NV12 and Main10 10-bit YUV420/P010 through the production capability intersection.
- H.264 adapter backpressure and lifecycle invariants: `CheckEvents` drains events and retries the same unconsumed NAL without double-consume; `NotEnoughOutputBuffers` preserves the pending access unit/offset and returns output backpressure to the decoder thread; seek flush/reconfigure clear pending input owned by the old stream generation. `H264AccessUnitPreparer` owns a reusable Annex B scratch buffer; `H264PendingAccessUnit` owns converted bytes until full consume; only after complete consume are bytes returned to scratch with capacity preserved. Parameter-set injection is codec-neutral at the VAAPI boundary via `VaapiPacketDecodeHints { inject_parameter_sets }`; H.264 interprets it as SPS/PPS, and H.265 interprets the same intent as VPS/SPS/PPS. Explicit EOF/DPB drain is a separate adapter intent (`begin_end_of_stream_drain`) and must fail if an access unit is only partially submitted; the H.264 implementation uses the cros-codecs flush primitive internally only to emit DPB tail events, not as player seek semantics. H.264 output remains NV12/DMA-BUF zero-copy only; CPU decode/upload/readback fallback is not allowed.
- `VaapiVideoDecoder` owns decoder event drain policy. Publish policy turns `FrameReady` into `DecodedFrame`, exports DMA-BUF, queues it in backend `ready_queue`, and assigns the caller-supplied seek generation at event-drain time. Discard policy is used by seek `flush()` after adapter flush: `FrameReady` handles from H.264 DPB tail are dropped without DMA-BUF export or `ready_queue` insertion, then decoder-owned ready frames are released; frames already handed to player/render remain untouched. `FormatChanged` is handled the same under both policies: release decoder-owned ready frames, invalidate idle resource mappings, and resize the VA output frame pool from adapter `stream_info()`.
- Accurate seek preroll output-floor is implemented inside `VaapiVideoDecoder` and exposed only through neutral `video-core` contracts on `VideoDecodeThread`/`VideoDecoderThreadHandle`. Active floor state tracks generation, floor PTS, retain-latest policy, and whether a target-or-after frame was published. Matching `FrameReady` with `pts < floor` is suppressed without DMA-BUF export or publish, emits `SeekPrerollFrameSuppressed`, and optionally retains only the latest pre-floor `VaapiDecodedFrameHandle` as EOF fallback candidate. Suppressed/candidate drop paths are backend-local reclaim ownership now: `VaapiVideoDecoder` queues dropped suppressed/candidate handles in a bounded `suppressed_reclaim_queue`, normal passes only call `VaapiDecodedFrameHandle::surface_ready()` and return `Ok(true)` handles, `Ok(false)` and query errors stay queued, and blocking `sync()` is reserved for rare overflow/lifecycle forced drain. Decode loop must run a cheap reclaim before submitting a new packet and return `VaapiDecodePacketOutcome::OutputBackpressured` before adapter submit if the queue remains full, preserving packet ACK/accounting. If queue overflow happens during event drain after an accepted packet, the backend may forced-sync only the oldest suppressed handle as a rare fatal-fallback path; forced sync failures are fatal decoder errors, not warnings. Lifecycle boundaries (`flush`, stream reconfigure, format change, output-floor set/clear, decoder drop) must force-drain retained candidate plus queue before old stream/pool state can be invalidated; flush/discard tail frames use sync+return rather than raw drop and log sync latency for Session E. Repeated seek/scrub during active preroll can pay blocking force-drain cost only on lifecycle boundaries; this is an intentional v1 safety trade-off that needs hardware measurement before designing async pending-destroy/detached-destroy. A matching target-or-after frame drops the candidate before normal `process_ready_frame`; target-or-after publish itself still uses the normal sync/export/register/publish path. EOF drain promotes the retained candidate at most once through `process_ready_frame` only when no target-or-after frame was published for the active floor generation. The reclaim bound is derived inside `VaapiDecoderRuntimeConfig` from surface pool accounting and can be varied for validation through the backend-local env override `RUSTIPLAYER_VAAPI_MAX_SUPPRESSED_RECLAIM_FRAMES`; do not add `video-core`/TOML API for this without an explicit architecture decision. Session E hardware validation relies on backend-local debug/warn logs rather than a neutral `video-core` diagnostic event: reclaim logs must expose queue depth, configured max, approximate available reclaim slots, approximate reserved surface headroom, enqueued suppressed handles, reclaimed count per pass, query errors, ring-full pre-submit backpressure, and forced sync fallback latency/counters.
- `decoder_thread` has internal control messages for `ConfigureStream(VideoStreamDecodeConfig, ack)`, `SetPrerollOutputFloor(VideoPrerollOutputFloor, ack)`, `ClearPrerollOutputFloor(VideoPrerollOutputFloorClear, ack)`, and explicit `BeginEndOfStreamDrain(generation, ack)`. Sender-side `configure_stream` prevalidates and updates cached config only after the decoder thread has recreated the adapter. Preroll floor set/clear returns neutral `VideoPrerollOutputFloorResult`, preserving Applied/Unchanged/Cleared/Backpressure/Fatal; backpressure uses `VideoDecoderControlBackpressureReason::ControlChannelFull`. EOF drain is acknowledged separately from seek flush, publishes tail frames through the normal frame channel, and keeps the player-visible state as `Draining` while backend-ready/pending/channel frames still exist. VAAPI now implements the neutral decoder activity boundary: `VideoDecodeThread::new_with_config` creates `VideoDecoderActivityNotifier`/`Subscription`, the handle stores the subscription and returns `decoder_activity_snapshot()`, and the decoder loop emits non-blocking activity on packet ACK, ready/published frame progress, diagnostic/error events, and EOF drain transitions (`Draining`, `Drained`, `Fatal`). Dropping the activity receiver is not fatal for decoder thread; it remains a typed wait-side state. This keeps cros/VAAPI implementation details inside the backend and avoids exposing VAAPI-specific public `video-core` API.
- VAAPI stream config validation is centralized through `VaapiCodecAdapterFactory::stream_config_rejection`; `decoder_thread::reject_unsupported_vaapi_stream_config` delegates there. VP9 Profile 0 accepts only 8-bit YUV420/NV12; VP9 Profile 2 accepts only 10-bit YUV420/P010; H.264 accepts ConstrainedBaseline/Main/High only as 8-bit YUV420/NV12 with valid packetization and `avcC`; H.265 accepts Main 8-bit YUV420/NV12 and Main10 10-bit YUV420/P010 with proven `VideoStreamPacketization::H265`, rejects known 4:2:2/4:4:4/12-bit/SCC variants, parses `hvcC` when present but does not require full VPS/SPS/PPS arrays if in-band parameter sets are allowed. H.264 High10/4:2:2/4:4:4/MVC/Stereo and VP9 Profile 1/3 remain unsupported/future.
- VAAPI probe records raw VA profiles/entrypoints/RT formats for diagnostics, but advertised `supported_video_decode_formats` are filtered through the validated production matrix. H.264 is advertised only for ConstrainedBaseline/Main/High 8-bit YUV420 when hardware profile, zero-copy export, and renderer materializer checks pass. H.265 is advertised only for Main 8-bit YUV420 and Main10 10-bit YUV420 when the hardware profile, DMA-BUF export, and renderer materializer/color policy checks pass; AV1/VP8 and unsupported H.264/H.265 variants are not advertised.
- `capability-core::CapabilityScanner` filters available backend formats for the final system report by DMA-BUF export plus registered renderer support. This means advertised system decode formats are the production intersection, not raw hardware capabilities.
- Reconfigure/flush cleanup must release only decoder-owned ready frames. Frames already handed to player/renderer remain guarded and must be released through the normal renderer/player release path.
- `VaapiVideoDecoder` stores `VideoStreamDecodeConfig.display_orientation` as stream metadata and copies it to `DecodedFrame.display_orientation`. VAAPI/cros adapters still decode/export coded surfaces; they must not rotate frames or add WGPU/render dependencies for display orientation.
