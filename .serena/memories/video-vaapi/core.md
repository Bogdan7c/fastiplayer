# Video VAAPI Core

- `video-vaapi` owns VA display/probe/decode thread, cros-codecs adapters, VA surfaces, DMA-BUF export, neutral `FrameResourcePool`, and VA surface lifetime until renderer/player release. It must stay free of `wgpu`, `wgpu-types`, `ash`, `render-wgpu-video`, `render-wgpu-shell`, and `player-core` direct dependencies.
- Internal codec adapter shell lives in `crates/video-vaapi/src/codec_adapter.rs`. It is not public API. `VaapiVideoDecoder` owns backend-local queues/resource registration and delegates submit/flush/events/stream-info to a boxed internal `VaapiCodecAdapter`.
- Production implemented adapters are VP9 and H.264. VP9 wraps `cros_codecs::StatelessDecoder<Vp9, VaapiBackend<InternalVaapiFrame>>`. H.264 wraps `cros_codecs::StatelessDecoder<H264, VaapiBackend<InternalVaapiFrame>>` privately, requires configured `VideoStreamDecodeConfig` with H.264 packetization plus non-empty `codec_private`, parses `avcC`, injects SPS/PPS through `codec-core`, converts AVCC access units to Annex B, and feeds cros one NAL at a time until the access unit is fully consumed.
- H.264 adapter backpressure invariants: `CheckEvents` drains events and retries the same unconsumed NAL without double-consume; `NotEnoughOutputBuffers` preserves the pending access unit/offset and returns output backpressure to the decoder thread; flush/reconfigure clear pending input owned by the old stream generation. H.264 output remains NV12/DMA-BUF zero-copy only; CPU decode/upload/readback fallback is not allowed.
- VAAPI stream config validation is centralized through `VaapiCodecAdapterFactory::stream_config_rejection`; `decoder_thread::reject_unsupported_vaapi_stream_config` delegates there. VP9 Profile 0 accepts only 8-bit YUV420/NV12; VP9 Profile 2 accepts only 10-bit YUV420/P010; H.264 accepts ConstrainedBaseline/Main/High only as 8-bit YUV420/NV12 with valid packetization and `avcC`; High10/4:2:2/4:4:4/MVC/Stereo and VP9 Profile 1/3 remain unsupported/future.
- `decoder_thread` has an internal `ConfigureStream(VideoStreamDecodeConfig, ack)` control message. Sender-side `configure_stream` prevalidates and updates cached config only after the decoder thread has recreated the adapter. This keeps cros/VAAPI implementation details inside the backend and avoids exposing a new public `video-core` control API.
- VAAPI probe records raw VA profiles/entrypoints/RT formats for diagnostics, but advertised `supported_video_decode_formats` are filtered through the implemented adapter matrix. H.264 is advertised only for ConstrainedBaseline/Main/High 8-bit YUV420 when hardware profile, zero-copy export, and renderer materializer checks pass. AV1/H.265/VP8 and unsupported H.264 variants are not advertised until production adapters exist.
- `capability-core::CapabilityScanner` filters available backend formats for the final system report by DMA-BUF export plus registered renderer support. This means advertised system decode formats are the production intersection, not raw hardware capabilities.
- Reconfigure/flush cleanup must release only decoder-owned ready frames. Frames already handed to player/renderer remain guarded and must be released through the normal renderer/player release path.
