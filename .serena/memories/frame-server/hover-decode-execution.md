# Active-Playback Hover Decode Execution (software V1)

- Real active-playback hover feed/drain decode execution is wired for the SOFTWARE playback class only. Hardware playback still degrades typed (no shared-VA hover decode branch yet, no cross-class fallback per plan). Paused/stopped reused-decoder hover prepare is still not wired (`PausedStoppedDependencySpanResolverNotWired`).
- Driver lives in `crates/app-egui/src/timeline_hover_decode.rs`: `TimelineHoverDecodeSession` owns a wrapped (`wrap_video_backend_for_wgpu_submission`) FFmpeg software hover backend decoder-thread handle + its `PresentFrameResourceProviderHandle` + `FfmpegSoftwareHoverReservation`. `drive_hover_span_decode` is an incremental per-UI-frame feed/drain pass: budget `HOVER_DECODE_FEED_PACKETS_PER_UI_FRAME = 32` packets/frame; drain-first loop; stale-generation and pre-target frames are released via `release_frame` (never inserted); first target-or-after frame becomes a `VideoFrameLease` (release sink = provider handle) and is inserted through `PlayerTimelineHoverPrepareHandoff::insert_hover_prepared_frame` -> `PreparedHit { ExactTargetOrAfter }`. Backpressure keeps the unsent `DecodePacket` in `pending_packet` (exactly-once delivery) and returns `Pressure { DecoderBackpressure }`. Demux EOF starts decoder EOS drain; `Drained` without a target frame -> typed `IncompleteSpan { EndOfStreamBeforeTarget }` (new variant in app + `ScrubHoverDependencySpanIncompleteReason`). Same-span continuation NEVER reseeks/flushes: resolver `decode_point_before` seek happens once per span; new span (span_id change) does flush + generation bump + reconfigure-if-changed.
- Stream config is NOT derived in app: player-core publishes `PlayerHoverStreamDecodeContext { stream_config, resolved_color }` into the shared handoff from `configure_decoder_stream_for_track` (capability_selection) after the playback decoder accepts it. Executor reads it via `handoff.hover_stream_decode_context()`; missing context -> typed NoOp `ActivePlaybackExecutorUnavailable`. Software->software reuse is valid because hover session uses same backend class/HostPlanar contract.
- Production insert boundary: `PlayerTimelineHoverPrepareHandoff::insert_hover_prepared_frame(admission, lease, actual_pts)` — frame-only entry (no branch token; SeekLanding promotion of these entries yields visual-override/resume_pending input). Admission mode maps from playback mode (`ResumePendingAfterSeek` -> `ResumePendingAfterSeekPin`, else `NormalHover`); protected key == prepared key (current target). On admission NoOp the lease is dropped inside (release-once) and outcome is typed `NoOp { reason }` -> executor `Pressure { ProviderBudgetExhausted }`.
- Session lifecycle: built in `AppState::rebuild_video_pipeline_with_decoder_config` (`build_software_hover_decode_session` in `state/video_backend.rs`) only for `VideoBackendKind::FfmpegSoftware`; startup goes through existing `start_software_hover_session` budget capability/admission; failures degrade typed with playback untouched. `AppTimelineHoverPrepareExecutor::set_decode_session` replaces the session, releasing old hover-owned entries via `release_hover_owned_entries_for_session_end(SourceOrBackendSwitched)` (new reason variant) because old-provider leases become invalid. Hover source loss (`set_hover_source`/`invalidate_hover_source`/`update_open_config`) cancels span decode state (demux position belongs to the dropped demuxer) via `cancel_hover_span_decode` (flush, keep session). Decoder fatal errors mark the session failed -> typed `ActivePlaybackExecutorUnavailable`; `DemuxReadFailed`/`TracksChanged` invalidate the hover source.
- Materializer identity invariant: resource handles are only valid inside their own provider, so hover-session leases MUST NOT be materialized by the playback materializer (handle collision can show a wrong frame, not just Missing). `AppState.timeline_hover_decode_materializer` is a second `HostPlanarWgpuFrameMaterializer` over the hover provider; `timeline_hover_preview_materializer_for_borrow` (ui_runtime) picks per-lease via `VideoFrameLease::resource_provider()` + `PresentFrameResourceProviderHandle::same_provider` (Arc ptr identity). Working set can mix providers (playback-lease recent_superseded entries + hover-session entries).
- Continuation pump: `pump_timeline_hover_decode_continuation` (ui_runtime, called from `handle_control_actions` when no hover intent arrived this frame) re-drives `prepare_hover_target(active_span_latest_target())` while `executor.has_pending_span_decode_work()`, gated on snapshot `timeline_hover_prepare` present and interaction != `LiveScrubActive`. Without it a motionless pointer would stall incremental decode.
- Known V1 limits: live `[frame_server]` hover budget changes do not rebuild an already-running hover decode session (applies on next backend rebuild); `post_target_reorder_drain_frames` is 0 from the resolver and no post-target reorder drain is performed; pre-target byproducts are released, not retained.
- Focused tests: `cargo test -p app-egui timeline_hover_prepare` (mod `decode_execution`: fake decoder thread + scripted demuxer cover prepared-hit/pre-target-release/budget-continuation-no-reseek/backpressure-no-loss/EOS-typed/stale-release/missing-config), `cargo test -p player-core handoff_tests` (context round-trip, insert+borrow+release-once, admission no-op release-once).
