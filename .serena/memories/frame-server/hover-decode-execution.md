# Active-Playback Hover Decode Execution (software V1)

- Real independent hover feed/drain decode execution is wired for the SOFTWARE playback class only. The same software hover session path is used for active playback and paused/stopped local-source hover when a software hover decode session exists; paused/stopped no longer depends on playback ticks. Hardware playback still degrades typed (no shared-VA hover decode branch yet, no cross-class fallback per plan), and live scrub / resume-pending restrictions remain owned by the existing playback-mode policy.
- Driver lives in `crates/app-egui/src/timeline_hover_decode.rs`: `TimelineHoverDecodeSession` owns a wrapped (`wrap_video_backend_for_wgpu_submission`) FFmpeg software hover backend decoder-thread handle + its `PresentFrameResourceProviderHandle` + `FfmpegSoftwareHoverReservation`. `drive_hover_span_decode` is an incremental per-UI-frame feed/drain pass: budget `HOVER_DECODE_FEED_PACKETS_PER_UI_FRAME = 32` packets/frame; drain-first loop; stale-generation frames and non-first pre-target frames are released via `release_frame`; the first decoded pre-target frame of a new span becomes an app-owned approximate visual-preview `VideoFrameLease` in `crates/app-egui/src/timeline_hover_approx_preview.rs` and is not inserted into the shared working set; the first target-or-after frame becomes a `VideoFrameLease` (release sink = provider handle) and is inserted through `PlayerTimelineHoverPrepareHandoff::insert_hover_prepared_frame` -> `PreparedHit { ExactTargetOrAfter }`. Backpressure keeps the unsent `DecodePacket` in `pending_packet` (exactly-once delivery) and returns `Pressure { DecoderBackpressure }`. App-side hover state tracks sent-but-not-ACKed packets via `drain_completed_packet_count()`; demux EOF must wait until in-flight/queued normal packets are complete before sending decoder EOS drain, because FFmpeg treats `send_packet(NULL)` as draining mode and normal packets after it require a flush. `Drained` without a target frame -> typed `IncompleteSpan { EndOfStreamBeforeTarget }` (new variant in app + `ScrubHoverDependencySpanIncompleteReason`). Same-span continuation NEVER reseeks/flushes: resolver `decode_point_before` seek happens once per span; new span (span_id change) does flush + generation bump + reconfigure-if-changed and clears any old approximate slot. If the software host-upload pool is full while the approximate slot is occupied, the slot is evicted with typed trace reason `ExactDecodePoolPressure` so exact decode cannot deadlock behind the visual keyframe. After `PreparedHit`, the controller clears its active span, releases the approximate slot, and asks the executor to flush completed decode work without releasing the prepared exact frame, so the next hover target must resolve/seek as a fresh span rather than retarget a completed span or leave queued packets behind.
- Stream config is NOT derived in app: player-core publishes `PlayerHoverStreamDecodeContext { stream_config, resolved_color }` into the shared handoff from `configure_decoder_stream_for_track` (capability_selection) after the playback decoder accepts it. Executor reads it via `handoff.hover_stream_decode_context()`; missing context -> typed NoOp `ActivePlaybackExecutorUnavailable`. Software->software reuse is valid because hover session uses same backend class/HostPlanar contract.
- Production insert boundary: `PlayerTimelineHoverPrepareHandoff::insert_hover_prepared_frame(admission, lease, actual_pts)` — frame-only entry (no branch token; SeekLanding promotion of these entries yields visual-override/resume_pending input). Admission mode maps from playback mode (`ResumePendingAfterSeek` -> `ResumePendingAfterSeekPin`, else `NormalHover`); protected key == prepared key (current target). On admission NoOp the lease is dropped inside (release-once) and outcome is typed `NoOp { reason }` -> executor `Pressure { ProviderBudgetExhausted }`.
- Session lifecycle: built in `AppState::rebuild_video_pipeline_with_decoder_config` (`build_software_hover_decode_session` in `state/video_backend.rs`) only for `VideoBackendKind::FfmpegSoftware`; startup goes through existing `start_software_hover_session` budget capability/admission; failures degrade typed with playback untouched. `AppTimelineHoverPrepareExecutor::set_decode_session` replaces the session, releasing old hover-owned entries via `release_hover_owned_entries_for_session_end(SourceOrBackendSwitched)` (new reason variant) because old-provider leases become invalid. Hover source loss (`set_hover_source`/`invalidate_hover_source`/`update_open_config`) cancels span decode state (demux position belongs to the dropped demuxer) via `cancel_hover_span_decode` (flush, keep session). Cached-present-frame lifecycle now distinguishes `DropOpenedSourcePreservingIdentity` from `ForgetSourceIdentity`: media open/player stopped/source-label/render-generation/current-frame cache invalidations drop the opened hover demuxer/span but keep the remembered `TimelineHoverSourceIdentity` so the next software hover can reopen the same active media; hard media boundaries, failed/shutdown/fatal forget the identity. Decoder fatal errors mark the session failed -> typed `ActivePlaybackExecutorUnavailable`; `DemuxReadFailed`/`TracksChanged` invalidate the hover source.
- Materializer identity invariant: resource handles are only valid inside their own provider, so hover-session leases MUST NOT be materialized by the playback materializer (handle collision can show a wrong frame, not just Missing). `AppState.timeline_hover_decode_materializer` is a second `HostPlanarWgpuFrameMaterializer` over the hover provider; `timeline_hover_preview_materializer_for_borrow` (ui_runtime) picks per-lease via `VideoFrameLease::resource_provider()` + `PresentFrameResourceProviderHandle::same_provider` (Arc ptr identity) for both exact working-set borrows and app-owned approximate preview borrows. Working set can mix providers (playback-lease recent_superseded entries + hover-session exact entries), while approximate keyframe leases bypass working set entirely and live only in the app-owned visual slot.
- Continuation/retry pump: `pump_timeline_hover_decode_continuation` (ui_runtime, called from `handle_control_actions` when no hover intent arrived this frame) re-drives `prepare_hover_target(active_span_latest_target())` while `executor.has_pending_span_decode_work()`, gated on snapshot `timeline_hover_prepare` present and interaction != `LiveScrubActive`. Retryable hover prepare outcomes request an egui repaint so the passive pump gets the next UI frame under `ControlFlow::Wait`: `DecodeBudgetExhausted`, decoder/resource/host-upload backpressure, and accepted prepared/working-set hits repaint; terminal/no-op/provider-budget outcomes intentionally do not, avoiding idle repaint loops. Visual preview materialization has a separate repaint policy: `BusyEmpty`/`BusyKeptLastReady` and `ApproximateReady` repaint, `WorkingSetMiss` repaints only while span decode work is pending, and terminal Missing/Unsupported/Error/TimingRejected outcomes do not. Without these repaint signals a motionless pointer can stall incremental decode, approximate-slot display, or a HostPlanar upload retry.
- Known V1 limits: live `[frame_server]` hover budget changes do not rebuild an already-running hover decode session (applies on next backend rebuild); `post_target_reorder_drain_frames` is 0 from the resolver and no post-target reorder drain is performed; only the first pre-target frame of a span is retained as an app-owned approximate visual keyframe, while later pre-target byproducts are released and never enter the working set.
- Focused tests: `cargo test -p app-egui timeline_hover_prepare` (mod `decode_execution`: fake decoder thread + scripted demuxer cover exact prepared-hit after approximate keyframe publish, approximate release-once for leave/span/session switch, pool-pressure eviction so exact decode continues, budget-continuation-no-reseek/backpressure-no-loss/EOS waits for decoder packet ACKs/EOS-typed/stale-release/missing-config/paused software hover), `cargo test -p app-egui timeline_hover` (also covers visual approximate fallback, repaint policy, source-identity-preserving reset, and completed-span restart), `cargo test -p player-core handoff_tests` (context round-trip, insert+borrow+release-once, admission no-op release-once).
