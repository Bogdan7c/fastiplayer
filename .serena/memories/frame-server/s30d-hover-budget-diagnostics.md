# S30D Hover Budget Diagnostics and Live Preflight

- S30D adds a narrow active-backend hover-budget diagnostics boundary for Frame Server settings. `video-backend-api` owns backend-local DTOs (`BackendHoverBudget*`) plus `HoverBudgetDiagnosticsProvider`/`HoverBudgetDiagnosticsProviderHandle`; it intentionally does not depend on `frame-server-core`, avoiding the `frame-server-core -> video-present-core -> video-backend-api` dependency cycle. Concrete backends convert between backend DTOs and neutral `frame-server-core::hover_budget` DTOs locally.
- Active playback backend startup attaches an optional read-only provider to `StartedVideoBackend`. `render-wgpu-video::wrap_video_backend_for_wgpu_submission` must preserve this provider handle when wrapping decoder release through the WGPU queue. `app-egui` stores only the cloneable provider handle from the currently active playback backend; it must not read VAAPI owner internals or duplicate provider logic.
- VAAPI provider facts live in `video-vaapi::shared_hardware_owner` and are hosted by the existing VA decoder/thread context. `VaapiSharedHardwareOwner::hover_admission_report` is read-only and does not create a hover reservation; real reservation remains through `reserve_hover_branch`/`admit_hover_reservation`. The owner still enforces one playback reservation plus max one hover reservation, strict hover surface budget below playback, provider-capacity pressure, and no second `VADisplay`/session/display export to app.
- FFmpeg software provider facts live in `video-ffmpeg::software_hover`. `FfmpegSoftwareHoverOwner::hover_admission_report` is read-only and separate from the mutating `admit_hover_reservation` path. It reports current software frame-pool and decoder-thread minima/capacity from the current playback decoder config/context; it must not invent hardcoded `1`, use `playback - 1`, adaptive growth, or backend-global cache.
- `app-egui::frame_server_budget` is the app-owned bridge. It builds the neutral `HoverBudgetRequest` for the active backend class, calls `resolve_hover_budget`, then asks the backend provider for read-only admission pressure and maps the result through `admit_hover_budget` for diagnostics. Telemetry shows backend kind, resolution/admission outcome, backend-reported minimum, playback budget, and resolved hover budget only when real provider data exists; do not fabricate missing values.
- Settings runtime preflight is deliberately narrow and lives at the app/settings boundary: `SettingsRuntime::apply_draft_with_runtime_adapter` calls `SettingsRuntimeReconfigureHost::preflight_frame_server_hover_budget_change` before validate/persist/controller committed apply/snapshot sync. It runs only as a read-only check over committed vs draft `[frame_server]` budget fields. Fixed-too-large changes are rejected with an apply report before TOML persist, settings committed mutation, app snapshot sync, player policy apply, or controller mutation.
- Already-loaded fixed-too-large values are diagnostics-only when unchanged: the config is not rewritten to `auto`, not silently clamped, not temporarily shrunk, and unrelated live changes can still apply. Live fixed-too-large rejection applies only when the matching fixed budget field changed in the draft. Explicit `0` remains invalid via config/settings validation and must never become a hidden hover-off switch.
- Focused checks for this boundary: `cargo test -p frame-server-core hover_budget`, `cargo test -p video-ffmpeg software_hover`, `cargo test -p video-vaapi shared_hardware_owner`, `cargo test -p app-egui hover_software_session`, `cargo test -p app-egui frame_server_budget`, `cargo test -p app-egui settings_runtime`, `cargo test -p app-egui state`, `cargo test -p app-egui telemetry_panel`, `cargo test -p video-backend-api hover_budget`, `cargo fmt --all --check`, `git diff --check`, and `scripts/check-refactor-guardrails.py`.
