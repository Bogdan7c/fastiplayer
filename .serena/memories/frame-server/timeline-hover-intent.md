# Frame Server Timeline Hover Intent

- S24 wires the real timeline pointer-hover stream in `app-egui` without sending player commands. The durable UI boundary is still `TimelineInteraction { actions, hover_intent, display_position }`: `TimelineAction` remains command-oriented (`Seek`/live scrub), while hover stays `ControlAction::TimelineHover` and never maps to `PlayerCommand::Seek`.
- Since S25, `TimelineHoverIntent::Target` carries a `TimelineHoverVisualTarget`: the semantic `TimelineHoverTarget` is still media-position only, and visual geometry is separate `TimelineHoverPreviewPlacement` from egui `Response::hover_pos()` + `Response::rect` in logical points. Geometry changes can update visual placement without republishing invisible prepare/decode target.
- App boundary: `crates/app-egui/src/state/ui_runtime.rs` coalesces all hover actions for one egui/app frame through `TimelineHoverFrameCoalescer`; latest target wins, with no debounce delay and no config knob. The coalesced invisible target drives the existing `TimelineHoverPrepareController`; there is no second hover/predecode target stream.
- `hover_preview_enabled=false` suppresses only visual materialization/presentation. Invisible prepare intent still emits and can drive the controller. Device/source incapability must degrade through typed executor/no-op outcomes, not by disabling the hover intent.
- S28 hover leave grace lives in `app-egui` as `state/timeline_hover_leave_grace.rs`, not in `timeline_hover_intent` or player-core. `TimelineHoverIntent::Clear` still clears the semantic active hover target and visual slot; `AppState` immediately cancels the active `TimelineHoverPrepareController` span on leave so grace does not extend decode range/window coverage. Grace only delays release of already prepared hover-owned working-set entries. `hover_leave_grace_ms` default is 500 ms, valid persisted range is `0..=500`; `0` means immediate release on leave only, not disabled hover/predecode. Re-enter before expiry cancels the pending release and preserves entries. Expiry releases once during normal UI frame processing; non-timeline UI controls/actions/hotkeys and passive primary pointer presses outside a timeline target/seek cancel pending grace and release immediately. No background thread/queue is used.
- S25 preview presentation lives in app/render state, not in `timeline_hover_intent.rs`: `frame_prepare/timeline_hover_preview.rs` borrows a shared prepared working-set `VideoFrameLease` through `PlayerTimelineHoverPrepareHandoff`, materializes via the S15 helper with `SharedVideoFrameLeaseRole::HoverPreview`, and never promotes/removes/releases branch ownership. Busy keeps the last ready preview only for the same semantic target; miss/timing rejected/missing/unsupported/error clears only preview borrow state.
- S25 adds retry materialization from the current pending visual slot so an unchanged hover target can show a frame that appears in the shared working set after the initial miss, without republishing invisible prepare.
- Player invariant remains: timeline hover sends no `PlayerCommand`, does not publish public `PlaybackState::Scrubbing`, and paused/stopped snapshots stay `Paused`/`Stopped`. Paused/stopped reused-decoder decode is still not implemented. Since S27, active-playback hover source opening stays app-owned: local files open an independent hover demuxer synchronously; direct HTTP opens through `service-direct-media` seekable Range owner APIs; YouTube VOD opens through `service-youtube` compact `YoutubeSelectedStreamIdentity` + range-only hover API. Network hover opening is background-only through `timeline_hover_network`: latest-only, max one in-flight per source, no queue, no auto-retry for the same failed target, `network_hover_prepare_throttle_ms` applies between starts (`0` removes only the delay), and target/source/config cancellation stale-ignores late results when real service cancellation is unavailable. Live/non-seekable network sources return typed unsupported/unavailable, hover open failure does not reset playback, and successful source open still ends in typed `SourceReadyDecodeNotWired` until real hover decode wiring lands.
- Render invariant: hover preview is an optional second video overlay pass through `render-wgpu-shell::RenderVideoOverlayInput`; the pass uses `WgpuVideoRenderer::render_overlay` with target load `LoadExisting`, preserving main video/egui pixels. Main video render path still owns the black clear. No CPU RGBA thumbnail/cache path exists.
