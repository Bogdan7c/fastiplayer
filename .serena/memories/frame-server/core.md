# Frame Server Core

- `frame-server-core` is a neutral contract crate for future frame-server/scrub work. It must stay free of `player-core`, `app-egui`, render/concrete backend/service crates, concrete audio backend/device/buffer timing types, and real lifecycle execution.
- Current deps: normal deps only on `media-core` and `video-present-core`; test-only deps may use neutral frame/codec crates to build representative descriptors. No external library/API docs are needed unless a future change adds a new external dependency.
- Protocol split is `ScrubIntent -> ScrubDriverOutcome -> ScrubEvent`: intents ask an external owner/driver to do lifecycle work, outcomes preserve concrete driver result categories without UI semantics, events are normalized public app/diagnostics publication.
- `ScrubIntent` is intentionally coarse-grained: `PrepareTarget`, `SeekDecodePointBefore`, `FeedAndDrain`, `Finish`, `Cancel`. Do not add public lifecycle-step intents for flush, clear queues, send packets, drain decoder, or runway checks.
- `ScrubTargetContext` carries mandatory guards: `SourceRevision`, `BackendRevision`, track selection, target media time + selected-video PTS, exactness policy, request kind, derived priority, and `ScrubGenerationToken`. Its fields are private so priority cannot diverge from request kind; use named getters.
- `ScrubGenerationToken { playback_generation, scrub_generation }` uses typed newtype-like fields. Mismatch of either playback generation or scrub generation marks intent/outcome/frame/readiness stale.
- `SeekDecodePointBefore` carries target/revision/generation intent only. `frame-server-core` must not calculate decode-safe anchors, store container-specific decode point types, or depend on concrete demux behavior.
- `ScrubDriverOutcome` keeps typed distinctions: audio resume pending/timeout/error, demux unsupported/unavailable, decoder backpressure, host-upload backpressure, resource busy, stale generation, cancelled, timeout, fatal. Avoid broad categories without typed subreason and avoid replacing this with `Result<Ready, ScrubError>`.
- `ScrubEvent` exposes normalized public events only: `Started`, `Progress`, `PreviewFrameReady`, `ResumePending`, `Committed`, `MatchedPlayback`, `Cancelled`, `Failed`. Driver-only details stay in `ScrubEventDiagnostics` / driver outcomes, not as public UI phases.
- S16/S17 payload boundary: `ScrubPreviewFrame` carries `ScrubFrameTiming { media_time, pts }`, `VideoPresentFrameIdentity`, and a neutral resource descriptor. `Committed` carries `committed_position`, `committed_frame_timing`, and `ScrubEventFrameIdentity`; `MatchedPlayback` carries `playback_position`, `matched_frame_timing`, and `ScrubEventFrameIdentity`. Video paths use `ScrubEventFrameIdentity::Video(VideoPresentFrameIdentity)`; video-less paths must use an explicit `NoVideoFrame` reason instead of silently omitting identity.
- `PreviewScrub` is documented as the only main-video real preview entrypoint. Do not model a second real-preview command.
- Audio resume timeout budget and readiness remain future `player-core` responsibilities through audio gate/clock/output/device timing boundaries. `frame-server-core` only accepts neutral driver-supplied budget metadata/outcomes.
- Real execution remains player-owned and close to current seek lifecycle: clear old floor -> flush decoder -> begin/nest scrub generation -> clear pending queues -> demux seek decode-point-before -> feed/drain through existing decoder I/O boundaries. Since S17A, `player-core` uses the neutral `ScrubStateMachine` for video one-shot SeekLanding from ordinary `PlayerCommand::Seek` and `EndScrub` release; `frame-server-core` protocol/public API did not change, and decoder/demux/audio ownership stays in `player-core`.
- S07 pure scheduler layer: `crates/frame-server-core/src/scheduler.rs` owns neutral scheduler state only: active work identity, bounded latest-only lanes for `SeekLanding`, `LiveScrub`, `HoverPreview`, and `TimelineHoverPrepareWindow`, live scrub throttle bookkeeping, and hover prepare slot accounting. It emits existing coarse `ScrubIntent::PrepareTarget` / `ScrubIntent::Cancel` through `SchedulerAction`; it must not own demux/decode/backend/render worker execution or add fine-grained decoder lifecycle intents.
- Scheduler public boundary is intent-based: `submit_seek_landing_target`, `submit_live_scrub_target`, `submit_hover_target`, `submit_timeline_hover_prepare_window`, `tick`, `complete_active_work`, and read-only snapshots for active/latest targets. Internals remain bounded: live and hover are latest-only, `every_drag_event` attempts each target by cancelling stale active work without building an event queue, live scrub suspends competing hover preview/prepare lanes for the same timeline gesture, and hover preview has no debounce/delay config.
- Frame-server config includes scheduler/working-set-neutral fields: `live_scrub_max_hz` default `60`, valid `1..=240`; `live_scrub_decode_mode` default `LiveScrubDecodeMode::ThrottledLatest` with alternative `EveryDragEvent`; primary hover prepare capacities `hover_prepare_window_slots` default `1`, valid `1..=3`, and `software_hover_prepare_window_slots` default `1`, valid `1..=2`; recent-superseded retention `recent_superseded_prepare_slots` default `1`, valid `0..=3`, and `software_recent_superseded_prepare_slots` default `1`, valid `0..=2`. No `hover_debounce_ms` knob exists, and the old `timeline_hover_prepare_slots` field was replaced during S08D.
- S12 persisted app config lives in `rustiplayer-config` as its own `[frame_server]` TOML type, not by reusing `frame-server-core::FrameServerConfig`, and `rustiplayer-config` must not depend on `frame-server-core`. Persisted fields include visual `hover_preview_enabled`, `auto`/positive fixed `hover_pool_frames` and `hover_thread_count`, hover/recent/network/live scrub knobs, and `live_scrub_decode_mode = "throttled_latest" | "every_drag_event"`; fixed budget `0` is invalid, no static upper cap/provider minimum/clamp is applied. Settings metadata is read-only/metadata-ready with route id `frame_server.apply`, and `rustiplayer-settings` intentionally does not map that route to runtime apply until real Frame Server wiring exists.
- S21 active-hover budget contract lives in `crates/frame-server-core/src/hover_budget.rs` and stays pure/neutral: `HoverBudgetRequest` carries per-resource requirements for hardware surface frames, software frame pool frames, and software thread count; `HoverBudgetCapabilityReport` carries backend-owned per-context minimum reports; `resolve_hover_budget` resolves `auto` to the smallest reported positive backend-capable minimum that is strictly below the matching playback budget, validates fixed positive values pairwise against the same resource class, rejects duplicate resource requirements as typed unsupported, and never uses `playback - 1`, cross-resource compensation, static generic minimums, adaptive growth, or backend-global cache. `HoverBudgetAdmissionReport`/`admit_hover_budget` is a separate provider-pressure/reservation step that preserves admitted/resource-pressure/unavailable/fatal distinctions. S22 implemented the real shared VA hardware reservation owner inside `video-vaapi::shared_hardware_owner` as a VAAPI-local accounting boundary hosted by the existing VA decoder construction/thread context; `frame-server-core` still only owns the neutral budget resolver/admission DTOs. FFmpeg hover session startup, selector orchestration, paused playback-decoder reuse, UI hover execution, and diagnostics wiring remain outside this crate for future sessions.
- S08A hover prepare working set lives in `crates/frame-server-core/src/working_set.rs`, with submodules under `crates/frame-server-core/src/working_set/`. `TimelineHoverPrepareWorkingSet` owns only bounded in-memory key/value/index/validation for prepared hover entries. Keys include source revision, track selection, backend revision, hover generation (`ScrubGenerationToken`), separate `FrameExactnessPolicy`, and target bucket. Values hold `VideoFrameLease`, actual frame timing metadata, and optional generic opaque branch token; no decoded bytes/pixel buffers, global cache, disk IO, concrete backend, render, app, or player dependency is allowed. Eviction drops the stored lease and relies on `video-present-core` RAII release-on-drop exactly once. Bucket is only an index: lookup first matches bucket/key, then validates actual timing. V1 `FrameExactnessPolicy::TargetOrAfter` accepts only actual PTS >= requested target PTS via `TrackTimestamp::cmp_timeline_position`; estimated duration is metadata only and must not prove exactness for VFR/irregular timing.
- S08B promotion boundary is pure `frame-server-core::working_set`: `TimelineHoverPrepareWorkingSet::promote_prepared_frame` takes the same guarded lookup request, reuses bucket/key/timing validation, and only then removes the owned entry from hover indexes/storage. It returns typed `TimelineHoverPreparePromotionOutcome`: resume-ready branch when an opaque branch token exists, visual-override/resume_pending input for frame-only entries, or preserved `Miss`/`TimingRejected` without side effects. `TimelineHoverPromotedPreparedFrame` owns the moved `VideoFrameLease` + timing + optional token after promotion; hover eviction/drop/leave cleanup must not release that resource. Since S17B, `player-core` consumes this neutral promotion boundary for one-shot SeekLanding prepared hits: player-core performs branch-token semantic validation fail-closed, owns the promoted lease in its transaction state, publishes a scrub visual override, and avoids cold demux/decode on valid prepared hits. `frame-server-core` still does not know real player lifecycle, branch semantics, network prepare, or broader pressure policy; fake transaction owners live only in frame-server tests.
- S08C recent-superseded retention lives under `crates/frame-server-core/src/working_set/`: `TimelineHoverPrepareWorkingSet` owns primary hover slots separately, plus a `recent_superseded` compartment for click-back. `try_demote_promoted_frame_to_recent_superseded` accepts only pre-commit `CancelScrubReason::SupersededByNewTarget`, requires the promoted key to match the current guarded lookup request, revalidates actual timing, and returns typed `TimelineHoverPrepareDemoteBackOutcome`/`TimelineHoverPrepareDemoteBackRejection` instead of a bool. User cancel, commit, and audio failure stay transaction release paths and do not demote. Lookup/promotion check primary hover first, then recent fallback; recent timing is still validated before hit/promotion, and primary wins when both validate. Recent retention uses `TimelineHoverRecentSupersededBudget::from_validated_config(...)` for validated slot counts, then selects the active budget by lease resource descriptor: general/hardware default `1`, valid config `0..=3`; software default `1`, valid config `0..=2`; zero disables only click-back retention for that path. Full non-zero recent budget evicts the oldest demoted entry for that path, never primary hover entries. Pointer movement/primary insert does not clear recent; `clear_recent_superseded(TimelineHoverRecentSupersededClearReason)` clears it for generation change, retention-disabled reconfig, or resource pressure.
- S08D pressure/protection accounting is still pure `frame-server-core` and does not query real backend/provider state. `TimelineHoverPrepareWorkingSet::evaluate_prepare_admission` accepts typed `TimelineHoverPrepareAdmissionRequest` with prepared key, protected current key, `TimelineHoverPrepareAdmissionMode` (`NormalHover`, `ResumePendingAfterSeekPin`, `ActiveLiveScrub`) and `TimelineHoverPrepareProviderBudget` (`SpareSlotAvailable`, `ExhaustedAfterActivePins`). It returns typed `TimelineHoverPrepareAdmissionOutcome`/`TimelineHoverPrepareNoOpReason` and does not mutate storage or release leases. `try_insert_prepared_frame` returns the entry to caller on no-op so provider pressure does not create hidden release side effects. `release_one_for_resource_pressure` releases one hover-owned entry in S08D order: `recent_superseded` first, then oldest primary byproduct; it never releases the protected current pointer/focus target. Promoted S17 resources are protected because promotion removes them from hover storage and ownership lives in `TimelineHoverPromotedPreparedFrame` until transaction finish/demote. Primary byproducts use Latest-N by evicting the oldest byproduct while preserving the protected key; `ResumePendingAfterSeekPin` requires an actual spare primary slot and provider budget after the seek-owned pin, while active live scrub suspends hover prepare.
- S09 scrub state machine lives in `crates/frame-server-core/src/state_machine.rs`. `ScrubStateMachine` is pure and step-driven: it accepts generation-free `ScrubTargetUpdate` plus driver `ScrubDriverOutcome`/cancel requests, owns and increments `scrub_generation`, builds guarded `ScrubTargetContext`, and emits only existing coarse `ScrubIntent` plus normalized `ScrubEvent`. It does not own decoder/demux/audio/render resources, does not perform I/O, and must not add concrete backend/player-core deps.
- S09 state-machine boundaries: `ScrubTargetUpdateGuards` carries source/backend/playback guards without scrub generation; `ScrubExecutionPolicy` carries coarse feed/drain stop condition and finish policy; `ScrubStep` returns up to two coarse intents plus one event without heap allocation; active live scrub ignores hover/prepare target updates until live release/cancel, so hover resumes only through a new hover/focus target after live ownership ends.
- S09 focused tests live in `crates/frame-server-core/src/state_machine_tests.rs`: protocol order `PrepareTarget -> SeekDecodePointBefore -> FeedAndDrain`, fake driver lifecycle order `flush/clear before demux seek`, stale/mismatched guard rejection, `PreviewFrameReady -> Finish -> Committed` happy path without leaking driver-only details as public events, rich outcome mapping without collapsing typed backpressure/resource/demux/timeout categories to fatal, latest-only generation/cancellation, hover suspended during live scrub, and cancellation event+cancel intent.
- S10 exact fake transaction flow stays inside `frame-server-core` and keeps public intents coarse. Driver outcomes now distinguish `PreTargetReleased` and `ExactFrameReady`: pre-target release normalizes to public `ScrubEvent::Progress` and loops `FeedAndDrain`; exact ready normalizes to public `ScrubEvent::PreviewFrameReady` and emits `Finish`. `PreviewFrameReadyOutcome` remains for normalized preview-compatible readiness, but exact scrub tests should prefer `ExactFrameReadyOutcome` when asserting target-or-after semantics.
- S10 focused exact-flow tests live in `crates/frame-server-core/src/state_machine_tests/exact_flow.rs`. The fake transaction driver models one reused decoder handle (flush, not new session), records prepare/flush/clear before demux seek, releases every pre-target decoded frame without publishing, publishes only the first target-or-after frame, and verifies late exact frames after replacement/cancel are ignored.
- S11 diagnostics snapshot/counters live in `crates/frame-server-core/src/diagnostics.rs` and are re-exported from `lib.rs`: `ScrubDiagnosticsRecorder` accumulates bounded typed counters and returns copyable `ScrubDiagnosticsSnapshot`. Metrics cover request accepted/cancelled/completed by `ScrubRequestKind`, driver outcome/reason counts including `cold_decode_in_progress` for `Progressed`/`BeforeTarget`, scheduler diagnostics, queue age/decode/demux latency summaries, packet/drop count summaries, resource pressure split into resource busy/decoder backpressure/host-upload backpressure, working-set hit/miss/eviction/pressure-release counters, and since S20 latest-only live-scrub diagnostics. S20 neutral DTOs are `LiveScrubSettingsSnapshot`, `DeferredLiveScrubSettingsChange`, and `LiveScrubDiagnostics`; they carry the pointer-down decode settings snapshot, bounded deferred mid-drag settings change count + latest old/new snapshot only, and UI-side `throttled_latest` skip count distinct from decoder/resource backpressure. They intentionally contain no timestamp, drag id, source target, UI hint/status, ring buffer, or history. This remains neutral storage/protocol only: no player/app execution ownership, no I/O, no unbounded event history, and typed boundary results are recorded instead of reading scheduler/working-set internals.
- S11 diagnostics focused tests live in `crates/frame-server-core/src/diagnostics_tests.rs`: lifecycle counters by request kind, cancelled vs stale-generation separation, cold-decode progress, rich typed failure/resource-pressure counts, and queue/latency/count/working-set summaries.
- S18 app-owned timeline hover prepare boundary now lives in `app-egui` (`crates/app-egui/src/timeline_hover_prepare.rs`) while continuing to use `frame-server-core` neutral key/lookup/working-set vocabulary. `app-egui` has a direct dependency on `frame-server-core` for this controller boundary. The production S18 executor is working-set-only/no-op until a safe hover executor exists; it must not send ordinary `PlayerCommand::Seek`, accept actual PTS before the requested target as an exact prepared hit, insert approximate/keyframe hits, create a second VA display/session, or change real timeline UI before S24. S17 promotion still happens in `player-core` through the same shared working-set handoff.
- Focused checks for this crate: `cargo test -p frame-server-core`, `cargo check -p frame-server-core`, `cargo fmt --all --check`, plus `scripts/check-refactor-guardrails.py` when dependency/public boundaries change materially.
- Scheduler focused tests live in `crates/frame-server-core/src/scheduler_tests.rs`: priority/preemption, live latest-only, throttled vs every-drag live modes, hover latest-target coalescing, hover prepare window budget, live-scrub suspension of hover preview/prepare, and typed cancellation/throttle diagnostics.
- Working-set focused tests live in `crates/frame-server-core/src/working_set_tests.rs`: exact hit, stale source/backend/hover generation misses, bucket collision timing rejection, VFR estimated-duration non-proof, hardware/software lease-resource metadata only, opaque branch token identity, eviction release-once behavior, promotion validation-before-removal, typed promotion miss/reject side effects, shared preview+seek lease ownership, frame-only visual override vs resume-ready branch, fake transaction commit/cancel/audio-failure release-once behavior, recent-superseded demote/click-back/lookup-order behavior, S08D pressure order, protected current/promoted resources, primary byproduct Latest-N, provider-pressure no-op side effects, and resume_pending spare-slot admission.
