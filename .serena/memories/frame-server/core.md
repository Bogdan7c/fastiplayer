# Frame Server Core

- `frame-server-core` is a neutral contract crate for future frame-server/scrub work. It must stay free of `player-core`, `app-egui`, render/concrete backend/service crates, concrete audio backend/device/buffer timing types, and real lifecycle execution.
- Current deps: normal deps only on `media-core` and `video-present-core`; test-only deps may use neutral frame/codec crates to build representative descriptors. No external library/API docs are needed unless a future change adds a new external dependency.
- Protocol split is `ScrubIntent -> ScrubDriverOutcome -> ScrubEvent`: intents ask an external owner/driver to do lifecycle work, outcomes preserve concrete driver result categories without UI semantics, events are normalized public app/diagnostics publication.
- `ScrubIntent` is intentionally coarse-grained: `PrepareTarget`, `SeekDecodePointBefore`, `FeedAndDrain`, `Finish`, `Cancel`. Do not add public lifecycle-step intents for flush, clear queues, send packets, drain decoder, or runway checks.
- `ScrubTargetContext` carries mandatory guards: `SourceRevision`, `BackendRevision`, track selection, target media time + selected-video PTS, exactness policy, request kind, derived priority, and `ScrubGenerationToken`. Its fields are private so priority cannot diverge from request kind; use named getters.
- `ScrubGenerationToken { playback_generation, scrub_generation }` uses typed newtype-like fields. Mismatch of either playback generation or scrub generation marks intent/outcome/frame/readiness stale.
- `SeekDecodePointBefore` carries target/revision/generation intent only. `frame-server-core` must not calculate decode-safe anchors, store container-specific decode point types, or depend on concrete demux behavior.
- `ScrubDriverOutcome` keeps typed distinctions: audio resume pending/timeout/error, demux unsupported/unavailable, decoder backpressure, host-upload backpressure, resource busy, stale generation, cancelled, timeout, fatal. Avoid broad categories without typed subreason and avoid replacing this with `Result<Ready, ScrubError>`.
- `ScrubEvent` exposes normalized public events only: `Started`, `Progress`, `PreviewFrameReady`, `ResumePending`, `Committed`, `MatchedPlayback`, `Cancelled`, `Failed`. Driver-only details stay in `ScrubEventDiagnostics` / driver outcomes, not as public UI phases.
- `PreviewScrub` is documented as the only main-video real preview entrypoint. Do not model a second real-preview command.
- Audio resume timeout budget and readiness remain future `player-core` responsibilities through audio gate/clock/output/device timing boundaries. `frame-server-core` only accepts neutral driver-supplied budget metadata/outcomes.
- Future real execution order remains player-owned and close to current seek lifecycle: clear old floor -> flush decoder -> begin/nest scrub generation -> clear pending queues -> demux seek decode-point-before -> feed/drain through existing decoder I/O boundaries.
- Focused checks for this crate: `cargo test -p frame-server-core`, `cargo check -p frame-server-core`, `cargo fmt --all --check`, plus `scripts/check-refactor-guardrails.py` when dependency boundaries change.
- S07 pure scheduler layer: `crates/frame-server-core/src/scheduler.rs` owns neutral scheduler state only: active work identity, bounded latest-only lanes for `SeekLanding`, `LiveScrub`, `HoverPreview`, and `TimelineHoverPrepareWindow`, live scrub throttle bookkeeping, and hover prepare slot accounting. It emits existing coarse `ScrubIntent::PrepareTarget` / `ScrubIntent::Cancel` through `SchedulerAction`; it must not own demux/decode/backend/render worker execution or add fine-grained decoder lifecycle intents.
- Scheduler public boundary is intent-based: `submit_seek_landing_target`, `submit_live_scrub_target`, `submit_hover_target`, `submit_timeline_hover_prepare_window`, `tick`, `complete_active_work`, and read-only snapshots for active/latest targets. Internals remain bounded: live and hover are latest-only, `every_drag_event` attempts each target by cancelling stale active work without building an event queue, live scrub suspends competing hover preview/prepare lanes for the same timeline gesture, and hover preview has no debounce/delay config.
- Frame-server config now includes scheduler-neutral fields: `live_scrub_max_hz` default `60`, valid `1..=240`; `live_scrub_decode_mode` default `LiveScrubDecodeMode::ThrottledLatest` with alternative `EveryDragEvent`; `timeline_hover_prepare_slots` default `1`, valid `1..=3`. No `hover_debounce_ms` knob exists.
- Scheduler focused tests live in `crates/frame-server-core/src/scheduler_tests.rs`: priority/preemption, live latest-only, throttled vs every-drag live modes, hover latest-target coalescing, hover prepare window budget, and typed cancellation/throttle diagnostics.
