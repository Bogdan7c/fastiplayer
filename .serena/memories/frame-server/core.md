# Frame Server Core

- `frame-server-core` is a neutral contract crate for frame-server/scrub protocols. It must stay free of `player-core`, `app-egui`, render crates, concrete backend crates, service crates, concrete audio/device/buffer timing types, and real lifecycle execution.
- Current normal deps remain neutral: `media-core` and `video-present-core`. Test-only deps may use neutral frame/codec crates to build representative descriptors.
- Since 2026-07-03, hover preview / hover predecode / timeline hover prepare are removed from the project. Removed pieces include hover request kinds/priorities, hover scheduler lanes, hover budget resolver/admission DTOs, hover diagnostics DTOs/counters, prepared hover working set/recent-superseded storage, app-side hover executors/sources/network helpers, backend hover budget providers, FFmpeg software-hover session, VA shared-hover reservation path, and renderer hover overlay.
- Frame server is still intentionally kept for `SeekLanding`, `LiveScrub`, and future playback-rate frame serving. Do not reintroduce hover-specific lanes, settings, diagnostics, working sets, backend reservations, render overlays, or app executors when extending frame-server behavior.
- Protocol split remains `ScrubIntent -> ScrubDriverOutcome -> ScrubEvent`: intents ask an external owner/driver to do lifecycle work, outcomes preserve concrete driver result categories without UI semantics, and events are normalized public app/diagnostics publication.
- `ScrubIntent` stays coarse-grained: `PrepareTarget`, `SeekDecodePointBefore`, `FeedAndDrain`, `Finish`, `Cancel`. Do not add public lifecycle-step intents for flush, clear queues, send packets, drain decoder, or runway checks.
- `ScrubTargetContext` carries source/backend/playback guards, track selection, target media time + selected-video PTS, exactness policy, request kind, derived priority, and `ScrubGenerationToken`. Its fields are private so priority cannot diverge from request kind; use named getters.
- `ScrubGenerationToken { playback_generation, scrub_generation }` uses typed newtype-like fields. Mismatch of either playback generation or scrub generation marks intent/outcome/frame/readiness stale.
- `ScrubRequestKind` now covers only `SeekLanding` and `LiveScrub`. `ScrubPriority` now covers only `UserCommit` and `LiveScrub`.
- `ScrubDriverOutcome` must keep typed distinctions: audio resume pending/timeout/error, demux unsupported/unavailable, decoder backpressure, host-upload backpressure, resource busy, stale generation, cancelled, timeout, fatal. Avoid broad categories without typed subreason and avoid replacing this with a generic `Result<Ready, ScrubError>`.
- `ScrubEvent` exposes normalized public events only: `Started`, `Progress`, `PreviewFrameReady`, `ResumePending`, `Committed`, `MatchedPlayback`, `Cancelled`, `Failed`. Driver-only details stay in `ScrubEventDiagnostics` / driver outcomes, not as public UI phases.
- S16/S17 payload boundary remains: `ScrubPreviewFrame` carries `ScrubFrameTiming { media_time, pts }`, `VideoPresentFrameIdentity`, and a neutral resource descriptor. `Committed` carries committed timing/identity; `MatchedPlayback` carries matched playback timing/identity. Video paths use `ScrubEventFrameIdentity::Video(VideoPresentFrameIdentity)`; video-less paths must use explicit `NoVideoFrame` reason.
- Scheduler is pure state only. It owns active work identity, latest-only live-scrub target state, live-scrub throttle bookkeeping, and SeekLanding target state. It emits existing coarse `ScrubIntent::PrepareTarget` / `ScrubIntent::Cancel` through `SchedulerAction`; it must not own demux/decode/backend/render worker execution or add fine-grained decoder lifecycle intents.
- Public scheduler boundary is intent-based: submit SeekLanding or LiveScrub targets, tick, complete active work, and read snapshots. Live scrub may use `LiveScrubDecodeMode::ThrottledLatest` or `EveryDragEvent`; hover suspension rules no longer exist.
- Persisted config surface is in `rustiplayer-config`, not by reusing `frame-server-core::FrameServerConfig`. Current persisted frame-server fields are only live-scrub related: `live_scrub_enabled`, `live_scrub_decode_mode`, and `live_scrub_max_hz` (valid `1..=240`). `rustiplayer-config` must not depend on `frame-server-core`.
- Config schema v5 removed hover/predecode keys from `[frame_server]`. Legacy v4 loading strips those removed keys before strict serde so existing user TOML remains bootable, then migrates `schema_version` to current. Current v5 configs must reject, not silently accept, removed hover keys. The cleaned config must not expose, validate, show, route, or write those keys.
- Diagnostics remain neutral and bounded around lifecycle, driver outcomes, request counters, queue/decode/demux latency summaries, resource pressure, scheduler diagnostics, and live-scrub settings/deferred-change counters. Removed hover/prepared diagnostics must not be reintroduced.
- Real execution remains player-owned and close to current seek lifecycle: clear old floor -> flush decoder -> begin/nest scrub generation -> clear pending queues -> demux seek decode-point-before -> feed/drain through existing decoder I/O boundaries. `player-core` consumes the neutral state machine for one-shot SeekLanding and live scrub; decoder/demux/audio ownership stays in `player-core`.
- Focused checks for frame-server boundary changes: `cargo check -p frame-server-core`, `cargo check --tests -p frame-server-core`, `cargo check --tests -p player-core`, `cargo check --tests -p app-egui`, `cargo fmt`, and `scripts/check-refactor-guardrails.py` when dependency/public boundaries change materially.
