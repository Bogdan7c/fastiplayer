# Symphonia Demux DecodePointBefore Startup

- `DecodePointBefore` verification remains strict for ordinary seeks: the selected video decode-start packet must be at/before the requested target, within accepted preroll, and not a proven non-keyframe.
- The only accepted after-target exception is media startup after zero or a near-zero restored position. `requested <= DECODE_POINT_BEFORE_NEAR_ZERO_TARGET_TOLERANCE` (currently 1 ms) may accept a selected video packet after target only when it is not `PacketKeyframe::NotKeyframe` and its PTS is within `DECODE_POINT_BEFORE_STARTUP_LEAD_TOLERANCE` (currently 250 ms). The 1 ms bound covers persisted/container time-base drift such as the observed `10.417 µs`, while a regular 2 ms seek remains strict.
- On this accepted startup path, `seek_result_with_verified_video_packet()` still reports `actual_position` as the accepted packet PTS so player-core seek gates can wait for `frame_pts >= actual_position` instead of an unavailable zero frame.
- Regression coverage in `crates/symphonia-demux/src/symphonia_demuxer/tests.rs`: zero startup, exact `10.417 µs` restore drift, the negative 2 ms boundary, and lead-window rejection. Real H.264 fixture coverage in `crates/symphonia-demux/tests/h264_fixtures.rs::h264_bframe_startup_seek_to_zero_accepts_first_decode_point` covers the 4k30/4k60 problem assets.

## RC1: initial seek anchors near target (nearest keyframe), not target − preroll
- `seek_decode_point_before` initial backend seek now targets `requested − DECODE_POINT_BEFORE_INITIAL_SEEK_MARGIN` (1 ms), NOT `requested − decode_point_before_preroll`. So stss/cues snap to the NEAREST decode-safe keyframe ≤ target instead of a keyframe several GOPs earlier. `decode_point_before_preroll` (5 s) is now ONLY the retry backoff step (`decode_point_before_expanding_retry_timestamp`) when the first attempt lands on a non-keyframe / after target; `max_accepted_preroll = max(10 s, preroll)` is unchanged. The 1 ms margin keeps `initial < requested`, so the FirstVideoTooFarBeforeTarget rescue and after-target/expanding retries (and their tests) still trigger.
- Why: the old 5 s initial over-seek was the PRIMARY accurate-seek latency cause on iOS HEVC MOV (GOP ~0.93 s). It anchored ~5.7 s / 6 keyframes before target, blowing up BOTH the demux scan (dense PCM: ~237k pre-target audio packets read+dropped one-by-one, starving the idle video decoder ~5.6 s) AND the decode chain (decode ~170–320 frames vs ~3–36). Verified via `/tmp/fastiplayer-seek-probe` (media-core+symphonia-demux headless, `[replace]` isomp4 patch): ios-hevc-pcm.mov (pcm_s16le, 9.18M audio packets) actual 88655→94253, events_seen 237085→5; ios-hevc-main10-aac-4k60.mov (AAC) actual 4751→9453, pre-target video 318→36. RC2 (a demux audio-skip boundary / PCM coalescing) looks unnecessary once RC1 lands — residual scan is ~5 events.
- Verification not weakened: `decode_point_before_packet_issue` / `verify_decode_point_before_attempt` unchanged. New test `decode_point_before_initial_seek_targets_requested_not_far_preroll`; `h265_ios_mov_decode_point_before_seek_starts_on_sync_sample` strengthened to assert actual ≥ target − 1.5 s; dual-stream forwards target − 1 ms (test updated 5000→9999). Verification stays strict per `mem:symphonia-demux/decode-point-before-startup` core rules.

## Session G: WebM/VP9 too-far rescue stays inside accepted preroll window
- VP9/WebM fixture `<MEDIA_DIR>/vp9-opus-4k60-sdr.webm` exposed a DecodePointBefore retry oscillation at requested `66.93240338s`: initial attempts around target landed after the usable keyframe; expanding retry to `31.931s` produced `first_video_too_far_before_target`; old rescue jumped back to target, then retries fell to `0`, and final verification reported `first_video_pts=9.309s` after 7 attempts/1024 packets.
- Root cause was demux retry policy, not player-core Session F feed order and not zero-copy shutdown warnings. The nearest accepted VP9 keyframe before the target is in the accepted window (`61.728s`/`61.861s`, <10s before target), but the old rescue skipped the useful window.
- `decode_point_before_rescue_retry_timestamp` now jumps to `requested - decode_point_before_max_accepted_preroll` when the current backend target is earlier than that accepted window; if the backend target is already inside the accepted window, it preserves the old final rescue toward `requested`. No TOML/public API knob was added.
- Regression coverage: unit `decode_point_before_too_far_rescue_targets_accepted_preroll_window` and integration `crates/symphonia-demux/tests/vp9_fixtures.rs::vp9_sdr_decode_point_before_seek_reaches_near_target_keyframe`.
