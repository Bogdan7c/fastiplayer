# Symphonia Demux DecodePointBefore Startup

- `DecodePointBefore` verification remains strict for ordinary seeks: the selected video decode-start packet must be at/before the requested target, within accepted preroll, and not a proven non-keyframe.
- The only accepted after-target exception is startup seek-to-zero. If `requested == 0`, a selected video packet after zero may be accepted only when it is not `PacketKeyframe::NotKeyframe` and its PTS is within `DECODE_POINT_BEFORE_STARTUP_LEAD_TOLERANCE` (currently 250 ms). This handles MP4/H.264 B-frame files where the backend seek operates on nonnegative DTS and can land on the first packet after zero even though the media starts at zero.
- On this accepted startup path, `seek_result_with_verified_video_packet()` still reports `actual_position` as the accepted packet PTS so player-core seek gates can wait for `frame_pts >= actual_position` instead of an unavailable zero frame.
- Regression coverage: `crates/symphonia-demux/src/symphonia_demuxer.rs` tests `decode_point_before_seek_accepts_startup_keyframe_after_zero` and `decode_point_before_seek_rejects_startup_keyframe_beyond_lead_window`; real H.264 fixture coverage in `crates/symphonia-demux/tests/h264_fixtures.rs::h264_bframe_startup_seek_to_zero_accepts_first_decode_point` covers the 4k30/4k60 problem assets.

## RC1: initial seek anchors near target (nearest keyframe), not target − preroll
- `seek_decode_point_before` initial backend seek now targets `requested − DECODE_POINT_BEFORE_INITIAL_SEEK_MARGIN` (1 ms), NOT `requested − decode_point_before_preroll`. So stss/cues snap to the NEAREST decode-safe keyframe ≤ target instead of a keyframe several GOPs earlier. `decode_point_before_preroll` (5 s) is now ONLY the retry backoff step (`decode_point_before_expanding_retry_timestamp`) when the first attempt lands on a non-keyframe / after target; `max_accepted_preroll = max(10 s, preroll)` is unchanged. The 1 ms margin keeps `initial < requested`, so the FirstVideoTooFarBeforeTarget rescue and after-target/expanding retries (and their tests) still trigger.
- Why: the old 5 s initial over-seek was the PRIMARY accurate-seek latency cause on iOS HEVC MOV (GOP ~0.93 s). It anchored ~5.7 s / 6 keyframes before target, blowing up BOTH the demux scan (dense PCM: ~237k pre-target audio packets read+dropped one-by-one, starving the idle video decoder ~5.6 s) AND the decode chain (decode ~170–320 frames vs ~3–36). Verified via `/tmp/rustiplayer-seek-probe` (media-core+symphonia-demux headless, `[replace]` isomp4 patch): ios-hevc-pcm.mov (pcm_s16le, 9.18M audio packets) actual 88655→94253, events_seen 237085→5; ios-hevc-main10-aac-4k60.mov (AAC) actual 4751→9453, pre-target video 318→36. RC2 (a demux audio-skip boundary / PCM coalescing) looks unnecessary once RC1 lands — residual scan is ~5 events.
- Verification not weakened: `decode_point_before_packet_issue` / `verify_decode_point_before_attempt` unchanged. New test `decode_point_before_initial_seek_targets_requested_not_far_preroll`; `h265_ios_mov_decode_point_before_seek_starts_on_sync_sample` strengthened to assert actual ≥ target − 1.5 s; dual-stream forwards target − 1 ms (test updated 5000→9999). Verification stays strict per `mem:symphonia-demux/decode-point-before-startup` core rules.
