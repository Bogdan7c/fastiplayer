# pushed-media-source — источник «сегменты извне» (сессия 03a моста, 2026-10-29)

Crate `crates/pushed-media-source`: куски, которые кто-то другой приносит по полосам (у браузера — MSE `SourceBuffer`, любая нарезка, посреди боксов), → один `media_core::Demuxer` для `player-core`. Нейтрален к браузеру (решение 90): протокол моста, WebSocket и плеер в зависимостях запрещены guardrail-ом `PUSHED_MEDIA_SOURCE_ALLOWED_DEPENDENCIES` (anyhow, bytes, demux-api, media-core, mpeg-ts-demux, source-core, symphonia-demux, thiserror, tracing) + тест в `scripts/tests/test_check_refactor_guardrails.py`, crate в списке cargo-machete `scripts/ci-checks.sh`. План/решения: `user/browser-bridge/` (90–94), отчёт `results/03a.md`; контекст моста — `mem:browser-bridge/core`.

## Механизм («сортировщик», подтверждён владельцем)
- `framing/` — сканер ТОЛЬКО заголовков: fMP4 init=`ftyp`+`moov`, медиа=`moof`+`mdat` (служебные боксы пропускаются без буферизации); WebM init=EBML+`Segment`+`Info`+`Tracks` (размер `Segment` переписывается на «неизвестен» — иначе ранний конец эпизода = обрыв для mkv-патча), медиа=`Cluster` (кластер неизвестного размера кончается на элементе уровня Segment/EBML и получает известный размер); TS — целые 188-байтовые пакеты, большой кусок режется на сегменты ≤ предела. Пределы проверяются по ЗАГОЛОВКУ до накопления. `abort` = `reset` (недособранное выбрасывается; WebM после init ждёт кластер или новый init).
- `episode` — один существующий демуксер на один init: `DemuxRegistry::open_required_container` (symphonia fMP4/WebM + mpeg-ts) на `DemuxInput::byte_stream(труба)` в `ProgressiveDemuxer::new_deferred`. Бюджет sniff = ровно байты, уже лежащие в трубе (иначе sniff ждал бы следующих байтов страницы). Новый эпизод: init с ДРУГИМИ байтами, `changeType` (`change_container`, требует новый init), смена `timestampOffset`; начинается лениво с ближайшего медиасегмента. Тот же повторённый init эпизод не пересоздаёт.
- `pipe` — труба эпизода (Mutex+Condvar): писатель не ждёт, читатель (поток демуксера) блокируется; `finish_input` → чистый EOF, выброс (`EpisodeHandle::drop`: cancel + abandon) → `BrokenPipe` (не `Interrupted` — читатели его повторяют) и возврат байтов в учёт. `intake::IntakeLedger` — жёсткий потолок непрочитанных байтов потока (256 МиБ).
- `lane` (сторона приёма, поток соединения) + `LaneMailbox` (очередь запущенных эпизодов, флаги input_ended/consumer_closed; ≤4 ждущих эпизодов на полосу — `TooManyPendingEpisodes`, проверка ДО запуска потока) → `lane_demuxer` (сторона плеера, `next_event` не блокирует): `track_identity` (публичный ID по виду+порядку, первый эпизод сохраняет свои номера; `duration` дорожки обнуляется; `TracksChanged` только при реальной смене описания), смещение применяется к `pts`/`dts` И к `track_pts`/`track_dts` с перепиской номера дорожки (FFmpeg берёт время кадра из `track_pts` и сверяет `track_id`!), кадр с отрицательным временем выбрасывается, видео после него ждёт ключевой кадр (`random_access`, как MSE «need RAP»).
- `stream` — `pushed_stream(policy) -> (PushedStreamWriter, PushedStreamOpener)`; `poll_open` неблокирующий: готово, когда у каждой полосы открылся первый эпизод (пустые по концу входа — пропускаются), список полос замораживается (`LayoutFrozen`), одна полоса — как есть, видео+звук — `CompositeAvDemuxer` (lead 3 с, как HLS). Повторный `poll_open` → `AlreadyOpened`. `PushedStreamDemuxer`: длительность из `set_duration`, `NotSeekable` (перемотка — 03b). Первая ошибка потока побеждает для обеих сторон (`StreamState`); `failure_class()` → ProtectedContent / UnsupportedMedia / UnparsableMedia / InputMisuse — для `stream_rejected` в 03b. `Drop` писателя без `end_of_stream` доигрывает принятое (иначе плеер ждал бы вечно).
- `protection` — `encv`/`enca` в `stsd`, `ContentEncryption` в WebM → `ProtectedContent`; кривая структура init — ошибка, а не «чисто».

## Тесты и обвязка «до кадра»
- Модульные (64): сканеры на фикстурах протокола (нарезка 1 байт…файл), защита, труба/учёт, ID дорожек, граница потока (DRM, мусор → ошибка без паники, потолки, порядок вызовов, обрыв писателя, выброс до ключевого, лимит эпизодов, двойное открытие).
- Сквозные `tests/recorded_streams_to_frame.rs` (записанные потоки протокола через `StreamGate`, как сервер 02) и `tests/stream_changes_to_frame.rs` (фикстуры `fixtures/`, `generate.sh`: H.264 64/96, VP9 96, AAC 0,8 с, TS). Обвязка `tests/support/`: безоконная `PlayerSession` + настоящий программный FFmpeg (`video_ffmpeg::decoder_thread::start_decoder_thread`, ФИКСИРОВАННЫЕ 2 потока — иначе ядра машины решают, когда выйдет первый кадр) + `audio::ProductionAudioDecoderFactory` + симулятор звуковой карты (часы не обгоняют записанное); отчёт о возможностях как у приложения (FFmpeg provider + render `host_yuv420_planar8`, без него сессия выбирает аппаратный путь); декодер ставить по `VideoBackendSelectionRequested` ДО первого tick-а (поздняя замена перематывает — у несикабельного потока ошибка); время НАСТОЯЩЕЕ (часы видео без звука якорятся по `Instant::now()`). Синус ffmpeg: амплитуда 1/8, RMS≈0,088.
- `cargo test -p pushed-media-source` (~2 с реального времени).

## Ограничения (на 2026-10-29)
- Смена качества/кодека: `player-core` сбрасывается в момент разбора (теряет кадры впрок; при звуке далеко впереди видео — может зависнуть в Draining) → сессия 03d (решение 94); тесты 03a подают звук вровень и фиксируют нынешнее поведение.
- `InputAfterEnd` после `end_of_stream` (MSE разрешает), перемотка, «буферизовано до»/«полон», переходник протокола — 03b; `timestampOffset` для TS — отказ; `remove()` страницы не исполняется; кластер WebM неизвестного размера выдаётся только со следующим элементом (задержка на кластер в live); sniff-буфер и очереди воркера эпизода не учитываются леджером (ограничены числом эпизодов).
