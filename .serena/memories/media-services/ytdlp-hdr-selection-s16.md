# yt-dlp HDR selection — актуальный контракт (2026-07-27)

- Config schema v7 хранит `yt_dlp.hdr_selection` как `YtDlpHdrSelection::{SdrOnly, PreferHdrWhenAvailable}` со stable ids `sdr_only` / `prefer_hdr`, default `SdrOnly`. `SdrOnly` является жёстким policy-фильтром: HDR не выбирается автоматически и не публикуется в ручном playable catalog. `PreferHdrWhenAvailable` ранжирует capability-playable HDR выше SDR и откатывается к SDR; strict HDR-required режима нет.
- Current owner chain: `service-ytdlp::candidate` нормализует S19 descriptor и service-owned color evidence; `web-media-playback-plan` проверяет policy + полный transport/demux/decoder/frame-contract/renderer intersection; app `web_media_open::catalog` публикует только planner-playable rows. Queue/player/UI не интерпретируют extractor metadata.
- Exact `HDR10`/`HDR10+` становится service-owned BT.2020/PQ/limited evidence, `HLG` — BT.2020/HLG/limited. Evidence остаётся вне neutral `web-media-core`, входит в `yt-dlp-s19-v2` semantic identity и переносится при selected compound/composed A+V rematch. Общие `HDR` и `PQ` без доказанных primaries/range не получают color evidence и остаются capability-unplayable.
- YouTube shorthand `vp9.2` с explicit HDR отображается в VP9 Profile 2 / 10-bit / 4:2:0. Bare SDR `vp9` остаётся Profile 0 / 8-bit / 4:2:0; bare `vp9` с HDR не угадывается.
- Focused evidence: `candidate::planning_tests::{youtube_vp9_profile2_hdr_shorthand_maps_to_complete_runtime_requirement, ambiguous_hdr_label_does_not_create_color_evidence}` и composed rematch regression `inventory_video_and_audio_compose_and_semantically_rematch_without_format_id_or_url_leakage`.
