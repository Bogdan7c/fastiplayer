# yt-dlp A/V completeness regression (2026-07-26)

- Реальный YouTube `BestPlayable` мог выбрать `VideoOnly` 4K VP9 раньше единственного `Separate` A/V candidate, потому что codec preference сравнивался до layout completeness. Симптом: видео идёт, `audio_ms=0`, второй demuxer и CPAL output не создаются.
- `web-media-playback-plan::compare_playable` теперь ранжирует `Muxed | Separate` раньше `VideoOnly | AudioOnly`, затем применяет прежние HDR/codec/height/container/quality tie-breaks. Это относится только к `BestPlayable`; exact selection не сортируется. Single-component media остаётся playable, когда A/V candidate отсутствует.
- Progressive yt-dlp composition в `app-egui::web_media_open` использует отдельный bounded 4 MiB limit для одного retained packet на component. Его нельзя снова связывать с 64 KiB HTTP sniff/prefetch initial chunk: реальные YouTube keyframes превышают 64 KiB (воспроизведено 115173 bytes). One-packet-per-component и timestamp lead 500 ms сохранены; HLS/DASH/Smooth уже используют тот же 4 MiB класс bound.
- Focused tests: `web-media-playback-plan::tests::best_playable_prefers_complete_av_over_preferred_video_only_codec` и `app-egui::web_media_open::tests::progressive_composite_packet_limit_is_independent_from_sniff_chunk`.
- Real runtime verification with yt-dlp 2026.07.04 opened two one-track demuxers, created Opus fallback decoder and 48 kHz stereo CPAL output; former silent VideoOnly selection and 65536-byte fatal were absent.

## Composed hot-switch generation fix (2026-07-27)

- Причина общей sidebar ошибки при смене resolution/codec у composed video-only + audio-only YouTube playback: fresh extraction успешно semantic-rematch-ила обе components, но `app-egui::web_media_open::preparation` переносил старые `YtDlpComposedSelection` и video parent selection в новую generation. Fresh stream model не мог найти old-generation active identity и strong same-item reopen fail-closed завершался как `SourceUnavailable`.
- `service-ytdlp::YtDlpCandidateSnapshot::rematch_composed` теперь атомарно возвращает match kind, fresh `YtDlpComposedSelection` и fresh runtime candidate. `YtDlpComposedSelection::video_parent_selection` публикует только opaque secret-safe parent token, нужный app picker projection. App проверяет согласованность входного composed intent и после re-extraction использует только fresh selection tokens.
- Queue/playlist lineage, UI generation fencing, old-playback-until-Installed и player commit protocol не менялись. Missing/ambiguous component rematch остаётся fail-closed без provider-default fallback.
- Regression proof: service test `inventory_video_and_audio_compose_and_semantically_rematch_without_format_id_or_url_leakage` проверяет fresh generation у composed и video parent identities и равенство selection/candidate descriptors; полный `service-ytdlp` lib suite и `app-egui --no-default-features` suite проходят.

## YouTube `vp9.2` planning regression (2026-07-27)

- Real `yt-dlp 2026.07.04` output for `LXb3EKWsInQ` contains HDR formats 330–337 as shorthand `vcodec = "vp9.2"` beside playable SDR VP9/H.264 and AV1 HDR rows. S19 accepted the known VP9 family, but S21C mapping expected a full `vp09.*` bit-depth field; all-or-nothing `planning_snapshot()` therefore returned `RuntimeRequirement` and both direct open and playlist navigation failed before install.
- `service-ytdlp::candidate` now maps exact `vp9.2` plus explicit HDR to the stream-verified VP9 Profile 2 / 10-bit / 4:2:0 requirement. Exact `HDR10`/`HDR10+` supplies BT.2020/PQ/limited evidence and `HLG` supplies BT.2020/HLG/limited evidence; this evidence participates in `yt-dlp-s19-v2` semantic identity and survives compound/composed rematch. Ambiguous `HDR`/`PQ` remains capability-unplayable rather than guessed. Queue ownership, catalog I/O policy and media-open barriers are unchanged; configured `SdrOnly` intentionally hides HDR, while `PreferHdrWhenAvailable` can publish it after capability intersection.
- Regression tests cover strict HDR10 color fields, ambiguous-label fail-closed behavior and composed rematch evidence preservation. Full `service-ytdlp`, strict service Clippy, full `app-egui --no-default-features` (898 tests), rustfmt and refactor guardrails passed. `vainfo` confirmed the owner machine exposes VP9 Profile 2 and AV1 Profile 0 decode; manual `ffprobe` of format 330 confirmed Profile 2, `yuv420p10le`, BT.2020 and SMPTE ST 2084 without exposing the signed URL.
## Mixed-transport compound route fix (2026-10-18)

- Real YouTube `0e3GPea1Tyg`: yt-dlp `requested_formats` = `616` (HLS `m3u8_native` VP9 1080p "Premium" video-only) + `251-23` (HTTPS Opus audio-only). Planner checked Separate components independently, ranked the pair first (complete A/V), runtime `open_candidate` sent it to the progressive path → `YtDlpTransportRequestError::NonProgressiveTransportFamily` → `CandidateOpenError::Fatal` (no fallback) → whole open failed.
- Invariant now: a `Separate` pair is playable only if `TransportFamily::shares_component_composition_route` (web-media-core) holds — progressive HTTP/FTP pair freely; adaptive families must be identical (RTMP: same variant). Planner pushes `CandidateCapabilityRejection::ComponentRouteMismatch { video, audio }` (counted as transport rejection). Exact intent on such a pair now fails in the planner, not in runtime.
- BestPlayable substitute: `media-source-open::web_media_open::compound_route_substitute` builds exactly one replacement for a route-mismatched selected compound: audio = the compound's own inventory audio row (`YtDlpCandidateSnapshot::inventory_audio_of_compound`, keeps yt-dlp language), video = planner-ranked route-compatible video-only row, preferring the compound video height (avoids silent downgrade to latency-first 720p). Opened as a composed selection (`composed_selection` Some, active selection = video parent) and inserted before the first single-component ranked candidate; typed retry classification unchanged.
- Quality trade-off: 616 (HLS, highest tbr) is not played; substitute is the best progressive 1080p row per codec policy (e.g. 248/137/399). Mixed HLS-video + progressive-audio composition is not supported by runtime (would need HLS VideoOnly demuxer composed with progressive audio + shared seek/timeline ports).
- Known gaps: UI picker can still compose HLS video-only + HTTPS audio via `compose_inventory_av` (no route check there); a non-route compound rejection (e.g. HDR10 AV1 `701+251` under SdrOnly) still falls to silent VideoOnly — the substitute only triggers on route mismatch.
- Tests: `web-media-core normalized::tests::component_composition_route_*`, `web-media-playback-plan tests::component_route::*`, `service-ytdlp candidate::compound_audio_tests::*`, vertical `media-source-open web_media_open::compound_route_substitute::tests::mixed_hls_https_compound_opens_route_compatible_video_with_compound_audio` (fake yt-dlp + loopback WebM fixtures in `compound_route_substitute/fixtures/`).
