# Permissions rationale (for store review)

Fastiplayer Bridge hands the video of a web page to the Fastiplayer desktop player running on the same computer.
It has no servers, no accounts and no analytics. Nothing is sent to us or to any third party.

| Permission | Why it is needed |
| --- | --- |
| `nativeMessaging` | Talks to the small local helper program (`fastiplayer-browser-host`) that the Fastiplayer desktop app installs. This is the only channel to the player. |
| `contextMenus` | Adds a "Play in Fastiplayer" item to the right-click menu of a video. |
| `storage` | Remembers the user's own choices, locally only. Today it stores three things in `storage.local`: the "Video codec for sites" choice (`codecSetting`: auto / prefer_vp9 / always_h264 / off), the "Local network videos from internet pages" choice (`localAddressSetting`: block / ask, default block), and the list of video codecs the Fastiplayer app reported as cheap to play at its last connection (`cheapVideoCodecs`, derived from the app's own codec-priority and renderer settings). No page content, addresses or history are stored. It also uses `storage.session` (kept in memory only, erased when the browser closes) for one more thing: facts about the videos of the tabs that are open right now (which video elements a tab has, whether they play, their size, the site name of the frame and of the video file, and why the last hand-over of that tab was refused), so that the extension still knows them after the browser puts its background script to sleep. A tab's entry is erased when the tab is closed; when the background starts, it asks for the ids of the open tabs (`tabs.query`, ids only) to erase entries left from tabs that no longer exist. |
| `scripting` | When the user hands a tab over, asks each frame of that tab which videos it has (to pick the playing one). Also lets the extension attach to a page that was already open when the extension was installed or updated. While a codec choice is active, the extension registers one dynamic content script (id `fastiplayer-codec-policy`, `document_start`, all frames, isolated world): its only content is the list of video codec families that pages are told are not supported (for example AV1), so that the page's player picks another codec before it starts. It is replaced or removed whenever the choice changes. |
| `declarativeNetRequestWithHostAccess` | Two in-memory session rules on the extension's own downloads, and nothing else. (1) A site may refuse to serve a plain video file (`<video src>`) to a request without its `Referer`, and the browser does not let an extension's `fetch` set that header. While the extension background downloads one piece of a file the user handed over, one rule adds `Referer: <origin of the page>/` to that single request, the way the browser would compute it for that address under the page's referrer policy (the `referrerpolicy` attribute of the element or `<meta name="referrer">`): the page's site name only, never the page's path, and nothing at all under `no-referrer`. It matches only the exact file address and only requests that do not come from a tab (`tabIds: [-1]`), so requests of web pages are never changed, and it is removed as soon as the request is answered, fails or is cancelled. (2) A page on the internet must not be able to send the extension's download to the local network through a redirect, so block rules stop the extension's own `fetch` to local addresses (`localhost`, private and link-local addresses, `.local` and similar names). They match only `xmlhttprequest` requests initiated by the extension itself (`tabIds: [-1]` and `initiatorDomains` with the extension's own host): pages, other extensions and the extension's WebSocket to the local player are not touched. While a file the user is allowed to get from the local network is downloading, a one-request allow rule opens exactly that (the file's host, or the local network for a page that is itself on the local network). The extension's existing host permission covers the same addresses, so this adds no new access to any site. |
| `host_permissions: <all_urls>` | A video can be on any site. The extension runs a content script at `document_start` in every frame, because it must see the page's media before the page's own player starts. The script does not read page content, cookies or form data; it only observes media elements and Media Source buffers of the page (in Chrome also inside the page's dedicated workers: the page's `Worker` is started with the same observer in front of the site's worker code) and passes the video bytes to the local player. The same host permission lets the extension background download a plain video file (`<video src>`) that the user handed over, see below. |

Not requested: `cookies`, `webRequest`, plain `declarativeNetRequest` (no blocking of web pages' requests and no static rule lists), `tabs` (the title and site of a tab the user hands over are read with `tabs.get`, which the host permission already allows; only the title and the domain name are passed to the player), remote code.

Network access: when the user hands over a page whose video is a plain file (`<video src="https://…/movie.mp4">`), the extension background downloads that same file from the same address, piece by piece (HTTP `Range` requests), only while the player plays it and only the pieces the player asks for. The request goes through the browser's own network stack with the site's cookies and the `Referer` described above, like the page's own `<video>` element would load it; the page's element stops loading the file meanwhile, so the file is not downloaded twice. The bytes go only to the local player. The extension contacts no other address on the Internet.

Local addresses: a page on the internet cannot make the extension fetch a file from the local network or this computer (`localhost`, private and link-local addresses, `.local` and similar names). Such a hand-over is refused by default and the video stays in the page. The setting "Local network videos from internet pages" can change this to Ask, and then the user decides. Pages that are themselves on the local network (a home media server) work as usual. The check is repeated when the page names the file, and a redirect to a local address is stopped by the browser before the request leaves (the block rules above). A public domain name that resolves to a local address cannot be detected in advance.

Chrome: `message_serialization: "structured_clone"` (Chrome 148+) lets the content script pass the video bytes to the extension background as binary data instead of JSON text; it does not change what is sent or to whom.

The extension streams video to the local player only over `ws://127.0.0.1` (loopback).

Firefox: the background page's `connect-src` allows `http:` and `https:` for the file download described above (Firefox applies this policy to `fetch` of the background page); scripts stay `'self'` only.

Firefox: `data_collection_permissions` is `required: ["none"]` — the extension does not collect or transmit user data to anyone.
