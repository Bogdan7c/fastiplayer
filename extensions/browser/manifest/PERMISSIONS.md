# Permissions rationale (for store review)

Fastiplayer Bridge hands the video of a web page to the Fastiplayer desktop player running on the same computer.
It has no servers, no accounts and no analytics. Nothing is sent to us or to any third party.

| Permission | Why it is needed |
| --- | --- |
| `nativeMessaging` | Talks to the small local helper program (`fastiplayer-browser-host`) that the Fastiplayer desktop app installs. This is the only channel to the player. |
| `contextMenus` | Adds up to three items to the right-click menu, only on ordinary web pages (`http`, `https`, `file`): "Play in Fastiplayer" on a video, "Play video from this page in Fastiplayer" on a page or a frame (for sites that take the right click away from the video), and "Play link in Fastiplayer" on a link (`http` and `https` links only). Each item hands over exactly what the user clicked: the video under the pointer, the main video of the page, or the page the link leads to. Each group of items can be switched off in the extension settings; a switched-off item disappears at once. |
| `storage` | Remembers the user's own choices, locally only. Today it stores four things in `storage.local`: the choice of which entry points are on (`entrySettings`: right-click on a video or page, right-click on a link, button over videos; the first two default to on, the button to off), the "Video codec for sites" choice (`codecSetting`: auto / prefer_vp9 / always_h264 / off), the "Local network videos from internet pages" choice (`localAddressSetting`: block / ask, default block), and the list of video codecs the Fastiplayer app reported as cheap to play at its last connection (`cheapVideoCodecs`, derived from the app's own codec-priority and renderer settings). No page content, addresses or history are stored. It also uses `storage.session` (kept in memory only, erased when the browser closes) for one more thing: facts about the videos of the tabs that are open right now (which video elements a tab has, whether they play, their size, the site name of the frame and of the video file, and why the last hand-over of that tab was refused), so that the extension still knows them after the browser puts its background script to sleep. A tab's entry is erased when the tab is closed; when the background starts, it asks for the ids of the open tabs (`tabs.query`, ids only) to erase entries left from tabs that no longer exist. |
| `scripting` | When the user hands a tab over, asks each frame of that tab which videos it has (to pick the playing one). When a tab was already open before the extension was installed or updated and the user presses "Reload and open", the same call reads the position and duration of that tab's videos before the reload and sets the same position on the same video after it. While a codec choice is active, the extension registers one dynamic content script (id `fastiplayer-codec-policy`, `document_start`, all frames, isolated world): its only content is the list of video codec families that pages are told are not supported (for example AV1), so that the page's player picks another codec before it starts. It is replaced or removed whenever the choice changes. |
| `declarativeNetRequestWithHostAccess` | Two in-memory session rules on the extension's own downloads, and nothing else. (1) A site may refuse to serve a plain video file (`<video src>`) to a request without its `Referer`, and the browser does not let an extension's `fetch` set that header. While the extension background downloads one piece of a file the user handed over, one rule adds `Referer: <origin of the page>/` to that single request, the way the browser would compute it for that address under the page's referrer policy (the `referrerpolicy` attribute of the element or `<meta name="referrer">`): the page's site name only, never the page's path, and nothing at all under `no-referrer`. It matches only the exact file address and only requests that do not come from a tab (`tabIds: [-1]`), so requests of web pages are never changed, and it is removed as soon as the request is answered, fails or is cancelled. (2) A page on the internet must not be able to send the extension's download to the local network through a redirect, so block rules stop the extension's own `fetch` to local addresses (`localhost`, private and link-local addresses, `.local` and similar names). They match only `xmlhttprequest` requests initiated by the extension itself (`tabIds: [-1]` and `initiatorDomains` with the extension's own host): pages, other extensions and the extension's WebSocket to the local player are not touched. While a file the user is allowed to get from the local network is downloading, a one-request allow rule opens exactly that (the file's host, or the local network for a page that is itself on the local network). The extension's existing host permission covers the same addresses, so this adds no new access to any site. |
| `host_permissions: <all_urls>` | A video can be on any site. The extension runs a content script at `document_start` in every frame, because it must see the page's media before the page's own player starts. The script does not read page content, cookies or form data; it only observes media elements and Media Source buffers of the page (in Chrome also inside the page's dedicated workers: the page's `Worker` is started with the same observer in front of the site's worker code) and passes the video bytes to the local player. The same host permission lets the extension background download a plain video file (`<video src>`) that the user handed over, see below. |

Entry points: the user can also hand a video over from the right-click menu (video, page, link) or, when switched on in the settings, from a small button that appears over a video the pointer is on. All of them run the same hand-over as the toolbar button. For a link, the extension opens it in a new active tab next to the current one (`tabs.create`), waits up to one minute for a video to start there, hands it over, and closes that tab (`tabs.remove`) only when the player ends the session; a tab the user closes or a page that takes the video back is left alone. These calls need no `tabs` permission. The result of a hand-over started without the popup is shown as a small note on the page (an element in a closed Shadow DOM, added by the extension, removed after a few seconds) and, for a refusal, as "!" on the button of that tab only (`action.setBadgeText` with `tabId`). To tell which video the user right-clicked, a script of the extension in the page remembers the element of the last real (user-made) right click and forgets it with the next one; it keeps nothing else and sends nothing out.

Bringing a closed page back: if the user closes the tab (or leaves the page) while its video plays in the Fastiplayer window, the player can keep showing what was already downloaded, and pressing Play in that window asks the extension to bring the page back. Only then, the extension opens the same address again in the same browser window, or in another open window of the same kind (a private window only for a private page), and never opens a new window. If the same page is still open in a tab, that tab is used instead. A new tab is created in the background (`tabs.create`), muted (`tabs.update` with `muted`) and then made the active tab of its window (`tabs.update` with `active`): the browser plays video only in a visible tab, and creating it in the background first keeps the browser window from jumping in front of the player. To choose the window it reads the windows' ids, kind and type (`windows.get`, `windows.getAll`); to find an open tab of the same page it compares tab addresses (`tabs.query`, allowed by the host permission). The address, the window and the last position of the video are kept only in the memory of the extension background for this one session and are not stored. When the video of the reopened page is handed over again, the tab's sound is restored as it was. If the page cannot be brought back within half a minute, or the player window is closed meanwhile, a tab the extension opened is closed again (`tabs.remove`); a tab the user had open is left as it was. None of these calls needs the `tabs` permission.

Tabs opened before the extension: a page that was open before the extension was installed or updated has no working extension script, so its video cannot be handed over. The popup explains this and offers "Reload and open". Only that button reloads the tab (`tabs.reload`, no permission needed); nothing is reloaded on its own, because the user may be typing something on the page. The position stays in the memory of the extension background for that one reload and is not stored.

Toolbar button: clicking the extension's button hands the video of the current tab to the player right away; the popup then shows the result (or the reason it did not work) and a list of the videos found on the tab, so the user can pick another one. To know which tab is current and what it is called, the popup uses `tabs.query` for the active tab: the tab id is always available, and the title comes from the host permission below, so no `tabs` permission is added. Closing the popup does not cancel a hand-over. In Firefox the button is placed on the toolbar from the start (`action.default_area: "navbar"`, Firefox manifest only); this changes where the icon appears, not what the extension may do.

Not requested: `cookies`, `webRequest`, plain `declarativeNetRequest` (no blocking of web pages' requests and no static rule lists), `tabs` (the title and site of a tab the user hands over are read with `tabs.get`, which the host permission already allows; only the title and the domain name are passed to the player), remote code.

Network access: when the user hands over a page whose video is a plain file (`<video src="https://…/movie.mp4">`), the extension background downloads that same file from the same address, piece by piece (HTTP `Range` requests), only while the player plays it and only the pieces the player asks for. The request goes through the browser's own network stack with the site's cookies and the `Referer` described above, like the page's own `<video>` element would load it; the page's element stops loading the file meanwhile, so the file is not downloaded twice. The bytes go only to the local player. Subtitles: when the video's page offers subtitle tracks (`<track src>` elements of the handed-over video, or subtitle files its own player downloads), the extension background downloads each `<track src>` file once (a whole file, at most 8 MiB, with a 30-second limit) through the same browser network stack, with the site's cookies, the same `Referer` rule and the same local-address block as the video file, and passes the text to the local player, which shows it as a subtitle track. Only the document text goes to the player: the track's address is never sent. The extension contacts no other address on the Internet.

Local addresses: a page on the internet cannot make the extension fetch a file from the local network or this computer (`localhost`, private and link-local addresses, `.local` and similar names). Such a hand-over is refused by default and the video stays in the page. The setting "Local network videos from internet pages" can change this to Ask, and then the user decides. Pages that are themselves on the local network (a home media server) work as usual. The check is repeated when the page names the file, and a redirect to a local address is stopped by the browser before the request leaves (the block rules above). A public domain name that resolves to a local address cannot be detected in advance.

Chrome: `message_serialization: "structured_clone"` (Chrome 148+) lets the content script pass the video bytes to the extension background as binary data instead of JSON text; it does not change what is sent or to whom.

The extension streams video to the local player only over `ws://127.0.0.1` (loopback).

Firefox: the background page's `connect-src` allows `http:` and `https:` for the file download described above (Firefox applies this policy to `fetch` of the background page); scripts stay `'self'` only.

Firefox: `data_collection_permissions` is `required: ["none"]` — the extension does not collect or transmit user data to anyone.
