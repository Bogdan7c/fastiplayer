# Local GLES2 renderer qualification — AMD, 2026-10-26

**The OpenGL ES 2.0 renderer passed the quality gate on every measured scene,
with ≥ 99 % unique frames in both window modes. With hardware decoding it was
never worse than mpv's OpenGL output in CPU, in either window mode, once the X11
opacity fix landed. With software decoding it costs 1.5–3.6 percentage points of
one core more than mpv on three scenes.** The profile explains that gap: the
driver copies each frame in `glTexSubImage2D`, while mpv on desktop OpenGL decodes
straight into GPU-mapped buffers (direct rendering), which GLES2 lacks. The owner
accepted that gap for this machine: the comparison on the target laptop is
session 11, and removing the copy is session 12.

The series found four defects, and all were fixed during the session (details
below). Two of them also affected the default Vulkan (wgpu) renderer.

Task: session 10 of the GLES2 renderer plan (`user/gles2-renderer/`), tracking
goal [#6](https://github.com/Bogdan7c/fastiplayer/issues/6). Exit report:
[`user/gles2-renderer/results/10.md`](../../user/gles2-renderer/results/10.md).
Measurement tools: [local protocol, version 3](tools/local/README.md#measurement-protocol-version-3),
extended for this session as described under [Protocol changes](#protocol-changes).

## Protocol changes

- **Renderer per player** (`renderer = gles2 | wgpu`). An attempt is invalid
  unless the runtime log proves that renderer family.
- **Two or three players per series**: one subject and the references, in Latin
  square order. Each subject × reference pair gets its own verdict.
- **Window mode** (`wayland` / `xwayland`) for every player.
- **Second CPU verdict** (owner decision 12): the player's process tree plus the
  compositor (`kwin_wayland` + `Xwayland`) over the same window. The identity
  of the compositor processes is checked at both window boundaries.
- **Quality gate for a Fastiplayer reference**: wgpu must also reach ≥ 99 %
  unique frames.
- **A/V sync**: mpv's `avsync` is recorded at the window boundaries. It was at
  most 0.023 ms in every attempt. Fastiplayer exposes no A/V offset metric, so
  its A/V sync is **NOT TESTED**.
- 85 unit tests (`test_session10.py`); 20 deliberate mutations were all caught.

- Exit bands: 0.5 pp for hardware and 1.0 pp for software decoding.

## Defects found and fixed

| # | Commit | Cause | Effect (live A/B, 2 alternating repetitions) |
|---|---|---|---|
| 1 | `e5f0467a` | The window is created translucent for its rounded corners. Fullscreen and maximized frames are fully opaque, but KWin was not told, so it repainted everything below the window | Native Wayland, GLES2 HW: `kwin_wayland` 3.9 → 2.3 % (1080p30), 5.5 → 2.8 % (1080p60) |
| 2 | `7cabab4d` | Frame-threaded FFmpeg on 16 threads returns frame *k* only after ≈ 16 more packets: ≈ 533 ms at 30 fps. The decode-ahead window (≤ 500 ms) measured those packets as already ahead of the audio and throttled the decoder | Software H.264 1080p30: 600 of 600 frames for both renderers, CPU 33.9 → 29.7 % |
| 3 | `7b249cfc` | winit cannot change an X11 window's transparency after creation, so fix 1 did not reach XWayland | Square frames now declare `_NET_WM_OPAQUE_REGION`. XWayland, GLES2 HW 1080p60: `kwin_wayland` 4.5 → 2.2 %, tree + compositor 11.7 → 9.3 % (mpv ≈ 10.5 %) |
| 4 | `920687a2` | After KWin sends dmabuf feedback with scanout tranches, Mesa's Vulkan WSI marks the swapchain suboptimal (`VK_SUBOPTIMAL_KHR` on acquire) and leaves the rebuild to the application. The wgpu shell treated that as success and stayed on a non-scanout modifier | The swapchain is now rebuilt once. wgpu HW 1080p60, native Wayland: `kwin_wayland` 4.9 → 3.3 %, client buffer on the KMS plane (direct scanout). The wgpu process rose 1.1 pp, with every frame stage uniformly slower; this is probably CPU clocks while KWin idles, but not proven. Tree + compositor 11.4 → 10.9 % |

Each fix is its own commit, with a test that fails without it.

## Profiles (samply, main thread, 32 s)

| Scene | GLES2 main thread | wgpu main thread | Where it goes |
|---|---|---|---|
| HW H.264 1080p60 | 2.5 % of a core | 4.2 % | GLES2: 29 % of the thread in `eglSwapBuffers` (22 % `dri_flush`). wgpu: 26 % in the Vulkan submit `ioctl` |
| SW H.264 1080p60 | 6.1 % | 5.6 % | GLES2: 55 % in the driver's `memcpy` inside `glTexSubImage2D`. wgpu copies on the GPU (cpu-parity 08b) |
| SW AV1 4K60 | 8.2 % | 11.3 % | Both renderers copy, because dav1d cannot decode into our buffers. GLES2: 64 % `memcpy` in the driver; wgpu: 57 % `memcpy` into staging |

- The hardware path showed no extra work: no `glGetError` on the hot path,
  no redundant binds or uniform writes, no extra egui pass.
- mpv's log shows `DR enabled: yes` on desktop OpenGL, so it has no CPU copy.
  This machine provides that through `ARB_buffer_storage`. The target laptop
  has OpenGL 2.1 without it, so the gap is expected to vanish there. That is an
  expectation, not a measurement; session 11 will check it.

## Limitations

- Fastiplayer A/V sync is not measured: the player exposes no A/V offset metric.
- These are surface handoffs, not physical scanout. The gate does not prove
  equal smoothness.
- Software decoding under XWayland was not repeated after the X11 fix, and
  software 1080p30 under XWayland was not measured at all.
- The cause of the +1.1 pp wgpu process cost after fix 4 is not proven.
- One machine, one session; results do not transfer to other GPUs or drivers.
