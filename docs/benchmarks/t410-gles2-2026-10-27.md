# ThinkPad T410: OpenGL ES 2.0 renderer against mpv and VLC (2026-10-27)

Session 11 of the GLES2 renderer plan (`user/gles2-renderer/`), measurement protocol
version 4 (`tools/local/README.md`). Fastiplayer runs its OpenGL ES 2.0 renderer (the
only renderer this machine can run: it has no Vulkan device) in the `dynamic` decode
mode, against mpv and VLC 3 in their best mode per scene. Sanitized per-attempt data:
[`t410-gles2-2026-10-27.json.gz`](t410-gles2-2026-10-27.json.gz) (12 series, 450
attempts, including the invalid ones and their reasons).

**Summary.**
- Every Fastiplayer attempt in `dynamic` showed at least 99 % of the source frames, on
  ordinary scenes and on every ladder step, in both window modes.
- CPU on ordinary scenes: native Wayland has no WORSE verdict. Under XWayland, the
  process number is WORSE against mpv `--vo=xv` on the 60 fps scenes, and 720p60 is WORSE
  against VLC once the compositor is counted.
- With forced hardware decoding, Fastiplayer shows only 67–79 % of the frames, while mpv
  and VLC show all of them. The cause is GPU time. The ARGB window surface keeps KWin from
  scanning the frame out directly on Ironlake (verified by an A/B experiment, below), and
  Fastiplayer's video pass costs about twice mpv's.
- The stress ladder: no frame loss on any of 12 steps, the same ceiling as VLC, and less
  CPU on the top steps. mpv loses frames on AV1 1080p60 and HDR.

## Ordinary scenes, `dynamic`

`dynamic` starts on hardware decoding. It switched 720p60, 1080p30 and 1080p60 to software
6.6–6.7 s after start, before the window; 720p30 stayed on hardware. The quality gate
passed on every scene in both modes (600/600 and 1201–1202/1200 unique frames). mpv and VLC
lost no frames.

Δ is Fastiplayer minus the reference, in percentage points (pp) of one logical core,
mean of 9 quiet pairs; negative means Fastiplayer used less. Verdicts: WIN, WORSE or INC.
Exit band 1.0 pp. Each cell: process tree / process tree + compositor (`kwin_wayland` +

mpv `--vo=xv` moves colour conversion and scaling into the Xwayland server
(Xwayland 12–24 % here), so its process number is low and its sum is high. KWin's CPU
for Fastiplayer's window is about 2.5–3 pp higher than for the references' windows at
60 fps in both modes (8.4–9.3 % against 5.8–6.6 %). The experiment below shows why.

The intervals are wide because the protocol uses a conservative factor of 10 standard
errors. On H.264 1080p60, for example, Fastiplayer used 120.4–122.9 % in every Wayland
pair and mpv 122.6–129.5 %, yet the verdict stays INC.

### A/B experiment: opaque window surface (not a protocol series)

Fastiplayer creates its window with an alpha channel for rounded corners. Ironlake's primary
display plane has no ARGB format (`modetest`: XR24/XB24/XR30/RG16), so KWin has to composite
the window every frame, even though the window declares itself opaque in fullscreen. One run
per row, native Wayland, same 20 s window; Render/3D is the global GPU load from `intel_gpu_top`.

| Run | Render/3D | KWin CPU | Process CPU | Frames/s |
|---|---|---|---|---|
| HW 720p60, current build | 99.9 % | 4.8 % | 20.8 % | **40.1** |
| HW 720p60, opaque EGL surface (experimental build) | 95.5 % | 3.9 % | 20.2 % | **53.7** |
| HW 720p60, mpv | 95.8 % | 4.9 % | 21.3 % | (no losses in the series) |
| SW 1080p60, current build | 90.5 % | 9.2 % | 120.7 % | 60.0 |
| SW 1080p60, opaque EGL surface | **60.6 %** | **6.0 %** | 119.0 % | 60.0 |
| SW 1080p60, mpv | 30.2 % | 6.3 % | 124.8 % | — |

A second build kept the ARGB configuration and created the surface with
`EGL_PRESENT_OPAQUE_EXT` (`EGL_EXT_present_opaque`). Under native Wayland it gives the same
result (SW 1080p60: Render/3D 90.3 → 61.7 %, KWin 8.9 → 5.8 %; HW 720p60: 40.1 → 54.2
frames/s). Under XWayland, Mesa rejects the attribute (`BadAttribute`); there only the window's
visual decides opacity.

The opaque surface removes a third of the GPU load and brings KWin to mpv's level. The rest
of the gap is Fastiplayer's own video pass, about twice mpv's `profile=fast` path. The fix
changes window behaviour and is an owner decision (session 11b); it is not in this build.

Ceiling: Fastiplayer and VLC are loss-free on all 12 steps in both modes. mpv loses frames on
AV1 1080p60 in both modes and on HDR in native Wayland. With a tied ceiling the criterion compares CPU on the top
steps. Fastiplayer used less there (AV1 1080p60: 167 against 208 %; HEVC 1080p60: 218 against
230 %), but these are diagnostic attempts without a paired statistical verdict.

Before the ladder, session 11a changed two software decode rules for machines with at most four
logical CPUs, after a live run on this machine. AV1 up to 1080p may now keep two frames in
flight: AV1 1080p60 went from 16 to 60 frames/s. HEVC gets all logical CPUs: HEVC 1080p60 went
from 56 to 60 frames/s. Without the change, AV1 at 1080p and HEVC 1080p60 would have lost frames.

Fastiplayer uses less than VLC everywhere. Compared with mpv:
- the hardware path uses about 50 MiB more: Fastiplayer keeps a 24-surface VA-API pool;

## Invalid attempts

The archive keeps every failed attempt. Each series stopped at its first invalid attempt.
- **First two ladder runs** (`ladder-*`, `ladder2-*`): the HEVC attempt was invalid,
  `expected dynamic backend not proven`. The file starts on VA-API and moves to software when it
  is opened. At that point the player's log did not name the new route (fixed in `7dce9848`), and the protocol
  read the startup VA-API lines as a hardware trace (fixed in the tools).
- **MPEG-2** (`mpeg2-*`): `no advancing render handoffs`. Fastiplayer has no MPEG-2 video decoder
  and plays only the audio of these files. There is no Fastiplayer MPEG-2 number; the reference
  data of session 00 stands.

## Limits

- mpv and VLC lost no frames on ordinary scenes here. In session 00 they lost 16–405 frames on the
  same scenes. That sweep ran with a system monitor application open, which draws graphs on the
  same GPU. That is the likely cause; it was not verified separately.
- Fastiplayer's A/V synchronisation is not measured: the player has no A/V offset metric (protocol v3 rule).
- GPU busy time per process is NOT TESTED: i915 on Gen5 exposes no `drm-engine-*` counters. The
  Render/3D column is global and descriptive.
- The A/B experiment is one run per row with an experimental build. The ladder CPU is descriptive.
- Lost-frame definitions differ: Fastiplayer unique frames handed to the surface, mpv drop counters,
  VLC `frames lost`. None proves physical scanout.
