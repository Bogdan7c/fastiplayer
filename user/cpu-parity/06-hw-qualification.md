# Сессия 06: квалификация аппаратного пути против VLC

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 06 плана `user/cpu-parity/`: восстанови строгий протокол локального замера из PR #12, адаптируй его к решению владельца (эталон — VLC с Qt-интерфейсом) и проведи квалификацию аппаратного пути по 5 сценам с quality-gate. Требует завершённых сессий 01–05. Сначала прочитай `user/cpu-parity/README.md` и все `results/0N.md`.

## Что делать

1. **Восстановить инструменты.** Каталог `docs/benchmarks/tools/local/` (collect/run_series/analyze/compare_snapshots/evidence/host/service/smoke/window_owner.c, README, тесты) и отчёт `docs/benchmarks/local-cpu-baseline-2026-09-08.md` существуют только в осиротевшем merge-коммите `09ab9060` (история переписана при публичном cutover, в дереве остался лишь `__pycache__`). Достать `git archive 09ab9060 docs/benchmarks/tools/local`, прогнать его unit-тесты, починить, что сломалось с тех пор (пути, версии Python/VLC, `window_owner.c` сборка), и закоммитить как восстановление с указанием источника.
2. **Адаптировать протокол к решению владельца:** VLC запускается с Qt-интерфейсом (без `--intf dummy`), в остальном — протокол версии 1 из README инструментов: XWayland fullscreen у обоих, cgroup tree CPU, pre-read файла, чередование порядка, 3 → 6 → 9 пар, quiet/diagnostic как observer-control. Изменение протокола — новая версия (2) с явным diff в README, старые числа не пересчитываются.
3. **Сцены:** синтетические H.264 1080p60 и HEVC 4K60 (генератор `tools/t480s/make_fixtures.py`, хэши этой машины записать — они отличаются от исторических из-за версии Mesa), реальные ~24, ~30 и 60 fps H.264 1080p из приватного корпуса PR #12 (нейтральные метки). Дополнительно: HEVC Main10/P010 — хотя бы Fastiplayer-only, если VLC на этой машине снова не осилит.
4. **Quality-gate до таблицы CPU:** уникальные идентичности кадров за окно (diagnostic-режим) для Fastiplayer ≈ fps × окно на 60 fps источниках (закрыть открытый вопрос 809–898/900 из PR #12 или задокументировать как отдельный дефект и остановиться — «WIN по CPU с потерей кадров» не принимается); VLC `frames_lost` = 0.
5. **Память:** сравнение с собственным базисом `original` (PR #12) и с `results/00.md` через `compare_snapshots.py`; GPU — fdinfo gfx-движок как в `thread_cpu.py` (добавить в collector как отдельную, явно помеченную метрику, не смешивать с CPU).
6. **Отчёт** `docs/benchmarks/local-cpu-parity-<дата>.md` по правилам `docs/benchmarks/README.md` + `results/06.md`. Метки WIN/INCONCLUSIVE/WORSE/NOT TESTED по протоколу; PARITY не выдаётся без допуска владельца (решение из PR #12 остаётся).

## Критерий выхода

- По каждой HW-сцене результат Fastiplayer минус VLC(Qt) — WIN или INCONCLUSIVE с интервалом, целиком внутри ±0,5 п.п.; ни одного WORSE. Если есть WORSE — сессия заканчивается диагностикой причины и предложением следующей сессии, а не «почти».
- RSS/PSS не выше базиса; GPU gfx не выше VLC.
- Отчёт опубликован в `docs/benchmarks/`, сырые артефакты — вне репозитория.
