# Fastiplayer: паритет с VLC по CPU/RAM/GPU (issue #10)

Подготовлено 19 октября 2026 по результатам диагностической сессии 00 (замеры на AMD Ryzen 7 7840HS / Radeon 780M, KDE Wayland, VLC 3.0.24). Код плеера в сессии 00 не менялся. Это задания для следующих сессий.

**Цель владельца:** в аппаратном и в программном режиме декодирования потреблять не больше (а лучше заметно меньше) VLC по CPU, RAM и GPU, без потери качества воспроизведения и ничего не сломав.

Ссылки на строки кода — снимок на 19 октября 2026 (HEAD `16e723b5`); перед правкой сверять с текущим кодом.

## Решения владельца (19 октября 2026)

1. **Сначала аппаратный путь (VA-API → DMA-BUF → Vulkan), потом программный (FFmpeg → host upload).** Сессии 01–06 — HW, 07–08 — SW. Общие части (пробуждения, UI, россыпь) помогают обоим.
2. **Паритет достигаем архитектурой.** LTO и `codegen-units = 1` — отдельный бонус в конце (сессия 09), чтобы не смешивать эффекты и знать, что именно дало выигрыш.
3. **Эталон — обычный VLC с Qt-интерфейсом**, как его видит пользователь. Режим `--intf dummy` (как в PR #12) в итоговой квалификации не используется.
4. Работа в `main`, без веток и PR. Коммит — в конце сессии после зелёных проверок и замера «до/после». Push — по отдельному поручению.
5. (Из issue #10, остаётся в силе.) Запрещены: CPU-readback/конверсия/повторная загрузка аппаратных кадров; рост очередей, пулов и небоундед-кэшей; систематический рост памяти без явного решения владельца; альтернативный рендерер/бэкенд; «upload-ahead» для SW-пути (`mem:video-ffmpeg/software-upload-ahead-REJECTED`).

## Где мы сейчас (сессия 00, окно 20 с, % одного логического ядра)

| Сцена | Fastiplayer всего | главный поток (UI+рендер) | worker | декодер-поток | VLC (Qt UI) всего |
|---|---:|---:|---:|---:|---:|
| HW H.264 1080p60 | 8,3 | 5,1 | 1,1 | 1,5 | 2,9 |
| HW HEVC 4K60 | 12,3 | 8,4 | 1,1 | 2,2 | 4,2 |
| HW H.264 4K30 (без звука) | 7,6 | 5,5 | 0,9 | 0,9 | 1,6 |
| SW H.264 1080p60 | 30,3 | 6,6 | 1,2 | 21,9 (14 потоков) | 25,3 (23,7 в 7 потоках) |
| SW AV1 4K60 | 178 | 11,2 | 2,2 | 157 (14 dav1d) | 203 (193 в 16 dav1d + 8,2 vout) |

RSS у Fastiplayer ниже во всех сценах (115–303 МиБ против 153–598). GPU (gfx-движок, fdinfo): Fastiplayer 1,7 / 2,8 / 2,5 / 3,8 / 8,3 % против VLC 1,1 / 2,2 / 1,0 / 2,7 / 5,9 %. Подробности, метод и ограничения — `results/00.md`.

Вывод: **декодирование у нас не хуже VLC** (SW-потоки один в один). Весь перерасход — обвязка: главный поток, worker и аппаратный декодер-поток делают лишнюю работу на каждом кадре и каждом vsync.

## Корневые причины (подтверждены кодом и живым прогоном)

| # | Причина | Где | Доказательство |
|---|---|---|---|
| 1 | **Нет настоящего пула VA-поверхностей.** На каждый кадр `vaCreateSurfaces` → `vaSyncSurface` → `vaExportSurfaceHandle` → … → `vaDestroySurfaces`. `DmaFramePool` хранит только Copy-дескрипторы и никогда не исчерпывается. | `video-vaapi/src/frame_pool.rs`, `internal_vaapi_frame.rs:92-116`, `cros-codecs-patch/src/backend/vaapi/decoder.rs` (`VaapiPicture::new`), `cros-libva-patch/src/surface.rs:436` (Drop) | счётчик `imports_created` растёт ровно на 60/с, `imports_reused = 0` (контракт `explicit_external_memory_reuse_sync: false`), `imports_replaced ≈ created` |
| 2 | **Vulkan-импорт DMA-BUF на каждый кадр.** Кэш рендерера ключуется по `FrameResourceHandle`, который монотонно новый на каждый кадр → промах всегда: `vkCreateImage` + `vkAllocateMemory` + wgpu-обёртка + 2 view. | `render-wgpu-video/src/video/dma_buf_materializer.rs:173-232`, `video-vaapi/src/resource_pool.rs:109-117` | `video_prepare` 0,25 мс на 1080p и 0,72 мс на 4K при zero-copy (масштабируется с размером буфера — работа ядра по маппингу страниц) |
| 3 | **Полный проход egui и present на каждый vsync**, даже если ни UI, ни видеокадр не менялись. При 30 fps половина кадров — повтор, при 24 fps — 60 %. | `app-egui/src/redraw_pacing.rs:100-130`, `frame_prepare.rs:417-520, 834-1060`, `state/ui_runtime.rs:288` | `ui_prepare` 0,16–0,21 мс + `renderer_submit` 0,32–0,34 мс на каждом из 60 vsync; HW 4K30 — 4,6× хуже VLC |
| 4 | **Пустые пробуждения каждые 2 мс.** Декодер-поток при полном канале кадров крутит `recv_timeout(2 мс)` и на каждом повторе шлёт «пульс активности»; worker просыпается от пульса и гоняет полный тик; плюс собственный 2-мс опрос `DecodeReadiness`. | `video-vaapi/src/decoder_thread/runtime_loop.rs:160-216`, `runtime_loop/frame_publication.rs:190-205`, `player-core/src/session/tick/wakeup.rs:185, 564-640`, `worker.rs:91` | `pauses=38182` за 25 с (~1500 холостых тиков/с), `wake_reason="decode_readiness"`, `wake_delay_ms=2.0` |
| 5 | **Россыпь на горячем пути.** Два глубоких клона `PlayerSnapshot` на vsync и полная пересборка снимка на каждый тик; 3 клона MPRIS-снимка на кадр; `dup()`/`close()` fd на каждую выборку кадра ещё до проверки кэша; двойной `fstat`; bind group и uniform на каждый кадр; в SW-пути — `std::thread::scope` создаёт до 3 потоков на каждую загрузку кадра. | `player-core/src/worker/handle.rs:298-310`, `worker/runtime_publish.rs:236`, `app-egui/src/playlist_runtime/desktop_transport.rs:195-300`, `video-core/src/resource/descriptor.rs:389-393`, `render-wgpu-video/src/video/nv12_renderer.rs:190-200`, `host_planar_upload/wgpu_backend.rs:225` | чтение кода; по отдельности мелочь, вместе — заметная доля оставшегося |
| 6 | Релизный профиль без LTO, 16 codegen-units. | `Cargo.toml` (секции `[profile.release]` нет) | — |

## Куда целимся

HW H.264 1080p60: главный поток ≈ 1,5–2 % (только реальная работа на новый кадр), worker ≤ 0,3 %, декодер-поток ≤ 0,5 % → **≈ 2,5–3 % против 2,9 % у VLC**, а на 24/30 fps контенте — заметно ниже VLC за счёт пропуска кадров-повторов. GPU gfx — не выше VLC. RSS — не выше текущего собственного базиса (решение issue #10: рост памяти только по явному решению владельца).

## Общие правила для всех сессий

Работай в корне checkout репозитория. Сначала `AGENTS.md`. Перед кодом:
- Serena `initial_instructions`, активация проекта, `mem:core`, `mem:cpu-parity/core`, `mem:task_completion`, `mem:conventions`, `mem:testing/sandbox_policy` + memories, перечисленные в файле сессии;
- Context7 для каждой затрагиваемой внешней библиотеки (wgpu, ash, egui, winit, libva, crossbeam и т.п.);
- широкий поиск по репозиторию — read-only субагентом (модель Sonnet), основной агент читает только точные символы;
- перед реализацией — короткое описание архитектуры: владелец состояния, boundary-методы, инварианты, тесты (правило 9 AGENTS.md). Если по ходу всплывает решение, меняющее ownership/lifecycle или поведение для пользователя, — **стоп, вопрос владельцу**.

Замер — обязательная часть каждой сессии, а не «потом»:
- **до** правок: релизная сборка, `python3 docs/benchmarks/tools/dev/run_pass.py` на сценах сессии (минимум HW H.264 1080p60 и HW 4K30 для HW-сессий; SW H.264 1080p60 и SW AV1 4K60 для SW-сессий), сохранить вывод;
- **после** правок: то же самое на той же машине в тех же условиях; в `results/NN.md` таблица «до/после» по потокам и по GPU, плюс `agg_timing.py` по стадиям кадра, если менялся главный поток;
- запрещено сравнивать разные сцены, окна разной длины, debug с release или «я вроде вижу, что быстрее».

Quality-gate (ничего не сломать):
- число уникальных показанных кадров за окно не падает (`RUST_LOG=info,fastiplayer::video_render_acceptance=trace`, уникальные `(render_generation, decoded_generation, pts_ns)`; на 60 fps источнике ≈ 60/с);
- `drops_*` и `decoder_publish_*` в сводке `player_core=debug` не растут относительно базы;
- A/V-синхрон и seek/scrub/pause/resume/переключение бэкенда/смена файла проверяются вручную на двух файлах (HW и SW);
- RSS/PSS не выше базы сессии 00 (±5 МиБ шум); любой систематический рост — вопрос владельцу;
- `scripts/ci-checks.sh all` зелёный; существующие тесты не ослабляются.

Код:
- новая логика — у владельца состояния, не в удобном большом файле; файлы ≥ 700 строк не раздувать (hard limit 800, ratchet `scripts/module-size-baseline.json`);
- boundary API — самодокументирующиеся (enum/newtype/intent-method); absent / busy / fatal / no-op не сливаются в `bool`;
- каждый новый boundary/API — focused-тесты: отсутствующий ресурс, активный fake, ошибка, edge-accounting, «метод не трогает чужое состояние»;
- тест проверяет результат, а не вызов: для оптимизаций — тест, который падает без фикса (счётчик импортов/пробуждений/аллокаций, а не «функция вызвалась»);
- русская документация ключевой логики и инвариантов; без `unwrap/expect/panic` в production (`mem:panic-invariant-policy`);
- в `user/` только Markdown, без личных путей и логов; сырые логи/профили — в scratchpad.

Отчёт сессии `results/NN.md`: статус, решения владельца, SHA базы и итога, таблица «до/после», причина (root cause) и что именно изменилось, изменённые файлы/символы, тесты, что проверено вручную, известные ограничения, обновлённые memories.

## Инструменты диагностики

- `docs/benchmarks/tools/dev/thread_cpu.py PID` — CPU по потокам, RSS/PSS, GPU-движки процесса по DRM fdinfo. Не бенчмарк-протокол, а быстрый срез.
- `docs/benchmarks/tools/dev/run_pass.py label=player:mode:codec …` — запуск Fastiplayer/VLC в изолированном XDG с шаблоном конфига и срез выше.
- `docs/benchmarks/tools/dev/agg_timing.py player.log` — агрегат трассы `fastiplayer::render_frame_timing=trace` по стадиям кадра.
- Профилировщик: `samply` (установлен в `~/.cargo/bin`); требует `kernel.perf_event_paranoid ≤ 1` (`sudo sysctl kernel.perf_event_paranoid=1`). Альтернатива — `perf` из репозиториев дистрибутива.
- Протокол строгого замера (cgroup, XWayland fullscreen, чередование, quiet/diagnostic) из PR #12 в истории `main` отсутствует (история переписана при публичном cutover); он восстанавливается из осиротевшего коммита `09ab9060` в сессии 06.
