# Сессия 04: рендер по изменению, а не по каждому vsync

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 04 плана `user/cpu-parity/`: главный поток должен делать egui-проход только когда есть ввод, анимация или изменилась UI-модель, и не рисовать/не презентовать кадр вовсе, когда видеокадр — повтор и UI не менялся. Требует завершённой сессии 02 (пробуждения). Сначала прочитай `user/cpu-parity/README.md`, `results/00.md`, `results/02.md`. Это изменение lifecycle главного цикла — архитектуру описать и согласовать с владельцем до кода.

## Проблема

При активном воспроизведении `wants_continuous_redraw()` (`crates/app-egui/src/state.rs:777`) → `BackgroundPollScheduler` (`redraw_pacing.rs:100-130`) запрашивает redraw после каждого завершённого кадра; каждый `render_frame` (`frame_prepare.rs:834`) делает полный egui-проход (`take_egui_input`, `run_ui` в `state/ui_runtime.rs:288`, `tessellate` в `frame_prepare/ui_prepare.rs:114`), материализацию видео (`prepare_video_frame` не выходит рано при `acquisition_reused_previous_frame`), submit и present — 60 раз в секунду независимо от fps источника и от того, менялось ли что-то. Трасса стадий (1080p60 HW): `ui_prepare` 0,16 мс + `video_prepare` 0,25 мс + `renderer_submit` 0,32 мс на каждом vsync; при 30 fps половина этой работы — вхолостую, GPU gfx-движок в 2,5 раза загруженнее, чем у VLC.

## Архитектура (предложить владельцу, затем реализовать)

- **Источник пробуждений UI-потока при воспроизведении — события, не vsync:** (а) новый видеокадр готов к показу (worker уже публикует present-frame; нужен дешёвый wake UI-потока — `EventLoopProxy`/user event или существующий канал + `request_redraw`); (б) ввод пользователя (winit события — уже будят); (в) egui просит repaint (`ViewportOutput.repaint_delay` — анимации, курсор, tooltip); (г) таймер UI-модели (обновление времени раз в секунду, автоскрытие панелей в фуллскрине, `mem:app-egui/fullscreen-chrome-autohide-ux14`); (д) фоновые задачи (`WaitUntil` уже есть). Владелец политики — `app-egui::redraw_pacing` (переименовать/расширить `BackgroundPollScheduler` в явный планировщик причин redraw с enum причин).
- **Egui-проход по dirty-флагу:** владелец — `app-egui::frame_prepare` + `state/ui_runtime`. Проход выполняется, если: есть необработанный ввод; egui запросил repaint и срок настал; изменилась **UI-модель кадра** (позиция, квантованная до того, что UI реально показывает: пиксель слайдера и секунда текста; состояние play/pause/buffering; громкость; уведомления; видимость панелей; субтитры-оверлей; размер окна/масштаб; фокус окна). Иначе переиспользуются прошлые `paint_jobs`/`textures_delta` (пустая delta) — egui-wgpu `Renderer::render` можно вызвать с прежними примитивами без `update_buffers`/`update_texture` (проверить по Context7 для egui-wgpu 0.36: буферы живут в `Renderer`, пока не вызван следующий `update_buffers`). Модель «что показывает UI» должна быть явной структурой с `PartialEq`, а не хэшем всего `PlayerSnapshot`.
- **Пропуск кадра целиком:** если видеокадр не новый (тот же `FrameResourceHandle`/identity) и UI-проход не нужен и нет анимаций — не брать surface texture, не кодировать, не презентовать; следующий redraw — по событию. Это и снижает GPU, и убирает `present` с холостых vsync. На 60 fps источнике поведение по кадрам не меняется.
- **Субтитры:** оверлей субтитров (`mem:subtitles/on-screen-s03`, `mem:subtitles/render-thread-s09`) — часть UI-модели кадра: новая картинка/срок годности = изменение.
- **Что не меняется:** порядок boundary egui-wgpu (upload textures → update buffers → video → egui → submit → free retired textures → present, `mem:render-video/core`); `Busy` previous-frame fallback; поведение при seek/scrub (scrub-override — всегда «новый кадр»).
- **Риски, которые надо закрыть тестами/приёмкой:** зависший UI, если пропустили событие (страховочный таймер, напр. 250 мс, только как fallback с счётчиком «сработал fallback» в диагностике); hover-эффекты и tooltip без движения мыши; смена размера окна/масштаба; переход в фуллскрин и обратно; телеметрия-панель (она меняется каждый кадр — когда открыта, проход на каждый кадр законен); reduced_motion.

## Наследство сессии 02 (добавлено 20 октября 2026, решение владельца)

- После 02 главный поток на HW 4K30 стал дороже на ~0,4 п.п. CPU: 35 → 41 мс/с работы, пробуждений `schedstat` 200 → 220/с. Мощность пакета при этом не изменилась (8,7 Вт). Большая часть объяснена «остывшими» ядрами: раньше worker будил процессор каждые 2 мс. Опыт с посторонним 2-мс «будильником» возвращает главному потоку прежнюю цену. Остаток (~0,2 п.п. и +7 % пробуждений) не объяснён; разобрать здесь, т.к. 04 и так переделывает цикл главного потока. Подробности — `results/02.md`.
- Мерить не только CPU-% по потокам, но и мощность пакета: датчик `amdgpu` PPT (`/sys/class/hwmon/hwmonN/power1_average`, root не нужен; скрипт — в отчёте 02). Меньше пробуждений может поднять CPU-% одного потока при той же или меньшей энергии.
- Сюда же (решение владельца): ~3 служебных сообщения рендерера на кадр будят player-worker (`worker_render_feedback_wakeups` ≈ 180/с на 60 fps) — объединить в одно на кадр (см. бэклог README).

## Инварианты

1. Любой ввод пользователя и любое изменение UI-модели отрисовываются не позже следующего vsync — никакого «UI отстаёт».
2. Новый видеокадр показывается с той же задержкой, что и сегодня (или меньше): пробуждение от публикации кадра не хуже vsync-опроса.
3. Egui получает ввод без потерь: если проход пропущен, накопленные события не выбрасываются, а дожидаются прохода (или проход делается, если события есть — что и предполагается).
4. На 60 fps источнике число уникальных показанных кадров не меньше, чем сегодня.
5. В паузе и в простое — ноль проходов без причины (сегодня в паузе уже `Wait`; не регрессировать).

## Тесты

- Планировщик redraw: таблица причин → решение (проход UI / только видео / пропуск / ждать до T) — чистые тесты без окна, падают на текущем коде («всегда проход»).
- UI-модель кадра: квантование позиции (секунда/пиксель), равенство при неизменном состоянии, неравенство при каждом значимом изменении; тест, что открытая телеметрия → проход каждый кадр.
- Интеграционный тест на стенде app-egui (как в `playback_button_test_harness`): серия кадров-повторов без ввода → счётчик egui-проходов не растёт, submit не вызывается; ввод → ровно один проход.
- Ручная приёмка (uinput-скрипт по образцу UX-сессий): hover по кнопкам, tooltip, перетаскивание слайдера, фуллскрин/автоскрытие, смена размера окна, Alt+Tab, субтитры, 24/30/60 fps файлы, пауза, seek.
