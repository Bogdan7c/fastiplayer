# Сессия 08: программный путь — политика потоков декода и квалификация

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 08 плана `user/cpu-parity/`: пересмотри политику числа потоков программного декодера (сегодня «ядра − 2» вслепую), затем проведи квалификацию программного пути против VLC по протоколу сессии 06. Требует сессий 06 и 07. Сначала прочитай `user/cpu-parity/README.md`, `results/00.md`, `results/06.md`, `results/07.md`, `mem:video-ffmpeg/software-design` (разделы про threading, Session 24/26/29).

## Что найдено

- `crates/video-ffmpeg/src/ffi/codec_context.rs:291-308`: `SoftwareDecodeThreadBudget::Auto` → `max(2, available_parallelism − 2)` = 14 потоков на этой машине; `thread_type = FRAME | SLICE`. VLC на том же файле H.264 1080p60 использует 7 потоков при том же суммарном CPU декода (21,6 % против наших 21,7 %) — т.е. сумма одинакова, но 14 frame-потоков означают больше памяти (DPB × потоки), больше задержку декода и больше переключений контекста; на 4K60 AV1 — 14 dav1d-потоков против 16 у VLC при 157 % против 193 % (мы уже экономнее, но без доказательства равной плавности: VLC на T480s терял кадры).
- Память: RSS SW H.264 236 МиБ против VLC 285; AV1 303 против 593 — запас есть, но «ядра − 2» на 32-поточном CPU даст 30 потоков без пользы.

## Что делать

1. **Политика потоков по нагрузке, не по числу ядер.** Предложить и обосновать замером правило (например: 1080p ≤ 8, 4K ≤ 12, минимум 2; `thread_type` — frame для H.264/HEVC, для dav1d — его собственные `n_threads`/`max_frame_delay` уже настроены в Session 29). Проверить по Context7/FFmpeg docs 8.1 семантику `thread_count` для libdav1d (он игнорирует frame-threading FFmpeg и берёт `threads` опцию). Критерий: CPU суммарно не выше, FPS/плавность не хуже, RSS ниже. Настройка `sw_decode_threads` остаётся ручным override.
2. **Квалификация SW** по протоколу сессии 06 (VLC Qt, `--avcodec-hw=none`): SW H.264 1080p60, SW HEVC 4K60 (упрощённый паттерн — пометить), SW AV1 4K60 (Big Buck Bunny или другой лицензионно чистый файл). Для AV1 обязательно равенство доставленных кадров: наши уникальные идентичности против VLC `frames_lost`; если VLC теряет кадры — таблица CPU публикуется с явной оговоркой «при потерях у VLC», без заявлений о превосходстве (правило из T480s-отчёта).
3. Отчёт в `docs/benchmarks/` (тот же документ, что в сессии 06, новый раздел) + `results/08.md`.

## Инварианты

- Никакого CPU RGB/конверсии; FFmpeg-типы не выходят из `video-ffmpeg`; `software_frame_pool_frames` не растёт.
- Bounded EOF continuation, flush/drain семантика, `max_frame_delay=1` для libdav1d — не трогать без отдельного решения.

## Критерий выхода

- SW-сцены: WIN или INCONCLUSIVE внутри ±1 п.п. при равных доставленных кадрах; RSS не выше базиса.
- Обновить `mem:video-ffmpeg/software-design` (политика потоков).
