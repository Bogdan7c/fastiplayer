# Результат сессии 09: LTO-бонус

## Статус

**Закрыта откатом, 23 октября 2026 (решение владельца).** Thin LTO + `codegen-units = 1` не дали измеримого выигрыша по CPU, а пересборка после правки стала в 4,3 раза дольше. `[profile.release]` в `Cargo.toml` не добавлен, код и манифесты не менялись.

| Вопрос | Ответ |
|---|---|
| Быстрее ли плеер с LTO? | Нет. Все разницы по процессу и главному потоку −0,25…+2,4 п.п. — внутри шума (README инструментов: < ~0,3 п.п. — шум; AV1 4K60 шумит сильнее). RSS и GPU без изменений |
| Почему? | LTO оптимизирует только Rust-код. На SW-сценах ~90 % CPU — декодеры FFmpeg/dav1d (C, собираются своим configure/meson, LTO их не касается), на HW — драйвер VA-API и ядро. Rust-обвязка после сессий 01–08b уже лёгкая: главный поток 2,3–4 % на HW и SW H.264 |
| Цена | Чистая сборка 126 → 138 с (+9 %), **правка одного файла `app-egui` 12,4 → 53 с (×4,3)** — выше порога плана (> 2×) |
| Что получили бы | Бинарник 72,1 → 57,8 МБ (−20 %) |
| Решение | Откат: профиль не добавлять, отчёт с цифрами |

## Решение владельца в этой сессии

По пункту 4 плана (выигрыш < 3 % и/или сборка дольше 2×) вопрос ушёл владельцу. Выбран **откат**: `release` остаётся профилем Cargo по умолчанию.

- Отклонено: «принять как есть» (каждая пересборка для замеров и smoke — 53 с вместо 12 без выигрыша CPU).
- Отклонено: отдельный профиль `dist` с LTO только для выпуска бинарников (выигрыш — только размер файла, плюс ещё одна команда сборки, которую надо помнить).
- Отклонено: дополнительный замер fat LTO (сборка ещё дольше, тяжёлая работа всё равно в C-коде).

## SHA

- База и итог: `78144252` (`main`), бинарник `3af25a0e…` — тот же, что итог сессии 08b (сверено по SHA-256).
- Вариант LTO собран той же командой с `CARGO_PROFILE_RELEASE_LTO=thin CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` (то же, что секция `[profile.release]` в `Cargo.toml`), бинарник `1a71866e…`. В репозиторий не попал.

## Метод

- **Сверка по Context7 (Cargo reference, profiles):**
  - `lto` нельзя задать в `[profile.*.package.*]` — наши `[profile.dev.package.*]` (opt-level 3 для зависимостей и горячих crate-ов) относятся к `dev` и с release не пересекаются;
  - build-скрипты и proc-macro в release по умолчанию собираются с `opt-level 0`, `codegen-units 256` (`build-override`), LTO к ним не применяется;
  - `cargo test`, `cargo check`, MSRV-гейт и `cargo-llvm-cov` используют `dev`/`test` — им профиль release безразличен; `cargo bench` наследует `release`, но бенчмарков в workspace нет;
  - CI (`.github/workflows/ci.yml`, `scripts/ci-checks.sh`) release-сборок не делает. LTO затронул бы только локальные `cargo build --release`, `scripts/playback-smoke.sh` и `scripts/progressive-web-smoke.sh`.
- **Время сборки:** `cargo build --release -p app-egui --locked --timings` в пустой отдельный target-каталог, затем дважды `touch crates/app-egui/src/main.rs` и пересборка. Архивы FFmpeg/dav1d подложены локально (`FASTIPLAYER_FFMPEG_ARCHIVE`/`FASTIPLAYER_DAV1D_ARCHIVE`), чтобы сеть не попала в цифры. 16 потоков, линкер по умолчанию (rust-lld).
- **CPU/RSS/GPU:** `run_pass.py` + `thread_cpu.py`, окно 20 с после 15 с прогрева, плееры под XWayland с `--fullscreen` (как протокол v3 и сессии 08/08b), шаблоны конфига `hardware-`/`software-template.toml`. Бинарники обоих вариантов — на обычном диске (не tmpfs). Чередование внутри сцены: база → LTO → LTO → база → база → LTO, по 3 повтора.
- **Машина:** Ryzen 7 7840HS / Radeon 780M (RADV, Mesa 26.2), KDE, рабочий стол живой.
- **Сцены:**
  - HW H.264 1080p60 и SW H.264 1080p60 — `benchmark-matrix/1080p60/1080p60_h264-high_40mbps_aac.mp4`;
  - HW H.264 4K30 — `benchmark-matrix/4k30/4k30_h264-high_80mbps_aac.mp4`;
  - SW AV1 4K60 — BBB 4K60 SDR (тот же контроль, что в 08b).

«Декодер» — потоки `av:*`/`dav1d*`/`ffmpeg-video-de*` (SW) или `video-decode` (HW).

- Лучший случай — HW 4K30: −0,25 п.п. процесса (−4,5 %), из них главный поток −0,17. Это на грани шума и не стоит ×4,3 к пересборке.
- Остальные сцены: разница меньше разброса повторов. На AV1 4K60 один выброс LTO (122,3) — декодер dav1d, который LTO не меняет.
- Quality-gate отдельно не снимался: машинный код C-декодеров, очереди и логика одинаковы, а вариант LTO в итог не попал.

## Время сборки и размер

| | База | thin LTO + cu=1 | Изменение |
|---|---:|---:|---:|
| Чистая сборка `-p app-egui` | 126,1 с | 137,6 с | +9 % |
| Правка одного файла `app-egui` (2 раза) | 12,5 / 12,4 с | 53,1 / 53,0 с | ×4,3 |
| Бинарник `fastiplayer` | 72 134 616 Б | 57 844 160 Б | −20 % |
| `libavcodec`/`libavutil` (C) | одинаковы | одинаковы | — |

Куда уходит время (`--timings`): с LTO библиотеки собираются быстрее (naga 47,7 → 32,6 с, player-core 35,0 → 13,8 с), потому что машинный код откладывается в финальную линковку бинарника. Этот шаг идёт почти последовательно: 12,4 → 52,5 с. Любая правка платит именно за него. Чистая сборка почти не дорожает: её длину определяет сборка FFmpeg/dav1d (65–84 с), она идёт параллельно с Rust-crate-ами.

## Известные ограничения

- Проверен только thin LTO + `codegen-units = 1` вместе. Варианты по отдельности (только thin, только cu=1) и fat LTO не мерились: выигрыш не виден уже у полного варианта, а тяжёлая работа — вне Rust.
- Одна машина (780M). На T480s (сессия 10) профиль release тот же, мерить LTO там не нужно.
- Если в будущем горячая работа переедет в Rust (например, свой декодер), вопрос стоит переоткрыть отдельным замером.
