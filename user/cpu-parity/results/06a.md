# Результат сессии 06a: выбор кадра без повторов и пропусков на 60 fps

## Статус

**DONE.** 21 октября 2026.

Дефект D3 из сессии 06 («повтор + пропуск» на 60 fps, 2–3 % кадров в каждом 2–3-м прогоне) найден трассой и исправлен в корне. Два коммита:

1. **Кадры показа уходят в UI по порядку.** Подставка на два места вместо слота «последний побеждает».
2. **Видеокадр выбирается после получения буфера экрана, а не до.** Убрана лишняя задержка ~16 мс.

Критерий выхода выполнен:
- 60 fps сцены матрицы: **27 из 27** диагностических прогонов ≥ 99 % (до правки — 23 из 27);
- 30 fps — 8 из 8, все по 600 из 600;
- CPU главного потока и worker-а не вырос.

## Решения владельца в этой сессии

1. **Вариант 1 — «ящик на 2 места».** Отклонены:
   - фазовая подстройка worker-а под vsync — связывает два потока знанием о времени друг друга, хрупко;
   - выбор кадра на стороне UI (display-sync, как у mpv) — перенос владельца выбора кадра, отдельный план на 2–3 сессии.

   Цена, которую владелец принял: до +1 удержанного кадра в памяти и до +1 кадра (16,7 мс) отставания картинки после совпадения фаз.
2. **Попутную задержку 16 мс чинить сразу в этой сессии**, а не в бэклоге. Сделано отдельным коммитом (правило 8: изменение границы — отдельной правкой).

## Как нашли причину (трасса, а не гипотеза)

Трасса: `fastiplayer::video_render_acceptance=trace`, `fastiplayer::render_frame_timing=trace`, `player_core::session::tick::presentation_scheduler=debug`. Файлы — 1080p60 H.264 и AV1 из `test-assets/benchmark-matrix/`.

Скрипт сопоставлял три вещи: выбор кадра worker-ом («Presenting scheduled video frame»), отправку кадра на surface и стадии кадра UI.

**1. Под нативным Wayland (окно) дефекта нет.** 3 прогона по 41 с, ≥ 99,8 %. Под XWayland в фуллскрине (так работает протокол замера) он есть: в 2 из 5 прогонов не показано 54 и 48 кадров.

**2. Все потерянные кадры worker выбрал вовремя.** Планировщик (`presentation_scheduler.rs`) ни при чём: кадры терялись между слотом показа и окном.

**3. Под XWayland главный поток ждёт буфер swapchain на каждом кадре.**

| Режим | Кадров с ожиданием `surface_acquire` > 4 мс | Медиана ожидания |
|---|---:|---:|
| XWayland-фуллскрин, 5 из 5 прогонов | 100 % | 15,6–15,9 мс |
| нативный Wayland, 3 прогона | 0 % | 0,05 мс |

Причина ожидания: FIFO, `max_frame_latency = 2`, видео 60,00 fps против дисплея 59,96 Гц. Очередь показа всегда полна, и главный поток привязывается к vsync.

**4. Кадр брался из слота до этого ожидания.** Хронология плохого прогона:

```
-2,05 мс   UI отправил 1450 (взял его из слота ~16 мс назад, затем ждал буфер)
 0,00      worker опубликовал 1483
+16,38     UI отправил 1466
+16,69     worker опубликовал 1500   ← 1483 перезаписан в слоте, на экран не попал
+31,35     UI отправил 1500
```

**5. Всё решает фаза.** Смотрели момент начала кадра UI относительно последней публикации worker-а:
- хорошие прогоны: кадр UI начинается через 5,7–12,9 мс после публикации, 0 % столкновений;
- плохие: через 14,1–14,5 мс, то есть чтение слота попадает на следующую публикацию; 24–34 % чтений в пределах ±1 мс от неё.

Фаза держится весь прогон и выбирается случайно при старте. Отсюда «каждый 2–5-й прогон».

**Корень.** Worker выбирает кадр в ритме видео, а UI читает слот на одно место в ритме дисплея. При совпадении фаз дрожание в доли миллисекунды решает, «успел» ли кадр. Слот то повторяет прежний кадр, то перезаписывает незабранный.

**Попутный корень задержки.** Видеокадр выбирался до блокирующего `get_current_texture` и на экран уходил на ~16 мс старше, чем мог бы.

## Что изменилось

### Шаг 1: упорядоченная передача кадров (`player-core`)

- **Новый модуль** `render_lease_bridge/ordered_present_handoff.rs`, тип `OrderedPresentFrameHandoff`. Хранит последний забранный UI кадр плюс до `UNTAKEN_PRESENT_FRAME_CAPACITY = 2` незабранных, строго по порядку.
- **Итог публикации** — enum `OrderedPresentFramePublish`:
  - `Queued` — кадр встал в очередь;
  - `DroppedOldestUntaken` — UI отстал больше чем на 2 кадра, старший незабранный сброшен;
  - `RestartedSequence { discarded_untaken_frames }` — seek, смена поколения или PTS назад: незабранные кадры старой последовательности отбрасываются, устаревшую картинку после seek UI не увидит.
- **Освобождение lease-ов** — только вне mutex-а.
- **Счётчик** `present_frames_dropped_untaken` в сводке плеера (`Playback diagnostics summary`). Раньше перезапись незабранного кадра не видел ни один счётчик.
- **app-egui:** после настоящего показа, если в передаче ждёт другой кадр текущего поколения, сразу просится ещё одна перерисовка (`request_follow_up_redraw_for_waiting_present_frame`). Без неё на паузе последний выбранный кадр мог бы не показаться. Для одного кадра она просится один раз (`WaitingFrameFollowUpMemory`), иначе кадр, который не удаётся показать, крутил бы redraw на каждом vsync. Сама перерисовка — показ без egui-прохода (флаг снимается планировщиком в том же кадре).
- **Слот scrub-override** остаётся «последний побеждает» (там нужен именно последний кадр жеста). Запись в него в production не используется — так было и до сессии; `publish`/`clear` помечены `cfg(test)`, находка в бэклоге.

### Шаг 2: буфер экрана до выбора кадра (`render-wgpu-shell` + `app-egui`)

- **render-wgpu-shell:**
  - `Renderer::acquire_surface_frame(screen)` возвращает `SurfaceFrameAcquire::{Acquired(AcquiredSurfaceFrame), Dropped(RenderFrameDropReason)}`;
  - `RenderFrameInput.surface` — уже полученный буфер, `render_frame` его только записывает и показывает;
  - получение и восстановление surface вынесено в `shell/surface_acquire.rs`, `shell.rs` уменьшился с 799 до 705 строк.

  Неиспользованный буфер при drop-е возвращается swapchain-у. Это проверено по Context7, wgpu 30: `SurfaceTexture::drop` → discard; в FIFO «get_current_texture will block until there is a spot in the queue».
- **app-egui:**
  - `present_frame_for_plan`: буфер → выбор кадра и субтитров → запись и показ. Если буфер не получен, кадр плеера не забирается и остаётся в передаче;
  - стадия `SurfaceAcquire` в контракте последовательности кадра стоит строго до `MaterializerLookup`;
  - учёт итога кадра вынесен в `account_render_frame_outcome` (общий для обычного пути и пути без буфера).
- **Трасса acceptance:** новое поле `selection_to_present_ms`.

### Опробовано и отклонено: «очередь двигается только по подтверждению показа»

Остаточные потери после шага 2 (0–3 кадра за 40 с) один в один совпали со счётчиком `render_resource_previous_frame_reuse_count`. Это давний запасной путь: если пул ресурсов декодера занят, рендер показывает предыдущий кадр. Совпадение по прогонам: 3↔3, 1↔1, 0↔0, 2↔2, 2↔2.

Попробовали двигать очередь только после подтверждения показа. Не помогло:
- на 60 fps при 59,96 Гц у UI нет запаса скорости, чтобы догнать отставание, поэтому потеря просто переезжала в сброс из подставки;
- отставание на кадр держалось дольше. Задержка «публикация → показ» по прогонам вышла 2,7–25 мс против 3–16 мс без подтверждения.

Откатили. Потерю при отказе буфера экрана и так закрывает шаг 2.

## Известные ограничения

- **«Текстура занята» стоит кадр на 60 fps.** 0–5 событий за 40 с, были и до сессии. На 60 fps при 59,96 Гц каждое такое событие стоит один кадр (≤ 0,2 % — в пределах 99 %). Причина — неблокирующий `try_lock` пула ресурсов VA-API на пути рендера. Чинить отдельно, в бэклог.
- **Отставание после совпадения фаз.** Под XWayland/FIFO на 60 fps после совпадения фаз UI может идти на 1 кадр позади последнего выбранного worker-ом кадра, до ближайшего неизбежного сброса. Но шаг 2 убрал ~16 мс возраста кадра, поэтому итоговая задержка «публикация → показ» всё равно ниже базы.
- **Сбросы, которые счётчик считает штатно.** `present_frames_dropped_untaken` растёт, когда окно свёрнуто, буфер экрана не получается или идёт scrub-override: кадры выбираются, но не показываются. Это честный счёт, а не дефект.
- **24 fps проверены только моделью.** В матрице нет 24 fps файла.
- **mpv в этой сессии не запускался.** Эталон показал 0 потерь в сессии 06, CPU-сравнение против mpv — в сессии 06c.
- **Слот scrub-override** в production никто не заполняет (давнее, не в этой сессии).
