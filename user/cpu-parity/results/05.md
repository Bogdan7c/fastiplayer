# Результат сессии 05: россыпь на горячем пути

## Статус

**DONE.** 21 октября 2026.

Убрана работа, которая выполнялась на каждом пробуждении окна, каждом кадре и каждом тике worker-а и ничего не давала:
- глубокие копии снимка плеера;
- пустые MPRIS-публикации;
- пересоздание bind group и перезапись uniform видеорендера;
- INFO-span-ы кадра;
- имя файла карантина плейлиста;
- сдвиг всей аудиоистории на каждом пакете;
- пересчёт всех счётчиков задержек на каждом замере;
- аллокации ресэмплера.

Каждый пункт подтверждён профилем «до/после» и тестом, который падает без фикса.

Выигрыш в CPU-% скромный, как и прогнозировалось перед сессией:
- главный поток −0,2…−0,4 п.п. на HW;
- на SW — в пределах шума;
- worker — в пределах шума CPU-%, хотя по профилю из него ушло ~25 мс работы за 35 с.

Зато в установившемся показе видеорендер больше не создаёт ни одного GPU-объекта на кадр: это видно по счётчикам живого прогона.

## Решения владельца в этой сессии

1. **Снимок плеера — вариант A.**
   - Worker отдаёт окну общий снимок (`Arc`), окно его не копирует.
   - Снимок, равный уже опубликованному, не публикуется.
   - Счётчики показанных кадров переехали из снимка плеера в кадровый контекст окна: это данные окна.
   - Типы полей снимка не менялись. Вариант B (общие тяжёлые части внутри снимка) отклонён: сотни правок ради ≈ 0,05 п.п.
2. **Bind group — вариант A: кэш живёт вместе с текстурой.** Он хранится у импортированной DMA-BUF текстуры (HW) или у слота загрузки (SW) и умирает с ней. Гарантия сессии 03 «смена формата освобождает старую видеопамять до импорта новой» сохраняется. Uniform пишется только при изменении.
3. **Находки профиля вне плана чинятся в этой же сессии:** аудиоистория и счётчики задержек в worker-е.
4. Для профиля владелец разрешил `kernel.perf_event_paranoid = 1` и `kernel.perf_event_mlock_kb = 8192` до перезагрузки.

## Метод: сначала профиль

В сессиях 00–04 профиля не было (`perf_event_paranoid = 2`). Здесь его сняли samply, разбор по функциям и потокам сделан своим скриптом. Веса — реальное время CPU потока (`threadCPUDelta`).

Профиль изменил план в трёх местах:
- **Самым дорогим пунктом оказалось обслуживание окна в `about_to_wait`.** Его не было в списке сессии 00. Оно забирало 8,7 % главного потока. На каждом витке event loop-а там:
  - заново забирался снимок плеера (ещё 2 глубокие копии, итого **4 на кадр, а не 2**, как считалось);
  - строился MPRIS-вид;
  - форматировалось имя файла карантина плейлиста с timestamp. Оно нужно только при старте, когда файл состояния повреждён.
- **В worker-е сдвигалась вся аудиоистория.** Это история для смены темпа: `Vec` + `drain(..)` с начала, то есть memmove всего буфера (до 600 мс звука) на каждом аудиопакете. Цена — 3,5–4,7 % потока.
- **Пункты, закрытые раньше.** `dup()`/`fstat` убрала сессия 03, пробуждения worker-а от телеметрии — сессия 04.
- **SW-путь.** `std::thread::scope` при загрузке каждого кадра забирает 20 % главного потока на SW 1080p60. Это уже записано в сессию 07, здесь не трогали.

## Корневые причины и что изменилось

| Что | Корень | Что сделано | Владелец |
|---|---|---|---|
| Копии снимка плеера | Канал нёс `PlayerSnapshot` по значению. Handle копировал кэш на каждом чтении, приложение копировало ещё раз в `last_player_snapshot`. Worker публиковал после каждого тика и команды без проверки изменений, а сборка начиналась с глубокой копии старого снимка, которая тут же перезаписывалась. | Канал `Arc<PlayerSnapshot>`. `LatestSnapshotPublisher` помнит последний опубликованный снимок и не публикует равный: `SnapshotPublication::{Published, Unchanged, NotDelivered}`. `latest_snapshot() -> Arc`. Builder собирает снимок литералом, без начальной копии. `frame_counters` убраны из снимка в `AppFrameContext`. | `player-core::worker`, `app-egui::state` |
| Обслуживание окна в `about_to_wait` | См. выше. Снимок и MPRIS там стали дешёвыми благодаря двум соседним строкам этой таблицы. Имя файла карантина формировалось до проверки, есть ли что применять. | Имя файла запрашивается только при реальном startup completion. | `app-egui::playlist_runtime` |
| MPRIS | На каждом вызове: revision+1, заново собранные строки метаданных, 2 полные копии вида, write-lock. При этом D-Bus молчит, потому что позиция сигналов не шлёт. | Полная публикация — только если изменилось что-то, кроме позиции. Иначе новый intent-метод `DesktopIntegration::publish_position`: без revision, без копий, без сигнала. Входы метаданных сравниваются без аллокаций. Getter `Position` в D-Bus читает только позицию. | `app-egui::playlist_runtime::desktop_transport`, `desktop-integration` |
| Bind group + uniform | `create_bind_group` и `write_buffer` на каждом кадре без проверки изменений. Кэш «одна запись на рендерер» не помог бы: HW-кадры по кругу идут из ~20 поверхностей пула. | `render-wgpu-video::video::frame_bind_group_cache`. Uniform пишется только при новых байтах (по слоту). Bind group кэшируется у владельца views по ключу «экземпляр пайплайна + слот» и умирает вместе с текстурой. Счётчики выведены в трассу кадра. | `render-wgpu-video` |
| INFO-span-ы | `#[instrument]` по умолчанию INFO. Span `render_frame` на каждом пробуждении форматировал `Debug` координатора рендерера в строку. | `#[instrument(level = "trace", skip_all)]` на `render_frame` и `render_ui`. | `app-egui` |
| Аудиоистория | `Vec::drain(..)` с начала. | `pipeline/passthrough_audio_history.rs`: `VecDeque`, ёмкость резервируется один раз (не больше прежнего пика), выход побайтно прежний. | `player-core::pipeline` |
| Счётчики задержек | На каждом замере пересчитывались все 13 стадий (13 делений `u128`). | Замер обновляет в снимке только свою стадию: `diagnostics/latency_stage_update.rs`. | `player-core::diagnostics` |
| Ресэмплер | 2 `Vec` на каждый блок (при несовпадении частот). | Scratch внутри ресэмплера, выходной буфер — поле `AudioOutput`. | `audio` |

**Промах, найденный замером «после».** Первая версия правки счётчиков задержек переносила пересчёт с записи на чтение. Но снимок читается на каждом тике и каждой сборке, а это чаще, чем приходят замеры. Профиль показал рост с 3,0 до 8,8 мс за прогон. Исправлено обновлением только одной стадии на замер. Попутно исчезла ловушка «поле хранимого снимка устарело, не читать».

**Что сохранено:**
- семантика «последний опубликованный снимок»;
- poison-обработка барьера публикации;
- latest-wins;
- MPRIS-сигналы и `Seeked`/detached-путь (сверено с базой через `dbus-monitor`);
- порядок release текстур и освобождение импортов (сессия 03);
- поведение HostPlanar без кэша, если у кадра нет владельца views;
- побайтный выход аудиоистории, диагностики и ресэмплера.

## Известные ограничения

- **CPU-% главного потока на 60 fps по-прежнему ~3,8–4,3 %.** Основная цена — submit/present (0,43 мс × 60) и драйверный `ioctl`. «Россыпь» была ~0,6 п.п. ядра, и её съедает дневной шум. Цель README «главный поток ≈ 1,5–2 %» этой сессией не достигается и не могла: дальше только меньше submit-ов. Это отдельное направление, если владелец захочет.
- **Снимок плеера по-прежнему публикуется на каждом тике воспроизведения**, потому что меняется позиция. Сборка создаёт строки пути файла на каждом тике (~27 мс за 35 с в worker-е). Устраняется вариантом B (общие тяжёлые части), отклонённым владельцем.
- **`refresh_player_snapshot` вызывается ≥ 2 раз за пробуждение.** Теперь это `Arc::clone` + разбор потоков субтитров.
- **`VideoDecodeThread::resource_pool_stats`** (VA-API, lock + статистика на каждом тике через `texture_pool_snapshot`) — ~4 % worker-а, не трогали. В бэклог.
- **Поток `smithay-clipboard` (0,3 %).** Причина выяснена профилем: поток слушает то же Wayland-соединение, что и окно, и просыпается на каждом событии композитора (кадр, освобождение буфера). Это устройство зависимости egui-winit/smithay-clipboard, вслепую не патчили. В бэклог.
- **Записи старого рендерера в кэше bind group.** При пересоздании рендерера они живут в кэшах текстур до вытеснения (≤ 4 на текстуру). Они держат старые uniform-буфер и sampler, но не текстуру.
- **Не проверено вживую:**
  - seek/scrub мышью, переключение HW ↔ SW в настройках, смена файла N/P;
  - plasma media controller глазами (проверено через `busctl` + `dbus-monitor` — тот же D-Bus).
  - Seek через MPRIS и пауза проверены.
