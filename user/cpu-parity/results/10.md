## Решения владельца в этой сессии

1. **Эталон — mpv по протоколу v3**, как на 780M (а не «VLC с Qt» из текста сессии): одна таблица на две машины.
2. **Файлы — реальные видео из `test-assets`**, а не синтетика. Оказалось, что там лежит и мастер матрицы 780M (тот же SHA `88344504…`), и BBB AV1 из сентябрьского отчёта (тот же SHA `e647620f…`). Сцены H.264 1080p60 и HEVC 4K60 собраны на T480s тем же рецептом из того же мастера.
3. **Добавить SW H.264 1080p60** — проверить импорт кадров на Intel.
4. **HEVC 4K60, где mpv теряет кадры** — сравнивать с пометкой (`reference_losses = annotate`), а выигрыш подать честно, но красиво: «Fastiplayer успевает там, где эталон — нет».
5. **Первую SW-серию не учитывать, перезапустить с нуля.** Владелец мог трогать ноутбук во время неё. В публичном отчёте исключённые серии упомянуты одной строкой с причиной (правило 5 `docs/benchmarks/README.md`), без цифр в таблицах.

## Как шла сессия

1. Подготовка:
   - Для сборки на T480s не хватало `meson` (вендорный dav1d), а для протокола — `xrandr`. Владелец поставил оба.
   - Сборка заняла 7 мин 12 с.
   - Тесты инструментов: 48/48 → после правки 55/55.
2. Smoke всех четырёх сцен:
   - mpv на HW выбрал `vaapi`;
   - у нас SW-кадры импортируются в Vulkan без CPU-копии.
3. Первая пара серий (исключена):
   - HW остановилась на quality-gate из-за потерь mpv на HEVC 4K60 (политика `stop`).
   - SW остановилась на нашем AV1: 1168 из 1202 кадров, пропуски кучно на 28–32 с фильма.
4. Разбор провала AV1 (вне протокола, в scratchpad):
   - Окно, сдвинутое на тяжёлый участок, с 6 и с 8 потоками: 960/960 кадров во всех 4 прогонах. 8 потоков только дороже (+75…85 п.п.).
   - Гипотеза «перегрев» не подтвердилась: в упавшей попытке и в удачных повторах одинаково 65–68 °C.
   - Найдено: в упавшей попытке прочие процессы системы ели 111 % CPU против 41–49 % в повторах, load average 6,2 против 3–5. Что-то постороннее съело ~0,7 ядра.
   - 6 повторов с окном плана (в том числе сразу после mpv, как в серии): 1201–1202 кадра, провал не воспроизвёлся.
5. Новые серии 14:24–14:50:
   - HW 16/16 валидных попыток, SW 28/28.
   - Quality-gate: у нас 1201 на всех сценах.
6. Найдена и починена проблема обработки GPU-метрик на i915 (ниже). Сводки пересчитаны.
7. Скриншот реального окна (BBB AV1 4K60 на T480s, нативный Wayland) — `docs/assets/fastiplayer-t480s-av1-4k60.png`.

## Найдено и исправлено: GPU-метрики на Intel (i915)

- **Симптом:** в сводке T480s «gfx engine counter missing» и GTT = 0 у обоих плееров.
- **Корень:** сырые данные записывались правильно, но разбирались по именам amdgpu. В DRM fdinfo имена задаёт драйвер:
  - движок рендера: у amdgpu `gfx`, у i915 `render`;
  - память вне RSS: у amdgpu `drm-memory-gtt`/`vram`, у i915 `drm-resident-system0`/`local0`.
- **Исправление** (`docs/benchmarks/tools/local`):
  - `host.py`: таблицы `RENDER_ENGINE_NAMES` и `GPU_MEMORY_FIELDS`; имена amdgpu в приоритете, поэтому серии 780M считаются как раньше. Общая функция `gpu_memory_summary(samples)` для collector-а и анализа.
  - `analyze.py`: `gfx_percent` ищет движок по таблице. `gpu_memory_metrics` пересчитывает память из сохранённых сырых samples, но только у попыток, чей collector уже писал память: старые серии до 08b остаются без этих колонок.
- **Тесты** (`test_protocol_v2.py::DriverNamingTests`, 7 штук):
  - реальная форма fdinfo i915;
  - local0 → VRAM;
  - приоритет amdgpu при дубле `drm-memory-gtt` / `drm-resident-gtt`;
  - движок под именем драйвера;
  - сквозной анализ серии i915 → вердикт GPU WIN и память из сырых samples;
  - пересчёт для amdgpu равен сохранённому;
  - старая попытка не пересчитывается.
  - Мутация «только имена amdgpu» роняет 4 теста i915, а тесты amdgpu остаются зелёными.
- **Важно для чтения памяти:** на HW-пути у плеера два DRM-клиента (VA-API и Vulkan), и общие поверхности видны обоим, так что сумма по клиентам считает их дважды. Поэтому в отчёте две колонки: «простая сумма» и оценка «общее один раз» = Σ(resident − shared) + max(shared). По оценке у нас на HW 4K60 память драйвера 330 против 305 МиБ у mpv (пул 4K-поверхностей больше), но RSS + GPU — 424 против 612.

## Известные ограничения

- Кодирование сцен на T480s дало другие байты, чем на 780M (FFmpeg 9.0.2), поэтому сцены «одинаковые по рецепту», не по байтам.
- Точные байты конфигов серий 780M не опубликованы, поэтому равенство конфигов между машинами не утверждается (на T480s — шаблоны из репозитория).
- Причину посторонней нагрузки в исключённой SW-серии задним числом не установить.
- Код плеера не менялся, поэтому `scripts/ci-checks.sh` для Rust не запускался заново; менялись только Python-инструменты (их тесты зелёные) и документы.

## Бэклог (новое)

- На HW 4K память драйвера GPU у нас немного выше mpv (пул 24 поверхностей). Если это станет важным, понадобится отдельное решение владельца о размере пула на 4K (влияет на перемотку и упорядоченный показ).
- Протокол: колонку «общее один раз» можно встроить в `analyze.py`, если владелец захочет её в будущих сериях.

> The plan was reorganized after session 00. Session 00 showed that decoding was not the problem; the overhead was in Fastiplayer's own plumbing. Mapping of the original list:
>
> - **00 tooling and baseline** — done: the PR #12 protocol was restored and extended (v2: mpv reference, GPU engine time, automatic quality gate; v3: `--fullscreen`), and a per-thread diagnosis was published (session 00, 06).
> - **01 repeated frame identities / 02 proven quality defect** — done: a real repeat+skip at 60 fps was found and fixed with ordered presentation handoff (06a); the quality gate went from 23/27 to 27/27.
> - **03/04 allocation reuse and external synchronization** — done: a bounded VA-API surface pool instead of create/destroy per frame (01); `VK_QUEUE_FAMILY_FOREIGN_EXT` acquire/release barriers (03).
> - **05 bounded import cache** — done: one Vulkan import per pool surface instead of per frame (03).
> - **06 Vulkan context work** — not needed after 03.
> - **07 residual profiling / 08 bind groups / 09 UI CPU** — done: event-driven wake-ups instead of 2 ms polling (02, 02b), render-on-change UI (04, 06b), snapshot/MPRIS/bind-group churn found by profiling (05), and the 30 fps residue explained (06d).
> - **10/11 software path** — done: no per-frame threads (07), a decode thread policy (08), and frames decoded into importable memory with no CPU copy (08b). LTO was measured and rejected as noise (09).
> - **12 local qualification** — done on the AMD 780M: 17 hardware scenes with no WORSE and the quality gate passed on all; software WIN on VP9/HEVC/AV1 4K60, INCONCLUSIVE on H.264 1080p60.
> - **13 fresh T480s qualification and public update** — done: on the T480s every scene kept all frames, with CPU WIN on hardware H.264 1080p60 and INCONCLUSIVE on software H.264 1080p60. On both 4K60 scenes mpv lost 37–56 % of frames while Fastiplayer used less CPU and render time (reported with that caveat).
>
> Not achieved / remaining: no PARITY label (the protocol never emits one). Several 60 fps comparisons stay INCONCLUSIVE because of reference run-to-run spread. On hardware 4K Fastiplayer's GPU-driver memory is slightly above mpv's, although its total is lower. The backlog is in [the plan README](https://github.com/Bogdan7c/fastiplayer/blob/main/user/cpu-parity/README.md).
>
> Memory: process RSS is below the reference on every T480s scene and on all 780M hardware scenes; the only growth, +24…34 MiB on the software path (08b), was an explicit owner decision.
