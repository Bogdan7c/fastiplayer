# Результат сессии 08b: программный путь — показ кадра и память 4K

## Статус

**DONE, 22–23 октября 2026. Критерий выхода выполнен на 4 сценах из 5.** На H.264 1080p60 WORSE ушёл (+3,7 → +0,66 п.п.), но интервал шире коридора ±1 п.п.

| Вопрос | Ответ |
|---|---|
| Почему показ SW-кадра у нас дороже, чем у mpv? | Не рисование, а одна копия. Главный поток копировал каждый кадр на CPU в буфер для видеокарты: 43 % потока на H.264 1080p60 и 59 % на VP9 4K60 (профиль samply). mpv по умолчанию декодирует прямо в память, которую читает видеокарта (direct rendering, DR) |
| Доказательство | mpv с выключенным DR (`--vd-lavc-dr=no`) стоит столько же или дороже нас: `vo` 5,5 и 9,5 % против нашего главного потока 5,9 и 9,8; копию за него делает драйвер |
| Почему RSS на VP9/HEVC 4K выше, чем у mpv? | Не лишние кадры. Кадры mpv лежат в памяти видеокарты (GTT), а RSS её не видит: у mpv 417 МиБ отображений `/dev/dri` с Rss = 0. В сумме RSS+GTT мы экономнее mpv на всех сценах. Кадров в памяти у обоих примерно поровну: у нас ~25 4K-кадров, у mpv 22 DR-кадра |
| Что сделано | Декодер кладёт кадры в свои блоки обычной памяти, видеокарта импортирует блок (`VK_EXT_external_memory_host`) и копирует сама — CPU-копии нет. AV1 и драйверы без расширения — прежняя копия |
| Итог «до/после» (процесс, % ядра) | H.264 1080p60 51,9 → 49,0; VP9 4K60 112,0 → 102,6; HEVC 4K60 166,8 → 161,2; AV1 без изменений |
| Квалификация против mpv | VP9 4K60 **WIN** −5,4 (было WORSE +3,4), HEVC 4K60 **WIN** −14,6 (было INCONCLUSIVE), AV1 WIN, H.264 1080p60 INCONCLUSIVE +0,66 [−2,30; +3,62] (было WORSE +3,7) |
| Цена | RSS +24…34 МиБ на 1080p60/4K60, GTT −18…28 МиБ — общая память примерно та же (принято владельцем) |

## Решения владельца в этой сессии

1. **Путь показа — «импорт памяти кадра».** Владелец уточнил, что это zero-copy для CPU. Ответ: CPU кадр больше не копирует, видеокарта сама переносит его в текстуру (одна GPU-копия остаётся, как у mpv). Решение: «то, что выиграет по перфомансу и не убьёт стабильность».
   - Выбран импорт обычной памяти (а не «как mpv», где декодер пишет в память, выделенную рендерером). Выигрыш по CPU одинаковый, но декодер не зависит от устройства видеокарты, а любой отказ уходит на старую отлаженную копию.
   - Отклонено: «как mpv» (новая граница decoder ↔ renderer, буферы декодера умирают вместе с устройством) и «принять разрыв».
2. **Дискретные видеокарты не должны сломаться** (требование владельца по ходу работы). Импорт включается, только если драйвер сам объявляет расширение. Ошибка импорта выключает его до конца жизни устройства, кадры идут прежней копией.
3. **Память:** причину принять, а в протокол квалификации добавить GTT и RSS+GTT.
4. **RSS +24…30 МиБ** ради шага строк, кратного 256 байт, — принять. Отклонены: копия в обход wgpu сырым Vulkan (ручные барьеры, риск стабильности) и откат.

## Разбор

### Профиль главного потока (база, 45 с записи)

| Сцена | memcpy в staging | submit кадра | acquire / present |
|---|---:|---:|---:|
| H.264 1080p60 | **43 %** | 12 % | 6 % / 5 % |
| VP9 4K60 | **59 %** | 9 % | 4 % / 3 % |

У mpv в потоке `vo` memcpy занимает 1,3 %. Остальное — рисование libplacebo и ioctl драйвера.

### Опыт: mpv с DR и без

| Сцена | Наш процесс / главный поток | mpv с DR: процесс / `vo` | mpv без DR: процесс / `vo` |
|---|---|---|---|
| H.264 1080p60 | 51,0 / 5,9 | 49,1 / 2,9 | 51,8 / 5,5 |
| VP9 4K60 | 111,8 / 9,8 | 107,7 / 3,1 | 114,4 / 9,5 |

Без DR 57 % потока `vo` уходит в `libvulkan_radeon.so`: это копия драйвером через `VK_EXT_host_image_copy`. По `-v` mpv на VP9 4K выделяет 22 «host-cached DR image».

### Память: где лежат кадры

| Сцена | Мы: RSS + GTT | mpv: RSS + GTT | mpv без DR: RSS + GTT |
|---|---|---|---|
| H.264 1080p60 | 241 + 75 = 316 | 275 + 130 = 405 | 338 + 34 = 372 |
| VP9 4K60 | 420 + 171 = 591 | 236 + 567 = 803 | 499 + 185 = 684 |
| HEVC 4K60 | 672 + 170 = 842 | 514 + 576 = 1090 | 777 + 205 = 982 |

У mpv отображения `/dev/dri` занимают 417 МиБ при Rss = 0. Наш anon на VP9 4K — 308 МиБ, это ~25 кадров по 12,4 МиБ. Лишних очередей у нас нет.

### Что всплыло во время реализации (по замерам, не по догадкам)

Первая рабочая версия убрала memcpy, но процесс на VP9 4K60 подорожал: 109 → 134 %. Разделение по user/system time показало две независимые причины.

| Вариант (VP9 4K60) | Декодер, user | Главный поток, user / system | Процесс |
|---|---:|---:|---:|
| База (staging) | 103 % | 8,6 / 1,3 % | ~114 % |
| Шаг строк 4096/2048, кэш импортов | 133 % | 2,5 / 5,1 % | 134 % |
| A: шаг строк — нечётное кратное 256, кэш импортов | 99,6 % | 3,2 / 4,2 % | ~108 % |
| B: то же + импорт на каждую копию | 99 % | 2,8 / 2,5 % | ~105,5 % |
| C (итог): то же + блоки с началом на 2 МиБ | 97,5 % | 3,3 / 1,65 % | ~103 % |

1. **Шаг строк — степень двойки.** Сначала я, как FFmpeg, растил ширину до общего кратного 256 у всех plane-ов. Для 4K это 4096/2048: соседние строки попадают в одни и те же наборы кэша CPU, и декодер стал дороже на 30 п.п. Теперь шаг каждой plane — нечётное кратное 256: 3840/2304 на 4K, 2304/1280 на 1080p.
2. **Импорт в amdgpu — это `userptr`.** Ядро проверяет страницы каждого живого такого буфера на каждом submit, а RADV кладёт в submit все буферы устройства. Поэтому кэш импортов (~25 блоков) вреден: импорт создаётся на каждую GPU-копию и уничтожается после неё. Блоки с началом на границе 2 МиБ ложатся на большие страницы, и ядру ещё дешевле. Добивать длину блока до 2 МиБ не нужно: это +2 МиБ RSS на кадр без выигрыша (проверено отдельным прогоном).

### Инварианты

1. CPU не копирует кадр, если импорт сработал. GPU-копия в текстуру одна, как раньше.
2. Декодер не перепишет блок, пока GPU его читает: обёртка держит дескриптор кадра до выполнения последнего submit-а с ней — с кадром или отдельным submit-ом невостребованной копии.
3. Страницы блока не освобождаются, пока жив Vulkan-импорт.
4. Живых импортов — только копии в полёте (`live_imports`), а не все блоки декодера.
5. Fail-closed: без расширения, при выравнивании драйвера больше страницы, без coherent memory type или после ошибки Vulkan работает прежняя копия через staging.
6. FFmpeg-типы не выходят из `video-ffmpeg`, CPU-конверсии нет, очереди и пулы прежние. Политика потоков 08 не менялась.

## Известные ограничения

- **H.264 1080p60: коридор ±1 п.п. не пройден** (интервал шире, среднее +0,66). Оставшийся ~1 п.п. — работа ядра amdgpu с `userptr`-импортами. Убрать его может только память, выделенная драйвером (вариант «как mpv», отклонён ради независимости декодера) — кандидат в отдельное решение владельца.
- **RSS** на VP9/HEVC 4K выше mpv (кадры mpv в GTT); RSS+GTT ниже на всех сценах. Против сессии 08 RSS +27…34 МиБ (принято). В RSS+GTT у нас 2–3 кадра в полёте посчитаны дважды.
- **Проверено только на Radeon 780M (RADV).** Дискретные видеокарты и Intel (T480s, сессия 10) не проверялись. Механизм тот же, что у копии из staging в host-памяти, а отказ уходит на staging.
- **AV1 по-прежнему через staging:** у libdav1d свой пул кадров, `get_buffer2` ему не ставится. На AV1 мы и так выигрываем.
- **Переключение HW ↔ SW вживую не проверялось:** материализатор пересоздаётся вместе с конвейером, импорты живут только на время копии.
