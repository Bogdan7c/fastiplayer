## Решения владельца в этой сессии

1. **Эталон SW — mpv** (`--hwdec=no`), как и в HW-квалификации, а не VLC из исходного плана: единый отчёт и проверенные инструменты.
2. **H.264/HEVC/VP9 — «ядра − 2» без потолка.** Предлагался потолок 8 (−36 МиБ на 1080p, −120…140 МиБ на 4K ценой перемотки на ~20–30 % медленнее). Владелец выбрал скорость перемотки: плеер — движок редактора Fasticut.
3. **AV1 — не больше 4 потоков до 1080p и 6 выше.** Отклонено: 4/2 (дешевле по CPU, но перемотка 4K вдвое медленнее) и общая политика с H.264.
4. **Одно-тайловый AV1 4K60 — чинить в этой сессии сабагентом**, отдельно проверить и опереться на эту проверку. Вариант правила — **«выше 1080p всегда 2 кадра»**. Отклонены: адаптивное переоткрытие декодера (трогает жизненный цикл) и «2 только для 4K выше 30 fps» (нужна частота кадров в общем API `video-core`).
5. **Закрыть 08 и спланировать 08b** (путь показа SW-кадра и память на 4K, затем повтор SW-квалификации). Отклонены: «копать сейчас в той же сессии» и «принять как есть».

План сессии уже содержал правило для потерь у эталона: «таблица публикуется с оговоркой, без заявлений о превосходстве». Инструменты научены ему полем `reference_losses = annotate`.

## Разбор

### Число потоков: H.264, HEVC, VP9 (базовая сборка, 2 круга)

| Сцена | Потоки | CPU всего, % | RSS, МиБ | Кадров из 1200 | Перемотка, медиана / p90, мс |
|---|---|---|---|---|---|
| H.264 1080p60 | 2 / 4 / 8 / 14 | 51,5–52,1 при любом N | 159 / 173 / 201 / 237 | 1200 | 178 / 422; 158 / 352; 88 / 148; 67 / 99 |
| H.264 4K60 | 4 / 8 / 14 | 151–153 | 368 / 469 / 588 | 1200 | 298 / 859; 192 / 439; 158 / 311 |
| HEVC 4K60 | 4 / 8 / 14 | 163–172 | 414 / 531 / 671 | 1200 | 264 / 1136; 258 / 525; 227 / 1465 (шумит) |
| VP9 4K60 | 4 / 8 / 14 | 110–111 | 279 / 337 / 420 | 1200 | 220 / 456; 183 / 411; 166 / 373 |

**Почему так (исходники FFmpeg 8.1.3).**
- Frame threading держит по копии контекста декодера на поток и добавляет `thread_count − 1` кадров задержки.
- Суммарная работа декодирования от N не зависит: CPU плоский, а память и скорость догоняющего декода после seek растут с N.

|---|---|---|---|---|
| AV1 4K60 BBB (тайлы) | 4 / 6 / 8 / 14 | 95 / 103 / 112 / 165 | 1200 | 756 / 534 / — / 362 мс |

**Почему лишние потоки дорогие.** С `max_frame_delay = 1` (Session 29) в полёте один кадр (dav1d `n_fc = 1`), и все потоки делят его тайлы и строки. Вне плеера (`ffmpeg -benchmark`) цена кадра BBB растёт с 10,5 мс CPU (4 потока) до 18,4 мс (14 потоков) — это синхронизация.

Вне плеера dav1d на этом файле выдаёт 58–67 кадров/с при `max_frame_delay = 1` и любом числе потоков (≈ 1,2 ядра — упор в последовательный разбор единственного тайла). При 2 кадрах в полёте — ~121 кадр/с, при автоматическом выборе dav1d — ~170.

### Холостой цикл worker-а (найден перебором)

- **Симптом.** AV1 4K60 из матрицы, 14 потоков: поток `player-worker` занимает 79 % ядра, 351 тыс. тиков за 2 с, все с причиной `pipeline_work_ready`.
- **Корень** (`player-core::session::tick::wakeup::pending_video_work_available`):
  - проверка «канал пакетов декодера полон» действовала только в preroll точной перемотки;
  - в обычном воспроизведении pending-пакет считался готовой работой, и worker будился с задержкой 0;
  - тик упирался в `PacketQueueFull` и сразу повторялся.
  
  Проверка появилась в июне, когда обычный путь ещё опрашивал декодер раз в 2 мс (до сессии 02), поэтому раньше дыра не проявлялась.
- **Исправление.** Полный канал — всегда повод ждать готовности декодера: ACK пакета через activity notifier или 2-мс bounded poll.
- **Результат.** Та же сцена: worker 79 → 1,8 %, 1079 тиков за 2 с.
- **Старый тест.** Тест `immediate_video_work_keeps_zero_wakeup_without_decoder_activity_wait` закреплял баг (глубина канала 4 из 4) — теперь 3 из 4.

## Изменения

- **`video-ffmpeg::decoder_thread::send_receive::decode_threading`** (новый чистый модуль):
  - `SoftwareDecodeWorkload { decoder, coded_size }`, `CodedFrameSize::{Known, Unknown}`;
  - `apply_to_request`: число потоков (`Auto` → «ядра − 2» с потолком AV1 → `Fixed(n)`; ручной `Fixed` как есть) и `max_frame_delay` AV1 (1 до 1080p, 2 выше и при неизвестном размере);
  - вызов из `RealFfmpegDecodeApi::open` вместо безусловного `with_max_frame_delay(1)`.
  
  API `video-core` и `codec_context` не менялись: в codec context уходит уже разрешённый `Fixed(n)`, ровно как описано в документации `SoftwareDecodeThreadBudget::Fixed`.
- **`player-core::session::tick::wakeup`** — `decoder_packet_channel_full_waits_for_decoder_readiness` вместо `accurate_seek_pending_video_waits_for_decoder_readiness`.
- **Тексты настройки `video.sw_decode_threads`** (схема, комментарий default-конфига, фикстура v23) упоминают потолок AV1.
- **Инструменты протокола** (`docs/benchmarks/tools/local`): поля плана `decode`, `exit_band_percentage_points`, `reference_losses`; README.

## Известные ограничения

- **Критерий выхода не выполнен** на H.264 1080p60, VP9 4K60 (WORSE) и HEVC 4K60 (интервал шире ±1) → сессия 08b.
- **Память на 4K:** HEVC/VP9 выше mpv; AV1 4K вырос на ~110 МиБ (принятая цена) → 08b.
- **T480s (4 ядра / 8 потоков) не проверялся:** там «ядра − 2» = 6, потолок AV1 4K совпадает с прежним поведением; «2 кадра параллельно» на слабом CPU — проверить в сессии 10.
- **Перемотка AV1 4K стала медленнее** при меньшем числе потоков (0,36 → 0,53 с на файле с длинным GOP), на одно-тайловом файле — быстрее (0,65 → 0,32 с) благодаря «2 кадрам».
- **HEVC 4K60 перемотка шумит:** p90 0,5–2,0 с при любом N. Причина не разбиралась (бэклог).
- **Метод:** скрипты, запускающие плеер с относительным путём к каталогу попытки, теряют конфиг и молча уходят в VA-API. Все прогоны сессии проверены по логу (`ffmpeg-host-upload-wgpu` во всех 144 + 62).
