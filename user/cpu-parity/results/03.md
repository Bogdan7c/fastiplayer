# Результат сессии 03: кэш Vulkan-импорта по стабильной идентичности и явная синхронизация

## Статус

**DONE.** 20 октября 2026.

DMA-BUF каждой поверхности пула декодера импортируется в Vulkan один раз, а не на каждом кадре. За 20-секундное окно на всех восьми аппаратных сценах импортов 19–24 (размер пула) вместо ~2050. Стадия `video_prepare` главного потока упала с 0,07–0,12 мс до 0,009 мс и перестала зависеть от разрешения. Синхронизация «декодер записал → Vulkan читает» оформлена явно по спецификации Vulkan (acquire/release через `VK_QUEUE_FAMILY_FOREIGN_EXT`), validation layer на релизном бинарнике чист (кроме известного `VUID-StandaloneSpirv-None-10684` от шейдера).

Цена: два маленьких command buffer-а с барьерами на кадр. На 780M это ≈ +0,3 п.п. GPU gfx на всех сценах (см. отдельный замер ниже) и +2 МиБ RSS. CPU главного потока −0,3…−1,0 п.п.

## Решения владельца в этой сессии

- **Барьер — вариант A: `VK_QUEUE_FAMILY_FOREIGN_EXT` с включением расширения `VK_EXT_queue_family_foreign` при создании устройства.** Это семейство спецификация описывает для «устройств других вендоров и не-Vulkan устройств, например fixed-function обработчиков изображений» — ровно аппаратный декодер. wgpu-hal 30 расширение не включает, поэтому shell создаёт устройство через официальный хук wgpu-hal `open_with_callback`. Без расширения — fail-closed: импорт на кадр, как раньше.
- Замер — на живых ассетах из `test-assets/` (H.264 4K30 без звука, H.264/HEVC/HEVC Main10/VP9/AV1 4K60), плюс синтетические фикстуры 1080p60 и HEVC 4K60.

## Корневая причина

Кэш импортов рендерера (`DmaBufWgpuTextureCache`) ключевался по `FrameResourceHandle`, который уникален на каждый декодированный кадр. Поэтому после сессии 01 поверхность в пуле декодера уже была стабильной (тот же `VASurfaceID`, тот же DMA-BUF объект), а рендерер всё равно на каждом кадре делал `dup()` fd, `vkCreateImage`, `vkGetImageMemoryRequirements`, `vkAllocateMemory` с импортом, `vkBindImageMemory`, обёртку wgpu и два view, а через 24 кадра уничтожал. Контракт декодера `explicit_external_memory_reuse_sync: false` держал `Replace` вместо `Reuse` именно потому, что импорт-слой не умел оформить переход владения между VA-писателем и Vulkan-читателем: при переиспользовании image tracker wgpu считает его уже в `SHADER_READ_ONLY_OPTIMAL` и барьера не ставит.

Дополнительно на каждый кадр: `fstat` дважды на один экспорт (lifecycle-пул и нейтральный дескриптор считали identity независимо), и `dup()`+`close()` fd ещё до проверки кэша.

## Что изменилось

**`video-core`** (новый `resource/identity.rs`):
- `DmaBufFrameIdentity` — стабильная идентичность буфера без fd: `resource_id` (VASurfaceID), identity объектов (`st_dev`/`st_ino`/`st_rdev` + размер + modifier), layout, fourcc, размеры; `DmaBufFrameDescriptor::identity()`; `FrameResourceIdentity::DmaBuf(Arc<..>)`.
- `validate_dma_buf_identity_against_frame_contract` — проверка кадра против уже импортированного image (layout + coded size), чтобы попадание в кэш не обходило контракт.

**`video-backend-api`** (новый `resource_identity.rs`):
- `PresentFrameResourceProvider::try_resource_identity_lookup` → `PresentFrameResourceIdentityLookup { Ready/Busy/Missing/Fatal/Unsupported }`. Default — `Unsupported` (host-planar backend), рендерер тогда идёт обычным путём с дескриптором.

**`video-vaapi`:**
- `fstat` один раз на экспорт: `dma_buf_object_identities` питает и `ZeroCopySurfaceDescriptor::from_dma_buf_image(image, &identities)`, и нейтральный дескриптор.
- `ResourceSlot` хранит `Arc<DmaBufFrameIdentity>`; `FrameResourcePool::resource_identity(handle)` отдаёт её без дублирования fd; провайдер и адаптер пробрасывают в нейтральный lookup.
- Контракт `vaapi_vulkan_dma_buf()`: `explicit_external_memory_reuse_sync: true` → `begin_import_or_reuse` даёт `Reuse` для той же поверхности; счётчики `imports_reused/replaced/created` обрели смысл. Прежняя `Replace`-политика осталась под тестом для контракта без синхронизации.

**`render-wgpu-video`:**
- `video/dma_buf_texture_cache.rs` — generic LRU-кэш по идентичности: ёмкость = ёмкость zero-copy пула декодера (`DmaBufImportCacheCapacity::matching_surface_pool`, app передаёт из `decoder_thread_config.zero_copy_surface_pool_slots`); тот же surface id с другой identity заменяет запись; смена формата потока уничтожает все записи старого формата ДО импорта нового; политика `AcrossFrames` / `SameFrameHandleOnly` (fail-closed без синхронизации: попадание только для того же кадра, как раньше).
- `video/dma_buf_materializer.rs` переписан и стал generic по importer-у (hermetic-тесты с fake): identity lookup → кэш (на попадании — проверка контракта) → descriptor lookup с dup fd только на промахе → проверка контракта → импорт. Счётчики `dma_buf_import_stats()` в трейте materializer-а и в trace-строке `render frame stage timings` (`dma_buf_vulkan_imports`, `dma_buf_cache_hits`, `dma_buf_cache_entries`, `dma_buf_image_reuse`).
- `dma_buf_import/external_sync.rs` — `ImportedImageExternalSync`: acquire-барьер (`FOREIGN → graphics`, `dstAccess = SHADER_READ`, layout `SHADER_READ_ONLY_OPTIMAL` без перехода) перед каждым video pass-ом и release (`graphics → FOREIGN`, `srcAccess = SHADER_READ`) после него; один раз после импорта — `initialize_ownership`: acquire `UNDEFINED → SHADER_READ_ONLY_OPTIMAL` плюс release отдельным submit-ом, текстуры удерживаются до `on_submitted_work_done`. Барьеры пишутся в отдельные encoder-ы через `CommandEncoder::as_hal_mut`, потому что wgpu-core 30 паникует при смешивании raw-команд с обычными в одном encoder-е. Обоснования со ссылками на VUID — в документации модуля.
- `dma_buf_import/image_create_state.rs`: `imported_dma_buf_start_state(sync)` — при синхронизации tracker wgpu стартует из `RESOURCE` (первый переход из `UNDEFINED` делает наш acquire при импорте), без неё — прежняя пара `UNDEFINED` + `UNINITIALIZED`.
- `external_sync_device.rs` — `create_video_device_with_external_sync`: wgpu-hal `open_with_callback` с добавлением `VK_EXT_queue_family_foreign`, явные проверки features/limits (как делает `request_device`), `Ok(None)` без расширения.
- `video/external_frame_sync.rs`: `render_or_clear`/`render_overlay` возвращают `WgpuVideoRenderOutcome { frame_drawn, external_sync }` (`#[must_use]`); `WgpuDmaBufPlaneViews` несёт синхронизацию от `dma_buf_views()` в `WgpuRenderableFrame`.
- `WgpuSubmittedResourceProvider` пробрасывает identity lookup (тест: иначе кэш в приложении никогда не попадал бы дёшево — тот же класс дыры, что в сессии 02).

**`render-wgpu-shell`:** `vulkan_device.rs` — устройство с расширением, fallback на `request_device` с логом; submit одного кадра — `[acquire, egui callbacks, основной encoder, release]`.

**`app-egui`:** callsite-ы materializer-а получают queue и ёмкость кэша; `frame_prepare` собирает `WgpuRenderableFrame` из `WgpuDmaBufPlaneViews`; trace-строка стадий кадра дополнена счётчиками кэша.

**Что сохранено:** `FrameResourceHandle` уникален на кадр; порядок release `Leased → WaitingGpuCompletion → WaitingDecoderReuse → Free`; возврат поверхности декодеру только после `on_submitted_work_done`; `vaSyncSurface` до публикации; семантика `Busy/Missing/Unsupported/Error` materializer-а; HostPlanar-путь не тронут (`external_sync = None`, identity lookup `Unsupported`).

### Цена синхронизации на GPU: что именно стоит

Отдельный замер финального бинарника против базы и временного варианта без release-барьера (один acquire-command-buffer на кадр; вариант собран только для замера и в код не попал). Две сцены, два круга, чередование `до → финал → без release`:

| Сцена | GPU gfx % база | GPU gfx % финал (acquire + release) | GPU gfx % без release | Главный поток база → финал |
|---|---:|---:|---:|---:|
| HW H.264 1080p60 | 1,61 / 1,66 | 1,81 / 1,85 | 1,82 / 1,75 | 3,94 / 3,54 → 3,54 / 3,59 |
| HW H.264 4K30 | 2,51 / 2,52 | 2,73 / 2,71 | 2,71 / 2,67 | 4,09 / 3,89 → 3,84 / 3,74 |

Вывод: release-барьер практически бесплатен (разница 0,0–0,1 п.п., в шуме), а +0,2 п.п. даёт acquire-command-buffer, без которого переиспользование image некорректно по спецификации. Поэтому в коде остаётся полная пара acquire/release. Снизить эту цену можно не отказом от барьеров, а меньшим числом проходов: сессия 04 (рендер по изменению) уберёт повторные проходы на 24/30 fps контенте, а с ними и повторные барьеры — на 4K30 это половина vsync-ов.

## Quality-gate

- Уникальные показанные кадры за 35 с (`fastiplayer::video_render_acceptance=trace`, `(pts, render_generation, decoded_generation)`): 1080p60 2097 → 2097, 4K30 1049 → 1049 (handoff-ов 2098–2100). `drops = 0` до и после; `decoder_publish_channel_full_count` 32 → 39 (1080p60), 85 → 81 (4K30) — шум.
- Validation layer (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`) на релизном бинарнике, 1080p60 NV12, 4K60 H.264 NV12, 4K60 HEVC Main10 P010: только известный `VUID-StandaloneSpirv-None-10684` (12 сообщений от шейдеров при старте). Ни одного сообщения о барьерах, queue family или layout-ах.
- 10-битный путь (P010, HEVC Main10 HDR → SDR): в замере `hevc10-4k60` — 19 импортов, 2032 переиспользования, drops 0.
- Ручной сценарий на финальном бинарнике (клавиатура через `/dev/uinput`, изолированный XDG, validation layer включён; очередь из двух CLI-файлов: синтетический H.264 1080p60 NV12 → HEVC Main10 HDR 4K60 P010): пауза и продолжение, 4 seek-а вперёд/назад на первом файле, N (смена файла: пул поверхностей перенастроен 1920×1088 → 3840×2160 `rt_format=256`, новый materializer), seek, пауза/продолжение и P (перезапуск файла, seek в 0) на втором, ещё один seek назад. Итог: 7 подтверждённых seek-ов (`Final seek resume intent applied`), `drops = 0`, 2533 уникальных показанных кадра за ~45 с, импортов 21 на первом файле и 20 на втором при 999 и 1244 переиспользованиях, ни одной ошибки в логе (единственный WARN — старый `Ignoring unknown button type: icon` от UI), validation layer — только известный SPIR-V VUID. Возврат на NV12-файл в одном процессе не проверялся: клавиша P перезапускает текущий файл, а не возвращает предыдущий.

## Доработки по независимому ревью

Read-only ревью диффа (Sonnet) до коммита нашло две средние и восемь мелких проблем; все закрыты, кроме L9 (рост legacy-файлов, см. ratchet выше):
- **попадание в кэш обходило проверку контракта кадра** — добавлена `validate_dma_buf_identity_against_frame_contract` на попадании + тест;
- **`create_device_from_hal` обходит проверки features/limits** — явные проверки до `open_with_callback`;
- ёмкость кэша была константой 24, не связанной с пулом декодера — теперь `DmaBufImportCacheCapacity` из конфига декодера;
- init-submit без удержания текстур wgpu — keepalive через `on_submitted_work_done`; `#[must_use]` на исходе pass-а; защита от дубликата расширения; poisoned-счётчики логируются; записи старого формата уничтожаются до импорта (`prepare_for_insert`); слот ресурса собирается до изменения lifecycle-пула; поле guard переименовано; устаревший тест-helper контракта заменён.

## Известные ограничения и наблюдения

- **GPU gfx +0,3 п.п. и RSS +2 МиБ** — плата за спецификационно строгую синхронизацию (два command buffer-а на кадр). Варианты снижения — в разделе замера GPU; решение за владельцем.
- Переход из `UNDEFINED` остаётся в момент импорта (единственный разрешённый `initialLayout` для external memory); при переиспользовании image в `UNDEFINED` больше не возвращается — риск потери содержимого на сжатых modifier-ах стал меньше, чем был.
- Без `VK_EXT_queue_family_foreign` (нет на этом стенде ни у RADV, ни у ANV — расширение есть у обоих) импорт остаётся покадровым; этот fallback проверен только hermetic-тестами политики `SameFrameHandleOnly`.
- Переключение hardware ↔ software в настройках вживую не проверялось (нужна мышь); на уровне кода смена бэкенда создаёт новый materializer с пустым кэшем.
- Профиль функций (samply/perf) не снят (`perf_event_paranoid = 2`); эффект доказан счётчиками импортов и трассой стадий.
