# Результат мини-сессии 07a: видео замирает после продолжения с паузы

## Статус

**DONE, 22 октября 2026.** Причина — ошибка в Vulkan WSI драйвера Mesa на Wayland, а не в Fastiplayer. Плеер обходит её у себя. Решение владельца — после приёмки сессии 07: «давай мини-сессию по замиранию после паузы сейчас».

| Вопрос | Ответ |
|---|---|
| Что видел пользователь | После продолжения с паузы видео изредка стоит 1,5–2 с, звук идёт, потом картинка догоняет |
| Как часто | Примерно 1 раз на 50–150 продолжений; было и до сессии 07 |
| Где причина | Mesa 26.2.4 (RADV) + KWin 6.8: Mesa сам отодвигает показ следующего кадра на длину паузы через протокол `wp_commit_timing_v1` |
| Что сделано | Плеер при старте выключает эти метки времени флагом Mesa `MESA_VK_WSI_DEBUG=nowlts`; кадры по-прежнему идут по vsync через `wp_fifo_v1` |
| Цена | Нет: CPU, GPU и плавность на HW и SW те же |

## Решения владельца

1. **Плеер сам выключает планирование Mesa** (`nowlts` в своём окружении, дописывая к флагам пользователя).
   - Отклонено: только задокументировать и ждать исправления в Mesa.
   - Отклонено: перейти на режим показа Mailbox. Это меняет задержку и нагрузку для всех и ломает выводы 06a о выборе кадра.
2. **Сообщить разработчикам Mesa.** Владелец попросил отправить отчёт самому агенту. Этого сделать нельзя: на машине нет учётной записи freedesktop GitLab, а сайт закрыт антибот-защитой. Готовый текст отчёта передан владельцу для публикации.

## Как искали причину

### 1. Подпись дефекта

Во время замирания:
- worker работает как обычно: выбирает кадры по расписанию («Presenting scheduled video frame» 60/с);
- UI их не забирает: `present_frames_dropped_untaken` растёт на 90–120;
- обращения к ресурсам кадра почти прекращаются (4 за 2 с вместо ~120), ожидание замка 0,001 мс.

Подпись одинакова на базе 07 и на новой сборке.

### 2. Карта пути пробуждения

Read-only сабагент прошёл путь «worker опубликовал кадр → `PlayerWorkerPresentationWake` → `AppWakePort` → `user_event` → `request_redraw` → кадр».
- В нашем коде гонки нет: флаг пробуждения сбрасывается до чтения слота.
- Проверены и отброшены гипотезы «UI решил Skip» и «блокировка в `get_current_texture`».

### 3. Трасса стадий кадра (120 циклов «пауза → продолжение»)

В пойманном случае за 1,55 с замирания главный поток **не выполнил ни одного кадра**: нет ни трассы стадий, ни «render frame skipped». Соседние кадры брали буфер swapchain за 0,06–0,11 мс.

Значит, `RedrawRequested` не приходил. В winit на Wayland (`winit-patch`, `FrameCallbackState::Requested`) после нашего `pre_present_notify()` `RedrawRequested` не выдаётся, пока композитор не пришлёт frame callback. Таймаута у этого ожидания нет.

### 4. Протокол Wayland (`WAYLAND_DEBUG=client`, 120 циклов)

В пойманном случае (часы композитора, CLOCK_MONOTONIC, период 16,667 мс):

| Шаг | Что в протоколе |
|---|---|
| До паузы | Mesa шлёт каждому коммиту `wp_commit_timer_v1.set_timestamp` = прошлая цель + 16,667 мс |
| Пауза ~1,6 с | Плеер не рисует (так задумано) |
| Продолжение | Первые кадры получают цели из старой цепочки: 123420,49 и 123420,51 при текущем ≈ 123422,06 |
| | Композитор показывает такой кадр в 123422,093, то есть «на 1,584 с позже цели» |
| | Следующая цель нормальная (123422,109), но следующая за ней — **123423,692**: +1,583 с, ровно 95 периодов ≈ длина паузы |
| | Наше приложение сразу шлёт `wl_surface.frame` и коммит, а `wl_callback.done` приходит через **1,524 с** |

Композитор честно держит коммит до заказанного времени, а с ним и frame callback. winit всё это время не даёт нам рисовать. Даже без winit очередь FIFO встала бы за этим коммитом.

### 5. Обход

Отладочное слово Mesa `nowlts` (no Wayland timestamps) отключает только `set_timestamp`. Подтверждено:
- слово есть в таблице флагов WSI установленного `libvulkan_radeon.so` рядом с `noshm`/`linear`/`dxgi`;
- с ним в протоколе 0 `set_timestamp` (было 6716 за прогон), барьеры `wp_fifo_v1` остались.

Аналогичный обход используют другие проекты ([OmacVM PR #450](https://github.com/gillesgoetsch/OmacVM/pull/450)). Похожий отчёт с тем же симптомом у другого драйвера — [NVIDIA forums](https://forums.developer.nvidia.com/t/vulkan-wayland-fifo-commit-timing-target-extrapolated-minutes-into-the-future-after-an-idle-gap-app-freezes-for-that-long/386504).

## Что изменилось

- **Новый модуль `crates/app-egui/src/mesa_wsi_workaround.rs`:**
  - чистая функция `mesa_wsi_debug_with_commit_timing_disabled(текущее значение) → Write { value, outcome } | Keep`;
  - применение `disable_mesa_wayland_commit_timing()` с `unsafe { std::env::set_var }` и обоснованием SAFETY: в Rust 2024 менять окружение безопасно только в однопоточном процессе.
- **`main.rs`:** вызов первой строкой `main` (до tracing, event loop-а, потоков и Vulkan) и строка лога `Mesa Wayland commit timing disabled for this process … outcome=Enabled | AppendedToUserFlags | AlreadyPresent`.
- **Флаги пользователя сохраняются:** `nowlts` дописывается через запятую; если он уже есть (через запятую или пробел), окружение не трогается. Не-UTF-8 значение сохраняет исходные байты.
- **Драйверы кроме Mesa и сессии X11/XWayland** эту переменную не читают. Если Mesa когда-нибудь уберёт слово, оно перестанет действовать, ничего не сломав.

## Проверка

- **Тесты `mesa_wsi_workaround::tests`** (6): отсутствующая и пустая переменная, флаги пользователя, уже стоящий флаг (запятая/пробел), похожее слово `nowltsx`, не-UTF-8.
- **Живая проверка итоговой сборки без внешней переменной:** 0 `set_timestamp` в протоколе, 858 барьеров fifo, 855 показанных кадров, строка лога `outcome=Enabled`.
- **Циклы «пауза → продолжение» с `nowlts`:** 107 настоящих продолжений, 0 замираний.
  - Честная оговорка: без обхода дефект ловился примерно 2 раза на 276 продолжений, так что статистически это слабое подтверждение.
  - Решающее доказательство детерминированное: без метки `set_timestamp` у композитора нет причины держать коммит.
- **Замер «до/после» обхода** (`run_pass.py`, нативный Wayland, окно 20 с, 2 круга с чередованием):

## Известные ограничения

- **Это обход, а не исправление Mesa.** Отчёт для разработчиков Mesa подготовлен (шаги, версии, фрагмент протокола); публикует владелец.
- **На других композиторах** (Hyprland, GNOME) обход не проверялся. Механизм тот же: метки commit timing отключены, fifo остаётся.
- **В нескольких прогонах терялись нажатия виртуальной клавиатуры** (raw-uinput), поэтому детектор замираний учитывает только реальные переходы `Paused → Playing` по логу плеера.
