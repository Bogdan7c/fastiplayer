# Результат сессии 04: рендер по изменению, а не по каждому vsync

## Статус

**DONE.** 20 октября 2026.

UI-поток больше не просыпается на каждый vsync. Он рисует по событиям: новый кадр от worker-а, ввод, запрос egui, таймер UI-модели (секунда текста, пиксель ползунка, тост, автоскрытие) и страховка раз в 250 мс. На каждом пробуждении кадр решает одно из трёх: полный egui-проход, показ видео с прежним интерфейсом или пропуск без surface/present.

Главный поток на HW 4K30 подешевел на 42 % (4,2–4,4 → 2,4 %), GPU gfx там же на 45 % (2,6–2,7 → 1,4 %). На 60 fps источниках три из четырёх кадров идут без egui-прохода. Worker просыпается от рендера 60 раз в секунду вместо 120–180.

## Решения владельца в этой сессии

1. Режим «показать видео с прежним интерфейсом» делаем в этой же сессии (fail-closed: любая неуверенность → полный проход).
2. Страховочный таймер 250 мс во время воспроизведения; счётчик `redraw_fallback_found_work` показывает, срабатывал ли он по делу.
3. Release-ack кадра по-прежнему будит worker (одно пробуждение на кадр); диагностические замеры рендера больше не будят.
4. Открытая панель телеметрии даёт полный проход раз в 250 мс (ритм её кэша), а не на каждый кадр.
5. Критерий сессии от владельца: ничего не сломать, UX не менять.

## Корневая причина

Три дефекта, из которых складывалась цена главного потока:

1. **Redraw по vsync.** `wants_continuous_redraw()` при воспроизведении давал `Wait + request_redraw` после каждого кадра (`redraw_pacing.rs`). Каждый `RedrawRequested` делал полный проход: `take_egui_input` → `run_ui` → tessellate → video prepare → submit → present, 60 раз в секунду независимо от fps источника. На 30 fps половина работы (включая оба барьера DMA-BUF сессии 03) шла впустую.
2. **Нет пробуждения UI от нового кадра.** Worker клал кадр в слот показа и события плеера в очередь молча; UI узнавал о них только на очередном vsync. Поэтому отказаться от vsync-опроса было нельзя, пока нет события «есть что показать».
3. **Запросы egui читались неверно.** `has_requested_repaint()` отвечал «да» и на отложенные `request_repaint_after` (подсказка, строка проблемы плейлиста на 10 с), превращая их в немедленный redraw; а `request_repaint_after` после прохода (preview настроек) терялся: egui сбрасывает его в начале следующего прохода.

Плюс наследство 02: три диагностических sample-сообщения рендерера на каждый проход (acquire, resource lock, timing) имели собственные ветки в `select!` worker-а и будили его ~120–180 раз в секунду, хотя нужны только диагностике.

## Что изменилось

**`player-core`**
- `worker/presentation_wake.rs` (новый): трейт `PlayerWorkerPresentationWake` без payload; `PlayerWorkerConfig::with_presentation_wake`. Worker дёргает его в `publish_session_outputs`, если `RenderLeaseBridge::publish_latest_present_frame` вернул `PresentFramePublication::{Published, Cleared}` (новый `#[must_use]` enum), и в `publish_worker_event` на каждое lifecycle-событие. Порядок инварианта: сначала слот/очередь/snapshot, потом wake.
- `runtime_wait.rs`: из трёх `select!` убраны ветки acquire/timing/lock/reuse-samples. Они по-прежнему `try_send` без блокировки и вычитываются `drain_render_feedback()` в начале витка и перед `session.tick` (`run_tick_for_wakeup_plan`). Будит worker только release-ack. Неиспользуемые методы bridge-а удалены.
- `wakeup_counters.rs`: счётчик `worker_render_release_wakeups` (был `worker_render_feedback_wakeups`).
- `PlayerWorker::try_present_frame_identity()` → `PresentFrameIdentityProbe::{Known(Option<identity>), Busy}`: дешёвая проверка «кадр новый?» без clone lease-а и без diagnostics sample.

**`render-wgpu-shell`**
- `RenderFrameInput.egui: EguiFrameContent::{Fresh { paint_jobs, textures_delta }, ReusePrevious}`.
- `EguiCompositor` удерживает примитивы и `ScreenDescriptor` последнего `update_buffers`: `begin_frame_content` → `prepare_pending_content` → `render_retained_overlay` → `free_retired_textures_if_any`. `ReusePrevious` допустим только при том же размере/scale и при наличии удержанного кадра; иначе `RenderFrameDropReason::RetainedUiUnavailable` до acquire. Основание по Context7/исходнику egui-wgpu 0.36.2: `Renderer::render` читает vertex/index буферы последнего `update_buffers`, uniform размера экрана пишется только там; paint callbacks в проекте не используются.
- `Renderer::can_reuse_retained_ui(screen)` — проверка до решения на стороне app.

**`app-egui`**
- `frame_prepare/frame_work_plan.rs` (новый): чистое решение `plan_frame_work(UiPassReasons, PresentReasons) → FullPass | PresentReusingUi | Skip` с именами причин для трассы.
- `frame_prepare/frame_decision.rs` (новый): сбор фактов у владельцев — триггеры, запросы egui, анимации, дедлайны, UI-модель, слот показа, shell.
- `state/ui_frame_model.rs` (новый): явная `UiFrameModel` с `PartialEq`; позиция квантуется до секунды текста и пикселя ползунка (ширина дорожки — `TimelineUiState::observed_track_width_px`, пишется при рисовании таймлайна); `next_visible_position_change` — дедлайн следующего видимого изменения позиции (нужен звуку без видео и 24 fps фильмам); возраст тостов квантуется «проявляется/проявился».
- `state/redraw_runtime.rs` (новый): владелец состояния решения — порт `AppWakeOwner::PlayerPresentation`, триггеры (`note_window_input_for_redraw`, `note_presentation_wake`, `note_visible_mutation_for_redraw`, `note_redraw_fallback_probe`, `force_full_ui_pass`), приёмник `Context::set_request_repaint_callback` (различает «сейчас» и «не позже момента»), память последнего полного прохода, backoff дедлайна позиции (если прошлый дедлайн прошёл, а snapshot не сдвинулся, ждём тик worker-а, не меньше 8 мс).
- `redraw_pacing.rs`: воспроизведение даёт `WaitUntil(min(дедлайны UI, страховка 250 мс))` вместо `Wait + request_redraw`; `RedrawControlAction.redraw_cause` вместо `bool`.
- `frame_prepare.rs::render_frame`: ввод+snapshot → desktop publish → `advance_ui_timers` → решение → `prepare_ui_frame_for_plan` → действия и runtime-опросы (на каждом пробуждении, с пустыми действиями без прохода) → `present.rs::present_frame_for_plan` либо `log_skipped_frame` → pacing. Preview настроек планируется дедлайном, а не `request_repaint_after`. `FrameSequenceContract` требует монотонный порядок, пропуски стадий разрешены.
- `app_shell/event_loop.rs`: обработчик `PlayerPresentation`; любое оконное событие помечает «был ввод»; owner-wake с видимой мутацией помечают полный проход; страховочный redraw помечается для счётчика.
- `telemetry.rs`: счётчики `ui_full_passes`, `ui_reused_presents`, `redraw_skips`, `redraw_fallback_found_work`, `retained_ui_refusals`; трасса кадра получила `frame_work_plan`, `ui_pass_reason`, `present_reason`; пропуск — строка `render frame skipped`.
- Мелкое: `SettingsRuntime::ui_model_revision()`, `PlaylistInteractionModel: PartialEq`, `PlaylistViewModel::revision()` в production, дедлайн inline-статуса таймлайна, `NotificationId::for_tests`.

**Что сохранено:** порядок boundary egui-wgpu (upload → update buffers → video → subtitles → egui → submit → free → present); `Busy` previous-frame fallback; seek/scrub (override всегда «показать»); housekeeping (persist по таймерам, транспорт плейлиста, автопереходы очереди, preview) идёт на каждом пробуждении независимо от плана; пауза и простой — `Wait` без страховки.

## Два дефекта, найденные первым прогоном «после»

1. Wake показа помечался как «видимая мутация интерфейса» → полный проход на каждый кадр (режим повтора срабатывал 1 раз из 1200). Исправлено: `PlayerPresentation` только просит redraw, что рисовать — решает кадр.
2. Спин дедлайна позиции: позиция в snapshot-е обновляется только тиком worker-а; дедлайн, посчитанный от отставшего snapshot-а, созревал через 1 мс снова и снова до тика (пачки пустых пробуждений по 4–5 мс, ~74/с на 4K30). Исправлено backoff-ом до тика worker-а (`position_wake_with_backoff`, тест).

## Ручная приёмка

Финальный бинарник, изолированный XDG с шаблоном конфига бенчмарка, но `reduced_motion = false` (анимации видны); очередь из трёх CLI-файлов: Sintel 720p 24 fps (MKV + .srt рядом), синтетика H.264 1080p60 + AAC, H.264 4K30 без звука. Ввод — два uinput-устройства (клавиатура и относительная мышь; первая попытка с комбинированным «клавиатура + абсолютная ось» до плеера не дошла — libinput такое устройство игнорирует). Трасса `render_frame_timing` + `video_render_acceptance` + `player_core=debug`, ~75 с.

Сценарий и что подтверждает лог:
- F (фуллскрин) → проводка мышью по центру, по нижней панели (hover-эффекты кнопок), остановка над таймлайном, перетаскивание по таймлайну, Space, →, →, Space, ←, M, M, пауза мыши 4,5 с (автоскрытие панелей и курсора), движение мыши (панели возвращаются), F (выход), Alt+Tab туда-обратно, N (следующий файл), Space, Space, P (перезапуск), Esc.
- Планы кадров за прогон: 551 полных проходов (131 — ввод, 54 — анимация sidebar/chrome, 346 — изменение UI-модели, 14 — события плеера, 3 — owner-wake, 2 — нет удержанного интерфейса после смены файла/размера, 1 — принудительный первый), 1583 показов видео с прежним интерфейсом, 255 пропусков; `redraw_fallback_found_work = 0`, `retained_ui_refusals = 0`.
- Пауза: за 1,9 с паузы на первом файле и 2,8 с паузы на втором — ноль пробуждений UI (инвариант 5).
- Seek-и в паузе и в игре подтверждены за 115–170 мс (`Final seek commit completed`), post-seek прогресс позиции наблюдён; P — коммит в 0 за ~25 мс.
- Mute/unmute дошли до worker-а (`ToggleMute`), N переключил файл (новая `media_instance_id`), события плеера дали полные проходы.
- Автоскрытие в фуллскрине: в окне 6,5 с без ввода — 54 прохода «анимация» (уезд панелей и курсора) и показы видео без прохода; после движения мыши — проходы по вводу (панели вернулись).
- Уникальных кадров 1938 из 2119 handoff-ов (три файла, seek-и и паузы), `drops = 14` — все в момент seek/scrub (seek discard), не в стационарном показе.
- WARN/ERROR: только известный `Ignoring unknown button type: icon`.

Не подтверждено логом (нужна визуальная проверка владельцем): hover-подсказка времени на таймлайне и само перетаскивание ползунка мышью (жест scrub в логе не появился — координата дорожки в фуллскрине, видимо, не совпала с траекторией), видимость картинки субтитров .srt (загрузка sidecar-а в лог не пишется), A/V-синхрон на слух (громкость шаблона 0). Переключение hardware ↔ software в настройках вживую не проверялось.

## Тесты

Новые тесты падают на старом коде (проверено логикой: они закрепляют новое поведение планировщика и каналов).

- **`redraw_pacing.rs`:** воспроизведение после кадра даёт `WaitUntil(+250 мс)` без redraw (на старом коде — `Wait + redraw`); страховка перед idle wait не просит redraw до срока, созревшая даёт один redraw с причиной `PlaybackFallback` и перевзводится; нарисованный кадр перевзводит страховку; пауза — чистый `Wait`; ближний дедлайн позиции побеждает страховку; прежние тесты фоновых опросов и UI-дедлайнов сохранены.
- **`frame_prepare/frame_work_plan.rs`:** таблица причин → план (без причин — пропуск; новый кадр — показ без прохода; каждая из 11 причин интерфейса — полный проход, с кадром и без; seek/scrub/смена backend-а — показ; приоритет имён причин).
- **`state/ui_frame_model.rs`:** позиции внутри секунды и пикселя дают равный ключ; переход секунды или пикселя меняет ключ; без дорожки пиксель не считается; дедлайн — ближайшая граница в настенном времени; скорость 2× делит ожидание; пауза не планирует; на границе — следующая граница; возраст тостов квантуется.
- **`state/redraw_runtime.rs`:** приёмник запросов egui (немедленный, ближайший дедлайн, `take` сбрасывает); настоящий `Context::request_repaint*` доходит через callback; backoff дедлайна позиции при отставшем snapshot-е.
- **`state/startup_context.rs`:** bridge показа доходит до event loop одним wake до drain-а, после drain-а будит снова.
- **`frame_prepare/sequence.rs`:** пропуск стадий разрешён, возврат к пройденной стадии ловится.
- **`state/timeline_inline_status.rs`:** дедлайн исчезновения статуса.
- **`render-wgpu-shell`, `egui_compositor/tests.rs` (GPU):** повторный кадр рисует те же пиксели интерфейса поверх другого «видео» без `update_buffers`; без свежего кадра или при другом размере/scale повтор отвергается, pass не открывается.
- **`player-core`:** `worker/tests/wakeup.rs` — вертикальный стенд: 20+ timing-замеров за прогон не дают ни одного пробуждения и все доходят до диагностики через tick; release-ack кадра будит worker (≥ 1, не больше числа отпущенных кадров); `worker/tests/presentation_wake.rs` — новый кадр будит UI ровно раз, повтор молчит, событие будит без кадра, без bridge-а no-op; итог публикации `Unchanged/Published/Cleared`.
- Прогоны: `cargo test -p player-core` (931), `-p render-wgpu-shell` (59), `-p app-egui` (2480) — зелёные.

## Известные ограничения

- На коротких клипах (≤ 60 с) пиксель ползунка меняется чаще кадра, и режим «показ с прежним интерфейсом» почти не работает: это честное поведение, интерфейс меняется. На 4K30 это ещё даёт ~23 пустых пробуждения в секунду (дедлайн пикселя созревает раньше тика worker-а, backoff ограничивает одним пустым пробуждением на пиксель; цена ~15 мкс каждое).
- Главный поток на 60 fps ограничен стоимостью submit/present и двух клонов snapshot-а на кадр → сессия 05.
- Панель телеметрии: FPS теперь равен частоте показа (30 на 30 fps файле), `playback_repeated_frames` ≈ 0 — цифры честнее, но другие.
- Полнота `UiFrameModel` — главный риск: неучтённое поле дало бы «застывший» элемент интерфейса. Страховки: любой ввод, любое событие плеера, любой owner-wake и анимации дают полный проход; счётчик `redraw_fallback_found_work` = 0 за все прогоны.
- Профиль функций не снят (`perf_event_paranoid=2`); выводы — из счётчиков, трассы стадий и срезов по потокам.
