## Машина и условия

- AMD Ryzen 7 7840HS (16 логических CPU), Radeon 780M, Mesa 26.2.4, ядро 7.2.10-cachyos, KDE Plasma Wayland. Оба плеера — нативные окна по умолчанию (не fullscreen, не XWayland), обычный рабочий стол, без изоляции cgroup. VLC 3.0.24 с Qt-интерфейсом, `--ignore-config --no-one-instance --gain=0`, `--avcodec-hw=vaapi|none`. Fastiplayer — изолированный XDG с шаблоном `docs/benchmarks/tools/t480s/{hardware,software}-template.toml`, `RUST_LOG=info`.
- Фикстуры: синтетические H.264 1080p60 и HEVC 4K60 из `tools/t480s/make_fixtures.py` (хэши на этой машине: `c430a7a1…`, `7181f68f…` — отличаются от исторических из-за версии Mesa/энкодера); SW AV1 4K60 и HW H.264 4K30 (без звука, ~30 fps, 50 с) — из приватного корпуса владельца.
- Метод: `thread_cpu.py` — утилизация по потокам из `/proc/PID/task/*/stat` за окно 20 с после 15 с прогрева, RSS/PSS из `smaps_rollup`, GPU по DRM fdinfo (`drm-engine-*`, дедуп по client-id). **Это не протокол бенчмарка** (один прогон на сцену, без чередования и интервалов) — достаточно для поиска причин, недостаточно для публикации.

## Корневые причины

См. таблицу в README (пункты 1–6). Кратко, что подтверждено чем:

1. Пул VA-поверхностей отсутствует — чтение `frame_pool.rs`/`internal_vaapi_frame.rs`/патча cros-codecs + счётчики выше.
2. Vulkan-импорт на кадр — кэш по `FrameResourceHandle` + рост `video_prepare` 0,25 → 0,72 мс с размером буфера при zero-copy.
3. egui-проход и present на каждый vsync — `redraw_pacing.rs`, `frame_prepare.rs`; на 4K30 мы в 4,6× хуже VLC при вдвое меньшем числе новых кадров.
4. 2-мс петли и пульсы — `runtime_loop.rs`, `frame_publication.rs`, `wakeup.rs` + `pauses`/`wake_delay_ms` в сводке.
5. Россыпь — чтение кода (список в сессии 05).
6. Нет `[profile.release]` — `Cargo.toml`.

Декодирование в SW-режиме равно VLC по суммарному CPU (21,7 % против 21,6 % на H.264), в AV1 мы уже экономнее (157 % против 193 %), но равенство доставленных кадров не доказано.
