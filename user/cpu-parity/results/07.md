## Решения владельца в этой сессии

1. **Копия в staging — в один поток, без помощников.**
   - Владелец спросил, что надёжнее и быстрее. Ответ: однопоточная копия. Нет `unsafe impl Send`, нет жизненного цикла потоков, меньше CPU. Цена: p90 на 4K +0,3 мс в бюджете 16,7 мс.
   - Отклонено: постоянный пул из 3 помощников. Он почти не быстрее (копия упирается в память), но платит 9 пробуждений на кадр и добавляет код с `unsafe`.
   - Оговорка: полосы когда-то ввели на слабом T480s под нагрузкой dav1d. Проверить хвост там в сессии 10; при регрессии постоянный пул — правка одной функции.
2. **GPU-копия загрузки — в том же submit, что и кадр.**
   - Невостребованная копия (кадр загрузили, но не нарисовали, или рендер упал) уходит отдельным submit-ом перед следующей загрузкой.
   - Отклонено: оставить отдельный submit.
3. (20.10, из бэклога) Проброс `host_upload_resource_snapshot` в обёртке рендерера — в этой сессии, вместе с SW-замером.

## Что изменилось

- **`render-wgpu-video::video::host_planar_upload::wgpu_backend`**
  - `copy_plane_block_into_staging` — однопоточная копия строк. Ушли `std::thread::scope`, `StagingCopyBand` с `unsafe impl Send` и константы полос.
  - Запись GPU-копий кадра — `FrameUploadRecording { encoder, destination }`.
  - `flush_plane_uploads` не делает submit: `StagingBelt::finish_and_recall_on_submit(&encoder)` (wgpu 30.0.1, чанки вернутся после submit-а именно этого command buffer-а), а готовый command buffer кладётся в слот.
  - `ensure_frame_upload_recording` / `submit_unclaimed_upload` отправляют невостребованную копию до следующей записи.
- **Новый модуль `host_planar_upload/pending_upload.rs`:**
  - `PendingHostPlanarUpload` — ожидающая копия у слота (`WgpuHostPlanarUploadedTextures::pending_upload`);
  - `HostPlanarUploadCommands` — `#[must_use]`, публичный тип забранной копии;
  - `HostPlanarWgpuTextureViews::plane_views()`;
  - `WgpuRenderableFrame::claim_host_upload()`.
- **`video/mod.rs`:**
  - кадр несёт `host_upload`; `from_decoded_host_planar` его заполняет;
  - рендерер забирает копию после **успешной** записи host-planar pass-а;
  - `from_decoded_host_yuv` стал `pub(crate)` (отдельные views без слота — только тесты рендерера);
  - неиспользуемая обёртка `from_decoded_host_yuv420` удалена: оба входа позволяли нарисовать слот до его загрузки.
- **`WgpuVideoRenderOutcome::host_upload`** (`external_frame_sync.rs`) — копию shell обязан отправить первой.
- **`render-wgpu-shell::shell`** — порядок в общем submit: загрузка host-planar → acquire DMA-BUF → egui callbacks → encoder кадра → release DMA-BUF.
- **`render-wgpu-video::resource_provider::WgpuReleaseVideoDecoderThreadHandle::host_upload_resource_snapshot`** — проброс, как `decoder_activity_snapshot` в сессии 02.
- **Тестовые потребители** (`video-ffmpeg/tests/support/wgpu_acceptance.rs`, `app-egui/.../content_probe_tests/direct_progressive_webm.rs`) собирают кадр через `from_decoded_host_planar` и отправляют копию в своём submit-е.
- **Ratchet размера** (`scripts/module-size-baseline.json`):
  - `video/mod.rs` 1106 → 1116: поле кадра, `host_upload: None` в конструкторах, забор копии;
  - `host_planar_upload.rs` 1502 → 1503: объявление модуля.

  Логика живёт в новом модуле. В legacy-файлах только проводка поля, которое принадлежит самому `WgpuRenderableFrame`, так что вынос дробил бы один инвариант.

### Инварианты

1. **Копия ровно одна и всегда раньше чтения.** Записанная копия попадает в очередь ровно один раз и раньше любого submit-а, который семплит слот. Повторный показ слота копию не повторяет.
2. **Одна копия host → GPU на кадр.** Копий на CPU не прибавилось: путь «кадр декодера → staging → GPU» тот же.
3. **Пул слотов не менялся:** 24 слота, `MIN_REUSE_RING_SLOTS = 4`, `Busy` при полном. `uploaded_textures_are_idle` по-прежнему считает ссылки на слот: ожидающая копия держит свою `Arc`, а не слот.
4. **Release кадра декодеру** — по-прежнему через `on_submitted_work_done` после submit-а кадра.
5. **Матрица форматов** (8/10/12 бит, 4:2:0/4:2:2/4:4:4) без изменений.

## Что проверено вручную

На итоговой сборке, очередь «AV1 4K60 → H.264 1080p60»:
- пауза: показан 1 кадр;
- продолжение: 184 кадра за 3,1 с;
- → (seek +5 с), ←, ← с новым поколением после каждого;
- N — следующий файл с нуля;
- → на втором файле;
- пауза и продолжение на втором файле.

Уникальные кадры ≈ 60/с на каждом участке. Предупреждения те же 3, что у базы: `Ignoring unknown button type: icon` и 2 × «seek transaction is still waiting» на перемотке назад по AV1 4K. Паник нет. Плюс 8 циклов «пауза → продолжение» на AV1 4K60 — без замираний.

## Известные ограничения

- **p90 `video_prepare` на 4K** выше на ~0,3 мс (см. выше). Хвост на слабом железе (T480s) не проверен — сессия 10.
- **Переключение HW ↔ SW вживую не проверялось.** Материализатор пересоздаётся вместе с конвейером, а незабранная копия уходит вместе со старым слотом.
- **Ветка «загрузка упала посреди плоскостей и следующий кадр пошёл в тот же слот»** покрыта кодом (невостребованная копия уходит в `flush_plane_uploads`), но не тестом. Спровоцировать её трудно: дескриптор валидируется до загрузки.
- **Давний дефект, найденный приёмкой** (есть и на базе, к сессии не относится):
  - что видно: после продолжения с паузы UI иногда 1,5–2 с не забирает кадры. Worker публикует и выбирает их по расписанию, `present_frames_dropped_untaken` растёт на 90–118, затем показ сам восстанавливается;
  - частота: новая сборка 2 из 21 продолжения, база 1 из 19;
  - подпись совпадает. Показ возобновлялся сразу после 2-секундной сводки worker-а. Гипотеза — потерянное пробуждение UI (`PlayerWorkerPresentationWake` / follow-up redraw) на переходе «пауза → игра»;
  - внесено в бэклог README.
