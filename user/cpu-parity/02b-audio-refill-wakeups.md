# Сессия 02b: пробуждения аудио-подпитки по событию звуковой карты

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 02b плана `user/cpu-parity/`: убери холостые пробуждения player-worker-а, которые даёт подпитка звука в установившемся воспроизведении. Сначала прочитай `user/cpu-parity/README.md` и `user/cpu-parity/results/02.md`. Правила подпитки (запас, порция, high-water) не меняются, меняется только момент пробуждения. Замер «до/после» обязателен, счётчики пробуждений из сессии 02 уже есть в сводке диагностики.

## Откуда взялась сессия

Сессия 02 убрала 2-мс опрос декодера: на файле без звука worker тикает ~60 раз в секунду вместо ~500, CPU worker-а упал на ~40 %. На файлах со звуком CPU worker-а не изменился, потому что открылся второй источник, раньше скрытый 2-мс опросом. По новым счётчикам (HW H.264 1080p60 + AAC, окно 2 с): `worker_ticks=529`, из них `pipeline_work_ready=378`, `frame_pts_deadline=151`.

Решение владельца (20 октября 2026): звук — отдельной сессией, а не в 02. Правила подпитки сохраняются (вариант «долив порциями / гистерезис» отклонён как изменение поведения звука).

## Причина (разбор кода, сессия 02)

- `session/audio_runtime.rs` (`process_pending_audio_packets_with_buffer_limit`) доливает в кольцо вывода пакеты, пока уровень не превысит high-water: 200 мс по умолчанию (`audio.buffer_target_ms`). Пакет AAC — 21,3 мс, поэтому обычно доливается один пакет за тик.
- `session/tick/wakeup.rs::audio_buffer_refill_wakeup_delay` планирует пробуждение через `level − high_water`, будто звук утекает непрерывно.
- На деле уровень (`audio/src/clock.rs`: `samples_written − samples_played`) меняется ступенькой только в CPAL callback-е. Размер периода callback-а в коде не задан (`build_output_stream(..., None)`), его выбирает PipeWire/ALSA.
- Worker просыпается раньше следующего callback-а и видит тот же уровень выше high-water. Работы нет, он снова планирует такую же короткую задержку. Получается ~4 пробуждения на один полезный долив (~47 доливов/с у AAC 48 кГц).

## Архитектура (предложение, уточнить по коду)

- **Владелец знания о callback-ах:** `audio` (clock/output). Нужен нейтральный read-only факт для планировщика: «момент последнего callback-а и наблюдаемый период» (или «уровень изменится не раньше чем…»), без блокировок в realtime callback-е (только атомики).
- **Владелец решения о сне:** `player-core::session::tick::wakeup`. Если уровень выше high-water, будить не по `level − high_water`, а на ближайшем ожидаемом callback-е, после которого уровень опустится до high-water или ниже. Если данных о callback-ах нет (вывод ещё не играл, устройство пересоздаётся), остаётся прежняя формула.
- **Инварианты из `audio_refill_wakeup.rs` / `audio_fallback_wakeup.rs` сохраняются:**
  - пробуждение не позже, чем кончится наблюдаемый буфер;
  - callback посреди планирования не уводит в coarse 250 мс (AC-3 #19);
  - EOF drain продолжает доливать;
  - планирование read-only.

## Тесты

- Планировщик: уровень выше high-water, callback-и раз в N мс → пробуждение на ожидаемом callback-е, а не через `level − high_water`. Без данных о callback-ах — прежняя формула.
- Вертикальный тест worker-а с fake-выводом, у которого уровень падает ступеньками: за модельную секунду пробуждений по `pipeline_work_ready` ≈ число доливов, а не в разы больше. Тест должен падать на текущем коде.
- Существующие тесты подпитки не ослабляются.
