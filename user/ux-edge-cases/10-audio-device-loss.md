## Предыстория (факты аудита, сверить с кодом)

1. Ошибка потока cpal только логируется: `err_callback = move |err| warn!("CPAL error: {}", err)` (`audio/src/output.rs:~426`). Обработки device-lost / watchdog в `audio` и `player-core` нет (device-lost есть только для render device).
2. Сохранённое (не default) устройство отсутствует → `DeviceUnavailable` (`devices.rs:187-210`) → `disable_selected_audio_path()` + recoverable ошибка (`audio_runtime.rs:196-201`) → **видео без звука**, `audio_tracks = None` → звук не вернётся, даже если наушники подключили обратно, до переоткрытия файла.
3. Нет аудиоустройства вообще при старте — то же: видео играет, ошибка только записана.
4. Смена устройства в настройках во время воспроизведения уже сделана хорошо: `recreate_active_audio_output` строит новый выход до удаления старого и сохраняет позицию (`audio_runtime.rs:~370-420`) — это готовый механизм для п.1.
5. PipeWire может сам перенаправить поток при отключении USB/Bluetooth — тогда cpal ошибку не сообщит. Поведение на этой машине **не проверено**.

## Задание

### Часть A. Исследование и воспроизведение
1. Context7 cpal (версия из `Cargo.lock`): какие `StreamError` приходят при пропаже устройства на ALSA/PipeWire; можно ли пересоздать stream из callback-а (нельзя блокировать audio thread — только сигнал).
2. Ручной эксперимент на машине владельца (вне sandbox, с его участием): USB/Bluetooth наушники выбраны в настройках → отключить → записать логи, что слышно, что в snapshot. Отдельно — «устройство по умолчанию» и отключение.
3. Где сейчас проходит граница audio → player-core для ошибок (контракт), чтобы событие «поток умер» шло через него.

### Стоп: согласование с владельцем
- поток умер → переключиться на устройство по умолчанию автоматически + уведомление «Наушники отключены, звук переключён на …» (рекомендация); или пауза + уведомление;
- сохранённое устройство вернулось — переключаться обратно? (рекомендация — нет в этой сессии, бэклог);
- нет устройства при старте — пробовать default, иначе видео без звука + уведомление и автоматическая попытка при следующем открытии.

### Часть B. Реализация
- Error callback только сигналит (lock-free/канал), без работы в audio thread.
- Владелец реакции — player-core audio runtime; позиция сохраняется; устройство в config не меняется.
- Отсутствующее сохранённое устройство → fallback на default с типизированным исходом «используется устройство по умолчанию вместо …», а не отключение звука.

## Тесты
- fake output backend сообщает stream error → player пересоздаёт выход на default, позиция сохранена, звук (fake consumer) снова получает сэмплы;
- сохранённое устройство отсутствует при открытии → используется default, `audio_tracks` не обнулены, событие для уведомления;
- нет ни одного устройства → видео играет до рендера, понятный исход, без паники;
- повторные ошибки потока подряд не создают шторм пересозданий (ограничение);
- config не изменён.

## Ручная приёмка
Выбрать USB/Bluetooth наушники, включить видео, отключить → звук в колонках (или по решению), уведомление; позиция не прыгнула.
