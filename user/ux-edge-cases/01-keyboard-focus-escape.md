## Предыстория (факты аудита, сверить с кодом)

1. **Хоткеи глохнут после клика.** `event_loop.rs:191-193`: `keyboard_captured = consumed || egui_wants_keyboard_input() || text_edit_focused()`. В egui 0.36.2 `Context::egui_wants_keyboard_input()` = `memory.focused().is_some()` — true для **любого** виджета в фокусе. Кнопки play/prev/next/скорость вызывают `request_focus()` при клике (`ui/player_controls.rs:552`, `transport.rs:159`, `playback_rate.rs:254`, `indicator.rs:134`); таймлайн тоже focusable. Итог: клик по play → F, M, J, L, P, N, стрелки не работают (`hotkeys.rs:61` возвращает `None` при captured). Стрелки egui вдобавок двигают фокус-рамку. Первый Esc лишь снимает фокус.
2. **Space сейчас работает «случайно»:** при фокусе на кнопке egui сам активирует кнопку, а хоткей подавлен → двойного переключения нет. Любое исправление п.1 обязано не создать двойной toggle (кнопка + хоткей).
3. **Esc закрывает приложение:** `hotkeys.rs:72` `KeyCode::Escape → ShellHotkeyAction::Close`; `event_loop.rs:~196` `close_runtime_and_exit("Выход по Escape")`. Выхода из фуллскрина по Esc нет; модальные окна (подтверждение замены очереди, preview импорта) — это CentralPanel, Esc их не закрывает, а убивает плеер. Shutdown корректный (resume checkpoint сохраняется), но ожидание пользователя нарушено.
4. Тесты `hotkeys.rs` классифицируют клавиши, Escape не проверяют; интеграционного теста фокуса нет.

## Задание

### Часть A. Исследование и воспроизведение
1. Context7 egui 0.36: семантика `egui_wants_keyboard_input`, `text_edit_focused`, `Memory::focused`, `wants_keyboard_input` у `Response`, как egui обрабатывает Space/Enter/стрелки на focused кнопке, как снять фокус (`surrender_focus`), есть ли «focus без keyboard capture».
2. Зачем кнопкам `request_focus()` — найти причину в истории (`git log -S request_focus`) и в accessibility-коде. Не удалять без понимания.
3. Падающий тест: клик по play → затем `KeyF`/`ArrowRight` → ожидаемое действие хоткея (сейчас `None`).
4. Перечислить все места, где Esc уже значит «отмена» (playlist selection clear, drag cancel, редактор URL, settings sidebar, popup ComboBox).

### Стоп: согласование с владельцем
1. **Что делает Esc** (рекомендация — вариант A):
   - (A) по приоритету: закрыть открытый popup/диалог/редактор → выйти из фуллскрина → больше ничего (выход — крестик окна / Ctrl+Q, если владелец захочет добавить);
   - (B) как A, но в последнюю очередь — выход из приложения (как сейчас);
   - (C) как A + выход только двойным Esc / с подтверждением.
2. **Как чинить фокус** (выбор после исследования, простыми словами): «кнопки не забирают клавиатуру» vs «хоткеи игнорируют только текстовые поля и открытые popup-ы». Объяснить риск для accessibility и Space.

### Часть B. Реализация
- Одна чистая функция политики «чем занята клавиатура» с типизированным результатом (например текстовый ввод / popup / ничего), без позиционных bool; event loop только вызывает её.
- Esc — отдельное intent-действие по решению владельца, не `Close`.
- Space при фокусе на кнопке play — ровно одно переключение.

## Тесты
- клик по play/next/таймлайну → F/M/J/L/←/→ выполняют хоткей;
- фокус в TextEdit (URL, поиск, настройки) → хоткеи подавлены, текст печатается;
- Space при фокусе на кнопке play → одно переключение, не два;
- Esc в фуллскрине → выход из фуллскрина, приложение живо; Esc при открытом подтверждении замены очереди → диалог закрыт (по решению); Esc без контекста → поведение по решению;
- media keys работают всегда (регрессия).

## Ручная приёмка
Клик по play → F (фуллскрин) → Esc (выход из фуллскрина, плеер жив) → → (перемотка) → клик в поле URL, печать «f» и пробела (текст, без хоткеев).
