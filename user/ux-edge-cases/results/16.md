## Решения владельца (8 октября 2026)

1. **Чиним все три слоя причины**, а не только повторы, как было в файле сессии (объём согласован после исследования).
2. **Политика повторов:**
   - паузы 0,5 → 1 → 2 → 4 → 8 с, дальше по 8 с;
   - общий бюджет **60 с**;
   - `Retry-After` уважается, но не дольше 60 с;
   - повторяются только сетевые сбои и ответы 5xx/408/429, а 401/403/404/410 — нет;
   - пока идут повторы, плеер в Buffering (спиннер из сессии 15).
3. **После бюджета** — понятная ошибка **без кнопки** «Повторить». Кнопка — в бэклог.
4. **Очередь при пропаже сети останавливается, а не пропускает элемент** (решение 9 октября, после приёмки). Элемент не помечается битым, toast «пропущен» не показывается: причину уже показывает центр окна.
5. **Config:** одна настройка `network.reconnect_wait_ms` («Ожидание восстановления сети», 0–600 000 мс, `0` = не ждать). Шаги пауз — именованные константы в коде.

## Исследование (часть A): почему обрыв убивал просмотр

Сначала тест-воспроизведение: локальный сервер посреди ответа рвёт соединение и 3 с отказывает в подключении. Результат до правки: **ошибка через ~0,1 с**, из 3 МБ прочитано 16 КБ. Нашлись три слоя причины:

1. **Повтор один и мгновенный** (`source-core/src/http.rs`): без сети второй запрос тоже падал сразу.
2. **Ошибка перебивала уже скачанное** (`media-prefetch/src/source.rs`). Ошибка фоновой докачки отдавалась читателю раньше буфера, хотя впереди могли лежать минуты видео (окно по умолчанию — 256 МБ).
3. **Поток player-а засыпал внутри чтения.** Seekable HTTP отдавал player-у «голый» Symphonia demuxer, и разбор шёл в рабочем потоке player-а. Поэтому при обрыве состояние оставалось `Playing`, Buffering и спиннер не включались, пауза не отвечала. Это открытый риск из `results/15.md`.

При реализации нашлись ещё две причины:

4. **Закрытие media не могло прервать ожидание.** Адаптер Symphonia читает с вечным токеном отмены, поэтому фоновые повторы шли бы до конца бюджета.
5. **Пометка отмены.** `SourceError::Cancelled` превращается в `io::ErrorKind::Interrupted`, а Symphonia и `read_exact` молча повторяют `Interrupted`. Отменённое чтение крутилось бы в бесконечном цикле.

Таймауты reqwest проверены по исходникам 0.12.28: `ClientBuilder::timeout` у blocking-клиента действует на каждое чтение, а не на весь запрос. Медленная сеть сама по себе ошибку не даёт.

## Что сделано (владельцы и границы)

- **`source-core`:**
  - **`http_reconnect.rs`:** `HttpReconnectPolicy` (бюджет из config) и чистое расписание `HttpReconnectSchedule` (тесты на фальшивом времени). Ожидание проверяет отмену каждые 10 мс.
  - **`http/range_reconnect.rs`:** цикл повторов `HttpRangeSource`. Уже полученные байты сохраняются, и повтор продолжает с первого недостающего байта. Каждый `206` сверяется с первым: полный размер, ETag и Last-Modified, если они есть у обеих сторон. При расхождении — `HttpRepresentationChanged`, без склейки.
  - **`SourceError`:** новые `is_transient_network_failure()` и `http_retry_after()`. Range-ответы 429/503 теперь передают `Retry-After`.
  - **Новый вариант `SourceError::SourceClosed`:** «владелец закрыл источник». Он не `Cancelled`, поэтому не превращается в `Interrupted`.
  - **`HttpSourceHop::Seekable`** теперь в `Box`: Range source вырос, сработал clippy `large_enum_variant`.
- **`media-prefetch`:**
  - `read` сначала отдаёт буфер, потом ошибку.
  - `with_lifecycle_cancellation(token)` привязывает чтение к жизни ресурса. `web-media-http` передаёт токен open-а, отмена будит ждущее чтение ошибкой `SourceClosed`.
- **`media-source-open`, новый модуль `progressive_player_demux.rs`:** `into_player_demuxer`.
  - Seekable вход запускается в `ProgressiveDemuxer::new_receipted_seekable` и получает нейтральный seek port, как у HLS/DASH.
  - Forward-only вход обёрнут как раньше.
  - Используется для прямых ссылок и progressive-ссылок yt-dlp; у yt-dlp обёрнут весь composite A/V.
  - `DirectProgressiveOpenResult::into_runtime_parts()` теперь возвращает `DirectProgressiveRuntimeParts { demuxer, demux_seek_port, endpoint_recovery }`. app-egui передаёт порт player-у как `WorkerReceipted`.
- **Пометка «нет сети»:** `symphonia-demux` и `demux-api` помечают временный сетевой сбой стандартным `io::ErrorKind::NetworkDown`. Player-core (`session/tick/demux_read_failure.rs`) превращает его в `PlayerErrorKind::NetworkError`, без зависимости от `SourceError`.
- **Очередь (`app-egui/playlist_runtime`).**
  - `EndedSnapshotKind::ErrorAssociated` несёт `PlaybackFailureCause::{MediaFault, NetworkLost}`. `discovery/navigation.rs::automatic_snapshot_kind` ставит `NetworkLost` по `PlayerErrorKind::NetworkError`.
  - Контроллер останавливается с `AutomaticStopCause::NetworkLost`, без бейджа и без пропуска. `skip_report` при этой причине итога не публикует.
  - Тест: `navigation/tests.rs::runtime_snapshot_boundary_stops_queue_on_network_loss_instead_of_skipping`, парный к тесту «битый файл → следующий».
- **Текст (`app-egui/state/notifications/player_feed.rs`):** «Нет связи с сервером: воспроизведение остановлено. Проверьте подключение к сети и откройте видео снова.» Остальные виды ошибок player-а не менялись.
- **Config:** `network.reconnect_wait_ms`, валидация, метаданные, golden v12, контракт применения `MediaSourceRebuild`. Версия схемы не менялась: поле подставляется из `#[serde(default)]`.
- **Не трогали:** adaptive fetcher (HLS/DASH/HDS/Smooth), VOD endpoint recovery и FTP-логику.

## Ручная приёмка на настоящем Wi-Fi (агент, 9 октября 2026)

Владелец поручил провести приёмку агенту. Видео: публичный Big Buck Bunny 720p с archive.org (62 МБ, ~10 мин, Range). Wi-Fi выключался через `nmcli radio wifi off/on`. Config — отдельные копии (`XDG_CONFIG_HOME`), config владельца не трогался.

- **A. Config по умолчанию, Wi-Fi выкл. 5 с** (сеть пропала на ~10 с с учётом переподключения). Плеер не заметил: запас окна 256 МБ, ни одной сетевой ошибки, ни одного Buffering. **PASS.**
- **B. Окно 1 МБ, Wi-Fi выкл. 10 с** (~15 с без сети). TCP-соединение пережило обрыв само (не дошло до таймаута чтения 15 с). Короткая буферизация 1,3 с, потом продолжение. **PASS.**
- **B2. Окно 1 МБ, Wi-Fi выкл. 25 с.**
  - Таймаут чтения через 13 с, затем повторы 0,5 → 8 с.
  - Buffering со спиннером на 26,5 с (скриншот).
  - Сеть вернулась, «чтение восстановилось», Playing с той же позиции 26 479 мс. **PASS.**
  - Попутно: archive.org дважды отдал 500, оба раза штатно пережито повтором.
- **D. Смена файла во время спиннера.** Wi-Fi выключен, идёт Buffering. Второй запуск передал локальный файл, диалог «Заменить очередь?», клик «Подтвердить» (виртуальная мышь `uinput`). Новый файл в Playing через 1,4 с без сети, повторы старого источника прекратились сразу. **PASS.**
- **C. Обрыв дольше бюджета** (бюджет 15 с в копии config-а, чтобы не держать владельца без сети минуту). Buffering → таймаут → через 15 с `Failed`, `kind=NetworkError`. В центре «Нет связи с сервером: …» целиком с ×. **PASS.**

**Найденный баг (исправлен):** с окном 1 МБ seekable видео навсегда застревало в Buffering со старта.

- **Причина.** Ёмкость очереди событий фонового demuxer-а считалась как «окно / кусок» (формула старого streaming-пути): 1 МБ / 1 МБ = 1 пакет. Почти каждый проход player-а кончался `TemporarilyUnavailable`, а незакрытый demux-retry по правилам player-core запрещает выход из Buffering.
- **Исправление.** `PROGRESSIVE_EVENT_QUEUE_CAPACITY = 256` пакетов (как у HLS), байты по-прежнему ограничены окном.
- **Проверка.** Регресс-тест `tiny_prefetch_window_still_queues_a_batch_of_packets` падает при ёмкости 1. После правки видео стартует мгновенно.

## Открытые риски и бэклог

- **Открытие следующего элемента без сети** по-прежнему идёт политикой `skip`. Если сеть пропала между элементами или очередь запущена офлайн, она переберёт элементы и скажет «ни один файл очереди не открылся». Чтобы и тут останавливаться, нужно протащить тип отказа открытия (`WebOpenFailureReason::NoConnection`) в отчёт об отказе цели очереди (сейчас там только текст). Бэклог.
- **yt-dlp forward-only компоненты** (`web_media_open/runtime.rs::progressive_limits`) по-прежнему считают ёмкость очереди как «окно / кусок». При крошечном окне там возможна та же застревающая буферизация (старое поведение, вне объёма).

- **Задержка после возвращения сети до 8 с.** Так задумано политикой (потолок паузы 8 с). Ещё одна задержка — на медленной сети: после переподключения докачивается остаток текущего prefetch-куска (до 8 МБ), и только потом данные идут player-у. Улучшение — частичная публикация куска или «медленный старт» после обрыва (бэклог).
- **Строгая сверка ETag/Last-Modified** может сломать просмотр у CDN, который отдаёт разные validator-ы с разных узлов. Отсутствующий validator подменой не считается.
- **Сервер без Range** (полный ответ `200`) не переподключается: продолжить с того же места нельзя. Теперь он хотя бы показывает «нет связи» вместо технического текста.
- **Перемотка во время обрыва** ждёт возвращения сети или конца бюджета: у Symphonia над prefetch нет прерывания активного чтения (`active_read_interruption`). Player при этом отвечает (Seeking + спиннер).
- **Кнопка «Повторить»** — бэклог (решение владельца).
- **При открытой телеметрии** длинный текст ошибки в центре обрезается слева: телеметрия сужает область. Это старая особенность разметки центра, без телеметрии текст целиком.
- **Адаптер DASH (`prepared_dash_seek_port`) и новый `ProgressivePreparedDemuxSeekPort`** почти одинаковые. Объединить их — отдельная задача: adaptive в этой сессии трогать запрещено.
