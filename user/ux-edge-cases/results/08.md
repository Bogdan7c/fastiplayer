# Результат сессии 08: понятные причины отказа открытия web-ссылки

## Статус

**PASS.** Ручной прогон 6 октября 2026 провёл агент по поручению владельца: настоящий GUI на рабочем столе, изолированный `XDG_CONFIG_HOME`, все 5 сценариев проверены. Прогон нашёл две неточности, обе исправлены и закреплены тестами (ниже). Коммит — по решению владельца.

## Решения владельца (6 октября 2026)

1. **HTTP 404/410/429/5xx** исправляем в `web-media-http` в этой сессии: мёртвая ссылка больше не «нет сети». Выбор «попробовать другой вариант качества» для этих ошибок остаётся прежним.
2. **Причины отказа yt-dlp** различаем (приватное, нужен вход, регион, удалено, сайт не поддерживается). Для этого вывод ошибок разбирается внутри `service-ytdlp`, сам текст наружу не уходит.
3. **В тексте показываем только домен**: «Не удалось открыть ссылку (youtube.com): …».
4. **Где показываем:** CLI и восстановление очереди (окно и бейдж), бейдж строки очереди. Пересборка после смены настроек и тексты классификации URL («NetworkError: …») остаются в бэклоге.

## Исследование (часть A): где терялась причина

- **HTTP** (`web-media-http::map_source_open_error`). 404, 410, 429, 5xx, DNS, отказ соединения и TLS попадали в одну корзину `NetworkUnavailable`. Retry-After отбрасывался.
- **yt-dlp**:
  - stderr вообще не читался, считались только байты. Любой отказ сайта был `ExtractorRejection { stderr_bytes }`;
  - отсутствие программы терялось внутри общего `ProcessFailure`.
- **media-source-open.** Всё возвращается как `anyhow`. Типизированные ошибки лежали в цепочке, но их никто не доставал.
- **app**:
  - подготовка сводила ошибку к `DirectOpen` / `ExtractorOpen` / `Native*Open` без причины;
  - стартовые задачи (CLI, восстановление) делали `format!("{error:#}")`, и в окно попадал технический дамп на смеси языков.
- Отличить TLS от «нет соединения» нельзя: reqwest отдаёт их одной категорией. Поэтому текст общий.

## Архитектура (часть B)

- **`web-media-transport-api`.**
  - `TransportFailure` получил варианты `NotFound`, `Gone`, `RateLimited`, `ServerError`.
  - Intent-метод `allows_alternate_candidate()` сохраняет прежний выбор alternate.
- **`web-media-http`.** `http_status_transport_failure`: прочие статусы (400, 405 и т.п.) остаются в прежней категории.
- **`service-ytdlp`.**
  - `ExecutableNotFound` (запуск вернул `NotFound`).
  - Новый модуль `rejection_reason.rs` разбирает поток stderr: держит не больше одной строки (2 КиБ) и сразу её стирает.
  - Метки взяты из исходников yt-dlp 2026.08.19.
  - `ExtractorRejection { stderr_bytes, reason }`.
- **`media-source-open::web_open_failure`.**
  - `WebOpenFailureReason` + `classify_web_open_failure`.
  - Классификация только через `downcast_ref` звеньев цепочки, строки не разбираются.
  - Побеждает первое осмысленное звено.
- **app-egui:**
  - веб-варианты `MediaPreparationFailureKind` несут причину;
  - `MediaOpenUserFailureReason::WebOpen` — одна модель «почему не открылось» для local, web и player;
  - тексты лежат в `web_open_message.rs`, отдельно от классификации;
  - стартовые задачи возвращают `StartupWebPreparationFailure { reason, diagnostic }`;
  - домен вычисляет `StartupUrlLocator::display_host()` (через `Url::host_str`, без логина, пароля и порта);
  - `StartupInstallTarget { Local, Web, PlaylistEntry }`: отказ player-а для web-ссылки при старте тоже получает понятный текст;
  - в native-путях «yt-dlp выключен» теперь типизированная ошибка, а не строка.

**Не менялось:** retry, backoff, таймауты, VOD recovery, выбор кандидатов, барьер установки, topology yt-dlp (сессия 09).

## Тесты (что ловят)

- **Настоящий loopback HTTP:**
  - 404/410/429 (+Retry-After)/5xx → свой вариант; 400 → прежняя категория; обрыв → «нет соединения»;
  - сквозь `open_direct_media` и app `prepare_source` до точного текста окна и бейджа;
  - в тексте нет логина, пароля, пути и токена.
- **Настоящий процесс yt-dlp:**
  - пустой PATH → «не найдена программа yt-dlp»;
  - скрипт с «Private video» → «видео приватное»;
  - секретный URL из stderr не попадает в ошибку.
- **Классификатор:** каждая причина; первое звено побеждает; обёртка demux пропускается; отмена не выдумывает причину.
- **«Предыдущее воспроизведение продолжается».** Настоящий `PlayerWorker` держит старое media: 404 при подготовке ссылки → `DirectOpen(NotFound)`, у старого media тот же label и `MediaInstanceId`.
- **Тексты:** все 26 фраз русские, со строчной буквы, без имён типов, попарно различны.
- **Выбор альтернативы:** 404/410/429/5xx по-прежнему дают ровно один alternate и сохраняют точную причину.

## Ручная приёмка (сценарий для владельца)

Запуск: `cargo run -p app-egui --release -- <ссылка>` (или установленный бинарь). Для каждого пункта ожидается сообщение в центре окна с × и бейдж строки очереди.

1. **Несуществующая страница:** `fastiplayer https://raw.githubusercontent.com/github/gitignore/main/no-such-file.mp4` → «Не удалось открыть ссылку (raw.githubusercontent.com): страница не найдена (ошибка 404) — проверьте ссылку».
2. **Без сети:** выключить Wi-Fi, `fastiplayer https://www.youtube.com/watch?v=dQw4w9WgXcQ` → «…(youtube.com): нет соединения с сервером — проверьте интернет».
3. **Нет yt-dlp:** `sudo mv /usr/bin/yt-dlp /usr/bin/yt-dlp.off`, та же ссылка → «…: не найдена программа yt-dlp — установите пакет yt-dlp». Вернуть: `sudo mv /usr/bin/yt-dlp.off /usr/bin/yt-dlp`.
4. **Приватное видео:** ссылка на заведомо приватное YouTube-видео → «…: видео приватное». YouTube может вместо этого потребовать вход («Sign in to confirm you're not a bot») → «…: сайт требует войти в аккаунт…». Оба текста корректны.
5. **Очередь:** добавить в очередь битую ссылку из п.1 рядом с рабочим файлом, перейти на неё → бейдж «Страница не найдена (ошибка 404) — проверьте ссылку», рабочий файл продолжает играть.

### Итог приёмки (6 октября 2026, агент по поручению владельца)

Как прогоняли:
- release-бинарь, `XDG_CONFIG_HOME` во временном каталоге с копией `config.toml` владельца; очередь, lock экземпляра и состояние плеера владельца не тронуты;
- скриншоты — `spectacle`, навигация — MPRIS.

Отступления от сценария, чтобы не трогать систему владельца:
- «без сети» — Wi-Fi не выключали: плеер запущен в отдельном сетевом namespace без сети (`unshare -rn`); для плеера это то же самое;
- «нет yt-dlp» — без `sudo mv`: плеер запущен с `PATH`, в котором нет yt-dlp.

### Найдено и исправлено во время приёмки

1. **Реальная формулировка YouTube.** Для несуществующего id YouTube сейчас отвечает `This video is unavailable` (текст причины приходит с сервера). Этой метки не было, поэтому показалась бы общая фраза. Добавлена метка `video is unavailable` и тест с настоящей строкой. Без метки тест падает.
2. **Demux без сетевой причины.** mp4 без `faststart`, отданный сервером без Range, не разбирается, и причина была `Unclassified` («не удалось получить видео по ссылке»). Теперь если глубже типизированной причины нет, а backend demux-а отказал, показывается «по ссылке нет видео или звука, которые плеер узнаёт». Тест: `demux_backend_failure_without_deeper_cause_is_unrecognized_format`. Само ограничение (mp4 без faststart и без Range) старое и в эту сессию не входит.

Попутно: импорт `.m3u` при старте ждёт кнопку «Импортировать». Поэтому сценарий 5 собран через сохранённую очередь, а не через `.m3u`.

## Открытые риски / вне объёма

- Метки yt-dlp могут измениться в новой версии. Тогда покажется общая фраза «сайт не отдал видео…»: честно, но менее точно.
- TLS неотличим от «нет соединения».
- По решению владельца не трогали: пересборку после настроек (`web media rebuild failed: {kind:?}`), тексты классификации URL («NetworkError: …»), строки ошибок запуска потоков startup (редкий OS-сбой).
- Ручной клик по web-строке очереди показывает только бейдж и строку статуса, без окна (прежнее поведение).
- Сессия 09 может переиспользовать `classify_web_open_failure` для импорта URL.
