# Результат сессии 07: битый файл в очереди — пропуск по умолчанию и видимая причина

## Статус

**PASS (автоматические проверки + ручной прогон агентом по поручению владельца).** Ручной прогон нашёл давний баг — автоматический пропуск не срабатывал на удалённом файле. С согласия владельца баг исправлен в этой же сессии (вариант A), прогон повторён. Коммит — после подтверждения владельца, push не делается.

## Решения владельца (5 октября 2026)

1. **Существующие конфиги** (вариант A). Миграция v10→v11 меняет `playlist.error_behavior = "stop"` на `"skip"` у всех. Default-документ v10 записывал `stop` явно, поэтому «выбрал сам» не отличить от «осталось по умолчанию». Вернуть `stop` можно в настройках, и в v11 такой выбор больше не трогается.
2. **Текст пропуска.** Показываем до трёх имён и «и ещё K». У локального файла это только имя, без папки. У ссылки — название строки, как в плейлисте. Информационная плашка живёт 8 с.
3. **«Ни один не открылся» и «дальше ничего нет» — разные случаи.**
   - Ошибка в центре с × появляется, только если до цепочки ничего не играло **и** перебрана вся очередь. Пример: рестарт, а все файлы удалены.
   - Если что-то уже играло, показывается обычная плашка «… Дальше в очереди ничего нет».
4. **Явно выбранный `stop`** даёт временную плашку на 5 с: «Очередь остановлена из-за ошибки: b.mkv».
5. **Корень, найденный ручным прогоном, чинится здесь же** (вариант A): если файл не подготовился, неиспользованный план очереди возвращается владельцу.

## Исследование (часть A)

- **Цепочка пропусков растянута по кадрам.**
  - Шаг цепочки: B не открылся → controller (`finish_automatic_target_failure`) ставит бейдж и даёт команду на C → и так далее.
  - Порядок перебора, `attempted_item_ids` и лимит `maximum_steps` живут в непрозрачном плане `playlist-core`. Наружу выходит только количество, имён там нет.
- **Корень «причина только в логе».**
  - Причина остановки в исходах `Stop`/`Stopped` существовала только под `#[cfg(test)]`.
  - `PlaylistRuntime` проглатывал `Stopped`. Это видно в `report_playlist_navigation_failure`: ветка `Stopped{..} => {}`.
  - Как следствие, приложение не узнавало ни о пропусках, ни об остановке.
- **Миграция.** Схема мигрируется в два шага: шаг на сыром TOML (`normalize_document`) и поднятие версии (`upgrade_config`). Переход v11 стоил:
  - одно правило миграции;
  - переименование golden-файла;
  - около 15 литералов `schema_version = 10` в тестах, smoke-скрипте и бенчмарк-шаблонах.

## Что сделано (часть B)

- **`config`.**
  - `CURRENT_SCHEMA_VERSION = 11`, добавлен `LEGACY_SCHEMA_VERSION_10`.
  - Default `error_behavior` теперь `Skip`.
  - Новый шаг `migrate_playlist_error_behavior_to_skip`: меняет только точное значение `"stop"` и только при версии ≤ 10.
  - Golden-файл переименован в `current_schema_v11.toml`.
- **Владелец сводки — controller плейлиста, новый модуль `controller/automatic_lifecycle/skip_report.rs`.**
  - `AutomaticSkipReport` ведёт текущую цепочку: сколько пропущено, первые 3 безопасных имени, имя последнего неудачного элемента. Ещё он помнит, играло ли что-то до цепочки (`SkipChainStart`).
  - Готовые итоги кладутся в «почтовый ящик».
  - Итоговый тип `AutomaticQueueNotice::{SkippedFailedItems, SkippedToEndOfQueue, NothingInQueueOpened, StoppedOnFailedItem}` не содержит текста.
- **Хуки (только вызовы, алгоритм не менялся).** Цепочка:
  - **начинается** — на terminal edge в `observe_automatic_snapshot` и при первой неудаче restore;
  - **пополняется** — в `finish_automatic_target_failure`, при ошибке воспроизведения active, при каждой неудаче restore;
  - **закрывается** — в `stop_for_active`, в ветках остановки `finish_automatic_target_failure` и restore, а также при commit-е install-а. Удачей считается только происхождение `AutomaticAdvance`/`RestoredCurrent`;
  - **выбрасывается без итога** — при ручном intent-е (`cancel_automatic_continuation_for_manual_intent`) и при явном открытии другого файла (`register_external_strong_install`).
- **Граница.** `PlaylistRuntime::drain_automatic_queue_notices()`: без controller-а возвращает пустой список, каждый итог отдаётся ровно один раз.
- **Приложение.**
  - `playlist_skip_message.rs` — чистые формулировки и выбор вида показа, по образцу `local_open_message.rs`. Русское согласование числа: «файл/файла/файлов».
  - `AppState::show_playlist_queue_notices` направляет итог в `notify_info`, `notify_transient` или `set_startup_error`.
  - Вызов раз за кадр стоит в `frame_prepare.rs` после `poll_playlist_transport`. Ratchet обновлён: 1409 → 1411.
- **Размеры.** `automatic_lifecycle.rs` 709 → 728, `install.rs` 699 → 704. Это только хуки-вызовы, вся логика в новом модуле (315 строк). Выносить хуки нельзя: они стоят ровно в точках жизненного цикла.

## Корень, найденный ручным прогоном

- **Симптом.** A доиграл, B удалён — плеер встал, C не заиграл, плашки нет.
- **Причина** (была и до сессии, но при default `stop` не проявлялась):
  - controller принимает план следующего элемента только на staging, после успешной подготовки файла;
  - если подготовка падала (файл удалён, битый), план выбрасывался вместе с pending-транзакцией strong-open;
  - controller не узнавал request ID и уводил провал в ручную ветку (D55: ждать пользователя);
  - прежние тесты имитировали только синхронный провал до выдачи request ID.
- **Исправление.**
  - `PlaylistStrongMediaOpenPoll::TargetFailedBeforeAdmission` возвращает план вместе с ошибкой. Его выдаёт `poll_prepared_playlist_media_strong` (`state/strong_media_open/pending.rs`, функция `return_unadmitted_playlist_plan`).
  - План возвращается только при ошибке самого файла. Отмена (в том числе `PreparationFailed { kind: Cancelled }`) по-прежнему его не возвращает.
  - Прежний `poll_prepared_media_strong` для startup, VOD recovery и same-item switch ведёт себя как раньше.
  - `state/playlist_transport/unadmitted_target_failure.rs` применяет тот же порядок, что и обычная ошибка: сначала замена, потом снятие guard-ом, потом владелец очереди.
  - `PlaylistRuntime::report_playlist_target_failure_before_admission`: автоматический план (`PlannedPlaylistInstall::is_automatic_traversal`) уходит в controller с понятной причиной для бейджа; ручной — прежним маршрутом по request ID.
- **Ещё не закрыто.** Отказ player-а на самом staging (`stage_media_open_at_player`) тоже теряет план — это редкий путь, вынесен в риски.

## Ручная приёмка

Прогон выполнил агент 5 октября 2026. Условия: реальный бинарник, настоящее окно KDE Wayland, временная папка настроек `XDG_CONFIG_HOME`, клипы ffmpeg по 4–6 с, файл открывался аргументом командной строки. Скриншоты и логи остались в scratchpad сессии, в репозиторий не попали. Средств ввода нет, поэтому перемотку заменили короткие клипы.

- **1. A → B (удалён на 2,5 с) → C, конфиг v10 со старым `stop` — PASS** после исправления.
  - Первый прогон — FAIL: плеер встал на конце A (корень описан выше).
  - После исправления C стартовал через 80 мс после провала B. Плашка «Пропущен из-за ошибки 1 файл: b-broken.mkv». Миграция `stop`→`skip` подтверждена поведением.
- **2. Рестарт, все файлы удалены — PASS.**
  - Current = C (последний): ошибка в центре «Не удалось открыть «c-ok.mkv»: файл не найден» и плашка «… Дальше в очереди ничего нет». A и B не пробовались, потому что очередь не зацикливается — по решению 3 это не «ни один».
  - Current = A: ровно 3 попытки и одна ошибка в центре «Ни один файл очереди не удалось открыть».
  - Зависаний нет.
- **3. Конфиг v11 с явным `stop` — PASS.** Остановка на конце A, C не запускался, плашка «Очередь остановлена из-за ошибки: b-broken.mkv». Файл конфига не изменился, контрольная сумма совпала.
- **Наблюдение.** Конфиг v10 после запуска на диске остаётся v10. Миграция применяется в памяти при каждой загрузке (идемпотентно), а v11 пишется при следующем сохранении настроек.
- **Попутно, не регрессия сессии.** Один из пяти запусков с CLI-файлом завис на старте: пауза, 0 пакетов, раньше любой логики очереди. Два повтора прошли. Нужна отдельная проверка.

## Открытые риски

- Сообщения дублируются, если restore после рестарта упал при политике `stop`: в центре уже есть ошибка файла (её показывает startup orchestration), и к ней добавляется плашка «Очередь остановлена…». Это безвредно.
- Если файл упал **во время** воспроизведения, при skip он тоже попадает в «пропущено». Пока он играл, ошибку player-а и так было видно в центре.
- Default `PlaylistController::new()` остался `Stop`. В обычном запуске он всегда перезаписывается значением из config-а и влияет только на тесты.
- Отказ player-а на staging (`stage_media_open_at_player`) до admission всё ещё теряет план: тогда провал уходит в ручную ветку. Путь редкий, отдельная задача.
- Разовое зависание старта CLI-файла (см. ручную приёмку) — вне скоупа сессии.
- Бенчмарк-шаблоны `docs/benchmarks/tools/t480s/*.toml` подняты до v11 с сохранённым `stop`, чтобы их поведение не менялось.
