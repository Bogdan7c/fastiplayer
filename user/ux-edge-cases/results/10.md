## Исследование (часть A)

- **Context7:** cpal есть только для версий 0.17/0.18. У нас 0.15.3, поэтому поведение сверено по исходнику крейта из реестра cargo (`src/host/alsa/mod.rs`, `src/error.rs`).
  - xrun (`EPIPE`) cpal обрабатывает сам, в error callback он не попадает.
  - Выдернутое устройство приходит как `StreamError::BackendSpecific` (POLLERR/ENODEV), а не `DeviceNotAvailable`.
  - После ошибки цикл ALSA-потока продолжает крутиться, то есть возможен шторм callback-ов.
  - Пересоздавать stream внутри callback-а нельзя: это поток, который кормит устройство.
- **Эксперимент A2 на машине владельца** (Alsa host, PipeWire 1.6.9, единственный sink — сетевой `roc-android`).
  - cpal 0.15 видит ALSA-устройства: `pipewire`, `pulse`, `default`, `hdmi:…`, `front:CARD=…`. Bluetooth/сетевые выходы отдельными пунктами **не появляются**, до них можно добраться только через `default`.
  - Поток через `pipewire` вывели на временный null-sink, а sink выгрузили. PipeWire сам перевёл поток на `roc-android`, cpal **не получил ни одной ошибки**, звук не прерывался. Сценарий «Bluetooth отключился при выборе По умолчанию» работал и до этой сессии.
  - Прямое устройство (`front:CARD=Generic_1`) открывается и играет параллельно с PipeWire. Его выдёргивание — реальный случай поломки, но проверить его вживую нечем.
- **Граница audio → player-core:** раньше контракта для ошибок потока не было (`err_callback` только писал `warn!`). Добавлен `PlayerAudioOutput::stream_health()`.

- **`audio`:**
  - error callback только взводит lock-free `StreamFailureSignal` (`output/stream_callbacks.rs`) и пишет в лог одну первую ошибку;
  - порядок «выбранное → default» вынесен в функцию `output_device_fallback.rs`, которая не зависит от CPAL;
  - имя устройства для уведомления даёт `devices::output_device_display_name`. Формат stable id не менялся.
- **`player-core`:**
  - lazy init просит `SelectedOrSystemDefault` и при запасном маршруте отправляет `PlayerEvent::AudioOutputSwitchedToSystemDefault(SelectedDeviceUnavailable)`;
  - новый `session/audio_output_recovery.rs` на каждом tick-е проверяет здоровье потока. Если поток сломан, вызывает `recreate_active_audio_output(SystemDefault)` и отправляет событие `ActiveDeviceStopped`;
  - защита от шторма: не больше 3 попыток с интервалом ≥ 1 с. Если попытки исчерпаны, плеер отключает звук и переводит видео на monotonic clock с той же позиции, плюс recoverable `AudioDeviceUnavailable`;
  - смена устройства в настройках просит `SelectedOnly`, поэтому прежняя семантика ошибки и rollback сохраняются.
- **`app-egui`:** тексты в `audio_output_message.rs`. `player_feed` показывает их информационной плашкой (8 с), «Звук недоступен…» заменил технический Display.

### Для владельца

1. В настройках выбери любое прямое устройство (`front:…`) или поставь в config несуществующее. Открой видео: должна появиться плашка про default, звук должен быть.
2. При наличии USB-гарнитуры: выбери её, включи видео, выдерни. Ожидаемо — звук в колонках/default, плашка «Звуковое устройство отключено…», позиция не прыгнула.

## Открытые риски / вне объёма

- **Физическое выдёргивание USB/BT вживую не проверено** (нет железа). Та же ветка кода (ALSA `BackendSpecific` → восстановление) проверена вживую через `pulse` + перезапуск `pipewire-pulse` и тестами на fake output-е.
- **При пересоздании output-а теряется PCM, уже стоявший в очереди старого выхода.** До следующей перемотки звук может опережать видео на размер этого буфера (~200 мс). То же самое происходит и раньше при смене устройства в настройках. Clock/синхронизацию сессия менять не имела права.
- Автовозврат на вернувшееся устройство — бэклог (решение владельца).
- Имя устройства в плашке — ALSA-имя (`front:CARD=…`), так же, как в списке настроек.
