## Исследование (часть A): причина и root cause

- **player-core причину не теряет.** `MediaInstallCompletion::Failed { failure: MediaInstallFailure { stage, error: PlayerError } }` несёт `PlayerErrorKind`: кодек/профиль/битность/HDR, аудиокодек, нет HW/нужного backend-а, таймаут preflight и т.д. Новый enum в player-core не нужен: знание UI туда не тянем.
- **Причину теряло приложение:**
  - `coordinator/player_staging.rs::drain_player_staging`: `take_completion().is_some()` — completion выбрасывался;
  - `coordinator.rs`, ветка `AuthorizationRejectedBeforeCommit`: `Failed { request_id, .. }`.
- **«worker недоступен»** (`state/media_jobs.rs`) писался для любой ошибки strong open, включая отмену и Busy. Английский дамп брался из `StrongMediaOpenError::Terminal` (`{0:?}`). Тот же дамп видел CLI-старт (`startup_media/pending_install.rs`).
- **`PlayerRejected`** означает не «player отказал по содержимому», а «команда не доставлена» (очередь Full / поток Disconnected).
- **Таймаут ожидания (п.4 предыстории):**
  - на UI-потоке таймаута нет: `MediaInstallReceipt::wait_until_signal_available` — blocking `recv()`, `drive_media_open_to_terminal` ждёт без deadline;
  - сверху время ограничено только player-owned `staged_video_preflight_timeout` (15 с), поэтому кнопка Open может «подвесить» окно до ~15 с на медленном файле;
  - startup и плейлист используют неблокирующий stepwise-путь;
  - зафиксировано, не исправлено (отдельное решение).

## Тесты (что ловят)

- **Реальный путь:** настоящий `PlayerWorker`, старое media установлено. Новый файл с неизвестным видеокодеком проходит через coordinator → `PlayerFailed { UnsupportedVideoFormat }` → «Не удалось открыть «clip.mkv»: формат видео не поддерживается». Старое media (label + `MediaInstanceId`) осталось на месте.
- **Coordinator (fake):**
  - Failed на staging → причина;
  - `AuthorizationRejectedBeforeCommit` → причина;
  - неожиданный Cancelled → `PlayerFailed { InternalError }` (семантика сохранена);
  - недоставленный stage → `PlayerRejected { PlayerNotResponding }`, а caller по-прежнему получает `PlayerDispatch(Disconnected)`.
- **Классификация:** каждый `PlayerErrorKind`; таймаут-стадия побеждает kind; стабильность по всем стадиям.
- **Пользовательский исход:** Busy/Cancelled → Silent; неклассифицированное → InternalError; Rejected остаётся pre-barrier.
- **Тексты:** для каждой причины точный текст с именем файла, без «worker», `{`, «Player» и родительской папки.
- **Старт:** локальный CLI/restored → текст с именем + бейдж; web → прежний текст окна + понятный бейдж.
- **Плейлист:** `PlayerFailed` → бейдж «Формат видео не поддерживается»; неклассифицированная ошибка → `Generic`.

## Открытые риски / вне объёма

- **Подвисание окна до ~15 с** на кнопке Open при медленной подготовке (blocking ожидание без deadline на UI-потоке). Нужно отдельное решение: перевести Open на неблокирующий stepwise-путь, как у startup.
- **Отмена без supersede при старте** (TransportStop/LifecycleShutdown) по-прежнему показывает технический текст (прежнее поведение); сделать молчаливой — это изменение startup-политики.
- **Сообщения окна для web при старте** — прежний технический текст (сессия 08).
- **Бейдж восстановленного элемента для неклассифицированной ошибки** — прежний технический текст.
- `DemuxError`/`NetworkError` от player-а → «внутренняя ошибка» (по утверждённой таблице); для web уточнит сессия 08.
- `PlayerError.message` пишется в лог; путей там не нашли (сообщения codec/preflight), но гарантии «никогда» нет.
- Неожиданный `Installed` до Ready по-прежнему схлопывается в `PlayerFailed` (было и раньше; теперь хотя бы с `warn!`).
- Пересборка после смены настроек — английский текст (бэклог).
