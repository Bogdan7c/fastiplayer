# Результат сессии 06: видимые фатальные ошибки запуска

## Статус

**PASS (автоматические проверки + ручной прогон агентом по поручению владельца).** Кнопку «OK» руками не нажимали: средств ввода в окружении нет. Окна закрывались сигналом, и так заодно вживую проверилась цепочка запасных каналов. Коммит — после подтверждения владельца, push не делается.

## Решения владельца (5 октября 2026)

1. **Способ показа:**
   - сначала системное окно ошибки: `kdialog` на KDE, `zenity` в остальных окружениях; вторая утилита запасная;
   - если окно показать не удалось — критическое уведомление рабочего стола;
   - текст всегда дублируется в терминал, деталь — в лог.
2. **Окно показывается и при запуске из терминала**: поведение одинаковое при любом способе запуска.
3. **«Плеер уже запущен» показывается окном**. Когда в сессии 13 появится передача файла в первый экземпляр, это окно заменится нормальным поведением.
4. **В ошибке папки настроек — путь (с `~`) и команда для исправления** (`sudo chown -R "$USER": ~/.config/fastiplayer`).

Решено по умолчанию: код выхода при любой фатальной ошибке — 1. Отдельный код 70 (shutdown не уложился в срок) не трогали.

## Исследование (часть A)

- **Пути до окна** (аргументы, папка настроек, lease, config):
  - ошибка уходила через `?` из `main`, Rust печатал `Error: …` в stderr, код 1;
  - tracing включался только после bootstrap, поэтому в лог эти ошибки не попадали;
  - lease-ошибки выглядели как Debug-имена: `небезопасный instance-lock artifact: ConfigDirectoryOwnerMismatch`.
- **Пути внутри event loop:**
  - ошибки renderer (нет Vulkan, surface, device), окна, render color settings, `AppState::new`, binding и attachment плейлиста;
  - везде было `tracing::error!` + `event_loop.exit()`, `run_app` возвращал `Ok`, **код выхода 0**;
  - renderer логировался через `{}`, и причина от wgpu терялась.
- **Варианты показа:**
  - `rfd::MessageDialog` (rfd уже в зависимостях) отклонён. На Linux он вызывает только `zenity`, kdialog не поддерживает, а неудачу глотает: всегда `Cancel`;
  - своё окно без GPU (`softbuffer` + шрифты) отклонено: новые зависимости и много кода ради редкого случая;
  - D-Bus (`zbus`) уже был в `desktop-integration`, поэтому новых внешних зависимостей не появилось, `Cargo.lock` не изменился.

## Что сделано (часть B)

- **Новый модуль `crates/app-egui/src/fatal_startup/`** — единственный владелец фатальной ошибки запуска. Его части:
  - `mod.rs`:
    - `FatalStartupError` (причина + техническая деталь);
    - `FatalStartupReason`, `ConfigDirectoryProblem`;
    - `FatalStartupErrorSlot`: первая ошибка побеждает и сразу пишется в лог;
    - `conclude_process` → `ProcessConclusion::{Completed, FailedToStart}` → `ExitCode`.
  - `messages.rs` — русские тексты: что случилось и что делать.
  - `bootstrap_mapping.rs` — `ProcessBootstrapError` → причина.
  - `config_location.rs` — путь с `~` и shell-безопасный аргумент для команды.
  - `presentation.rs` — `FatalStartupPresenter`, цепочка каналов `deliver_notice`, порядок каналов по `XDG_CURRENT_DESKTOP`.
  - `dialog_utility.rs` — kdialog/zenity через `std::process::Command`. Канал считается сработавшим только при коде выхода 0. У zenity стоит `--no-markup`.
  - `desktop_notification_channel.rs` — адаптер к D-Bus.
- **`desktop-integration`:**
  - новый `notification` с функцией `send_critical_desktop_notification`;
  - работает через блокирующий zbus: urgency critical, без автоскрытия, разметка в тексте экранируется, ответа ждёт не больше 5 с;
  - ошибки различаются: «шины нет» и «служба отказала».
- **`main.rs`:**
  - tracing инициализируется первым;
  - `run_application() -> Result<(), FatalStartupError>`;
  - после `run_app` shell (а вместе с ним lease) освобождается **до** показа. Иначе повторный запуск, пока висит окно ошибки, ответил бы «уже запущен».
- **`app_shell`:**
  - все шесть путей ошибки идут через `exit_with_fatal_startup_error`;
  - в путях binding и attachment фиксация стоит до очистки `AppState`. Аварийный выход 70 из очистки иначе потерял бы деталь.
- **`app_instance`:** `ProcessBootstrapError::Lease` и `LoadConfig` несут `config_dir`; `ConfigError` лежит в `Box` (clippy `result_large_err`). В `Display` (лог) путь не добавлен.

## Ручная приёмка (сценарий для владельца)

1. В терминале: `VK_ICD_FILENAMES=/nonexistent cargo run -p app-egui`.
   - Ожидание: окно плеера мигает, затем появляется окно KDE «Fastiplayer не запустился» с текстом про Vulkan.
   - После «OK» команда `echo $status` (fish) показывает `1`.
2. Создать `.desktop`-ярлык или запустить из Dolphin с неизвестной опцией (например, ярлык с `Exec=…/fastiplayer --bogus`).
   - Ожидание: окно ошибки «Плеер запущен с неизвестным параметром…».
3. При открытом плеере открыть файл через «Открыть с помощью → Fastiplayer».
   - Ожидание: окно «Fastiplayer уже запущен.»

## Открытые риски

- kdialog сам решает, считать ли текст HTML (Qt `mightBeRichText`), и флага `--no-markup` у него нет. Наши тексты тегов не содержат, но путь к папке настроек с `<…>` теоретически мог бы исказиться.
- Если пользователь закроет окно zenity/kdialog крестиком (ненулевой код), он дополнительно получит уведомление. Это лишний, но безвредный показ.
- Голая система без kdialog, zenity и службы уведомлений → только stderr. Своё окно без GPU сознательно не делали.
- Рендерер, упавший после suspend/resume (не при старте), тоже показывается как «ошибка запуска» с текстом про Vulkan.
- Утечка медиапутей исключена: CLI-аргумент в тексты не попадает, показывается только папка настроек (решение владельца).
