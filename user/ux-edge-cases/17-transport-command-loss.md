## Предыстория (подозрения аудита, НЕ доказаны)

1. Все UI-команды идут через неблокирующий `try_send_command` (`worker/handle.rs:112`) в канал ёмкостью 128 (`worker.rs:89`); при отказе — только `warn!` (`ui_runtime.rs:~419-420, ~456-464`).
2. Во время drag громкости `SetVolume` шлётся каждый кадр → при занятом worker-е можно потерять финальную громкость.
3. Опаснее: потеря `EndScrub`/`CancelLiveScrub` → player остаётся в Scrubbing; `playback_toggle_will_pause` считает это «будет play».
4. `map_timeline_interaction` (`ui/timeline/gesture.rs:143-148`) при `bounds = None` посреди drag (media стала не-seekable/сменилась) чистит жест без `CancelLiveScrub`. Core, вероятно, отменяет scrub при внешних командах и reset media — проверить.

## Задание

### Часть A. Исследование
1. Тестами (fake/заторможенный worker) проверить: можно ли реально переполнить канал при обычной работе (кто ещё пишет в канал, как быстро worker читает, `drain_pending_command_batch`).
2. Для каждой команды классифицировать: «потеря безопасна» (промежуточный SetVolume, промежуточный PreviewScrub), «потеря ломает состояние» (End/Cancel scrub, финальная громкость, Pause/Play, Seek commit).
3. Проверить п.4: что делает core, если жест исчез без End/Cancel.
4. Отчёт простым языком: есть ли реальный дефект, при каких условиях.

### Стоп: согласование с владельцем
Если дефект подтверждён — варианты, например: (A) «терминальные» команды не теряются: отдельный слот «последнее терминальное намерение» с гарантированной доставкой; (B) coalesce промежуточных команд в UI (последний SetVolume за кадр); (C) A + B. Если не подтверждён — закрыть с доказательствами, production не трогать.

### Часть B. Реализация (только по решению)
- Классификация команд — типом, а не комментарием; доставка терминальных команд гарантирована, промежуточные сливаются; счётчики потерь в diagnostics сохраняются.
