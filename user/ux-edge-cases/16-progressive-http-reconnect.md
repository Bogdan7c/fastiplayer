## Предыстория (факты аудита, сверить с кодом)

1. Range-чтение повторяется **один раз** (`source-core/src/http.rs:224-246`); затем progressive worker пушит `Failure` и останавливается (`demux-api/src/progressive/worker.rs:~306-316`) → `mark_fatal_error` → `PlaybackState::Failed` (`player-core/src/session.rs:~454-458`). `frame_prepare.rs:~335-337` только логирует `FatalError`.
2. Пользователь видит красный технический текст и должен переоткрыть элемент (позиция теряется, если resume не сработает).
3. Retry-After в progressive-пути игнорируется (`Unavailable` в `http.rs:~333, ~364, ~552`); в adaptive — учитывается, cap 60 с.
4. Для signed yt-dlp URL при 401/403/404/410 есть bounded re-extraction с восстановлением позиции — не путать с обрывом сети.

## Задание

### Часть A. Исследование и воспроизведение
1. Падающий тест: локальный HTTP-сервер отдаёт часть файла, рвёт соединение на N секунд (отказывает в подключении), потом снова отвечает с поддержкой Range → сейчас playback = Failed.
2. Где повтор правильнее: на уровне source (прозрачно для demux, сохраняет позицию байтов) — предпочтительно; почему (не) на уровне worker.
3. Как сейчас взаимодействуют таймауты чтения и буфер player-а: сколько времени есть до starvation.

### Стоп: согласование с владельцем
Политика повторов простыми словами, например: экспоненциальный backoff 0,5 → 1 → 2 → 4 → 8 с, общий бюджет 30–60 с, учитывать Retry-After (cap), повторять только сетевые ошибки и 5xx/408/429 (не 404/403); пока идут повторы — Buffering (индикатор из 15); после бюджета — понятная ошибка + кнопка/хоткей «Повторить»? (кнопка — по решению). Рекомендация, риск, объём.

### Часть B. Реализация
- Повтор продолжает с того же байтового смещения (Range), проверяет, что ресурс тот же (ETag/Last-Modified/Content-Length, если доступны) — иначе типизированная ошибка «файл на сервере изменился».
- Каждое ожидание отменяемо (cancellation token); закрытие/смена media прерывает повторы немедленно.
- Параметры — в config с валидацией и миграцией, если меняется схема (согласовать).

## Тесты
- обрыв на 3 с → воспроизведение продолжается до рендера с той же позиции (кадры после обрыва презентуются, аудио-потребитель получает сэмплы);
- обрыв дольше бюджета → Failed с понятной причиной (тексты сессии 08);
- 404 после обрыва → без повторов, сразу ошибка;
- 503 + Retry-After → ожидание по заголовку (fake time, cap);
- ресурс изменился (другой ETag) → типизированная ошибка, без склейки разных файлов;
- закрытие media во время ожидания → повтор отменён, поток завершён без зависания.

## Ручная приёмка
Сетевое видео по прямой ссылке, отключить Wi-Fi на 5 с и включить → воспроизведение продолжилось, был виден индикатор буферизации.
