# Сессия 00: разведка сайтов, браузеров, native messaging и Flatpak

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 00 плана `user/browser-bridge/`: разведка без кода плеера. Составь список эталонных сайтов (YouTube, Twitch, украинские сайты с фильмами и сериалами, обычные HTML5-сайты; российские — никогда) и разбери, как их веб-плееры получают видео, качества, озвучки, серии и субтитры. Проверь вживую native messaging в Firefox, Chromium и Google Chrome из Flatpak одноразовым хостом в scratchpad, гипотезу «Flatpak через Flatseal + D-Bus activation» и выбор Firefox MV2/MV3. Сначала прочитай `user/browser-bridge/README.md`.

## Зачем

Весь план опирается на то, как реально ведут себя сайты и браузеры. Ошибка здесь стоит переписывания экстеншена потом. Код плеера не меняется. Одноразовые прототипы (хост на Python или shell, пустой экстеншен) живут только в scratchpad.

## Что сделать

1. **Эталонные сайты — список на утверждение владельцу.**
   - **YouTube:** обычное видео, плейлист, live, Shorts, видео с субтитрами и с несколькими дорожками звука.
   - **Twitch:** live, запись, клип. Реклама вшита в поток — отметить.
   - **Украинские сайты с фильмами и сериалами:** 4–6 популярных. Критерии: живые, массовые, плеер во iframe, выбор озвучки и серий. **Российские сайты, плееры и CDN исключены.** Если происхождение плеера во iframe неясно — пометить и спросить владельца, а не подставлять.
   - **Обычные HTML5-сайты:** 3–4 (новости, курсы, блог-хостинг) с mp4 / HLS / DASH.
   - **Отрицательные:** 1–2 сайта с DRM (Netflix-подобные) — проверяем, что экстеншен их не трогает. Плюс видеозвонок — проверяем стоп-лист.
   - Итог — таблица «сайт → зачем он в эталоне». Утверждает владелец, это решение в README.
2. **Разбор каждого эталонного сайта** (DevTools, `about:networking`, вкладка «Сеть») — таблица:
   - что качает плеер: progressive / HLS / DASH / свой протокол; `blob:`/MSE; MSE в фоновом потоке;
   - во iframe ли плеер и с какого origin;
   - какие заголовки нужны CDN: `Referer`, `Origin`, куки, токены в query; срок жизни ссылки;
   - где живут качества, озвучки, серии и субтитры: в манифесте, в отдельных запросах, в DOM / JSON страницы;
   - реклама: как отличить (домен, длина, IMA SDK);
   - что даёт yt-dlp на этой странице (`yt-dlp -F --cookies-from-browser`) — запасной путь гибрида.
3. **Native messaging вживую** — одноразовый хост, который пишет в stderr полученное и отвечает эхом:
   - Firefox (пакет системы), Chromium, **Google Chrome из Flatpak**;
   - пути файлов подключения для всех браузеров из решения 21 — подтвердить по документации производителей, неподтверждённые пометить;
   - чем браузер запускает хост (аргументы, окружение, cwd), что с процессом при закрытии порта и вкладки, лимиты размера сообщений;
   - как хост видит ID экстеншена (аргумент у Chrome, у Firefox — путь манифеста и ID).
4. **Flatpak — главная гипотеза:**
   - хост лежит в папке, доступной песочнице, и говорит с плеером по D-Bus сессии;
   - плеер запускается через D-Bus activation (`.service`-файл для app ID);
   - Flatseal: какие ровно права нужны (`filesystem=…:ro`, `talk-name=io.github.Bogdan7c.Fastiplayer`) и где браузер из Flatpak ищет файлы подключения (`~/.var/app/<id>/…`);
   - проверить одноразовым `.service` и эхо-хостом. Если не выходит — какие ещё пути есть (`flatpak-spawn --host`, xdg-native-messaging-proxy) и их цена. Итог — черновик инструкции «Flatpak за 3 шага».
5. **Snap:** только как распознать браузер из Snap, чтобы показать сообщение «не поддерживается» (решение 22). Ставить Snap не нужно — достаточно признаков по документации.
6. **Firefox MV2 или MV3.** Что даёт каждый: блокирующий `webRequest`, `filterResponseData`, фоновая страница против service worker, будущее MV2 по заявлениям Mozilla, требования AMO. Рекомендация владельцу с причиной.
7. **Chrome MV3:** проверить на Chromium `webRequest` + `extraHeaders` (видны ли `Cookie`/`Referer`), `declarativeNetRequest` для медиа-запросов вкладки, контент-скрипты во всех фреймах (`all_frames`, `match_origin_as_fallback`), MAIN-мир на `document_start`, `optional_host_permissions` + `activeTab` для режима 1 без широких прав.
8. **Куки для yt-dlp без диска:** как передать куки из браузера в yt-dlp, не записывая файл (pipe / memfd через `/dev/fd/N`, `--cookies`). Проверить на установленной версии yt-dlp.
9. **Убийцы архитектуры (решение 36)** — проверить вживую на эталонных сайтах и стенде. По каждому — вывод «ломает / не ломает план» и что менять:
   - **Отдельные куки iframe (CHIPS).** Видит ли `cookies` API куки CDN плеера во iframe без `partitionKey`; как их достать в Chrome и Firefox (у Firefox своя изоляция — Total Cookie Protection).
   - **Контейнеры Firefox** (`cookieStoreId`). Куки вкладки из контейнера должны браться из её хранилища, а не из общего.
   - **Привязка к браузеру.**
     - Отдаёт ли CDN поток, если отличается только User-Agent (передавать UA браузера?).
     - Привязана ли ссылка к IP.
     - Пускает ли Cloudflare-защита (`cf_clearance`) наш HTTP-клиент с теми же куками и UA. Если нет — отпечаток TLS не совпадает, и для таких сайтов работает только «браузер качает сам». Это меняет архитектуру; цену варианта — владельцу.
   - **HTTP/2- или HTTP/3-only CDN** и серверы без `Range`.
   - **Куки с префиксами** `__Host-` / `__Secure-`, `SameSite`, host-only против domain — как их правильно положить в наш `SecretRequestContext`.
10. **Memory:** создать `mem:browser-bridge/core` (решения владельца, эталонные сайты, факты зоопарка, где лежит план) и добавить ссылку на неё в «Открытые направления» `mem:core`.
