# Сессия 02: браузерный режим — отдельный процесс, D-Bus и канал данных

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 02 плана `user/browser-bridge/`: заложи браузерный режим плеера как отдельный процесс со своим окном (решение 41), D-Bus-интерфейс управления в `desktop-integration` (транспорт под ОС за нейтральным trait), канал данных через fd, переданный по D-Bus, и D-Bus activation. Источник байтов — заглушка до 03, окно — каркас до 04. Сначала прочитай `user/browser-bridge/README.md`, `results/00.md` (Flatpak, fd), `results/00c.md`, `results/01.md`.

## Зачем

Посредник (05) должен говорить с плеером, даже если тот не запущен, и гнать байты без D-Bus-сообщений на каждый сегмент. Решение 41: браузерный режим не смешивается с обычным окном и очередью.

## Что сделать

1. **Процесс браузерного режима.** Тот же бинарь с ключом `--browser-session` (решение 60). После конца сеанса процесс выходит сразу (решение 56).
   - Своё имя на шине (например, `io.github.Bogdan7c.Fastiplayer.BrowserSession`), один процесс на все сеансы браузера: новый сеанс заменяет текущий (решение 40).
   - Не читает и не пишет state очереди, позицию, track-memory (инвариант 7). Config читает и пишет через настройки (решение 46): два процесса с одним config. Правило записи без потерь: перед записью config перечитывается и меняются только ключи, которые тронул этот процесс (атомарная запись уже есть); второй процесс подхватывает изменения по уведомлению или при следующем чтении (04).
   - Обычный экземпляр плеера при старте браузерного сеанса ставится на паузу (решение 41): сигнал на его имени шины, если он запущен. После сеанса он остаётся на паузе (решение 48).
2. **D-Bus-интерфейс управления** `io.github.Bogdan7c.Fastiplayer.BrowserSession1`:
   - метод «открыть сеанс» (JSON протокола) → возвращает fd канала данных (pipe или socketpair, создаёт плеер);
   - метод «команда / событие страницы»;
   - сигнал событий плеера (позиция, буфер, команды странице, закрыт);
   - допуск — общий с `instance_forwarding/admission.rs`: свой uid, лимиты.
3. **D-Bus activation:** `.service`-файл для имени браузерного режима. Ставит `scripts/install-desktop-entry.sh`, позже — установщик 06. Старый путь «второй запуск → первый» не ломается.
4. **Приёмник в процессе:** ящик с ограниченной ёмкостью и пробуждением UI, подтверждение UI-потоком с таймаутом (как UX13). Канал данных читается отдельным потоком в источник 03 (пока — счётчик байтов и отбрасывание).
5. **Швы Windows:** нейтральный trait транспорта (управление + канал данных). Linux — D-Bus + fd, у остальных ОС — `UnsupportedPlatform`.

## Тесты

- Частный `dbus-daemon`: открыть сеанс → получен fd → байты, записанные в fd, дошли до приёмника (счётчик и содержимое); чужой uid, мусор, лимиты, несовместимая версия → точные ошибки D-Bus; зависший UI → «не отвечает».
- **Активация:** на частной шине с `servicedir` вызов будит тестовую заглушку.
- **Гонки запуска:**
  - два клиента одновременно будят незапущенный процесс → ровно один экземпляр;
  - второй сеанс во время первого → первый закрыт событием «заменён», второй открыт;
  - сообщение во время завершения → `ShuttingDown`, а не потеря.
- Повтор «открыть сеанс» с тем же ключом → один сеанс.
- Обычный экземпляр получает «пауза» при старте браузерного сеанса и ничего больше.
- Пересылка второго запуска проходит все свои старые тесты.

## Поправки по итогам 00c (29.10.2026, решения 81–84)

- **Канал данных — WebSocket на loopback, а не fd** (решение 82).
  - Процесс браузерного режима слушает `127.0.0.1` на случайном порту.
  - «Открыть сеанс» по D-Bus возвращает порт и одноразовый токен, а не fd.
  - Чужой токен, второй клиент, превышение лимитов — разрыв соединения.
- Проверить на Chrome и Firefox из Flatpak, что loopback песочницы достаёт до плеера снаружи (`--share=network`).
- Fd-канал из первой редакции не нужен.

## Поправки по итогам 01 (29.10.2026, решения 85–86)

- **D-Bus несёт только «вход»** (решение 85): `hello` и `open_session` — JSON `ExtensionControlMessage` из `browser-bridge-protocol`, ответ — `PlayerControlMessage`. Методов «команда / событие страницы» и сигнала событий плеера нет: всё живое идёт по WebSocket сеанса.
- **Сервер WebSocket сеанса** на `127.0.0.1` в процессе браузерного режима:
  - первое текстовое сообщение — `attach` с ключом и пропуском;
  - пропуск сверяется `SessionToken::matches` (постоянное время);
  - ответ — `attached`, иначе закрытие с кодом `SessionCloseReason` (4000–4008): чужой пропуск — 4004, второе соединение — 4008, нет `attach` вовремя — 4007.
- **Таблица сеансов** решает по `decide_open_session`: тот же ключ — тот же сеанс (`reused_existing`), другая вкладка — замена, у старого сеанса код 4001.
- Посредник может умереть посреди сеанса — сеанс продолжается. Это проверяется тестом.
- Строгая политика версий (решение 86): разные `major` → `refused{incompatible_version}`, `minor` — меньшая из двух.
