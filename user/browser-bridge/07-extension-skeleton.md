# Сессия 07: каркас экстеншена Fastiplayer Bridge

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 07 плана `user/browser-bridge/`: заложи экстеншен на TypeScript — одна кодовая база, два манифеста (Chrome MV3; Firefox по решению из `results/00.md`), сборка без фреймворков и с минимумом npm-зависимостей, тесты на общих фикстурах протокола из 01, CI-задача, связь с посредником (`Hello`, версии, «плеер не найден» → страница-инструкция). Сначала прочитай `user/browser-bridge/README.md`, `results/00.md`, `results/00c.md`, `results/01.md`, `results/05.md`.

## Зачем

Решения 27–28. Каркас задаёт порядок на годы: где что лежит, как собирается, как тестируется.

## Что сделать

1. **Раскладка** (например, `extensions/browser/`):
   - `src/background/` — порт к хосту, состояние вкладок, настройки, память выбора (решение 44);
   - `src/content/` — изолированный контент-скрипт: заглушка, связь со страницей;
   - `src/page/` — MAIN-мир: перехват MSE, виртуальный элемент (09);
   - `src/popup/`, `src/options/`;
   - `src/adapters/` — пустой каркас (14);
   - `src/protocol/` — типы протокола и проверка формы.

   Раскладку утвердить в отчёте.
2. **Протокол в TS:** типы зеркалят `browser-bridge-protocol`. Тесты разбирают **те же** фикстуры из `crates/browser-bridge-protocol/fixtures/`. Если фикстура меняется, ломаются обе стороны.
3. **Сборка:** `tsc` (и, если без него никак, один маленький бандлер с обоснованием). Скрипт собирает `dist/chrome/` и `dist/firefox/` с разными манифестами из общего кода. Зависимости:
   - `typescript`;
   - тесты на встроенном `node:test` (без jest и vitest);
   - `web-ext` — только dev-зависимость для Firefox;
   - каждая — с обоснованием в отчёте. `package-lock.json` в git.
4. **Связь с хостом:** `connectNative` при старте сеанса, `Hello` с версиями, переподключение с паузами, если хост упал. Нет хоста → иконка с пометкой, попап «Fastiplayer is not connected» со ссылкой на справку.
5. **Права** (решение 47): `nativeMessaging`, `contextMenus`, `storage`, `scripting` и `host_permissions` «все сайты» — экстеншен встаёт на каждую страницу на `document_start`. Кук, `webRequest` и `cookies` нет — по решению 37 они не нужны (если 00c показала, что `webRequest` / `filterResponseData` нужен для `<video src>` в Firefox, — только он). Каждое право с обоснованием для ревью магазинов (24).
6. **CI:** задача сборки и тестов экстеншена в GitHub Actions, линт (`tsc --noEmit` со `strict`). Проверка, что `dist/` не попадает в git.
7. **Справка:** `docs/browser-bridge/` — каркас пользовательской справки (установка, Flatpak из 06).

## Тесты

- Фикстуры протокола: валидные разбираются, невалидные отвергаются с той же причиной, что в Rust.
- Логика переподключения (на фейковом порте): плеер пропал → повторы с паузами → вернулся → `Hello` снова.
- **Сквозной вручную:** экстеншен загружен в Chromium и Firefox (`web-ext run`), установлен хост из 06 — связь есть, попап показывает версию плеера. Перехват и передача — в 09 и 10.

## Поправки по итогам 00 (29.10.2026, решения 61–72)

- Firefox — MV3 (решение 71). Один манифест: `background.service_worker` для Chrome и `background.scripts` для Firefox. `browser_specific_settings.gecko.data_collection_permissions` обязателен для новых экстеншенов AMO.
- Проверено в 00 одним тестовым экстеншеном в Chromium 156, Chrome 156 (Flatpak) и Firefox 158.
- Контент-скрипт MAIN-мира: `run_at: document_start`, `all_frames`, `match_about_blank`, `match_origin_as_fallback` — в 00 опередил скрипты страницы во всех фреймах обоих браузеров.

## Поправки по итогам 00c (29.10.2026, решения 81–84)

- **Firefox MV3:** `ws://127.0.0.1` из background работает только с явным `content_security_policy.extension_pages` в манифесте.
- **Chromium:** сообщения контент-скрипт → background идут через JSON. Байты кодировать в base64 в контент-скрипте, декодировать в background перед WebSocket. Firefox передаёт `ArrayBuffer` как есть.
- WebSocket открывать **только из background**: из страницы и контент-скрипта loopback упирается в запрос Local Network Access (оба браузера) и CSP страницы (Firefox).
- Обёртка `Worker` — только при `MediaSource.canConstructInDedicatedWorker === true`. В Firefox она ломает Twitch.
- `typeof browser` не признак Firefox: в Chrome 156 глобал есть. Признак — `runtime.getBrowserInfo`.

## Поправки по итогам 01 (29.10.2026, решения 85–86)

- **TS-тесты разбирают те же фикстуры:** `crates/browser-bridge-protocol/fixtures/manifest.json` (формат — `fixtures/README.md`), включая записанные потоки. Случай `too_large` каждая сторона собирает в тесте сама.
- **Разбор в TS такой же строгий** (решение 86):
  - лишнее поле — ошибка, в том числе у «пустых» вариантов (`{"type":"attached","x":1}`);
  - массив вместо объекта — `not_an_object`;
  - виды причин — те же имена.
- Время в протоколе — целые микросекунды, скорость — тысячные доли. 64-битный порядковый номер рамки в TS — `BigInt`.
- До отправки экстеншен сам:
  - чистит заголовок страницы (управляющие символы, U+2028/2029, символы переворота направления текста) и обрезает до 1024 байт по границе символа;
  - режет `appendBuffer` на рамки ≤ 1 МиБ.

## Поправки по итогам 04d (1.11.2026, решение 152)

- **Передача байтов не должна тормозить страницу.** На стенде 04d тестовый робот копировал каждый `appendBuffer`
  (у YouTube 4K — 10+ МБ за раз) через base64 в content script, то есть на том же потоке, где работает плеер страницы. Сам
  YouTube после прыжка тогда стоял 8–10+ с, не скачав ни байта, а чистый Chromium на тех же прыжках играл через 2–5 с.
  Настоящий экстеншен передаёт байты без base64 и без тяжёлой работы на главном потоке страницы (перенос `ArrayBuffer`,
  кодирование вне страницы).
- **Приёмка:** одни и те же 10 прыжков 4K — «чистый браузер» против «браузер с экстеншеном» (время от прыжка до игры
  `<video>` страницы); с экстеншеном не медленнее чистого больше чем на шум сети.
