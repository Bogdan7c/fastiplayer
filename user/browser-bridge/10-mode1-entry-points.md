## Зачем

Решения 7–9. Первая версия, которую можно дать человеку в руки.

## Что сделать

1. **Кнопка на панели:** клик → главный поток вкладки уходит в плеер (`Handoff` = кандидат + ссылка страницы + куки по инварианту 1). Без широких прав работает через `activeTab`: клик выдаёт доступ к текущей вкладке, обнаружение (09) запускается по требованию.
   - Если поток ещё не пойман (видео не запускали), отправляется ссылка страницы → yt-dlp.
2. **Попап:** список найденного (заголовок, тип, качество, если известно, метка «ad?» / «DRM»), выбор, «Open» / «Add to queue», состояние связи с плеером, ссылка на настройки.
3. **Контекстное меню:** на `<video>` (если сайт забирает правый клик — пункт на странице вокруг), на ссылке (ссылка → yt-dlp, без открытия страницы).
4. **Кнопка поверх видео:** небольшая, появляется при наведении, не ломает вёрстку (Shadow DOM, свой слой). По умолчанию выключена или включена — спросить владельца.
5. **Настройки** (options): какие входы включены; язык — английский.
6. **Ответ плеера** виден человеку: «Opened in Fastiplayer», «Added to queue», понятная ошибка (нет плеера, DRM, сайт не поддержан).

## Тесты

- Автотест стенда (08), Chromium + Firefox: каждый вход × страницы стенда (mp4, HLS, DASH, iframe + Referer/кука, ссылка) → **кадр в рендере**. «Add to queue» → строка в очереди, играет текущее.
- Модульные: формирование `Handoff` (какие куки прикладываются, какие нет).

## Веха M1 — живая проверка

- Основная машина, KDE Wayland. **Google Chrome из Flatpak** (с инструкцией Flatseal) и **Firefox** (пакет системы).
- Эталонные сайты из 00, все входы. Таблица «сайт × браузер × вход → играет / нет → причина». Каждое «нет» — либо исправлено, либо записано как известное ограничение с причиной, либо пунктом для адаптера (15).
- Сайты с логином — в профиле владельца (решение 32), в отчёте без личных данных.
- Владелец пробует сам — его вердикт в отчёте.
