# Сессия 02: приём моста в плеере по D-Bus и запуск плеера

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 02 плана `user/browser-bridge/`: добавь в `desktop-integration` D-Bus-интерфейс моста (транспорт под ОС за нейтральным типом, как пересылка второго запуска), D-Bus activation плеера для app ID и приёмник в `app-egui`, который доставляет запросы `Handoff` в UI-поток и шлёт события обратно. Открытие медиа — заглушка с типизированным отказом до сессии 03. Сначала прочитай `user/browser-bridge/README.md` и `results/01.md`.

## Зачем

Посредник (05) должен говорить с плеером, даже если плеер ещё не запущен, и получать события обратно (позиция, закрыт, «нужен свежий поток»). Сегодняшний канал второго запуска возит только ссылки и только в одну сторону.

## Что сделать

1. **Интерфейс** `io.github.Bogdan7c.Fastiplayer.BrowserBridge1` на том же объекте и имени шины, что `org.freedesktop.Application`:
   - метод приёма сообщения протокола (байты JSON → разбор `browser-bridge-protocol` у получателя);
   - сигнал событий плеера (позиция, закрыт, «вернуть», «нужен материал»);
   - допуск — общий с `instance_forwarding/admission.rs`: только свой uid, лимиты, без управляющих символов.
   Решить с владельцем: отдельный интерфейс на том же имени (рекомендация) или отдельное имя шины.
2. **D-Bus activation.** `.service`-файл `io.github.Bogdan7c.Fastiplayer.service` (Exec — бинарь плеера, `--gapplication-service`-подобный флаг или обычный запуск) и `DBusActivatable=true` в `.desktop`. Ставит `scripts/install-desktop-entry.sh`, позже — установщик 06.
   - Проверить, что старый путь «второй запуск → первый» не сломан.
   - Если плеер запущен активацией, окно не показывается, пока не пришёл `Handoff` (или показывается — решить с владельцем по UX).
3. **Приёмник в `app-egui`** (новый модуль рядом с `instance_forwarding/`): ящик с ограниченной ёмкостью и пробуждением UI, подтверждение UI-потоком с таймаутом (как UX13), до готовности окна запросы ждут.
   - Пока `Handoff` → `Rejected(NotYetSupported)`. Реальное открытие — 03.
4. **События обратно:** у приложения появляется intent-метод «опубликовать событие моста» (позиция раз в N с, закрытие, ошибка). Владелец позиции — плеер, мост только пересылает.
5. **Швы Windows:** нейтральный trait транспорта моста в `desktop-integration`, Linux-реализация — D-Bus, у остальных ОС `UnsupportedPlatform`.

## Тесты

- Частный `dbus-daemon` (как в `instance_forwarding/linux/tests.rs`): сообщение доходит до ящика UI; чужой uid, мусор, лимиты, несовместимая версия → точные ошибки D-Bus; зависший UI → «не отвечает»; сигнал события доходит до подписчика.
- **Активация:** на частной шине с `servicedir` вызов метода запускает тестовый бинарь-заглушку, и сообщение доходит.
- Пересылка второго запуска проходит все свои старые тесты.
- **Гонки запуска:**
  - два клиента одновременно будят незапущенный плеер → ровно один экземпляр, оба сообщения доставлены;
  - ручной запуск плеера в тот же момент, что активация → один экземпляр;
  - сообщение во время завершения плеера → `ShuttingDown`, а не потеря.
- Повтор сообщения с тем же ключом идемпотентности → одно действие.
