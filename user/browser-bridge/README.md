## Зачем: одна связка — широкий круг потребностей

**Замысел владельца:** с самого начала Fastiplayer строился как крепкая основа **плеера-компаньона браузера** — сверхбыстрого и оптимизированного. Мост — это то, ради чего закладывалась основа: свои демуксеры, свои рендеры для старого железа, цветокоррекция, субтитры.

По отдельности части давно существуют:
- перехват байтов из MSE — качалки и юзерскрипты;
- подмена «этот кодек не поддерживаю» — h264ify;
- передача видео во внешний плеер — ff2mpv, «Open in mpv», но голой ссылкой.

Связки из трёх частей мы не знаем (проверить в 00c):
1. байты от живой страницы;
2. виртуальный элемент, чтобы браузер не декодировал;
3. проигрывание в нативном плеере в реальном времени, где страница остаётся «пультом» с сериями, озвучками и перемоткой.

Эта связка одной фичей закрывает потребности, для которых раньше не было решения или нужны были разные инструменты:

| Потребность | Чем закрывалась раньше | Что даёт мост |
|---|---|---|
| Старый ноутбук тормозит в браузере | ничем: терпеть или качать файл | наш декод и рендер, H.264 на старом железе |
| Сайт с антиботом или логином | ничем: во внешний плеер не передать | браузер качает сам, со своим входом |
| Сериал с озвучками | только плеер сайта | меню ♪ нашего плеера, память выбора |
| Яркость, контраст, цвет | ничем | наша цветокоррекция |
| Субтитры своим стилем | ничем | наш рендер субтитров |
| Мини-окно поверх всего | PiP браузера, на его же декоде | наш PiP |
| Батарея и шум ноутбука | ничем | замер «страница против моста» (23) покажет цифру |

Человеку не нужно знать, что такое MSE, резолвер или кодек: он нажал play как обычно — и стало лучше. От человека со старым ноутбуком до любителя сериалов с конкретной озвучкой.

Эта формулировка — основа описания в магазинах и раздела README проекта (сессия 24).

## Главная идея: браузер качает — мы играем

Плеер страницы делает всю «сетевую» работу: логин, токены, антибот, выбор качества, следующую серию. Скачанные им куски видео экстеншен перехватывает и отдаёт нашему плееру. Наш плеер только распаковывает, декодирует и показывает.

```
 сайт ──► браузер качает (свои куки, свой «почерк», антибот проходит сам)
              │
              ▼
 плеер страницы кормит видеоэлемент кусками (MSE) ──► перехват в экстеншене
              ▲                                              │
              │  «виртуальный видеоэлемент»:                 │ байты + управление
              │  страница думает, что играет,                ▼
              │  браузер ничего не декодирует        fastiplayer-browser-host — «звонок в дверь»:
              │                                              │ hello и open_session по D-Bus → порт и пропуск;
              │                                              │ всё живое — WebSocket из background прямо в плеер (82, 85)
              └── время, пауза, перемотка ◄──── браузерный режим плеера:
                                                 разбор → декодирование → рендер
```

**Почему так** (решение 37):
- антибот, Cloudflare, токены и привязка ссылок к браузеру нас не касаются: сервер видит настоящий браузер;
- никаких кук и секретов у плеера;
- YouTube работает так же, как остальные сайты;
- следующая серия, качество и озвучка — забота плеера страницы.

Канал дешёвый: возим сжатое видео (на эталоне 0,1–1 МиБ/с, всплески после перемотки до 5 МиБ/с), а не кадры. Тяжёлая работа — декодирование и показ — остаётся у нас, а ради неё всё и делается.

## Режимы

1. **По клику.** Кнопка экстеншена (база), правый клик по видео, правый клик по ссылке (ссылка открывается в фоновой вкладке), кнопка поверх видео.
2. **Автозапуск.** Человек нажал play на странице — видео уходит в наш плеер, на месте видео заглушка.
3. **Плеер в странице.** Наш плеер визуально встаёт на место веб-плеера. Вердикт 00b: «Наклейка» на KDE, GNOME (через наше расширение) и X11, «Театр» — везде (решения 77–79).

Вход PiP: кнопка «Картинка в картинке» на сайте открывает наш плеер мини-окном. Исследуется вместе с режимом 3.

DRM в план не входит и не войдёт: страницы с защитой экстеншен не трогает.

## Идея «Наклейки»: плеер, который выглядит частью страницы

**Идея владельца** (решения 74–76), проверена прототипом в разведке 00a.

### Стена

Встроить картинку нашего плеера внутрь страницы нельзя:
- у браузера нет API, через которое чужой процесс рисует в страницу без копирования кадров;
- последними это умели плагины NPAPI и Flash, их убрали из всех браузеров (решение 49).

Значит, режим 3 «плеер в странице» в лоб не сделать.

### Смена вопроса

Вместо «как встроиться в страницу» — «что человек должен **увидеть**». Ему не важно, кто рисует видео. Ему важно, чтобы плеер стоял на своём месте, ехал вместе со страницей и исчезал за краем так же, как родной.

Поэтому мы не встраиваемся, а создаём **иллюзию встраивания**:
- страница рисует своё;
- наше окно без рамки лежит ровно поверх видео;
- человек видит один плеер и ощущает, будто плеер сайта подменили.

### Одно правило

**Окно = видимая часть родного плеера страницы.**

- Пока видео целиком на экране, окно размером с видео и едет вместе со страницей.
- Когда видео уходит за край области страницы (вверх, вниз, вбок), окно «съедает» эту сторону. Картинка внутри **обрезается, а не сжимается**, и каждый пиксель видео остаётся там, где был бы на странице.
- Видео ушло целиком, вкладку сменили, браузер перекрыт — окно прячется.
- **Край экрана режет так же, как край области страницы** (находка 00b). Видимая часть = видео ∩ область страницы ∩ рабочая область экрана. Иначе окно хочет встать частично за экраном, композитор прижимает его к краю, и картинка съезжает с видео.

Особых случаев нет: прокрутка в любую сторону, ресайз и перетаскивание окна браузера, панели браузера — всё это одна формула пересечения прямоугольников.

```
 страница прокручена вниз:       видимая часть      наше окно
 ┌─[вкладки, адрес]──────┐
 │ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  │  ← верх видео        ┌────────────┐
 │ ███ видно █████████   │    ушёл за край  →    │ ██ нижняя  │
 │ ███████████████████   │                       │ ██ часть   │
 │ комментарии           │                       └────────────┘
 └───────────────────────┘                       обрезка, не сжатие
```

### Кто чем владеет

- **Экстеншен — единственный источник геометрии.** Где видео во вкладке, что видно, зум, прокрутка, видимость вкладки. Начало области страницы в окне браузера он калибрует по событию мыши: формула по размерам окна ошибается.
- **Рендер плеера обрезает кадр** (решение 76): «какую часть кадра показать» — обычный параметр границы `RenderShell`, одинаковый для wgpu и GLES2. Это фича плеера, она пригодится и Fasticut.
- **Окно отвечает только за свой размер и место.**
- **Тонкий бэкенд стола ставит окно в точку экрана** и сообщает плееру то, что знает только композитор: положение окна браузера и рабочую область экрана. На Wayland клиент сам этого не может: KDE — KWin-скрипт или `layer-shell` (выбор в 17, решение 78), GNOME — наше расширение GNOME Shell (решение 77), X11 — само окно (край экрана — монитор winit). Переносимость — задача 17.

### Что доказано (00a, KDE, Chromium и Firefox)

- В покое наше окно совпадает с плеером страницы пиксель в пиксель.
- При прокрутке окно отстаёт:
  - 1–3 кадра через KWin-скрипт;
  - стабильно 1 кадр через `layer-shell` (но слой висит над всеми окнами);
  - 0–1 кадр на X11.
- Работают прокрутка вбок, ресайз и перетаскивание окна браузера, перекрытие чужим окном, смена рабочего стола, PiP «поверх всех».

### Что доказано в 00b (GNOME, Xfce, KDE при масштабе 1,25)

- **GNOME 51:** без расширения окно в точку не поставить — подтверждено. С нашим расширением GNOME Shell «Наклейка» отстаёт на 0–1 кадр (Chromium), меньше кадра (Firefox); от страницы до сдвига окна 2 мс. Работают ресайз, живое перетаскивание, край экрана, перекрытие, смена стола, «Театр», PiP «поверх всех».
- **Xfce X11 на T410:** окно ставит себя само, в покое 0 px, при прокрутке 0 кадров. Но без помощника браузер при клике встаёт поверх нашего окна — нужен `WM_TRANSIENT_FOR` (17).
- **KDE на T480s при масштабе 1,25:** в покое 2 px, край экрана и нижняя панель режут правильно.

### Что ещё не доказано

- **Цена настоящего рендера при смене размера окна на каждом кадре.** Прототип рисовал тестовый узор на CPU. Замер против `wp_viewporter` — в 17, на 780M и T410.
- **Порядок окон на X11 через `WM_TRANSIENT_FOR`** — в 17.
- **Живые сайты:** меню страницы над видео уходят под наше окно. Нужны свои контролы и адаптеры (14, 20).

**Уточнение главной идеи (28 октября 2026, тот же день)**

37. **Браузер качает — мы играем.** Экстеншен перехватывает байты, которые скачал браузер, и отдаёт их плееру. Ни резолверов, ни передачи адресов, ни yt-dlp в мосте, ни кук. Слова владельца: так не срабатывает антибот, меньше хаков, шире совместимость, и решается YouTube.
38. **Браузерный режим плеера — одно видео из живой вкладки, без очереди.** Следующую серию ведёт плеер страницы. Очередью ради этого жертвуем сознательно.
39. **Виртуальный видеоэлемент.** Плеер страницы думает, что играет, и качает дальше, но браузер ничего не декодирует и не показывает. Время, паузу, скорость и перемотку ему подсовываем мы. Прототип и вердикт — отдельная разведка **00c** до протокола.
40. **Новое видео из другой вкладки заменяет текущее.** Старая вкладка получает свой плеер обратно на той же секунде и на паузе.
41. **Браузерный режим — второе окно и отдельный процесс.** Обычная очередь плеера не трогается: обычное окно ставится на паузу. Браузерный режим ничего не хранит: ни истории, ни позиции (её помнит сайт), ни очереди. Инкогнито этим решается само.
42. **Вкладка ушла** (закрыли, ушли на другую страницу, закрыли браузер) — плеер доигрывает то, что уже скачано, показывает «Source tab closed» и закрывает окно.
43. **«GLES2 → H.264» включается автоматически** по возможностям плеера. Плюс переключатель в экстеншене: auto / always H.264 / off. Кодек выбирается до старта видео.
44. **Память выбора озвучки, качества и субтитров — в экстеншене,** по сайту и сериалу. В инкогнито не пишется. Стирается вместе с данными браузера.
45. **Правый клик по ссылке** открывает её в фоновой вкладке, запускает видео и передаёт его нам. Работает там, где страница сама запускает видео, или где есть адаптер.
46. **Окно браузерного режима:** без панели очереди, но **с настройками и инфо-панелью**. Настройки общие с обычным плеером и пишутся в тот же config: это настройки, а не история просмотра.

**Самопроверка плана (28 октября 2026, тот же день)**

47. **Доступ ко всем сайтам — при установке.** Экстеншен встаёт на каждую страницу раньше плеера сайта: надёжный перехват с самого начала потока, подмена кодеков (43) и ссылки в фоновой вкладке (45) работают везде. Риск строгого ревью Chrome Web Store принят. Заменяет решение 31.
48. **После браузерного сеанса обычный плеер остаётся на паузе.**

50. **Длина ролика неизвестна** (live, плеер сообщает позже) — режим 2 передаёт сразу, остальные фильтры работают.
51. **Возврат на страницу:** по кнопке «Return» — видео на странице играет дальше; при закрытии нашего плеера или замене из другой вкладки — на паузе.
52. **Заглушка — всегда**, в режиме 1 тоже.
53. **Кнопка поверх видео по умолчанию выключена.** База — кнопка на панели браузера.
54. **Субтитры, включённые на странице, включаются и у нас.** Иначе — память экстеншена (44), дальше наш автовыбор по языку.
55. **Превью на таймлайне** в браузерном режиме — только над уже скачанной частью, дальше только время. Страницу ради превью не дёргаем.
56. **Процесс браузерного режима выходит сразу** после конца сеанса.
57. **«Театр»: вкладку сменили или браузер свернули** — плеер прячется, звук идёт; вернулись — показывается.
58. **Зона хоткеев в режиме 3 настраивается:** вся страница кроме полей ввода (по умолчанию) или только зона видео.
59. **Переход на следующую серию полной перезагрузкой страницы:** если в той же вкладке за пару секунд появилось видео того же сайта — продолжаем в том же окне, фуллскрин не слетает. Другой сайт или страница без видео — решение 42.
60. **Браузерный режим — тот же бинарь** с ключом `--browser-session`.

    - YouTube: видео, микс со следующим роликом, live, Shorts, субтитры, несколько дорожек звука;

62. **Плееры Ashdi (ashdi.vip) и Tortuga (tortuga.tw) допущены.** Публично их происхождение не установлено, решение принято по знанию владельца. **eneyida.tv исключён:** у него плеер семейства HDVB.
63. **MSE в воркере — обязательный случай для Chrome.** Twitch держит `MediaSource` в Dedicated Worker (`MediaSourceHandle`), хук главного потока там слеп. Экстеншен оборачивает `Worker`/`SharedWorker` и внедряет хук в воркер. Firefox MSE в воркере не поддерживает.
64. **Нативный HLS в Chrome.** Chrome 156 играет m3u8 прямо в `<video src>`, и DW так и делает, минуя MSE. Экстеншен отвечает `""` на `canPlayType` и `isTypeSupported` для HLS, чтобы плеер страницы ушёл в MSE (hls.js). Что делать со страницами, которые всё равно отдают m3u8 в `src`, решает 00c.
65. **Признак DRM — `setMediaKeys` с ключами или событие `encrypted` на элементе.** Опрос `requestMediaKeySystemAccess` признаком не считается: Shaka Player опрашивает 11 систем и без DRM-контента. Уточняет инвариант 4.
66. **Реклама — часть потока, а не помеха.**
    - На Ashdi и Tortuga преролл крутится в отдельном `<video src=mp4>` перед фильмом, перед каждой серией и после смены озвучки.
    - На YouTube реклама идёт через тот же элемент новым MediaSource.

    Экстеншен рекламные элементы не передаёт, а смену MediaSource считает новым поколением потока.
67. **Смена серии или озвучки — новое поколение потока** на том же элементе: новый MediaSource, новые init-сегменты. Ashdi после смены озвучки начинает с 0, поэтому адаптер возвращает позицию сам.
68. **Главное видео ищется с учётом shadow DOM и видимости.** На archive.org `<video>` лежит в shadow root. Скрытый плеер Ashdi продолжал играть после переключения вкладки плеера.
69. **Посредник и установка.**
    - Хост сам выходит по EOF stdin: при закрытии браузера его никто не убивает.

    - Flatpak: хост живёт в папке песочницы, право — `talk-name=io.github.Bogdan7c.Fastiplayer.*`. Хост собирается под glibc рантайма браузера.
70. **Брендированный Chrome в автотестах** грузит экстеншен через CDP `Extensions.loadUnpacked` (`--enable-unsafe-extension-debugging`). Проверено на Chrome 156 из Flatpak.
71. **Firefox — MV3, один манифест на оба браузера** (`background.service_worker` + `background.scripts`).
72. **Блокировщик рекламы — обязательный случай** (решение владельца). Проверки:
    - с блокировщиком плеер страницы стартует без преролла;

    Проверяется в 00c, 08, 09, 21a, 22 на uBlock Origin (Firefox) и uBlock Origin Lite (Chrome).

## Архитектура (утверждена владельцем в сессии 01, решения 85–86)

**Кто чем владеет**

- **Экстеншен.** Перехват байтов (MSE, `<video src>`), виртуальный видеоэлемент, заглушка и возврат, адаптеры сайтов (озвучки, качество, серии, субтитры), память выбора (решение 44).
- **`browser-bridge-protocol`** (crate создан в 01, только типы и разбор). Участок «вход» (`hello`, `open_session`, пропуск или отказ) и участок «сеанс» (MSE-события по SourceBuffer, поколения, перемотка, часы, команды, события страницы, двоичная рамка куска). Версия, лимиты, сторож поколений, общие фикстуры для Rust и TS.
- **`fastiplayer-browser-host`** (новый бинарник). «Звонок в дверь» (решение 85): рамки native messaging, проверка отправителя, `hello` и `open_session` в D-Bus, ответ с портом и пропуском WebSocket. Ни байтов, ни команд сеанса через него нет. Медиа не понимает.
- **`desktop-integration`.** D-Bus-интерфейс браузерного режима: транспорт под ОС, общий допуск с пересылкой второго запуска. Готово в 02: `browser_session_entry` (служба, клиент `BrowserEntryClient`, `.service`), `player_pause`.
- **`browser-bridge-session`** (создан в 02). Пропуска, таблица сеансов с номером экземпляра, стойка входа (`hello`, `open_session`), сервер WebSocket на `127.0.0.1`, сторож поколений, швы `SessionByteSink` и `SessionEventSink`, машина «когда выходить». Без UI и D-Bus, на любой ОС.
- **Источник «байты из браузера»** — свой crate `pushed-media-source` (решение 90). Полка по времени, разбор сегментов существующими демуксерами, обратное давление (оно же — «сколько буфера» виртуального элемента), перемотка на полке или запросом к странице (решение 95).
- **Браузерный режим плеера.** Отдельный процесс со своим окном: без панели очереди, с настройками и инфо-панелью (решение 46). Композиция поверх `player-core` и рендеров, без записи state просмотра.
- **Управление окном** (режим 3 и PiP) — отдельный crate с нейтральным trait и бэкендами по композитору. Форма — по вердикту 00b.

**Инварианты, которые нельзя нарушить**

1. **Страница — враг.** Всё, что пришло со страницы (байты, время, события), проверяется на форму и лимиты. Битые байты — это ошибка разбора одного видео, а не падение плеера. Страница не может заставить плеер открыть файл, адрес или что-то кроме своих байтов.
2. **У плеера нет секретов.** Ни кук, ни заголовков, ни адресов потоков. Подписи в UI — домен страницы и заголовок.
3. **Посредник тонкий и недоверчивый.** Принимает только наш ID экстеншена, проверяет размер и форму каждого сообщения, а плеер повторно проверяет всё сам. Посредник может умереть в любой момент, и плеер от этого не падает.
4. **DRM не трогаем.** К элементу привязаны ключи (`setMediaKeys`) или пришло событие `encrypted` — экстеншен этот элемент не перехватывает (решение 65). Один опрос `requestMediaKeySystemAccess` признаком DRM не считается.
5. **Протокол версионирован.** Старый экстеншен с новым плеером (и наоборот) получает понятный отказ «обновите», а не тихую поломку.
6. **Каждый запрос идемпотентен, каждый поток данных знает своё поколение.** Повтор того же запроса не создаёт второго окна. Поколение — новый `MediaSource` (реклама, ролик, серия, озвучка). Байты старого поколения молча отбрасываются и не попадают в новое. Перемотка — событие, а не поколение: она ничего не выбрасывает, разрыв времени приёмник видит по меткам времени в байтах (уточнено в 01: пометить кусок «до» или «после» перемотки точно нельзя, у Twitch `MediaSource` живёт в воркере).
7. **Браузерный режим не пишет на диск ничего о просмотре** (решение 41). Настройки — можно (решение 46).
8. **Пользовательский текст** — английский (`mem:app-egui/user-facing-language`).

## Общие правила сессий

Работай в корне checkout-а. Сначала `AGENTS.md`. Перед работой:
- Serena: `initial_instructions`, активация, `mem:core`, `mem:browser-bridge/core` (после сессии 00), плюс memories из конца файла сессии.
- **Context7** — для API экстеншенов (Chrome Extensions, MDN WebExtensions, Media Source Extensions), `zbus`, `serde_json` и всего, что правится. Для поведения браузеров источник истины — документация производителя и живой браузер, а не память модели.
- Широкий поиск по репозиторию — read-only субагентом (модель Sonnet). Основной агент читает только точные символы.

Код:
- новые границы — по архитектурным правилам `AGENTS.md` (кто владеет, intent-методы, focused-тесты на отсутствие, ошибку, учёт и «не трогает чужое»);
- файлы ≤ 800 строк, новые фичи — в новых модулях;
- npm-зависимость добавляется только с обоснованием в отчёте (кто автор, размер, нужна ли вообще). Это то же правило, что auto-memory владельца «no unaudited big crates».

Тесты:
- **тест проверяет результат, а не вызов** (`AGENTS.md`);
- сквозной тест моста доказывает, что **кадр дошёл до рендера**, а не только что сообщение принято;
- живые сайты меняются, поэтому автотесты опираются на свой стенд (08), а живые сайты проверяются на вехах и в приёмке.

Машины:
- T410 и T480s — по ssh (`ssh t410`, `ssh t480s`), команды на них одобрены владельцем;
- **замеры и GUI — только когда владелец отдал машину**. Длительность называется заранее и не превышается (auto-memory владельца «measurement duration»);
- на T480s стоит GNOME, на T410 — Xfce (решение 80). Вход в нужный сеанс на экране входа делает владелец; после работы в чужом столе — проверка, что KDE цел.

Отчёты `results/NN.md`: статус, SHA, решения владельца, что сделано, доказательства (тесты, живые прогоны), известные ограничения, обновлённые memories.
- В `user/` только Markdown.
- Никаких личных путей, имён хостов, логов, ссылок, истории браузера и имён аккаунтов. Сырые данные — в scratchpad.

Git: работа в `main`. Коммит — в конце сессии после зелёных проверок, сразу после коммита — push (auto-memory владельца «commit then push»). Если в это время в репозитории работает соседняя сессия, коммитятся только свои пути (`git commit -- <пути>`), а перед push проверяется, что не уходят чужие коммиты.

## Известные технические факты (разведка планирования, 28.10.2026)

Помечены уровнем доверия: **[П]** — подтверждено источником, **[Р]** — из памяти модели, проверить в разведке. После сессии 00 у каждого факта стоит итог: **[00: подтверждено]**, **[00: уточнено]** или **[00: не проверялось → …]**.

- **MSE:** большинство современных плееров (YouTube, Twitch, hls.js, dash.js, Shaka, Video.js) кормят видеоэлемент кусками через `MediaSource` / `SourceBuffer.appendBuffer` — обычно fMP4 или WebM, отдельно видео и звук. Хук `appendBuffer` в MAIN-мире видит ровно эти байты. [Р] **[00: уточнено]**
  - Подтверждено на YouTube, Twitch, PeerTube, Ashdi, Tortuga и dash.js.
  - У PeerTube и Twitch live звук и видео лежат в одном SourceBuffer.
  - YouTube режет куски посреди бокса: байты склеиваются по каждому SourceBuffer.
  - Исключения — нативный HLS (решение 64) и MSE в воркере (решение 63).
- **MSE в фоновом потоке** (MSE-in-Worker, Chrome 108+): хук главного потока его не видит, нужно перехватывать внутри воркера. Кто из эталонных сайтов так делает — 00. [Р] **[00: подтверждено — Twitch live и запись]**
- **`<video src=…mp4>`** браузер качает сам, и JS эти байты не видит. Firefox умеет читать ответ (`filterResponseData`). В Chrome экстеншен скачивает тот же файл через сеть браузера, `fetch` из контекста страницы, — это тоже «качает браузер». [Р/П] **[00: подтверждено]** Такие сайты есть в эталоне: MDN, archive.org, клипы Twitch, рекламные прероллы. Способ скачивания проверяет 00c.
- **Фоновые вкладки:** Chrome замедляет таймеры скрытых вкладок, через 5 минут — сильнее (intensive throttling). Memory Saver может выгрузить вкладку целиком. Звучащие вкладки от этого защищены, а наша страница молчит. Это ключевой риск для 00c. [Р] **[00: не проверялось → 00c]** **[00c: риск не подтвердился]** Таймеры скрытой страницы в Chromium — раз в минуту, но YouTube и Twitch качают по сетевым событиям: 13 минут фона (вкладка и свёрнутое окно) без остановок в обоих браузерах. Время муляжа — от `performance.now()`, события — по тикам через порт экстеншена. Memory Saver вкладку не выгрузил (включился ли — не доказано). Документация Chrome подтверждает условия intensive throttling: скрыта > 5 мин, тишина ≥ 30 с, нет WebRTC.
- **Native messaging:** JSON по stdio. От хоста к браузеру — до 1 МБ на сообщение; от браузера к хосту — больше, но байты придётся кодировать в base64 (+33 %). `connectNative` держит процесс хоста, пока открыт порт. Альтернатива для данных — свой локальный канал; выбор — по замеру 00c. [Р] **[00: подтверждено и уточнено]** **[00c: выбран WebSocket из background, решение 82]** Chromium передаёт сообщения контент-скрипт → background через JSON (`ArrayBuffer` → `{}`), Firefox — structured clone. Loopback из страницы и контент-скрипта упирается в Local Network Access, background освобождён.
  - От хоста — ровно 1 048 576 байт.
  - От браузера: в Chrome 64 МиБ; Firefox пропустил и 130 МиБ.
  - Канал браузер → хост с base64 даёт 200–475 МиБ/с.
- **Chrome MV3:** блокирующего `webRequest` нет, фоновый service worker засыпает (открытый порт native messaging его держит). Контент-скрипты во всех фреймах, MAIN-мир на `document_start`. [Р] **[00: подтверждено]**
  - Открытый порт держит service worker больше 6 минут простоя.
  - Хук MAIN-мира опережает инлайн-скрипт `<head>`, чужой iframe, синхронный `about:blank` и `srcdoc`. В воркеры он не попадает.
- **Firefox** сохраняет блокирующий `webRequest` и `filterResponseData`. [П]
- **Брендированный Google Chrome с версии 137** не грузит экстеншен ключом `--load-extension`. Автотесты — на Chromium / Chrome for Testing и Firefox (`web-ext`), брендированный Chrome — руками на приёмке. [П] **[00: уточнено]** CDP `Extensions.loadUnpacked` работает на брендированном Chrome 156 (решение 70).
- **Flatpak:** штатного портала native messaging в стабильных выпусках нет. Гипотеза для 00: хост лежит в доступной песочнице папке, говорит с плеером по D-Bus и запускает его через D-Bus activation. Тогда Flatseal нужен только на «папка + имя на шине». [Р] **[00: подтверждено вживую на Chrome из Flatpak]**
  - Firefox 157+ умеет `xdg-native-messaging-proxy`, но во Flatpak-сборке Firefox он ещё не включён.
- **Wayland:** окно не может само встать в точку экрана относительно чужого окна.
  - KDE: KWin-скрипты и правила, `wlr-layer-shell`.
  - GNOME: ничего, кроме расширения GNOME Shell.
  - X11 позволяет.

  [Р] **[00a: уточнено]** На KDE Wayland абсолютную геометрию всех окон отдаёт KWin-скрипт, и он же двигает наше окно (долгий опрос по D-Bus): в покое пиксель в пиксель, при прокрутке 1–3 кадра. `layer-shell` ставит себя сам одним commit (1 кадр), но висит над всеми окнами. На X11 окно ставит себя само: 0–1 кадр. Начало области страницы в окне — только по событию мыши.

  **[00b: подтверждено]** GNOME 51 без расширения ставит новое окно по центру; расширение Shell (`move_resize_frame`, `get_buffer_rect`) даёт 0–1 кадр. Ловушки mutter: окно вне списка окон не сворачивается, `unmake_above()` поднимает окно наверх слоя, «положить сразу над другим окном» расширению недоступно, код расширения перечитывается только при перелогине. Mutter не пускает обычное окно за край экрана. Xfce X11: 0 кадров даже на T410, порядок окон без `WM_TRANSIENT_FOR` не держится.
- **Подмена кодеков** (`MediaSource.isTypeSupported` / `canPlayType` / `mediaCapabilities`): так работает известный экстеншен h264ify. YouTube тогда отдаёт H.264. [Р] **[00: не проверялось → 00c / 13]**
  - YouTube до старта делает 29–40 запросов `isTypeSupported`.
  - В Chromium на основном ПК YouTube выбирает AV1.
  - Последний выпуск h264ify — 2019 год.

## Контекст, который нельзя потерять

- Плеер — движок будущего редактора Fasticut (auto-memory «product goals»). Браузерный режим — композиция поверх ядра, а не изменение его поведения для обычных файлов.
- Швы под Windows — как у рендера (auto-memory «future platforms render seam»): транспорт D-Bus за нейтральным trait, у Windows будет named pipe и реестр вместо файлов подключения.
- В README проекта фичу подавать привлекательно, но честно, со скриншотом (auto-memory «README feature pitch»).
- Качество выпуска важнее скорости: без «детских болячек» у первых пользователей (auto-memory «release quality priority»).
