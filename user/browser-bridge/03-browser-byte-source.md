# Сессия 03: источник «байты из браузера»

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 03 плана `user/browser-bridge/`: источник медиа, который питается потоком из канала данных (02) — дорожки, init-сегменты, медиасегменты с поколениями — и отдаёт их существующим демуксерам (fMP4, WebM, MPEG-TS) в `player-core`. Ограниченный буфер, обратное давление (оно же сообщает странице «сколько буфера»), перемотка как запрос к странице, смена кодека и разрывы, конец потока. Сначала прочитай `user/browser-bridge/README.md`, `results/00c.md`, `results/01.md`, `results/02.md`.

## Зачем

Это сердце решения 37: из чужих кусков сделать то, что наш конвейер умеет играть. Образец — сегментный вход DASH (init + медиасегменты), но с важным отличием: качает не мы, мы только ждём.

## Что сделать

1. **Владелец и место:** новый модуль в `media-source-open` или свой crate — решить с владельцем по размеру. Нейтральный к браузеру: «сегменты извне с поколениями», чтобы годился и для будущих источников.
2. **Разбор:** видео и звук приходят отдельными `SourceBuffer` → отдельные дорожки. Собрать их в источник с двумя элементарными потоками на существующих демуксерах. `changeType` (смена кодека посреди потока) и новый init-сегмент (смена качества, серия) → пересоздание декодера по существующим правилам смены спецификации.
3. **Время:** время берётся из сегментов (`tfdt`, кластеры WebM), смещения `timestampOffset` из MSE учитываются. Разрывы и дыры — по правилам `player-core` (ожидание, а не скачок).
4. **Буфер и обратное давление:** ограниченный буфер вперёд (настройка с разумным умолчанием). Источник публикует «буферизовано до T», виртуальный элемент (09) отдаёт это странице как `buffered`, чтобы плеер страницы качал ровно столько, сколько нужно.
5. **Перемотка:** seek в нашем плеере → новое поколение → команда странице «seek на T» → старые сегменты отбрасываются, ждём новые (Buffering, спиннер). Перемотка внутри буфера — без запроса.
6. **Конец:** `endOfStream` → обычный EOF. «Вкладка ушла» → доиграть буфер, затем событие для окна (04, решение 42).
7. **Ограничения режима:** превью кадров на таймлайне (frame-server) требует случайного доступа к файлу. В браузерном режиме оно строится только из уже полученного буфера, дальше — только время (решение 55).

## Тесты

- **Сквозной:** запись потока со стенда (fMP4 видео + звук отдельно, как от MSE) подаётся в канал данных → **кадры доходят до рендера**, звук идёт, A/V синхронны.
- WebM-поток (VP9 + Opus) и MPEG-TS — так же.
- Перемотка: старые сегменты после seek отброшены (кадров из старого поколения на экране нет), новые играют с T ± 1 кадр.
- Смена качества посреди потока (новый init-сегмент, другое разрешение) и `changeType` (H.264 → VP9) без остановки.
- Обратное давление: при полном буфере источник не растёт по памяти, «буферизовано до» не убегает вперёд.
- Битые байты от страницы → ошибка одного сеанса, процесс жив (инвариант 1).

## Поправки по итогам 00c (29.10.2026, решения 81–84)

- Вход источника — рамки WebSocket (решение 82), по SourceBuffer, fMP4 или WebM, нарезка любая, бывает звук и видео в одном SB.
- Держать до ~2 минут вперёд: YouTube в фоне — 118 с, Tortuga — 120 с.
- Метка разрыва после перемотки: без неё время немонотонно.
- **Init-сегмент с `encv`/`enca`/`tenc`** — честный отказ «защищённое видео» (Vimeo шифрует CENC, а событие `encrypted` не приходит).

## Поправки по итогам 01 (29.10.2026, решения 85–86)

- **Вход источника** — `PageSessionMessage` и двоичные рамки (`decode_data_frame`) из `browser-bridge-protocol`. Каждое сообщение и каждая рамка проходят через `StreamGate` **до** демуксера:
  - устаревшее поколение — молча выбросить;
  - нарушение — закрыть сеанс кодом 4003.
- **Перемотка не выбрасывает байты.** `seek_started` — событие, сброс разбора — отдельное `source_buffer_aborted`. Разрыв времени видно по меткам времени в байтах, как в MSE браузера (уточнение инварианта 6).
- Учитывать `timestamp_offset_changed`. Шифрование в init-сегменте — ответ `stream_rejected{protected_content}`. Обратное давление — `buffer_state{intake: full}`.
- Готовый вход для тестов «до кадра» — записанные потоки `crates/browser-bridge-protocol/fixtures/streams/`:
  - два SourceBuffer fMP4 (H.264 + AAC) с разрезами посреди боксов;
  - смена поколения с хвостом рекламы;
  - WebM VP9 + Opus в одном SourceBuffer с перемоткой назад.

## Поправки по итогам 02 (29.10.2026, решения 87–89)

- Приёмник байтов — trait `SessionByteSink` из crate `browser-bridge-session` (`accept(SessionChunk)`, `session_ended`). В 02 его место занимает заглушка `CountingByteSink`: она считает байты и выбрасывает их. Источник 03 подставляется в `crates/app-egui/src/browser_session/mod.rs` вместо неё.
- Сторож поколений уже стоит в сервере. До приёмника доходят только байты текущего поколения, по порядку, по каждому SourceBuffer.
- Рамки `<video src>` (вид 2) сторож не проверяет. Источник сам сверяет их с выданными `fetch_range` и чужие отвергает (`stream_rejected`).
- Сообщения страницы приходят в ящик процесса (`BrowserSessionInbox`, очередь 256). В 02 главный цикл их только считает.
- **`tab_gone` сейчас закрывает сеанс сразу (4002), и процесс выходит.** Решение 42 («доиграть скачанное») требует, чтобы машина `ProcessLifecycle` ждала конца воспроизведения: событие «буфер доигран» от источника и окна (03–04).
- Обратное давление «полон» уходит странице через `SessionControl::send_to_page(buffer_state)`.
