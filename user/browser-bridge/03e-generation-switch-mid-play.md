# Сессия 03e: смена поколения потока на ходу (новый `MediaSource`)

Решение 110. Находка живой приёмки 03d, общий бэклог п. 26.

> Выполни сессию 03e плана `user/browser-bridge/`: процесс браузерного режима переживает любую смену `MediaSource` посреди просмотра — ручную смену качества YouTube, рекламу, следующую серию. Сначала прочитай `user/browser-bridge/README.md`, `results/03b.md`, `results/03d.md`, этот файл.

## Проблема

Живой прогон 03d на YouTube показал: ручная смена качества в меню плеера страницы — это **новый `MediaSource`**, то есть новое поколение потока (решения 66, 67), а не новый init в том же SourceBuffer. Так же устроены реклама YouTube (решение 84) и следующая серия на многих сайтах. Это главный путь моста.

Что видно (YouTube, обычный ролик, безголовый стенд 03b, смены качества через API плеера страницы):

| Смена | Поколение | Итог |
|---|---|---|
| 480p → 144p | 3 | чисто: плеер перемотался на позицию страницы (12,8 с) и играет дальше |
| 144p → 720p | 4 | процесс стоит в `Buffering` на позиции **0**, кадров нет |
| 720p → 360p | 5 | позиция идёт (1,36 с), кадров нет, звук встал |
| 360p → 480p | 6 | снова `Buffering` на 0 |

Итог прогона: 879 кадров за 75 с вместо ~2000, после второй смены — ни одного.

**Доказано:** сборка до 03d (`70db7a8f`) ведёт себя так же (883 кадра, те же поколения). Это путь «новое поколение» из 03b, не эстафета 03d.

## Что уже известно о коде (снимок на HEAD `5987b161`)

- Сообщение страницы `generation_started { generation }` (`browser-bridge-protocol`, `session/page.rs`) **не несёт позицию страницы**.
- Процесс грузит новое поколение (`app-egui/src/browser_session/session_media.rs`, `load`) с начала: `LoadStart::Playing/Paused`, без стартовой позиции.
- У поколения 3 в журнале есть «перемотка на 12 801 мс»: похоже, YouTube в тот раз сам выставил `currentTime`, и пришёл `seek_started{page_seek}`. У поколений 4–6 такой перемотки нет, плеер ждёт данные с нуля, а страница кладёт байты с 27 с и дальше.
- На каждом поколении процесс заново просит бэкенд видео («Active video backend does not pull stream; seamless backend reselection requested»): декодер не переживает смену media. Нужно выяснить, почему у поколения 5 позиция идёт, а кадров нет.
- Сырые журналы прогонов (с 03d и до 03d) и стенд с командой робота `yt_quality` сохранены вне git: `target/03e-evidence/`, `target/browser-bridge-rig/`. Если их нет (`cargo clean`), прогон `run03d.sh` повторяет всё за 2 минуты.

Это гипотезы для разведки, а не диагноз.

## Что сделать

1. **Воспроизвести без живого сайта.**
   - Записать с живого стенда поток сеанса: сообщения и куски байтов, три смены `MediaSource` подряд, как в протоколе 01.
   - Сделать из записи общую фикстуру и сквозной тест процесса браузерного режима «три смены поколения подряд доходят до кадра». Тест обязан падать на текущем коде.
2. **Найти причину** для каждого из двух симптомов: «стоит на 0» и «позиция идёт, кадров нет». Чинить причину, а не симптом.
3. **Архитектуру — владельцу до кода.** Кто знает, с какой позиции стартует новое поколение?
   - Страница: поле позиции в `generation_started`. Протокол 1.0 можно дописать, экстеншена ещё нет — так сделали в решении 101.
   - Последние часы страницы, которые процесс уже получает.
   - Время первой коробки на полке нового поколения.

   Что делать, если страница начинает новое поколение не с текущей позиции (реклама с нуля, следующая серия)?
4. **Смена поколения не должна пересоздавать декодер без нужды**: тот же кодек на том же бэкенде — без нового запроса бэкенда.

## Тесты

- Сквозной «до кадра» по записанной фикстуре: три смены `MediaSource` подряд, после каждой кадры идут с позиции страницы, звук не встаёт, время не идёт назад.
- Новое поколение, начатое страницей с нуля (реклама, следующая серия): плеер стартует с нуля, а не с прежней позиции.
- Новое поколение во время паузы страницы, во время перемотки, сразу после `end_of_stream` старого.
- Мутации: без стартовой позиции тест «три смены» падает.

## Живая проверка

Стенд 03b с роботом `yt_quality`, прогон `run03d.sh` (около 75 с, четыре смены качества). Ожидание по журналу:
- кадров ≈ 30 к/с × время;
- `position_regressions=0`;
- после каждой смены `presented_frames` растёт в течение 5 с.

Плюс одна смена с рекламой YouTube, если она попадётся.
