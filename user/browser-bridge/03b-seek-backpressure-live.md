# Сессия 03b: источник — перемотка, обратное давление, живой прогон

Общий замысел — [03-browser-byte-source.md](03-browser-byte-source.md), ядро — [03a](03a-pushed-source-core.md).

> Выполни сессию 03b плана `user/browser-bridge/`: перемотка, обратное давление и переходник протокола для crate `pushed-media-source`, живой прогон YouTube без окна. Сначала прочитай `user/browser-bridge/README.md`, `results/03a.md`, этот файл.

## Что сделать

1. **Полка.** Источник помнит время начала каждой коробки (`tfdt` fMP4, `Timecode` кластера WebM) и держит ограниченное окно уже полученного: около 2 минут вперёд плюс немного назад. Потолок в байтах.
2. **«Буферизовано до» и «полон».** Источник публикует запас вперёд в секундах видео. Переходник шлёт странице `buffer_state{ahead_us, intake}` через `SessionControl::send_to_page`. Порог «полон» и потолок памяти — настройки с разумным умолчанием (около 120 с, YouTube в фоне — 118 с, Tortuga — 120 с).
3. **Перемотка** через порт перемотки по квитанциям `player-core` (`PreparedDemuxSeekPort`):
   - T на полке — новый эпизод с коробки, где лежит T; страницу не трогаем;
   - T вне полки — команда странице `seek{seek_id, target_us}`, Buffering; коробки, которые кончаются раньше T, выбрасываются, пока не придёт коробка с T;
   - перемотка страницей (`seek_started{page_seek}`) — тот же путь, только без команды.
4. **Время назад без перемотки** (страница перемоталась сама, а `seek_started` пришёл позже байтов — Twitch держит MSE в воркере) — по меткам времени коробок, правило выбрать по тестам.
5. **Live и неизвестная длительность** — `DynamicMediaTimeline` плеера.
6. **Переходник протокола** в `app-egui/browser_session/`:
   - **единая очередь:** сообщения MSE (`source_buffer_added`, `timestamp_offset_changed`, `source_buffer_aborted` …) и байты сейчас идут двумя разными приёмниками (`SessionEventSink` и `SessionByteSink`), порядка между ними нет. Оба вызываются из одного потока соединения строго по очереди, поэтому переходник пишет их в одну очередь в порядке прихода. Это обещание сервера записать в документации `browser-bridge-session` и закрепить тестом;
   - `stream_rejected` при отказе источника (DRM, кодек, нечитаемые байты), `clock` странице;
   - новое поколение — новый источник.
7. **Живой прогон без окна** (решение 92): прототип экстеншена из 00c гонит YouTube в процесс браузерного режима, процесс играет через настоящий плеер без экрана и пишет в журнал число кадров до показа, звук, монотонность времени.

## Тесты

- Перемотка внутри полки без команды странице; вне полки — команда, Buffering, кадров старого времени на экране нет, новые играют с T ± 1 кадр.
- Обратное давление: при полном буфере память не растёт, «буферизовано до» не убегает вперёд.
- Порядок сообщений и байтов в единой очереди совпадает с порядком прихода.

## Поправки по итогам 03a (29.10.2026, решения 93–94)

- **Источник готов:** crate `pushed-media-source` (`pushed_stream(policy)` → `PushedStreamWriter` + `PushedStreamOpener`). Переходнику 03b остаётся переводить сообщения протокола в вызовы писателя: `source_buffer_added` → `add_lane` (MIME → `PushedContainer::from_mime_type`), байты → `append`, `source_buffer_type_changed` → `change_container`, `timestamp_offset_changed` → `set_timestamp_offset`, `source_buffer_aborted` → `abort`, `duration_changed` → `set_duration`, `end_of_stream` → `end_of_stream`. Образец — тестовый `tests/support/recorded.rs`.
- **Отказ странице** — по `PushedStreamError::failure_class()`: `ProtectedContent` → `stream_rejected{protected_content}`, `UnsupportedMedia` → `unsupported_codec`, `UnparsableMedia` → `unparsable_media`, `InputMisuse` — нарушение протокола (4003).
- **Открытие потока** — `PushedStreamOpener::poll_open()`, неблокирующее: готов, когда у каждой объявленной полосы открылся первый эпизод. Вызывать на стороне подготовки, не на потоке плеера.
- **Перемотка сейчас недоступна:** демуксер честно отвечает `NotSeekable`. Порт перемотки по квитанциям — эта сессия.
- **`endOfStream`, а потом снова байты.** В MSE `appendBuffer` после `endOfStream` снова открывает поток (так бывает при перемотке назад после конца). В 03a это `InputAfterEnd`; 03b решает вместе с перемоткой.
- **Поток только с видео стартует только после следующих байтов.** После «данных пока нет» плеер не начинает, пока источник не дал новый пакет: так устроен «забор» повторной попытки (`mem:player-core/audio-starvation-buffering-resume-2026-08-27`). Со звуком старт ведёт звук. Для живых потоков (Twitch: буфер 1,4 с, сегменты раз в ~2 с) это задержка старта — замерить вживую и решить.
- **Сообщения MSE и байты** должны идти в источник в порядке прихода — пункт 6 этого файла остаётся в силе.
- **Обвязка «до кадра»** готова и переиспользуется: `crates/pushed-media-source/tests/support/` — безоконная `PlayerSession` с настоящими декодерами (FFmpeg программно, 2 потока; звук `audio`), симулятор звуковой карты, настоящее время.
