# Сессия 00c: виртуальный видеоэлемент и канал байтов — прототип и вердикт

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 00c плана `user/browser-bridge/`: одноразовый прототип главной идеи — экстеншен перехватывает байты, которые плеер страницы скармливает видеоэлементу (MSE, а для `<video src>` — скачивание через сеть браузера), подменяет видеоэлемент «виртуальным» (страница думает, что играет, браузер ничего не декодирует) и отдаёт байты внешнему процессу. Проверь на эталонных сайтах из `results/00.md`, замерь канал данных и расход браузера, принеси вердикт. Код плеера не меняется. Сначала прочитай `user/browser-bridge/README.md` и `results/00.md`.

## Зачем

Решения 37–39. Вся архитектура стоит на том, что плеер страницы поверит в подменённый элемент и будет качать дальше, а браузер при этом почти не тратится. Если это не так — план 01–16 пересматривается до любого кода.

## Что сделать

1. **Прототип перехвата** (временный экстеншен в scratchpad):
   - хук `MediaSource`, `SourceBuffer.appendBuffer`, `addSourceBuffer` (кодек), `remove`, `abort`, `changeType`, `endOfStream` в MAIN-мире на `document_start` во всех фреймах;
   - MSE в воркере: можно ли подменить конструктор воркера или внедриться в него; если нельзя — какие сайты теряем;
   - `<video src>`: Firefox — `filterResponseData`; Chrome — скачивание того же файла `fetch` из контекста страницы с `Range` по запросу.
2. **Виртуальный видеоэлемент.** Варианты (опробовать и сравнить):
   - **(а) подмена объекта:** элемент `<video>` остаётся в DOM, но MediaSource и свойства (`currentTime`, `paused`, `buffered`, `readyState`, `playbackRate`, `duration`, `videoWidth/Height`, `getVideoPlaybackQuality`, `requestVideoFrameCallback`, события `timeupdate` / `waiting` / `playing` / `seeking`) отдаёт наша прослойка, а браузеру реальный источник не подключается;
   - **(б) настоящий элемент без вывода** — проверить, декодирует ли браузер, если элемент скрыт или размер 0 (ожидаемо декодирует — тогда вариант отпадает, решение 39).

   Время ведёт внешний процесс (в прототипе — простой таймер). Пауза, перемотка (плеер страницы должен запросить новые куски), скорость 2× (качает быстрее?).
3. **Сайты:** YouTube, Twitch live, 2–3 украинских сайта, обычный hls.js-сайт, `<video src>`-сайт. По каждому: поверил ли плеер страницы, качает ли дальше, работает ли перемотка, нет ли ошибок «видео зависло» и автоперезагрузки плеера, что с рекламой.
4. **Фоновая вкладка.** Chrome и Firefox: вкладка скрыта, браузер свёрнут, 10+ минут (intensive throttling), включённый Memory Saver. Качает ли плеер страницы с нужной скоростью. Что помогает (порт native messaging открыт, `chrome.power`, «вкладка играет звук» — можно ли честно, без хаков; решение — владельцу).
5. **Канал данных** до внешнего процесса (эхо-хост 00, процесс считает байты):
   - native messaging + base64 — пропускная способность и CPU браузера на 1080p, 4K;
   - альтернатива: локальный канал от экстеншена (WebSocket к хосту и т. п.) — проверить, допустим ли он в контексте экстеншена без запроса Local Network Access;
   - рекомендация с цифрами.
6. **Расход браузера в этом режиме:** CPU и GPU всех процессов браузера, когда виртуальный элемент работает и страница качает, против обычного проигрывания на странице. Это честная база для замера 23.
7. **Возврат на страницу:** как вернуть настоящий элемент на секунде N — переподключить источник, перезагрузить плеер страницы, API плеера. Что работает на каждом сайте.

## Критерий выхода

- `results/00c.md`:
  - таблица «сайт → перехват / виртуальный элемент / перемотка / фон / возврат → да, частично, нет → причина»;
  - выбранный вариант виртуального элемента;
  - канал данных с цифрами;
  - расход браузера.
- **Вердикт владельцу:** идём по решению 37 на N из M эталонных сайтов; что делаем с остальными (честное ограничение, адаптер, или другой путь — решает владелец).
- Список требований к протоколу 01 (формат потока, поколения, обратное давление, возврат) и к плееру (03, 04).
