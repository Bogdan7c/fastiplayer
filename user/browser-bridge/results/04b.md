## Решения владельца (31.10.2026; в README — 127–130)

1. **«Прощание»** (решение 127). Владелец подтвердил главный механизм до плана: последнее сообщение странице уходит раньше закрытия, у заменённой вкладки короткий коридор (до 1 с).
2. **Новая причина отказа `playback_failed` в протоколе 1.0** (решение 128). Экстеншена ещё нет, поэтому это не новая версия, а дописка 1.0, как в решении 101.
3. **Пункт 5 делаем** (решение 129): ожидание и отказ видны зрителю.
4. **«Магия возврата вкладки»** (решение 130, идея владельца). Слова владельца: «если человек вернулся в плеер и нажал плей после закрытия вкладки, значит вкладку надо вернуть (открыть страницу). Если экстеншн может открыть вкладку, то делаем так, если нет — сообщение и закрытие». Вкладку открывает экстеншен, поэтому решение записано сейчас, а код — в сессии 11 (поправки в её файле). В 04b — запасной путь.

Техническое решение агентов, принятое без владельца (**ждёт подтверждения**):
- **спиннер после клика по таймлайну — и в обычном плеере.** Ядро плеера ведёт обычную перемотку через состояние «Scrubbing», а правило спиннера сессии 15 считало «Scrubbing» кадрами под пальцем. Поэтому перемотка вне скачанного ждала данных без спиннера, с застывшей картинкой до `SeekTimeout`. Теперь «Scrubbing» — ожидание, только когда таймлайн отпущен. Пока зритель тянет бегунок, спиннера нет, как и раньше. Медленная перемотка по сети в обычном плеере тоже стала показывать спиннер — это совпадает со смыслом решения 15 («перемотка → спиннер»), но буква его поменялась.

## Что сделано

**Две корневые причины в сервере сеанса** (`browser-bridge-session`), найденные до правок:
1. Закрытие соединения проверялось раньше отправки очереди исходящих — всё, что плеер успел поставить в очередь, молча терялось. Теперь любое закрытие идёт одним путём: очередь → прощание → кадр закрытия.
2. При замене вкладки старый сеанс закрывался кодом 4001 в тот же миг и пропадал из реестра — ему уже нельзя было ничего отправить. Теперь у него коридор прощания: входящее не принимается, одно последнее сообщение отправить можно, по сроку сервер закрывает сам.

Новые намерения сервера: «закрыть сеанс с прощанием» и «попрощаться с заменённой вкладкой». Итоги различимы: прощание в очереди / соединения уже нет / сеанс не тот. Неверное сообщение — ошибка, а не молчаливый пропуск.

**Окно и процесс** (`app-egui`):
- **Позиция T** — одно правило с часами странице: позиция плеера, только если он показывает загруженное поколение. Пока ничего не загружено или новое поколение ещё ставится, честной позиции нет — прощание не уходит (иначе страница отмоталась бы в 0). `resume` всегда «пауза» (решение 51).
- **Замена вкладки:** прощание уходит в том же шаге и раньше, чем новый сеанс забудет старое поколение.
- **Закрытие окна:** прощание → код 4000 → выход. Если страницы уже нет (доигрываем), закрытие окна = «доиграно». Обычному плееру процесс по-прежнему шлёт только «пауза» (решение 48).
- **Пауза ждёт человека:** правило паузы выражено типом — безоконный процесс выходит сразу (правило 103), окно ждёт. Пока окно на паузе, срок застоя не идёт; после «играть» он отсчитывается заново. Конец видео и отказ плеера важнее паузы.
- **Сообщения о конце** — английские, по причине и итогу: «Source tab closed», «… — playback stalled», «… — playback failed», «… — you can still watch what was downloaded» (на паузе), то же с «Lost connection to the browser», если пропал браузер. Сообщение держится 2,5 с, процесс к этому времени уже ушёл с шины — новый звонок разбудит новый процесс.
- **Перемотка без страницы** — только по скачанному; иначе ожидание длилось бы вечно.
- **Отказ поколения:** плеер не смог поставить или играть поколение → странице `stream_rejected{playback_failed}`, зрителю короткое сообщение. Намеренная смена поколения отказом не считается. Если плеер уже сам показал ошибку, второго сообщения нет. Сообщение `SeekTimeout` («Seeking timed out; try again») доходило до окна и раньше — закреплено тестом.

## Доказательства

- Сквозные тесты процесса, окно под частным `kwin_wayland --virtual` и без окна:
  - замена: старая «страница» получает `return_to_page{T, paused}` раньше 4001, T — в пределах тика часов; новый поток играет до кадра в рендере;
  - закрытие окна — настоящим закрытием композитора (KWin-скрипт): прощание → 4000 → выход;
  - вкладка ушла с ~6 с скачанного: ~150 кадров → сообщение → окно закрыто не раньше 2,4 с → процесс завершён;
  - вкладка ушла на паузе: окно ждёт 3 с без конца доигрывания → закрытие → выход;
  - отказ поколения с неизвестным кодеком: ровно один `stream_rejected{unsupported_codec}`, процесс жив, следующее поколение играет;
  - `SeekTimeout` доходит до окна.
- Фокусные тесты на каждое правило: прощание (12), правило паузы (7), сообщения и ожидание окна, отказ поколения с настоящим учётом загрузок, спиннер на настоящем плеере и источнике.
- Каждое ключевое правило проверено временной поломкой: тест падает, правка откатывается.
- Гейт: `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`, тесты `app-egui` (3035 + 27 сквозных), `browser-bridge-session` (68 + 53 петлевых), `browser-bridge-protocol`, `pushed-media-source`, `fastiplayer-config`, guardrails границ и размеров модулей.

## Известные ограничения

- **Живая проверка на экране владельца** не проведена — отложена.
- Замена вкладки, пока новое поколение ещё ставится, уходит без прощания (честной позиции нет); страница остаётся там, где была.
- Без страницы перемотка внутри `<video src>` отвергается, даже если эти байты уже скачаны.
- Во время 2,5 с сообщения о конце кнопки транспорта не работают.
- `playback_failed` сквозным тестом получить не удалось: испорченные байты дают другие причины, а плеер слишком живуч. Путь закреплён фокусными тестами.
- Несколько отказов за один шаг — окно скажет о последнем.
- `state.rs` — 798 строк, у предела.
- Нажал «играть» после ухода вкладки — пока только досмотр скачанного и запасной путь; возврат страницы — сессия 11 (решение 130).
