## Flatpak: вердикт — гипотеза подтверждена

Проверено на Google Chrome 156 из Flatpak:
1. Хост в `~/.var/app/com.google.Chrome/data/…`; Chrome запускает его внутри своей песочницы.
2. Хост зовёт имя на шине сессии. Сервис поднимается **D-Bus activation** из `~/.local/share/dbus-1/services/*.service` (dbus-broker, примерно за 70 мс) и работает **снаружи** песочницы как systemd-юнит хоста.
3. Сервис отдаёт fd (pipe) — хост пишет 64 МиБ со скоростью 2,1–3,5 ГиБ/с.
4. Права проверены отдельными запусками `flatpak run`:

| Права песочницы | `…FastiplayerTest` | `…FastiplayerTest.Bridge` |
|---|---|---|
| фильтрованная шина, без `talk-name` | `ServiceUnknown` | `ServiceUnknown` |
| `talk-name=…FastiplayerTest.*` | работает | работает |
| `talk-name=…FastiplayerTest` (точное) | работает | `ServiceUnknown` |
| полная шина (`sockets=session-bus`, так у владельца во Flatseal) | работает | работает |

5. Кто звонит: при фильтрованной шине отправитель — `xdg-dbus-proxy`, при полной — сам хост. В обоих случаях cgroup `app-flatpak-<app id>-….scope` и `/proc/<pid>/root/.flatpak-info` называют приложение.
6. Rust-бинарь (zbus 5.15), собранный на хосте с glibc 2.44, требует GLIBC_2.39 и запускается в рантайме с glibc 2.42.

**Черновик инструкции «Flatpak за 3 шага»** (для сессии 06, английский текст делает 06):
1. Нажать «Connect to browsers» в настройках Fastiplayer. Плеер кладёт хост в папку браузера (`~/.var/app/<id>/…`), файл подключения — в `~/.var/app/<id>/config/<браузер>/NativeMessagingHosts/`, а `.service` для D-Bus activation — в `~/.local/share/dbus-1/services/`.
2. Во Flatseal для браузера добавить в «Session Bus → Talk» строку `io.github.Bogdan7c.Fastiplayer.*`. Либо одной командой: `flatpak override --user --talk-name='io.github.Bogdan7c.Fastiplayer.*' <id браузера>`.
3. Перезапустить браузер.

## Хук в MAIN-мире против скриптов страницы

Временный экстеншен: контент-скрипт `world: MAIN`, `document_start`, `all_frames`, `match_about_blank`, `match_origin_as_fallback`. Он помечает подменённые `appendBuffer` / `addSourceBuffer`, а страница проверяет метку самым первым своим скриптом.

| Случай | Chromium 156 (3 прогона) | Firefox 158 |
|---|---|---|
| Инлайн-скрипт в `<head>` | успели | успели |
| Чужой iframe (другой origin) | успели | успели |
| `about:blank`, который страница трогает синхронно сразу после создания | успели | успели |
| `srcdoc` | успели | успели |
| blob-воркер, файловый воркер | **не попали** | MSE в воркере нет вообще |

Документация Chrome порядок не гарантирует, но на практике хук успел во всех случаях. Опасение MDN про пустые iframe в Firefox не подтвердилось — во всяком случае, при `match_about_blank` + `match_origin_as_fallback`.

## Firefox MV2 или MV3 — рекомендация MV3 (принята, решение 71)

**MV3 в Firefox даёт всё нужное:**
- блокирующий `webRequest` и `filterResponseData` (нужны `webRequestBlocking` и `webRequestFilterResponse`);
- MAIN-мир (Firefox 128);
- права на все сайты, которые с Firefox 127 даются при установке. Пользователь может их отозвать, поэтому проверяем `permissions.contains`;
- event page, которую открытый порт native messaging держит живой (проверено, 380 с).

Один манифест на оба браузера работает (`service_worker` + `scripts`).

**MV2 не нужен:** Mozilla его не убирает, но он дал бы второй путь кода.

**AMO:**
- для новых экстеншенов обязателен `data_collection_permissions`;
- минифицированный код — только вместе с исходниками;
- права на все сайты придётся обосновать.

**Chrome Web Store:** права на все сайты отправляют экстеншен на углублённое ревью (обычно дни, до нескольких недель). Если пользователь выставит доступ «по клику», MAIN-мир на `document_start` не сработает — это надо объяснить в справке.
