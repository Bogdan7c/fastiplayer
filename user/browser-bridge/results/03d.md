# Результат сессии 03d: плавная смена дорожек — «эстафета»

## Статус

**DONE.** 30 октября 2026.

Смена качества или кодека посреди потока больше не сбрасывает плеер в момент разбора:
- кадры старого качества доигрываются;
- новый декодер начинает с первого кадра нового эпизода;
- звук не трогается.

Зависание «звук разобран далеко вперёд» (находка 03a) ушло вместе с причиной.

## Решения владельца (30.10.2026; в README — 105–109)

Перед кодом агент пересказал главный механизм простыми словами — «эстафета вместо фальстарта», — и владелец ответил «да».

1. **Смена описания дорожек — эстафета на границе показа** (решение 105). Старый декодер доигрывает пакеты до отметки и выжимается до последнего кадра, новый получает пакеты с первого кадра нового эпизода. Звук не трогается, если не менялся.
2. **Для всех источников**, не только для моста (решение 106): HLS, DASH, MPEG-TS, источник моста.
3. **Склейщик звука и видео (`demux-api`) чинится в 03d отдельным коммитом** (решение 107): при смене одной стороны готовый пакет другой стороны больше не выбрасывается.
4. **Архитектура утверждена** (решение 108). Номер описания на каждом пакете, передача видео за 6 шагов, звук меняет декодер по отметке. Старый сброс остаётся при перемотке и скрабе, смене состава дорожек, смене бэкенда.
5. **Живая приёмка с мышью через uinput на основном компьютере**, пока владельца нет (решение 109). Проверены воспроизведение, скорость, перемотка, drag, конец файла и переходы на обоих декодерах.

## Как это работает

```
 demuxer: … P P [TracksChanged: новое описание] P' P' …
                 │
 player-core     ▼  список дорожек обновлён сразу (UI видит новое качество),
                    новому описанию — номер N+1; пакеты дальше помечены N+1
 очередь видео:  P P │ P' P'          ← «шлагбаум»: пакет N+1 не уходит старому декодеру
 декодер (N):    1) дорабатывает отправленное  2) выжимается до последнего кадра
                 3) все кадры у плеера  4) flush + настройка на N+1, ждёт ключевой кадр
 очередь показа: старые кадры доигрываются, пока новый декодер стартует
 звук:           не менялся — ничего; сменился кодек — декодер меняется на первом
                 пакете N+1, выход и часы те же (смену формата PCM пересобирает выход)
```

**Кто чем владеет:**
- `player-core` `pipeline/track_description.rs` — учёт номеров описаний видео и звука, шлагбаум очереди (`front_sendable_video_packet`), сбросы учёта вместе с очередями;
- `session/track_transition.rs` — решение «эстафета или старый сброс» (чистая классификация с тестами), смена декодера звука, настройка на последнее описание после flush перемотки;
- `session/tick/video_track_handoff.rs` — шаги передачи видео раз в такт;
- `session/capability_selection/track_reconfiguration.rs` — перенастройка декодера с честными исходами: «настроен», «канал управления занят — повторить», «нужен другой бэкенд».

**Старый сброс остаётся**, когда эстафета неприменима:
- идёт перемотка или скраб (у них свои правила `TracksChanged`);
- изменился состав дорожек;
- активный декодер новое описание не принимает (другой бэкенд или кодек не играется);
- ждёт установка другого бэкенда;
- больше 4 смен ждут границы.

**Договор `video-core` уточнён:**
- `Drained` виден плееру, только когда все кадры старого описания уже у него, а канал кадров пуст (`visible_to_player`, общий для FFmpeg и VA-API);
- успешный `flush` возвращает декодер в «не выжат», поэтому настоящий конец файла после смены качества снова выжимает декодер.

## Что сделано

- `video-core`: `VideoDecoderEndOfStreamDrainState::visible_to_player`, документ договора `flush` и `end_of_stream_drain_state`.
- `video-ffmpeg`:
  - `Drained` видим только при пустом канале;
  - цикл декодирования больше не объявляет `Drained` раньше, чем worker положил хвост в канал (нашло ревью).
- `video-vaapi`: общее правило видимости вместо своей копии; новый аппаратный тест и сценарий `h264-mp4-vaapi-handoff-after-drain` в `scripts/media-regression.sh`.
- `demux-api`: `CompositeAvDemuxer` не выбрасывает пакет соседа и сбрасывает учёт опережения только у стороны, сменившей описание.
- `player-core`: модули выше; метки на пакетах в `demux_admission`; шлагбаум в отправке и в планировщике пробуждений; сброс при перемотке настраивает декодер на последнее описание.
- `pushed-media-source` (только тесты): строгие сквозные тесты. Симулятор звуковой карты теперь считает тишину посреди звука и звук, выброшенный вместе с уничтоженным выходом.

Источник 03a не менялся (требование плана).

## Доказательства

**Сквозные «до кадра»** (`stream_changes_to_frame.rs`, настоящие FFmpeg и декодер звука):

| Тест | Что доказывает |
|---|---|
| смена качества H.264 64 → 96 во время игры | все 20 кадров подряд, 64 px до 0,4 с, 96 px ровно с 0,4 с, звук ≥ 0,78 с без тишины и без выброшенного буфера, A/V ≤ 1 кадра |
| звук подан целиком заранее (разрыв больше всей первой половины видео) | то же, поток доигран до `Ended` — раньше здесь вечное доигрывание |
| `changeType` H.264 → VP9 | то же для смены кодека |

**Фокусные тесты новой границы (`player-core`, 27):**
- классификация: новые SPS/PPS, кодек звука, длительность и метки (не смена), состав, субтитры, невыбранная дорожка, только звук;
- учёт описаний: шлагбаум, две смены подряд, описание без пакетов, предел очереди, сброс после flush, звук ровно на первом пакете, «не трогает чужое», сбросы;
- сессия с подставным декодером:
  - порядок «старые пакеты → выжимание → flush → настройка → новые» по тактам;
  - старые кадры не выброшены, поколение не меняется;
  - конец потока после передачи выжимает снова;
  - без смены описания декодер не трогается;
  - смена состава и смена во время перемотки идут старым сбросом;
  - отвергнутое описание — старый сброс с ошибкой;
  - перемотка посреди передачи;
  - фатальная ошибка настройки;
  - занятый канал управления — повтор, а не ошибка;
  - смена кодека звука без перезапуска выхода.

**Бэкенды:**
- FFmpeg (настоящий VP9): «выжат» не виден, пока кадр лежит в канале;
- VA-API (780M, H.264 720p): второй drain в той же generation после flush отдаёт весь хвост.

**Мутации** (каждое место временно ломалось, его тест падал):
- в `player-core`: без шлагбаума, без flush после выжимания, без смены декодера звука, без настройки после flush перемотки;
- старый сброс вместо эстафеты: падают все три сквозных теста — теряются кадры, выбрасывается ~200 мс звука на смене, а случай «звук впереди» виснет;
- FFmpeg без правила видимости; VA-API без сброса состояния при flush.

## Живая приёмка (решение 109)

**GUI на основном компьютере.** Ввод — мышь и клавиатура через uinput. Фикстуры — с выжженным номером кадра и тоном 440 Гц, звук — запись монитора синка. Рендер GLES2, по прогону на VA-API и на программном декоде FFmpeg. Плеер — с изолированными настройками, настройки владельца не тронуты.

| Что | Итог (VA-API и FFmpeg) |
|---|---|
| воспроизведение, 1,5× и обратно, стрелки, клики по таймлайну | кадры верные, паузы звука только на перемотках (20–70 мс) |
| drag 8 → 22 с, пауза, play | посадка на цель (кадр 627 = 25,08 с × 25), тишина только пока тянешь |
| конец файла | последний кадр 749 показан, `Ended` |
| переход к следующему элементу очереди | дыра в звуке 50–60 мс |
| HLS 720p → 360p → 720p (TS), ускорение и drag через границы | без ошибок; на VA-API границы без пауз |

На GUI-источниках эстафета сама по себе не сработала: ни один из них не даёт `TracksChanged` посреди потока на исправном контенте. HLS на TS-сегментах меняет разрешение внутри потока (новый SPS), декодер перестраивается сам. Два других кандидата не открываются из-за старых дефектов (бэклог 27, 28). Поэтому эстафету доказывают сквозные тесты с настоящими декодерами и аппаратный тест VA-API, а GUI-прогон доказывает, что ядро не ухудшилось на обычном пути.

**Мост, безголовый стенд 03b, живой YouTube.** Четыре принудительные смены качества через API плеера страницы. Оказалось, что ручную смену YouTube делает новым `MediaSource` (новое поколение), а не новым init в том же буфере. Эстафету этот путь не задевает. Найден старый дефект смены поколения (бэклог 26).

**Сравнение с исходным `HEAD`.** Каждая найденная странность повторялась на сборке без правок 03d. Все четыре оказались старыми.

## Ревью и что оно нашло

Независимый агент без моих выводов прочитал дифф. Исправлено:
1. **FFmpeg объявлял `Drained` раньше, чем хвост попадал в канал**: окно, где плеер передал бы палочку при ещё не опубликованных кадрах. Теперь `Drained` пишет worker после публикации, модульный тест это сторожит.
2. **Кратковременно полный канал управления при перенастройке был фатальной ошибкой** — а перенастройка теперь происходит на каждой смене качества. Теперь «канал занят» — повтор на следующем такте (тест).
3. **Исход «нужен другой бэкенд» молча считался успехом.** Теперь шлагбаум остаётся закрытым, пока бэкенд не установлен; его перемотка сама настраивает декодер на последнее описание.
4. **Планировщик пробуждений не знал о шлагбауме** и будил worker вхолостую, пока передача ждёт декодер. Теперь он смотрит на тот же шлагбаум.

Принято как ограничение (ниже): звук без сквозного режима при смене кодека звука; поведение склейщика при скачке времени только у одной стороны.

## Найдено и не исправлено (старое, вне 03d; общий бэклог 26–29)

29. Программный декод: остановка ~1 с и дыра в звуке 840 мс на смене разрешения внутри TS-потока.

## Известные ограничения

- **Эстафета не работает во время перемотки и скраба**: там прежний сброс (осознанная граница первой версии). Внутри перемотки потерь нет: данные после её цели и так читаются заново.
- **Смена бэкенда** (новый кодек не тянет VA-API) идёт старым путём: пересоздание декодера и перемотка на текущую позицию.
- **Ошибка `flush` при передаче фатальна**, как при перемотке.
- **Новый эпизод не с ключевого кадра**: новый декодер пропускает пакеты до ближайшего ключевого. У MSE и HLS фрагменты начинаются с ключевого.
- **Звук:**
  - декодер звука меняется без выжимания своего хвоста — у AAC/Opus это доли кадра;
  - сквозной вывод (passthrough) при смене кодека звука заново не выбирается.
- **Склейщик `demux-api`:** при скачке времени только у одной стороны прогресс соседа остаётся на старой шкале до его собственной смены. Остановки не нашли, теста со скачком на одной стороне нет.
- **В GUI** эстафету вживую увидеть не на чем, пока не исправлены бэклог 26–28 (см. живую приёмку).
