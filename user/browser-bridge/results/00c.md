## Стенд (в scratchpad, в репозиторий не попал)

Одноразовый экстеншен MV3, один манифест на Chromium и Firefox:
- **Хук в MAIN-мире** во всех фреймах на `document_start`:
  - перехват `addSourceBuffer`, `appendBuffer`, `remove`, `abort`, `changeType`, `endOfStream`;
  - обёртка `Worker` с внедрением хука в воркер;
  - подмена HLS в `canPlayType` и `isTypeSupported`;
  - муляж элемента: свойства и методы `HTMLMediaElement` переопределены на прототипе, события настоящего элемента гасятся, свои генерируются.
- **Relay** в изолированном мире: порт страницы ⇄ background, байты в base64.
- **Хост native messaging** (Python):
  - пишет журнал и байты каждого SourceBuffer в файл;
  - принимает команды «внешнего плеера» (пауза, перемотка, скорость, возврат);
  - 4 раза в секунду шлёт «тик» часов.
- **Робот:**
  - Chromium — `--load-extension`, Firefox — временная установка через сервер DevTools (RDP, как `web-ext`);
  - навигация, вкладки, окно и скриншоты — через `tabs`/`windows` API самого экстеншена;
  - CDP и Marionette/BiDi не используются (причина — первая находка ниже).
- **Разборщик времени fMP4/WebM** для варианта «чистый муляж»:
  - 265 проверок против `ffprobe`;
  - нарезка кусков, включая разрез посреди бокса, результат не меняет.

Сценарий на каждом сайте:
1. Игра.
2. Пауза 20 с от «внешнего плеера».
3. Игра.
4. Перемотка от «внешнего плеера».
5. Перемотка через сам плеер страницы (`video.currentTime = …`).
6. Скорость 2×, потом 1×.
7. Возврат на страницу.

Для live — игра, пауза, игра, возврат.

## Находка для автотестов: CDP ломает YouTube

**Выбрана «тень»** (решение 81).

Цена тени и как её снизить:
- **Браузер чистит буфер MSE относительно настоящей позиции элемента, а не нашей.** Когда настоящий элемент стоит на 0, YouTube в фоновой вкладке за ~7 минут набрал 600 с звука и упёрся в `QuotaExceededError`. Плеер страницы пересоздал MediaSource, но в скрытой вкладке поднялся только после её открытия.
  - Лечение: раз в 15 с, если настоящий элемент отстал больше чем на 20 с, ставим ему `currentTime` = позиции муляжа (на паузе).
  - После этого YouTube 13 минут в фоне без единой остановки, буфер ~118 с.
  - Цена: Chromium декодирует 4–8 кадров на перестановку (~1–2 кадра/с против 24 при проигрывании). Firefox — 0 по `getVideoPlaybackQuality`. Видеоблок GPU 0,1–0,2 % против 1,3–2,6 %.
  - Альтернатива без декода — самим вызывать `remove()` позади позиции, скрыв это от плеера страницы. Сложнее: события `updateend` чужого `remove` нельзя показывать странице.
- **Перемотку муляжа ограничивает длительность.** Перемотка за конец ролика должна давать `ended`, как у настоящего элемента. Это требование к протоколу.

## Обёртка воркеров (решение 63)

- **Chromium:** blob-воркер с хуком + `importScripts` исходного кода работает на Twitch и DW.
- **Firefox:** та же обёртка **ломает Twitch** — `importScripts` blob-адреса страницы изнутри нашего blob-воркера даёт `NetworkError`. MSE в воркере Firefox всё равно не умеет, поэтому обёртка включается только при `MediaSource.canConstructInDedicatedWorker === true`. С этим условием Twitch в Firefox работает.
- Классический воркер проверен; модульный, CSP `worker-src` и вложенные воркеры на эталонных сайтах не встретились.

## Канал данных (замер сабагента)

Путь: MAIN-мир → контент-скрипт → background → внешний процесс. Синтетические куски с подтверждением от хоста, потерь 0.

Что выяснилось по дороге:
- Chromium 156 передаёт сообщения от контент-скрипта к background через JSON: `ArrayBuffer` превращается в `{}`, поэтому нужен base64. Firefox передаёт буфер как есть (structured clone).
- **WebSocket на `127.0.0.1` из страницы или контент-скрипта** в обоих браузерах упирается в запрос Local Network Access: сокет висит, пока человек не ответит. В Firefox его ещё режет CSP страницы. **Background от LNA и CSP освобождён.**
- Firefox MV3: `ws://127.0.0.1` из background заработал только с явным `content_security_policy.extension_pages`.

## Требования к протоколу 01

1. **Поток — по SourceBuffer:** MIME с кодеком, init-сегмент, медиакуски в порядке `appendBuffer`. Куски режутся посреди бокса, собирать по SB.
2. **Поколение = новый MediaSource на элементе.** Это реклама YouTube, следующий ролик, эфир после преролла, смена серии и озвучки. Старое поколение плеер бросает.
3. **Разрывы внутри поколения:** после перемотки время идёт не монотонно (ffmpeg: «non monotonically increasing dts»). Протоколу нужна метка «перемотка/разрыв» и, по желанию, `remove(start, end)` страницы.
4. **Часы ведёт плеер.** Экстеншен получает позицию, паузу, скорость, «жду данных» и «конец» и сам генерирует события страницы. Тики идут через порт экстеншена: таймеры страницы в фоне Chromium — раз в минуту.
5. **`buffered` при «тени» даёт браузер:** протоколу не нужно возвращать странице разбор кусков. При «чистом муляже» `buffered` должен быть известен к `updateend`, то есть нужен лёгкий разборщик в самом экстеншене (кругооборот через плеер слишком долгий).
6. **Обратное давление** — естественное: плеер страницы качает по своей цели буфера (от 1,4 с у Twitch live до 120 с у YouTube в фоне) и останавливается на паузе. Плеер-приёмник должен уметь держать до ~2 минут вперёд или сообщать «полон».
7. **Ограничение перемотки длительностью** и `ended` на конце, в том числе у рекламного поколения.
8. **Возврат:** позиция N + «играть/пауза». В «тени» возврат мгновенный.
9. **«Тень» требует перестановки настоящего элемента** (или своего `remove`). Это часть экстеншена, а не протокола, но плеер должен присылать время не реже раза в несколько секунд.
10. **`<video src>` качает background** с `Range` по запросу плеера. Протоколу нужен запрос «дай байты X–Y».
11. **Объём:** 0,1–1 МиБ/с в среднем, всплески до 5 МиБ/с. Base64 в Chromium обязателен при передаче через `runtime`.

Требования к плееру (03, 04):
- принимать fMP4 и WebM кусками любой нарезки, по SB; один SB может нести звук и видео (PeerTube, Twitch live);
- переключать поколения без перезапуска окна;
- **реклама YouTube приходит в тот же элемент — плеер её показывает.** Пропустить её нельзя, не сломав страницу: YouTube ждёт `ended` (решение 84);
- **последняя линия против DRM:** init-сегмент с `encv`/`enca`/`tenc` — честный отказ «защищённое видео», а не мусор на экране. Признак `encrypted` может не прийти вообще (Vimeo), ловит `setMediaKeys` с ключами (решение 65 подтверждено);
- YouTube по умолчанию выбирает AV1 даже на 780M — политика кодека (решение 43) нужна с первого дня для старого железа.

- Twitch в фоне Firefox не повторён после исправления обёртки.
- «Чистый муляж» проверен только на YouTube в Chromium, без возврата.
- Нативный HLS, который страница всё равно кладёт в `src` (после нашего «не поддерживаю»), на эталоне не встретился. Для таких страниц экстеншен качает HLS сам (решение 83).
- Расход измерен только на 780M; на T410 — в замере 23.
- Синтетические события муляжа имеют `isTrusted = false`. Ни один сайт этого не проверял, но защищённый плеер может.

## Решения владельца (29.10.2026, эта сессия; в README — 81–84)

1. **Муляж — «тень»** (решение 81). «Чистый муляж» не берём: без повторной подачи кусков нет возврата, в воркере не делается.
2. **Канал данных — WebSocket на loopback из background прямо в процесс браузерного режима** (решение 82). Выбран вместо рекомендованного агентом native messaging: на всплесках дешевле, особенно в Firefox. Цена — открытый порт с одноразовым токеном. Посредник native messaging остаётся для управления.
3. **m3u8 в `src`** после нашего «не поддерживаю» — экстеншен качает плейлист и сегменты сам через сеть браузера (решение 83).
4. **Реклама YouTube показывается как есть** (решение 84).
5. **Vimeo — DRM-негатив.** Плашку «нужно включить DRM» заметил владелец, проверка подтвердила шифрование CENC.
