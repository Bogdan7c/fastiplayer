# Результат сессии 09b: особые формы — воркер, `<video src>`, кодеки

## Статус

**DONE на стенде.** 3 ноября 2026. Живая проверка (Twitch, клип как `<video src>`, YouTube с «Always H.264») ждёт машину владельца.

1. **MSE в воркере (Chrome).** Перехват едет внутрь воркера сайта. Куски идут по цепочке воркер → страница → фон → Fastiplayer, тень стоит на тот же `<video>`. Новый MediaSource внутри воркера даёт у нас новое поколение. Firefox не трогаем (решение 63).
2. **Обычный файл `<video src>`.** Фон экстеншена качает куски файла по просьбе плеера (`fetch_range`) через сеть браузера с куками страницы. Свой `<video>` страницы под тенью не качает и не декодирует. Перемотка за скачанное идёт новым запросом байтов, возврат ставит файл странице на T.
3. **Подмена кодеков.** Ответы `isTypeSupported`, `canPlayType` и `mediaCapabilities` готовы до первого вопроса плеера страницы, во всех фреймах и в воркерах Chrome. Пункты: Auto / Prefer VP9 / Always H.264 / Off. Auto следует метке плеера: потолок по первому кодеку его «Video codec priority» и «GLES2 → только H.264». HLS отвечает «нет» всегда (решение 64).
4. **Нативный HLS** (m3u8 прямо в `src`) получает честное «not supported yet», видео остаётся в браузере. Сам HLS — сессия 10a (решение 185).

## Решения владельца (3 ноября 2026)

- **185.** Нативный HLS в `<video src>` — отдельная сессия 10a после вехи M1. В 09b — честное «not supported yet».
- **186.** Файл под тенью — источник настоящего элемента снят: браузер не качает и не декодирует. Цена: на странице чёрный прямоугольник вместо застывшего кадра, а при возврате файл перезагружается (тень прячет это от страницы).
- **187.** `buffered` файла под тенью — весь файл `[0, duration]`. Протокол не меняется.
- **188.** Механизм 09b подтверждён до кода.
- **189.** Auto экстеншена следует настройке плеера «Video codec priority» (вопрос владельца посреди сессии: «есть ли у нас настройка "предпочитать h264"»). Первый кодек списка — потолок: сайту запрещается всё, что сайты обычно ставят выше него (AV1 > VP9 > HEVC > H.264). Метка плеера = потолок ∩ рендер. В экстеншене добавлен пункт «Prefer VP9 (no AV1)». Цена: при списке по умолчанию (VP9 первым) YouTube в браузере у всех с экстеншеном идёт в VP9, а не в AV1.
- **190.** Автоопределение по железу (Vulkan есть, аппаратного VP9 или AV1 нет) — в сессии 13.
- **191.** Файл с сайта, который проверяет Referer, — честный отказ («Stream error»). Разведка в 09c: насколько это частое и работает ли `declarativeNetRequest` в Firefox.
- **192.** Обёртка воркера — только для воркеров из blob (находка независимого ревью). У воркера из обычного файла она меняла бы адрес на `blob:` на каждой странице Chrome, и сайты с WebAssembly могли бы сломаться даже без передачи видео.

## Технические решения (за агентом, владельцу сообщено)

- **Доставка настройки кодеков в MAIN-мир — синхронно.**
  - Фон держит один динамический контент-скрипт-«курьер» (`scripting.registerContentScripts`, изолированный мир, `document_start`, все фреймы). Запрещённые семейства запечены в файл: 15 вариантов на все подмножества {AV1, VP9, HEVC, VP8}.
  - Курьер и `page.js` встречаются синхронными DOM-событиями, и им не важно, кто запустится первым. Принимается только первое верное «tell», курьер снимает слушатель, как только его ответ принят. Глобалов на странице нет.
- **Политика — «запрещены эти», а не «разрешены только эти».** Иначе «Prefer VP9» заодно запрещал бы VP8. H.264 не запрещается никогда, HLS — всегда.
- **Метка плеера** — `crates/app-egui/src/browser_session/codec_label.rs`. Собирается один раз на процесс: изменённая настройка действует со следующего процесса браузерного режима. Экстеншен берёт метку из кэша последнего `hello`.
- **Источник настоящего элемента снимается через `srcObject = new MediaStream()`** (оригинальным сеттером). Атрибут `src` и DOM страницы не меняются. При возврате — `srcObject = null` → `loadedmetadata` → T → `seeked`. С `preload="none"` браузер откладывает загрузку, тогда T ставится как позиция старта.
- **Качальщик диапазонов** (`range-fetcher.ts`, `range-response.ts`):
  - рамки вида 2 строго подряд от смещения запроса;
  - короткий ответ — только на конце файла;
  - размер и его вид не меняются, смена ETag, Last-Modified или размера даёт `resource_changed`;
  - 200 вместо 206 принимается только со смещения 0;
  - сервер, урезавший диапазон, догоняется до 32 подзапросами;
  - новый `fetch_range` прерывает старый как `network_error` — это законно, приёмник считает старый устаревшим;
  - пауза чтения при очереди сеанса больше 32 МиБ;
  - новое поколение гасит старую закачку.
- **Firefox:** CSP фона дополнен `http: https:` в `connect-src` — без этого `fetch` файла из фона блокировался.
- **Воркер:** вторая сборка хука вшита строкой в `page.js`. Связь с хуком идёт по личному `MessageChannel`, ключи `w<N>/ms-K`.
  - Сопоставление «handle ↔ MediaSource воркера» — по порядковому номеру доверенного сообщения воркера. Разбор данных сообщения ограничен: глубина 4, не больше 256 значений.
  - Отзыв blob-адреса сайта откладывается, пока воркер не загрузил код сайта (до 60 с). Так работают воркеры Vite и webpack, которые отзывают адрес сразу после `new Worker()`.
- **SharedWorker не оборачивается:** MSE там создать нельзя по спецификации. Это отступление от буквы решения 63.
- **Выбор видео:** «играет сейчас» главнее формы (решение 8). При равенстве MSE (в том числе в воркере) важнее файла.

## Независимое ревью

Ревью кода (только чтение, Opus) нашло 12 мест. Закрыты все, кроме одного, — оно записано в 09c. Каждое закрытое — с тестом, который падал без фикса:

- обёртка воркера меняла адрес воркера у обычных файлов → решение 192;
- воркеры, чей blob-адрес отзывают сразу, умирали → отложенный отзыв;
- после перехвата страницей во время возврата файла звук оставался выключенным → единая точка восстановления `muted` (`page-muted.ts`);
- `preload="none"` замораживал возврат на 10 с;
- чужая смена источника во время возврата получала старую позицию;
- новая передача того же элемента во время возврата падала;
- видимое MSE на паузе побеждало играющий файл;
- курьер настройки слушал вечно, и страница могла узнать настройку;
- старая закачка файла жила после нового поколения;
- адрес файла выбирает страница (локальная сеть, `localhost`) → не исправлялось: решать в 09c, текст — в шапке `range-fetcher.ts`.

## Дефект рукопожатия в Firefox (найден повтором стенда)

Повторный полный прогон Firefox дал 56 PASS, 7 unsupported и 2 FAIL — снова «видео не найдено» на играющем видео (`iframe-cross-origin`, `cdn-guard`). Повтор на разных страницах исключил «сбой среды». Корень доказан диагностической сборкой:

- Изолированный мир отдавал MAIN-миру личный порт одним «слепым» `postMessage` на `document_start`. Расчёт был на то, что оба скрипта стартуют в одном такте.
- Firefox сохраняет порядок двух скриптов, но не одновременность. Каждый скрипт компилируется отдельно и ожидается (`ExtensionContent.sys.mjs`, `Script.inject`). Если `page.js` ещё не скомпилирован, задача `message` приходит раньше его слушателя.
- Порт терялся на всю жизнь документа: опрос кандидатов молчал 1 с → «видео не найдено». Кроме того, наше рукопожатие доходило до обработчиков `message` самой страницы.
- Дефект заложен в 09a. Раскрыл его 09b: `page.js` Firefox вырос со 171 до 374 КБ из-за вшитого хука воркера и стал компилироваться дольше.
  - Сборка 09a2 (`31071b18`): 14 из 14 PASS.
  - HEAD до фикса: 3 сбоя на 12 прогонов.
- Живой пользователь Firefox мог получить «no video» на первой загрузке сайта.

Фикс — встреча вместо слепой отправки:
1. Изолированный мир слушает READY и шлёт отменяемый OFFER.
2. MAIN ставит слушатель порта, отменяет OFFER («слушаю») и шлёт READY.
3. Порт уходит, только когда MAIN точно слушает.

Для страницы ничего не видно: после встречи OFFER больше не отменяется. Тесты: 9 новых на гонку в обе стороны, подделку повторного READY и «нет MAIN-мира — нет порта»; каждый проверен поломкой. Цикл 15 × 3 страниц Firefox — 45 из 45 PASS.

Заодно сборка Firefox больше не вшивает хук воркера: MSE в воркере Firefox не умеет, решение 63. `page.js` Firefox — 258 КБ вместо 374.

После фикса: `capture --browser both` — 40 PASS, 3 unsupported, 1 FAIL; `codecs --browser firefox` — 6/6.
- Единственный FAIL (`video-src-cdn`, Firefox) случился ещё до передачи: браузер сам не сыграл ни кадра.
- Повтор: `pages` (без экстеншена) ×3 и `capture` ×3 этой страницы — все PASS.
- Это та же редкая нестабильность Firefox в невидимом `kwin_wayland`, что уронила `pages` без экстеншена в первом полном прогоне. Записана в известные ограничения стенда.

## Известные ограничения

- Нативный HLS — сессия 10a.
- Файл с сайта, который проверяет Referer, — честный отказ (решение 191).
- MSE в воркере из обычного файла, во вложенном воркере, handle через `MessagePort`, воркер, запрещённый CSP, — честное «not supported yet».
- Классический воркер из blob: относительные `importScripts` сайта ломаются так же, как без нас (адрес blob был и раньше).
- Наш личный порт держит воркер живым, пока жив документ. `toString` обёртки — не «native code».
- Метка плеера:
  - автовыбранный в рантайме GLES2 не даёт метки;
  - автоопределения по железу нет (сессия 13);
  - первое подключение после установки идёт без политики: метка берётся из кэша прошлого `hello`.
- Файл под тенью:
  - запись страницы в источник = «страница забрала видео» (следующая серия файлом — сессия 16);
  - при такой записи страница видит два `emptied`;
  - `TimeRanges.prototype.end.call(нашОбъект)` бросает;
  - `audioTracks` и `videoTracks` пусты;
  - HLS по адресу без `.m3u8` и без `type` у `<source>` считается файлом.
- Пока нет фильтра рекламы (09c), преролл отдельным файлом выбирается раньше фильма в MSE на паузе.
- Стенд: Firefox в невидимом `kwin_wayland` изредка не играет видео вообще (0 кадров), в том числе без экстеншена. Страница падает ещё до передачи, повтор проходит.
- `shadow-session.ts` — 741 строка. Новую логику тени — только отдельными модулями, при следующем росте разрезать.
