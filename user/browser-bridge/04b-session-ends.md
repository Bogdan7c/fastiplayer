# Сессия 04b: концы сеанса в окне браузерного режима

Решение 123 (нарезка 04). Общий замысел — [04](04-browser-mode-window.md), итоги окна — `results/04a.md`.

> Выполни сессию 04b плана `user/browser-bridge/`: правильные концы сеанса в окне браузерного режима. Замена вкладки и закрытие окна возвращают странице «на T, пауза»; «вкладка ушла» → доиграть → «Source tab closed» → закрыть; на паузе окно ждёт человека, а не закрывается. Сначала прочитай `user/browser-bridge/README.md` (решения 40, 42, 51, 102–103, 120–125), `results/03c.md`, `results/04a.md`, этот файл.

## Что есть после 04a

- Окно работает поверх одного ядра процесса `BrowserSessionCore` (`browser_session/process_core.rs`). Закрытие окна сейчас сразу закрывает сеанс кодом 4000 и завершает процесс.
- `return_to_page{position_us, resume}` есть в протоколе (01), но **не отправляется нигде**: ни при замене вкладки, ни при закрытии окна. Для замены нужна правка `browser-bridge-session`: старому экземпляру сеанса надо успеть отправить сообщение до закрытия (решение 123).
- Доигрывание после ухода вкладки уже есть без окна (03c): `ProcessLifecycle` → `AwaitPlaybackDrain`, медиа-часть отвечает `DrainEnd::{PlayedToEnd, PlayerFault, NothingToPlay, PagePaused, Stalled}`.
- Правило 103 без окна: пауза в момент конца = выход сразу. В окне это неверно: человек мог просто отойти.

## Что сделать

1. **Замена вкладки (решение 40):** новый сеанс → старой вкладке `return_to_page{T, paused}` → её сеанс закрывается → новый источник играет в том же окне.
   - Порядок «сначала сообщение, потом закрытие» закрепить в `browser-bridge-session`: сейчас конец старого экземпляра не ждёт исходящих сообщений.
   - В «Наклейке» (19) окна живут одновременно, но в своём окне замена остаётся.
2. **Закрытие окна человеком** → странице `return_to_page{T, paused}` (решения 12, 51; на стороне страницы это исполняет 11) → закрытие сеанса → выход. Обычный плеер остаётся на паузе (решение 48).
3. **Вкладка ушла (решение 42):**
   - доиграть то, что уже скачано;
   - показать «Source tab closed»;
   - закрыть окно через 2–3 с;
   - если играть нечего — сразу сообщение и закрытие.

   Текст сообщения — по варианту `DrainEnd`. Пользовательский текст — английский.
4. **Пауза ждёт человека (замена правила 103 для окна):** если вкладка ушла, пока окно на паузе, окно не закрывается. Остаются кадр и сообщение. Человек может доиграть, перемотать по полке или закрыть. Закрытие человеком = «доиграно» (`on_playback_drained`).
5. **Ожидание и отказ видны зрителю** (предложение по итогам живого показа 04a, владелец может вычеркнуть):
   - ожидание данных после перемотки вне полки (`Scrubbing`/`Seeking`) — спиннер;
   - `SeekTimeout` и отказ поколения — короткое сообщение вместо молча застывшей картинки.

## Открытый вопрос владельцу (из 04a)

Если наш плеер не смог установить новое поколение (`PlaybackFailed`/`InstallAborted`), страница об этом не узнаёт: у `stream_rejected` нет подходящей причины. Добавлять ли причину в протокол (минорная версия)? Решить до начала 04b или в её начале.

## Тесты

- Замена сеанса: старая «страница» получает `return_to_page{T, paused}` раньше закрытия, новое поколение играет до **кадра в рендере**.
- Закрытие окна: странице ушло `return_to_page` с позицией наших часов (допуск — один тик часов), процесс вышел, обычный плеер на паузе.
- Вкладка ушла с ~5 с скачанного: играет ~5 с → сообщение → окно закрыто, процесс завершён (решение 56).
- Вкладка ушла на паузе: окно живо и ждёт; закрытие человеком → выход.
- Оба режима сквозных тестов: окно под `kwin_wayland --virtual` и безоконный.

## Живая проверка

Стенд 03b в режиме показа (на экране владельца) — замена вкладки (вторая вкладка открывает сеанс), закрытие окна, закрытие вкладки во время игры и на паузе. Робот стенда должен научиться принимать `return_to_page` (поставить `currentTime` и паузу) — правка стенда вне репозитория.
