# Сессия 09: обнаружение потоков на странице

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 09 плана `user/browser-bridge/`: научи экстеншен находить медиа на вкладке — `webRequest` (манифесты, progressive, субтитры, заголовки и куки через `extraHeaders`), MAIN-хуки (MSE, `src`, `createObjectURL`, EME → DRM, PiP) только как подсказки, все фреймы включая чужие iframe, отсев рекламы и угадывание главного потока. Проверь на стенде 08. Сначала прочитай `user/browser-bridge/README.md` (инварианты), `results/00.md`, `results/08.md`.

## Зачем

Решение 8 и основа всех режимов. Ошибка здесь — это либо реклама в плеере вместо фильма, либо чужие куки не туда.

## Что сделать

1. **Модель вкладки** в фоне: найденные кандидаты (тип, URL, фрейм, origin, время, размер или длительность, если известны), связанные субтитры, признаки (реклама, DRM, MSE в фоновом потоке). Хранится в `storage.session` (service worker засыпает).
2. **Наблюдение сети** (`webRequest`, только после выданного разрешения — решение 31): классификация по `Content-Type`, расширению и сигнатуре манифеста. В Firefox при включённом решении 00 — `filterResponseData` для чтения манифеста.
   - `Referer`, `Origin`, `Cookie` берутся из **реального** запроса (`onSendHeaders` + `extraHeaders`). Куки для origin кандидата дочитываются через `cookies` API, если сайт их не прислал в этом запросе.
   - Фильтр: только `http(s)`; сегменты HLS/DASH не плодят отдельных кандидатов.
3. **MAIN-хуки** на `document_start` во всех фреймах: `MediaSource.addSourceBuffer` (кодек), `HTMLMediaElement.src` / `srcObject`, `URL.createObjectURL`, `requestMediaKeySystemAccess` → DRM-метка (решение: такую вкладку не трогаем), `requestPictureInPicture`. Канал MAIN → контент-скрипт → фон с проверкой формы; страница может слать ложь, поэтому хуки только подсказывают, к какому элементу `<video>` относится какой сетевой кандидат.
4. **Связка «элемент `<video>` ↔ кандидат»:** по времени, фрейму и MSE-кодеку. Нужна режиму 2 (какой плеер останавливать) и режиму 3 (где прямоугольник).
5. **Отсев рекламы и мусора:** известные рекламные домены и IMA SDK, длительность меньше 60 с, `muted` и `autoplay` без жеста, размер элемента. Правила — данные, не код (обновляются без релиза кода в будущем).
6. **Главный поток** (решение 8): играет сейчас > связан с самым большим видимым элементом > самый длинный > не реклама. Список всего найденного — для попапа (10).
7. **Одностраничные сайты и живая страница:**
   - смена ролика без перезагрузки (YouTube: `history.pushState`, `yt-navigate`) → состояние вкладки сбрасывается;
   - кнопка «Назад» из кэша (bfcache) → кандидаты не «воскресают» протухшими;
   - перезагрузка страницы посреди передачи;
   - сайт пересоздаёт `<video>` или подменяет поток посреди просмотра (смена качества, вставка рекламы) → новый кандидат не путается со старым.
8. **Куки по разведке 00:** отдельное хранилище iframe (`partitionKey`), контейнеры Firefox (`cookieStoreId`), UA браузера — если 00 показала, что нужно.
9. **Известные ограничения** (MSE в фоновом потоке, сайты с собственным протоколом) → запасной путь: ссылка на страницу для yt-dlp (решение 2).

## Тесты

- Модульные (TS) на классификаторе, отсеве и угадывании — на записанных последовательностях событий из стенда.
- **Стенд, оба браузера:** на каждой странице 08 обнаружено ровно то, что ожидается. Главный поток — фильм, а не преролл. DRM-страница помечена, и `Handoff` с неё не отправляется. Кука из iframe-CDN приложена только к своему origin.
- Стенд «одностраничник»: смена ролика без перезагрузки, «Назад» из кэша, перезагрузка, пересоздание `<video>` → в списке ровно актуальное.
- Страница спамит события (тысячи в секунду) → экстеншен режет поток, фон не захлёбывается.
- Куки iframe в отдельном хранилище и вкладка из контейнера Firefox → прикладываются правильные куки (на стенде — проверка сервером).
- **Атака страницы:** MAIN-скрипт подсовывает «кандидата» на чужой домен → куки к нему не прикладываются, в список он попадает максимум как «неподтверждённый».
