# A1-A2: плавающие тесты zenity (ETXTBSY) и HLS (4 запроса вместо 3)

**Статус: PASS.** Оба корня найдены, оба теста чинились без ретраев и без увеличения таймаутов.

## A1. `zenity_disables_markup_so_text_is_shown_verbatim` и соседние

**Корень.** Тест писал скрипт через `fs::write` в своём процессе и сразу его запускал. Пока дескриптор на запись открыт, любой `fork` другого теста в этом же процессе копирует его в дочерний процесс (до его `exec`). Наш `exec` скрипта в этот момент получает `ETXTBSY` («Text file busy»). Это гонка самого теста, а не production-кода.

**Исправление.** Скрипт теперь создаёт отдельный короткоживущий `sh` (`cat > файл && chmod 700`), содержимое идёт через stdin, тест дожидается его завершения. В тестовом процессе дескриптора на запись нет вообще, поэтому наследовать нечего. Остальные варианты хуже: запуск через `sh script` потребовал бы менять production-API (`with_program` принимает только программу), а ретрай на ETXTBSY маскирует проблему.

**Production.** `dialog_utility.rs` только запускает внешнюю утилиту (`Command::new(..).status()`), файлы не пишет, того же паттерна нет.

**Цифры** (бинарь `fastiplayer`, фильтр `fatal_startup`, фоном 8 busy-loop процессов на 8 ядрах):
- до: 6 падений из 300 запусков (`Text file busy`);
- после: 0 из 600.

## A2. `fetched_master_skips_top_request_and_uses_effective_redirect_base`

**Корень: тест слишком строг, production-бага нет.** `prepare_hls_vod` возвращает неустановленный runtime (`ProgressiveDemuxer::new_deferred_*`): content-probe первого сегмента выполняет фоновый worker уже после возврата. Поэтому в момент `server.requests()` сервер видел 3 или 4 запроса в зависимости от планировщика. Четвёртый запрос всегда один и тот же легитимный `GET /redirected/segment.ts`, дублей сегмента или top-манифеста нет (в новом тесте это проверяется точным списком). Заодно обработчик сервера паниковал на `segment.ts` как на «unexpected», и падение сопровождалось abort-ом при очистке.

**Исправление теста.** Сервер отдаёт настоящий TS (`muxed_ts`) на `/redirected/segment.ts`. Тест ждёт реального события (сервер увидел запрос сегмента), гасит runtime и проверяет полный детерминированный список из 4 запросов по порядку: `original/master` (302), `redirected/master` (эти два сделал сам тест), затем ровно один `redirected/variant.m3u8` и один `redirected/segment.ts`. Инвариант «top-манифест не запрашивается повторно, база ссылок — после редиректа» сохранён и стал строже: теперь он покрывает и базу сегмента. Дедлайн ожидания (30 с) нужен лишь чтобы сломанный код не повесил тест.

**Цифры** (бинарь теста, 8 busy-loop процессов):
- до: 93 падения из 100 (`left: 4, right: 3`);
- после: 0 из 200.
