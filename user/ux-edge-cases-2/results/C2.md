# C2. Применение настроек подвешивает окно до ~15 с

Статус: PASS (вариант 1 владельца реализован: многокадровая транзакция настроек; живая проверка пройдена). Исследование — первые разделы, архитектура и итог — ниже.

## Корень (подтверждён по коду)
Цепочка целиком синхронная на UI-потоке:
`SettingsRuntime::apply_draft_with_runtime_adapter` -> `SettingsRuntimeApplyDelegate::apply_committed`
-> `FrameSettingsRuntimeAdapter::{apply_player_runtime_settings, apply_media_service_runtime_settings}`
-> `reconfigure_active_media` (`frame_prepare/settings_runtime_adapter.rs`)
-> `AppState::install_prepared_media_strong` -> `drive_media_open_to_terminal`
-> `PlaylistRuntime::wait_for_media_open_progress` (блокирующий `recv()` без срока).
Сверху время ограничено только player-owned `staged_video_preflight_timeout` (15 с).
Есть и второй блокирующий кусок ДО установки: `prepare_local_file` и
`prepare_source_synchronously` (web: сеть/yt-dlp) тоже идут прямо на UI-потоке и этим 15 с не ограничены.
Смена декодера/backend (`rebuild_video_pipeline_with_decoder_config`) тоже синхронна, но короче.

## Почему нельзя просто «перевести на stepwise, как Open»
Open — одиночная операция без побочных эффектов. Пересборка — часть транзакции настроек:
`validate -> preflight -> apply_committed (маршруты по порядку) -> persist -> finalize`,
и при сбое маршрута откатываются уже применённые маршруты (`rollback_committed`).
`apply_committed` обязан вернуть результат сразу (`settings-core/src/controller.rs`, `CommittedSettingsApplier`).
Сделать пересборку асинхронной = у транзакции появляется фаза «ждём результат пересборки»
между кадрами. Это меняет семантику транзакции (порядок запись на диск / откат / статус A11),
поэтому решение за владельцем.

## Варианты (простым языком)
1. Транзакция становится «многокадровой» (рекомендация исполнителя по честности).
   Apply сразу возвращает управление, статус «Применяем…», окно живое. Пересборка идёт тем же
   неблокирующим strong-open, что у Open (владелец pending-открытия, опрос каждый кадр).
   Только после успешной установки: запись config на диск и «применено». Ошибка -> откат
   прочих маршрутов и человеческий текст (как сейчас). Повторный Apply, пока идёт пересборка,
   -> «занято», первая не теряется; закрытие окна -> отмена. Плюс: сохраняется обещание A11
   «применено только после реального успеха». Минус: самый большой объём (новая фаза в
   settings-core, controller.rs уже 1624 строки, пришлось бы выносить в новый модуль; UI
   настроек должен показывать pending и блокировать правки).
2. «Сохранили сразу, пересобираем в фоне». Настройки применяются и пишутся на диск сразу,
   пересборка источника идёт отдельным фоновым действием; при ошибке настройки НЕ откатываются,
   показывается «Настройки сохранены, но источник не удалось переоткрыть, играет прежний вариант».
   Плюс: проще и быстрее. Минус: возможна рассинхронизация (в конфиге новая сеть, играет
   старый источник) и нет отката — меняет обещание транзакции.
3. Только смягчить: показывать «Применяем…» до блокировки и сократить таймаут для пересборки.
   Окно всё равно не отвечает какое-то время; это не лечение.
Дополнительно в любом варианте: подготовку источника (`prepare_*`) нужно вынести в фоновый
executor (как Open), иначе web-сеть/yt-dlp продолжат вешать UI.

## Исходное исследование (до реализации)
Живая репродукция тогда не выполнялась (код доказывает блокировку; аналогичное поведение Open измерено в сессии 18).


## Архитектура реализации (вариант 1, решение владельца)

### Владельцы состояния
- **settings-core / `SettingsController`** владеет фазой «ждём пересборку» транзакции: новое состояние `PendingApplyState` (план маршрутов, diff, результат validate) живёт в controller-е, пока маршрут не завершился. Вся новая логика — в новом модуле `settings-core/src/controller/pending_apply.rs` (`controller.rs` 1624 строки, туда только объявление `mod` и вынос общего «хвоста» apply: rollback/persist/finalize/commit становится приватным `finish_apply`, который используют и синхронный `apply`, и новый путь; файл при этом уменьшается).
- **app-egui / `SettingsRuntime`** владеет шагом по маршрутам между кадрами (`StepwiseRouteSequence`: упорядоченные маршруты, индекс следующего, накопленные отчёты, счётчик применённых для отката, маршрут «в полёте») — новый модуль `settings_runtime/stepwise_apply.rs`; и состоянием UI (`pending_apply`: Scheduled -> InFlight, `close_on_success`, громкость до Apply).
- **app-egui / `AppState`** владеет самой пересборкой media: `SettingsMediaRebuildOwner` (новый модуль `state/settings_media_rebuild.rs`, по образцу `LocalOpenInstallOwner` сессии 18): фазы `Preparing` (фоновый поток) -> `Installing` (общий слот stepwise strong-open) -> `RestoringState` (receipt восстановления позиции/дорожек) -> результат `AppRouteApplyResult`.

### Boundary-методы (по намерению)
- settings-core: `SettingsController::begin_apply(delegate) -> BeginApply::{Completed(ApplyReport), Pending, Busy}`; `poll_apply(delegate) -> PollApply::{Idle, Pending, Completed(ApplyReport)}`; `cancel_pending_apply(delegate) -> Option<ApplyReport>` (итог `ApplyFinalState::Cancelled`); `has_pending_apply()`. Трейт `StepwiseCommittedApplier<D>: CommittedSettingsApplier<D>` с `begin_apply_committed / poll_apply_committed / cancel_apply_committed` и `CommittedApplyProgress::{Finished(reports), Pending}`. Синхронные `apply` и `commit_runtime_setting` не меняют поведение; при pending они отказывают (транзакция одна).
- app route appliers: `begin_committed_route_stepwise(route, policy, host) -> RouteApplyStart::{Finished(report), Pending(continuation)}` и `finish_pending_route(continuation, rebuild_result, host)`. Pending бывает только у двух маршрутов: `Player` (шаг `media_pipeline`) и `MediaService` (пересборка источника). Остальные маршруты завершаются в `begin` за тот же кадр.
- host (`SettingsRuntimeReconfigureHost`): `begin_player_runtime_settings` / `finish_player_runtime_settings`, `begin_media_service_runtime_settings`, `poll_media_rebuild() -> MediaRebuildPoll::{Pending, Finished(result)}`, `cancel_media_rebuild()`. Старые синхронные методы остаются (блокирующий режим) для отката, `commit_runtime_setting` и тестов.

### Порядок маршрутов, persist, откат
1. Apply (кнопка) как и раньше сначала публикует статус на один кадр (`Scheduled`), на следующем кадре вызывается `begin_apply`: validate -> preflight -> маршруты по порядку. Синхронный маршрут завершается сразу, следующий берётся в том же вызове.
2. Маршрут с пересборкой отдаёт `Pending`; оставшиеся маршруты ждут (не стартуют), пока он не завершится. На каждом кадре `poll_apply` продвигает пересборку неблокирующе.
3. Persist и finalize происходят только когда ВСЕ маршруты завершились успехом (общий `finish_apply`): запись config и «применено» — после реального успеха.
4. Ошибка маршрута (в том числе Failed/PartialFailure из пересборки) -> тот же откат завершённых маршрутов в обратном порядке и человеческий текст A10/A11. Откат остаётся синхронным (блокирующий режим): он нужен только после сбоя и, если среди откатываемых есть маршрут пересборки, может подвесить окно (известный остаточный риск, вынесен в отчёт; отдельное решение владельца, если понадобится сделать и откат неблокирующим).

### Статус и UI
- Пока транзакция в полёте, `SettingsRuntime.pending_apply` остаётся `Some`: модель UI получает `is_busy = true` (Apply/OK неактивны — уже реализованный механизм), статус «Применяем настройки…» с пояснением «пересобираем источник, окно продолжает работать; в файл запишется только после успеха».
- Любое действие UI во время полёта (повторный Apply/OK, правки, Отмена/закрытие окна настроек) игнорируется с пометкой «занято»; первая транзакция не теряется. Решение про закрытие окна: **закрытие НЕ отменяет идущую пересборку** — Cancel означает «откатить draft и preview», что противоречит транзакции, уже применяющей этот draft; окно остаётся и показывает итог.
- Планировщик event loop считает pending-транзакцию фоновой работой (как pending strong-open), поэтому окно перерисовывается и опрос идёт без wake.

### Отмена при shutdown/suspend
`SettingsRuntime::cancel_pending_apply` вызывается в `flush_runtime_settings_for_lifecycle_boundary` до остальных flush-ей: отменяет фоновую подготовку (cooperative cancel), просит общий слот сделать lossless cancel (после enqueue пересборка обязана дойти до Installed — это правило coordinator-а), откатывает уже завершённые маршруты, controller возвращается к committed без persist (`ApplyFinalState::Cancelled`). Паники и запись config исключены.

### Подготовка источника с UI-потока
`prepare_local_file` и `prepare_source_synchronously` (web/yt-dlp) выполняет фоновый поток `SettingsMediaPrepareJob` (по образцу `LocalFileOpenJob` сессии 18: отдельный поток, результат через канал, cooperative cancel, join при отмене); UI-поток только опрашивает его. Блокирующий путь остаётся лишь у отката.

### Инварианты
1. Persist/finalize только после успеха всех маршрутов; до этого committed config и draft не меняются.
2. Не более одной транзакции: повторный `begin_apply` -> `Busy`, `commit_runtime_setting` во время pending отказывает.
3. Маршруты после pending-маршрута не стартуют, пока он не завершился; порядок и счётчик отката сохраняются.
4. Чужой terminal в общем strong-open слоте владелец не забирает (проверка request id); terminal забирается ровно один раз.
5. Синхронные маршруты без пересборки завершаются за один вызов (поведение не изменено).
6. UI-поток не вызывает `prepare_*` и blocking `recv()` в stepwise-пути.

### Тесты
settings-core (`controller/pending_apply/tests.rs`, fake delegate): pending не пишет persist и не меняет committed; завершение -> persist+finalize+committed обновлён; сбой -> rollback префикса, persist не вызван; повторный begin -> Busy и первая транзакция цела; cancel -> Cancelled без persist, committed цел; apply без pending-маршрутов = прежнее поведение.
app-egui: сквозные тесты `SettingsRuntime` с fake host (Apply с пересборкой: кадр не блокируется, статус «Применяем…», config не записан -> завершили -> «применено» и config записан; сбой установки -> откат прежних маршрутов, config не записан, человеческий текст; повторный Apply -> «занято»; shutdown во время pending -> отмена без паники, config не записан; транзакция без пересборки -> как раньше); `SettingsMediaRebuildOwner` с fake портом (подготовка вне вызывающего потока — фиксируется id потока; чужой request; exactly-once terminal).

## Итог реализации
Корень устранён: Apply больше не ждёт пересборку на UI-потоке. Транзакция стала многокадровой: `begin_apply` возвращает управление сразу, пока источник готовится в фоновом потоке, а установка идёт через общий неблокирующий strong-open; config пишется и «применено» показывается только после успеха всех маршрутов.

**Изменено.** `settings-core`: новый модуль `controller/pending_apply.rs` (`begin_apply`/`poll_apply`/`cancel_pending_apply`, трейт `StepwiseCommittedApplier`, `ApplyFinalState::Cancelled`; общий хвост `finish_apply`, `controller.rs` стал короче: 1624 -> 1443 строки). `app-egui`: `settings_runtime/stepwise_apply.rs` (очередь маршрутов между кадрами, статусы, отмена), `settings_runtime/route_apply/stepwise.rs` (Pending у Player/MediaService), новые методы host-а, `state/settings_media_rebuild.rs` + `prepare.rs` + `restore.rs` (владелец пересборки, фоновая подготовка, неблокирующее восстановление позиции), `media_open/cancellable_preparation.rs`, `begin_prepared_media_strong_with_backend_constraint`. Откат остаётся синхронным (блокирующий режим).

**Тесты (наблюдаемый результат).** settings-core (8): pending не пишет persist/не меняет committed; успех -> persist+finalize+commit ровно один раз; сбой после pending -> rollback без persist; ошибка делегата; повторный begin -> Busy и первая цела; sync `apply`/runtime-commit отказывают при pending; cancel -> `Cancelled` без persist; без pending-маршрутов = за один begin. app-egui `settings_runtime/tests/stepwise_apply.rs` (fake host, 7): пересборка не блокирует кадр, статус «Применяем настройки…», config НЕ записан, затем «сохранены и применены» и файл записан; сбой пересборки -> прежний маршрут (яркость) откачен, config нет, технический текст не в окне; повторный Apply/правка -> «занято», первая транзакция дошла до конца; shutdown во время pending -> отмена без паники и записи; транзакция без пересборки — за один кадр как раньше; Pending у Player route; ширина sidebar не пишется во время транзакции. `prepare/tests.rs` (8): подготовка идёт не на потоке вызывающего (id потока), опрос не блокируется, текст ошибки/паника, отмена доходит до задачи, токен выданного результата не отменяется при drop (регрессия из живой проверки), настоящий файл готовится. Source-guardrail: владелец и stepwise-ветка адаптера не вызывают блокирующие `install_prepared_media_strong`/`prepare_*`/`recv`/`wait_for_outcome`.

**Проверки.** `cargo test -p app-egui -p settings-core -p fastiplayer-settings -p fastiplayer-config --locked` зелёные (app-egui 1613, settings-core 38); `cargo clippy -p settings-core -p app-egui -p fastiplayer-settings --all-targets --locked -- -D warnings` (и app-egui `--all-features`); `cargo fmt --all --check`; `check-refactor-guardrails.py` и `check_s42_guardrails.py` OK (якорь guardrail на подготовку перенесён в `state/settings_media_rebuild/prepare.rs`, baseline `controller.rs` обновлён). Корректировка source-scan теста `state/tests.rs` под переехавший код.

**Живая проверка (release, изолированный профиль, KDE Wayland, uinput + spectacle).** Источник — mp4 по http (8 минут), сервер с задержкой ответа. Play -> Настройки -> network -> «RAM cache» -> Применить: статус «Применяем настройки…», Применить/OK неактивны, вкладки окна переключаются, видео и телеметрия продолжают идти (PTS 00:50 -> 00:52 -> 01:17, скриншоты c2_05..c2_08 и c2_13..c2_15 в рабочей папке сессии); при задержке 2,5 с/запрос рестарт источника шёл ~17 с без зависания окна, затем «Настройки сохранены и применены», в `config.toml` `memory_cache_mb = 700`, воспроизведение продолжилось с прежней позиции. Живая проверка нашла и закрыла баг: `Drop` фонового job-а отменял токен уже подготовленного источника и ломал его seek-поток («demux seek worker has stopped», PartialFailure -> откат); теперь токен отменяется только пока результат не выдан. При падении установки (до фикса) окно показало «Не удалось применить настройки; изменения отменены / «RAM cache»: применено только частично», config не записан.

**Ручная приёмка для владельца.** 1) Запустить с http-ссылкой на длинное видео, дать поиграть. 2) Настройки -> network -> изменить «RAM cache» -> «Применить». Видно «Применяем настройки…», окно живое, кнопки неактивны; через несколько секунд «сохранены и применены», видео продолжается с той же позиции. 3) Повторить с медленным/отвалившимся сервером: «Не удалось применить…», значение в config прежнее. 4) Закрыть плеер во время «Применяем…»: без зависания, config не меняется.

**Риски.** (1) Откат синхронный: если сбой случился после успешной пересборки (PartialFailure) или после второго маршрута-пересборки, откат может подвесить окно (решение владельца нужно, если важно). (2) Пауза/Play пользователем между началом установки и Installed даёт несовпадение intent -> PartialFailure -> откат. (3) AppState-цепочка (Preparing -> Installing -> RestoringState) проверена вживую и охранными тестами, но не юнит-тестом (нет AppState без Renderer). (4) Закрытие окна настроек во время применения игнорируется (решение: Cancel противоречит применяемому draft).
