# F1: плавающий тест metadata_sort (partial_probe_failure)

Статус: PASS.

## Корень
Не таймаут и не тест, а гонка в production. `MetadataSortOwner::drain` сначала читал события probe (`drain_probe_events`), потом забирал terminal (`take_final_summary`). События и terminal лежат в независимых слотах mailbox-а; worker публикует batch, затем terminal. Если оба публикуются между этими двумя чтениями, owner видит terminal, но batch уже «пропустил»: `patches` пустые, и Sort молча готовится без свежих метаданных. Соседние владельцы (`action_jobs::drain_manual/drain_visible`) этот случай уже закрывали повторным чтением после terminal, metadata_sort — нет.

Тот же дефект ронял второй тест, `premature_discovery_wakes_preserve_probe_then_commit_exact_sort` (`assert_eq!(patches.len(), 1)`), это, вероятно, «неопознанный» упавший тест из отчёта B1.

## Исправление
`crates/app-egui/src/playlist_runtime/discovery/metadata_sort.rs`, `MetadataSortOwner::drain`: после получения terminal повторно вызывается `drain_probe_events(probe)` до построения patches (с русским комментарием про инвариант).

## Тест
`probe_batch_published_with_terminal_is_never_lost_across_many_jobs` (tests.rs): 1000 job-ов подряд, каждый обязан вернуть 1 patch. Окно гонки микросекундное, поэтому тест нагружающий: на старом коде падает примерно в 1 из 5 запусков без нагрузки, на исправленном 0 из многих. Существующие тесты не менялись; в них синхронизация идёт через реальные состояния owner-а, дедлайн 2 с только страховка.

## Цифры (8 процессов `yes` на 8 ядрах, прогон модуля `metadata_sort`)

- После: 0 из 300 под нагрузкой; полный `cargo test -p app-egui`: 1623 passed.
