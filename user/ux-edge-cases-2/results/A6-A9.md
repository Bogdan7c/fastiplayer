# A6 + A9: poisoned URL-импорт и Undo удаления

Статус: A6 PASS; A9 PARTIAL (metadata-патчи исправлены, автопереход оставлен как есть и ждёт решения владельца).

## A6. Poisoned-владелец URL-импорта

Корень: `PlaylistUrlImportOwner::drain` при poisoned mutex на каждом вызове (каждый кадр) собирал новый `Failed(Internal)`, даже когда принятого запроса уже не было. Владелец не имел явного терминального состояния.

Решение (политика `mem:panic-invariant-policy`: poison не снимаем, fail-closed):
- poisoned = терминальное состояние владельца, перезапуска нет;
- о сбое сообщает `fail_active_request_after_poison`, который забирает `active_request`; отчёт поэтому одноразовый, а без принятого запроса молчит;
- новый `submit` после poison получает `WorkerUnavailable`, UI показывает это как явный отказ (`TopologyWorkerUnavailable`).

Изменено: `playlist_runtime/url_import.rs` (`drain`, новый `fail_active_request_after_poison`).
Тест: `poisoned_state_reports_failure_once_then_refuses_new_imports` (первый drain даёт `Failed(Internal)` с destination и доменом, следующие три дают `None`, индикатора нет, новый submit отказывает).

## A9. Undo удаления и фоновые правки

Корень: Undo сверял общую `dirty_revision`, которую двигает любое изменение, в том числе чисто фоновый metadata-патч (длительность, теги, обложка). Домен дополнительно требовал равенства `metadata_revision`, а при restore целиком подставлял snapshot, затёрлись бы свежие metadata соседей.

Сделано:
- `PlaylistController::undo_blocking_revision()`: растёт на всё, кроме чистых metadata-патчей (`commit_metadata_only_dirty`). Persistence по-прежнему получает dirty-сигнал патча. Undo сверяется с этой ревизией.
- `PlaylistQueue::restore_removal_snapshot`: больше не требует равенства `metadata_revision`; проверяет allocator-ы, structural +1 и порядок id оставшихся строк (по идентичности, не по содержимому); оставшиеся строки берёт из текущей очереди, возвращаемые из snapshot. Формат persistence не менялся.
- Структурные изменения (добавление, перемещение, сортировка, повторное удаление) по-прежнему инвалидируют Undo.

Изменено: `controller.rs`, `controller/metadata.rs`, `removal_undo.rs`, `playlist-core/src/queue/removal.rs`.
Тесты: `background_metadata_patch_of_other_row_keeps_undo_and_keeps_fresh_metadata`, `metadata_patch_then_structural_change_still_invalidates_undo` (app-egui), `snapshot_restore_after_metadata_patch_keeps_fresh_metadata_of_retained_rows` (playlist-core). Автопереход: существующий `successful_new_lineage_install_releases_undo_slot_immediately` фиксирует прежнюю семантику.

### Решение владельца: автопереход и Undo (не реализовано, не коммитилось)
Сейчас смена active lineage (автопереход к следующему треку) сбрасывает Undo. Просто убрать эту проверку нельзя: restore возвращает из snapshot «текущую строку» и историю shuffle на момент удаления, то есть откатит указатель на трек, который уже не играет. Варианты:
1. Оставить как есть (Undo живёт до автоперехода, 8 с окна). Просто, безопасно.
2. Если удалённая строка не была текущей: сохранять текущий указатель очереди, а из snapshot возвращать только строку. Без shuffle это несложно; с shuffle надо решать, как вписать возвращённую строку в историю/очередь воспроизведения.
3. Если удалена была играющая строка (tombstone): оставить сброс при автопереходе, так как возвращать «играющий» трек поверх уже играющего другого нельзя.
Рекомендация: вариант 2 для режима без shuffle, отдельной задачей после твоего решения про shuffle.
