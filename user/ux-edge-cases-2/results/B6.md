# B6: Hardware-only без VA-API — предупреждение в настройках

Статус: PASS.

## Решение владельца
Если выбран режим видео «Hardware», а VA-API на машине недоступен, окно настроек показывает одну строку предупреждения рядом с этой настройкой.

## Что происходило раньше
Режим «Hardware» не имеет запасного пути (`RequireBackend(vaapi)`). Без VA-API на открытии файла player отдаёт `RequiredVideoBackendUnavailable`, пользователь видел «Не удалось открыть «файл»: нет подходящего видеодекодера (проверьте настройку декодера)» — понятно, но без указания, что делать. В живых тостах player-а был ещё более общий текст «Выбранный способ показа видео недоступен…». Узнать о проблеме заранее было нельзя.

## Корень и решение
Вся информация уже была: при старте приложение выполняет capability probe (`probe_system_capabilities`, до первого кадра UI) и кладёт отчёт в `AppState`. Нового probe не добавлялось, UI-поток не блокируется.
- `settings_runtime/hardware_decode_hint.rs` (новый): `HardwareDecodeAvailability::{Unknown, Available, Unavailable}` выводится из отчёта (`from_system_capabilities`). «Недоступно» = VA-API не прошёл probe либо ни один его формат не проходит пересечение с renderer-ом. Нет VA-API в отчёте или отчёта нет — `Unknown`, строка не показывается.
- `SettingsRuntime::set_hardware_decode_availability` — intent-метод владельца; сбрасывает кэш модели только при реальной смене. Вызывается из `app_shell` сразу после probe.
- `SettingsRuntime::ui_fields` добавляет полю `video.preferred_backend` статус-строку, когда в черновике выбран «Hardware» и VA-API `Unavailable`. Рисует её существующий `render_field_messages`, UI-код не менялся. Строка следует за черновиком: появляется сразу при выборе «Hardware», исчезает при выборе «Авто», без Apply.
- Текст: «На этом компьютере аппаратное декодирование (VA-API) недоступно — видео не откроется. Выберите режим «Авто».»
- Ошибки открытия: «…нет подходящего видеодекодера (выберите режим «Авто» в настройках декодера)»; тост player-а: «Выбранный в настройках режим декодирования не подходит для этого видео или недоступен на этом компьютере. Выберите режим «Авто» в настройках». Названия режимов совпадают с UI.

## Тесты (app-egui 1535/1535)
`settings_runtime/tests/hardware_decode_hint.rs`: вывод доступности из отчёта (работает / probe провален / нет пригодных форматов / VA-API не упомянут); Hardware + недоступен — строка есть в модели и реально нарисована в egui-кадре; Hardware + доступен — нет; Auto + недоступен — нет; probe не готов — нет; смена режима в черновике и поздний результат probe при открытом окне. Текст ошибки: `player_error_message::tests::required_backend_unavailable_tells_to_pick_auto_mode`; обновлены ожидания трёх тестов про «нет подходящего видеодекодера».

## Проверки
`cargo test -p app-egui --locked`, `cargo clippy -p app-egui --all-targets --locked -- -D warnings`, `cargo fmt --all --check`, `scripts/check-refactor-guardrails.py` — зелёные. `settings_runtime.rs` вырос до ровно 700 строк (логика вынесена в новый модуль).

## Ручная приёмка (сделана)
Release-сборка, изолированный XDG-профиль, `video.preferred_backend = "hardware"`, `LIBVA_DRIVER_NAME=nonexistent`: в логе «1/2 video backend доступно», в Настройки → video строка предупреждения видна под выпадающим списком; выбор «Авто» убирает её. Для владельца: тот же запуск, скриншоты не коммитятся.

## Риски и улучшения
- Отчёт обновляется только при старте; пересоздание renderer-а отчёт app-а обновляет, а окно настроек — нет (VA-API на лету не появляется/исчезает, поэтому это принято).
- Возможное улучшение: если VA-API есть, но не умеет кодек конкретного файла — предупреждать по списку поддержанных кодеков (`playable_video_outputs`). Сейчас это покрывает только ошибка открытия.
- Тот же вид ошибки возвращается и для «Software», фразы поэтому общие («режим декодирования»), без слова «аппаратное».
