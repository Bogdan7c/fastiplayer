# D3. Stop во время подготовки источника отменяет открытие

Статус: PASS (код, тесты, живая проверка в release).

## Корень
Stop (единственный Stop-intent в приложении — MPRIS Stop; отдельной кнопки Stop в UI нет) шёл только в
`PlaylistRuntime::request_desktop_stop` и в exact-transport player-а. Подготовка, у которой ещё нет
coordinator-request-а, принадлежит другим владельцам: `StartupMediaController` (CLI-ссылка, restore;
yt-dlp, direct, нативные HLS/DASH/HDS/Smooth, локальный файл) и `AppState::local_file_open_job`
(кнопка Open, drag & drop, пересланный второй экземпляр, «Повторить» для файла). Они на Stop не
подписаны, поэтому Stop ничего не отменял и видео открывалось через ~30 с.

Элементы очереди (ручные и автоматические), «Повторить» для очереди и ссылки, а также установка из
Open получают coordinator-request сразу, и Stop отменяет их прежним guard-ом (`TransportStop`, тихая
отмена C5) — это закреплено новым тестом.

## Решение
- Словарь `media_open/preparation_cancel.rs`: `PreparationCancelCause::UserStop`, `PreparationCancelOutcome`.
- Intent-метод владельца стартовой подготовки: `StartupMediaController::cancel_pending_preparation`
  (`startup_media/user_stop.rs`). Поднимает уже существующие токены (флаг + токен источника: сеть и
  yt-dlp прерываются там, где слой их проверяет), сбрасывает winner, ставит Idle и запрещает restored
  fallback (Stop не перебирает очередь и не помечает элемент битым). Итоги job-ов отбрасываются молча
  (успех, ошибка и «завершился без результата»), без join на UI-потоке.
- Open-job: `LocalFileOpenJob::cancel_preparation` (диалог выбора файла не закрывается),
  `AppState::cancel_pending_local_file_preparation`; после отмены `drain()` превращает любой итог в `Cancelled`.
- Граница Stop: `transport_runtime/stop_preparation.rs`, вызывается перед обычным `request_desktop_stop`.
- Новых механизмов отмены нет: переиспользованы токены job-ов и `LocalFileOpenResult::Cancelled`.

`media_open/{mod,preparation_cancel}.rs`, `startup_media.rs`, `startup_media/user_stop.rs` (+`user_stop/tests.rs`),

## Тесты (наблюдаемый результат)
- Зависшая подготовка (синтетический worker): Stop поднимает флаг и токен, слот не освобождается без join,
  после «завершения» опоздавшая ошибка не показана, цель CLI не помечена проваленной, fallback запрещён, Idle.
- Cooperative worker (выходит без результата) — не превращается в ошибку; повторный Stop — `NothingPending`;
  Stop без подготовки ничего не меняет.
- Open-job: после Stop опубликованный итог становится `Cancelled`; без Stop тот же итог доходит как есть;
  диалог выбора Stop не трогает.
- Элемент очереди: Stop в AwaitingReady отменяет именно его request с `TransportStop`, очередь не идёт к B,
  отложенных команд нет, повторный Play строки открывает заново.
- Не покрыто тестами (нужен AppState с окном): сквозная цепочка UI; закрыто живой проверкой.

## Живая проверка (release, изолированный XDG, медленный http-сервер, задержка 30 с)
1. CLI-ссылка → «Подготовка direct media URL…» → MPRIS Stop → экран «Open a file or URL to start», через 40 с видео не
   открылось, ошибок и уведомлений нет (d3_00–d3_02).
2. Контроль без Stop (задержка 0): ссылка открывается в Paused как раньше (d3_10).
3. Restore (очередь с этой ссылкой, без CLI) → Stop во время подготовки → через 40 с пусто, ошибок нет (d3_20–d3_22) →
   кнопка Play в UI открывает элемент заново, воспроизведение идёт (d3_24).

## Ручная приёмка
Запустить плеер с медленной ссылкой, во время «Подготовка…» отправить Stop (`qdbus6 … Player.Stop`): подготовка пропадает,
видео не открывается, красных текстов нет; затем Play кнопкой в UI открывает заново.

## Риски и замечания
- Отдельной кнопки Stop в UI нет (только MPRIS), поэтому «кнопка Stop» из постановки не проверялась.
- MPRIS Play при пустом плеере не открывает элемент очереди (это делает только кнопка Play в UI через `idle_resume`) —
  существующее поведение, не менялось; можно вынести отдельной задачей.
- CLI-ссылка при отмене не попадает в очередь (элемент создаётся только после установки), поэтому Play после Stop
  с пустой очередью открывать нечего.
- Блокирующий read direct opener не прерывается (результат игнорируется, поток завершается сам).
- Retained startup actions при такой отмене не применяются (как и при других отказах до установки).
- Подготовка пересборки после настроек (C2) Stop не отменяет.
- Для измерения startup использована причина `Superseded` (файл `startup_readiness.rs` ровно на лимите 800 строк).
