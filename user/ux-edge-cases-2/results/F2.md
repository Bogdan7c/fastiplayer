# F2: «Audio underruns: 62» на старте live HLS

Статус: PASS

## Что выяснили
- Счётчик считает callback-и CPAL, где output выдал тишину из-за пустого ring buffer-а. Набегали они НЕ в воспроизведении, а до него.
- Корень: CPAL 0.15 на ALSA/PipeWire запускает stream сразу при построении. `AudioOutput` создаётся лениво по первому decoded PCM, а `play()` приходит позже, когда набран preroll (у live ~2 с). Код считал новый stream «на паузе», хотя он уже крутился: callback-и каждые ~32 мс с пустым ring-ом дали ~60 «underrun-ов» (62 у владельца). Слышимых дыр это не давало (тишина до старта, clock тишину не считает), но метрика врала, а PCM, записанный до `play()` (в т.ч. тишина-prefill из C3), мог уйти на устройство раньше времени.
- Воспроизведено до фикса (release, изолированный XDG, ts-live): radio 61, muxed live 60. VOD audio-only на старте 0, но ~119 после конца короткого файла (output после `Ended` продолжает крутиться; отдельное наблюдение, не чинил).

## Исправление (владелец — `crates/audio`, output)
- `output/lifecycle.rs`: `hold_new_stream` — stream ставится на backend-паузу сразу после построения; если backend паузу не умеет, остаётся logical gate.
- `output.rs`: clock замораживается ДО построения stream-а (без гонки с первым callback-ом), `backend_stream_state` берётся из реального исхода паузы. `play()` снимает заморозку как раньше.
- `output/callback_fill.rs` (новый): чистая часть data callback-а `fill_from_ring` с итогом `CallbackFill::{Held, Played}`; `Held` — не underrun, ring и clock не тронуты. Логика вынесена из `fill_buffer` без изменения поведения (`output.rs` 964 -> 953 строк, baseline обновлён).

## Тесты (`cargo test -p audio`: 100 PASS)

Тест с fake output в player-core не добавлен: фейк не моделирует CPAL callback, underrun — свойство concrete output-а.
