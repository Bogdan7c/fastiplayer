# F3: циклы Playing -> Buffering -> Playing у края live HLS

Статус: PASS

## Корень
- Демуксер live HLS уже читал по RFC 8216 §6.3.3: старт не ближе трёх target duration к концу плейлиста. Но часы плеера по контракту live-таймлайна (S31L) стартовали на самом live edge, а звук раньше часов плеер обрезает. Запас в 3 сегмента выбрасывался, фактический hold-back был нулевым: новый сегмент приходил ровно к моменту, когда он нужен, и плеер на каждом сегменте уходил в Buffering (пауза 10-120 мс, звук ставился на паузу).
- Правка порога входа в Buffering не нужна: он честный (запас кончился), а запаса просто не было.

## Исправление (владельцы)
- `web-media-hls/src/live/hold_back.rs` (новый): `HOLD_BACK_TARGET_DURATIONS = 3` (минимум по RFC), `join_position` (для main + отдельного audio берётся более поздний старт), `start_index_for_join`. Coordinator считает позицию входа один раз при открытии и публикует её; demux читает с сегмента этой позиции.
- `media-core::DynamicMediaTimelineState`: `join_position()` и `with_join_position()` (по умолчанию равна live edge, правее него нельзя; DASH и прочие источники не меняются).
- `player-core`: часы и позиция стартуют с `join_position` при первом открытии, при live same-item restore и при staged `AdjustedToLiveEdge`. Публичный `live_edge` остаётся настоящим краем эфира.

## Цена: задержка эфира
Плеер отстаёт от края на 3 target duration плюс остаток до следующего сегмента: target 2 с -> 6-8 с, target 6 с -> 18-24 с (на скриншоте `f3_radio6_after_25s.png` позиция 00:31 при конце окна 00:53). Это стандартное поведение (hls.js, Safari, ffplay). Не поддержан `EXT-X-SERVER-CONTROL:HOLD-BACK` (парсер его пропускает): когда добавим, значение сервера заменит константу. Если окно плейлиста короче hold-back (ffmpeg с `-hls_list_size 5` и target 6 с даёт 30 с, а 18 с нужны), играем с самого старого сегмента.

## Тесты
- `web-media-hls/src/live/hold_back.rs`: расстояние до края ровно 3 target (2 и 6 с), короткое окно, вытесненная позиция, main + audio, модель 60 с по расписанию (с hold-back запас не меньше двух сегментов; вход на краю даёт нулевой запас, то есть воспроизводит баг). Мутация «hold-back = 0» роняет 3 теста.
- `web-media-hls/tests/live_hold_back.rs`: реальный runtime по loopback: таймлайн отдаёт join = край - 3 с, первый пакет лежит в нужном сегменте.
- `player-core/src/session/tests/live_join_position.rs`: часы на join, не на edge; DVR-вариант; источник без hold-back стартует на краю; restore садится на join.
- `media-core`: валидация join (не правее edge) и доставка через порт.
- Регрессия обрыва сети (16): тесты `demux_retry` (runway меньше retry -> Buffering) без изменений и зелёные. Отдельный сквозной тест «60 с в player-core» не добавлял: нужен управляемый аудио-выход со временем; покрыто моделью и живой проверкой.

## Приёмка владельцем
Раздать ffmpeg live HLS (`-re`, `-hls_list_size 5`), открыть, включить telemetry: за минуту ни одного `Buffering`/спиннера, звук без микро-пауз; позиция заметно позади «конца окна».

## Риски и не сделано
- Play после долгой паузы (позиция вышла из DVR) по-прежнему прыгает на сам край: запас там нулевой, возможен один Buffering.
- DASH live (S35) hold-back не получил (join = край).
- Решения владельца не требуется; если задержка 18-24 с у 6-секундных сегментов покажется большой, нужна настройка (компромисс «задержка vs устойчивость»), но по RFC минимум именно 3.
