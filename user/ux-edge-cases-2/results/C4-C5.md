# C4-C5: тексты ошибок при пересоздании renderer и при отмене старта

## C4. Провал renderer-а после suspend/resume — статус PASS

**Корень.** `AppShell::restore_runtime` вызывается и при первом старте, и после suspend/resume. Провал `Renderer::new` в обоих случаях давал одну и ту же `FatalStartupError::graphics_unavailable`, а текст показывал «Fastiplayer не запустился… нужна видеокарта с Vulkan». Тип фатальной ошибки не различал фазу.

**Решение.** Фаза типизирована у владельца политики (`fatal_startup`): `FatalErrorPhase { Startup, RuntimeRecreation }`, поле `FatalStartupError::phase`, `notice_for(reason, phase)`. `AppShell` хранит `fatal_error_phase`: `Startup` до первого полного успеха `restore_runtime`, затем `RuntimeRecreation`; проставляется в единственной точке `exit_with_fatal_startup_error`. Тексты runtime-фазы: заголовок «Fastiplayer остановлен», «Не удалось восстановить вывод видео после выхода из сна или сворачивания окна: видеокарта или её драйвер не отвечают. Плеер закрывается. Запустите его снова…» (для внутреннего сбоя — аналогично с подсказкой про терминал). Технические причины в лог сохранены (в лог добавлено `phase`), в окно не попадают.

**Файлы.** `crates/app-egui/src/fatal_startup/{mod,messages,presentation}.rs`, тесты `fatal_startup/tests.rs`, `fatal_startup/messages/tests.rs`, `app_shell/mod.rs`.

**Тесты.** Startup → прежний заголовок и текст про Vulkan; RuntimeRecreation → новый заголовок/текст, без «Vulkan», «запустить вывод», «не запустился», в `technical_detail` остаётся причина; слот сохраняет фазу первой ошибки. Проводка `AppShell` (смена фазы) без живого event loop не тестируется: проверена ревью.

**Возможное улучшение (не сделано, нужно решение владельца).** После resume не закрывать процесс сразу, а один раз повторить создание renderer-а (драйвер после сна часто готов через долю секунды) и только потом показывать ошибку; либо перейти в режим «без видео». Сейчас поведение прежнее: ошибка → shutdown → код 1.

**Ручная приёмка.** Живьём не воспроизвести (нужен реальный сбой GPU после сна); достаточно тестов.

## C5. Отмена при старте без показа ошибки — статус PASS

**Корень.** Терминал coordinator-а `Cancelled` нёс причину отмены только в тестовой сборке (`#[cfg(test)]`), поэтому startup-политика не могла отличить «пользователь нажал Stop / приложение закрывается» от настоящей ошибки. Отмена без supersede шла по пути обычной pre-barrier ошибки: технический текст через `handle_install_failure` (CLI) либо пропуск восстановленного элемента как «битого».

**Решение.** `cause` стал полем production-терминала. `StrongMediaOpenError::is_cancelled_by_user_or_shutdown()` (match без `_`): `UserCancelled`, `TransportStop`, `LifecycleShutdown` — тихие; `Superseded`, `StructuralInvalidation`, `LifecycleSuspended` — как раньше. Новая политика `SilentUserCancel` в `startup_media/pending_install.rs`: ни окна, ни уведомления, ни перехода на следующий элемент или fallback; retained-действия применяются как при cancel-win; phase Idle; лог info. Реальные провалы (player/подготовка/протокол) не затронуты и тестами закреплены.

**Файлы.** `media_open/{types,coordinator}.rs`, `state/strong_media_open/user_failure_reason.rs` (+tests), `startup_media/pending_install.rs`.

**Тесты.** Классификация всех шести причин; политика для каждой причины (тихие → `SilentUserCancel`, остальные → `HandlePreBarrierFailure`, supersede-флаг главнее); реальный провал player-а → прежний человеческий текст «Не удалось открыть «clip.mkv»: …»; `MissingTerminal` остаётся sticky. Сквозного теста с `AppState` (нужно окно) в startup-слое нет: наблюдаемый результат закреплён на уровне решения политики.

**Живая проверка (release, изолированный XDG, медленный http-сервер).** CLI-ссылка, Stop через MPRIS во время «Подготовка direct media URL…»: ни ошибок, ни уведомлений, видео открылось в Paused (скриншоты c5_*). Закрытие окна во время открытия: штатное завершение, код 0, без диалога. Находка: Stop на стадии подготовки (до coordinator-request) сейчас ничего не отменяет — это отдельное решение владельца (должен ли Stop отменять подготовку источника).

**Проверки.** `cargo test -p app-egui --locked` (1622 passed), fmt, clippy `-D warnings`, оба guardrails — OK.

**Ручная приёмка.** Запустить плеер с медленной ссылкой, во время «Подготовка…» отправить Stop (MPRIS) или закрыть окно: красных текстов и окон ошибок нет.

**Риски.** Тихая отмена не различает «Stop» и «закрытие» в UI — оба просто молчат (лог info). Другие причины отмены (supersede/структурная/suspend) намеренно не менялись.

**Memories.** Обновлены `app-egui/startup-orchestration-s17` (C4) и `app-egui/media-open-coordinator-s10c` (C5). Прочитаны: core, app-egui/startup-orchestration-s17 (+ media-open-coordinator-s10c по grep). Context7: winit (`/rust-windowing/winit`, «ApplicationHandler resumed/suspended») — подтвердил, что `resumed` повторяется после suspend.
