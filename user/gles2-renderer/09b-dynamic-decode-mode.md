# Сессия 09b: режим декода Dynamic

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 09b плана `user/gles2-renderer/`: добавь режим декода `dynamic`. Он начинает на аппаратном декоде, а если аппаратный декодер не успевает за видео, сам переходит на программный, чтобы картинка оставалась плавной. Обратно на HW — только со следующим файлом. На рендере GLES2 покажи предупреждение с советом включить Dynamic. Сначала прочитай `user/gles2-renderer/README.md`, `results/00.md`, `results/09.md` и `results/09a.md`.

## Зачем

Решения владельца 13–15. На слабом железе аппаратный декодер может быть медленнее нужного. На T410 потолок H.264 1080p — ~39 кадров/с, и HW 1080p60 невозможен. Программный декод того же видео при этом успевает. mpv и VLC выбирают путь один раз и вслепую: в HW-режиме они теряют кадры, в SW жгут батарею на лёгком видео. Dynamic даёт лучшее из двух: батарея на лёгком видео (GPU), плавность на тяжёлом (CPU).

## Решения владельца (не пересматривать без него)

- Новое значение `video.preferred_backend = "dynamic"` рядом с `auto` / `hardware` / `software`. **По умолчанию остаётся `auto`.**
- Dynamic = «предпочитать HW» + переход на SW, когда HW-декодер не тянет поток.
- Возврат с SW на HW — **только со следующим файлом** (внутри файла — бэклог).
- **Предупреждение на рендере GLES2**: «производительность может теряться, желательно включить Dynamic». На wgpu его нет. Та же политика потом — для legacy-рендера на Windows. Где именно его показать (строка в настройках, как у `hardware-decode-warning-b6`, и/или уведомление) — предложить владельцу варианты в начале сессии.
- Критерий успеха на T410 (сессия 11) мерится в режиме Dynamic.

## Архитектура — описать владельцу до кода (правило 9)

- **Сигнал «HW не успевает»** — только про декодер, не про сеть и не про рендер:
  - кадры декодера стабильно опаздывают к дедлайну показа / очередь готовых кадров пустеет, пока пакеты есть;
  - буферизация сети, пауза, seek/scrub и стартовый preroll — не сигнал (окно тишины после них);
  - гистерезис: устойчиво N секунд, а не один медленный кадр.
- **Кто решает**: политика — у владельца выбора бэкенда (сейчас `app-egui::video_pipeline_selector` + player-core). Сигнал — нейтральный счётчик/событие из player-core, без знания VA-API. Найти точного владельца разведкой, а не дописывать «куда удобно».
- **Как переключает**: существующий путь живой смены HW↔SW (`mem:video-ffmpeg/sw-to-hw-backend-swap-frame-contract-fix`, `mem:render-video/live-backend-swap-present-frame-freeze`) с сохранением позиции, без чёрного кадра.
- **Без пинг-понга**: если и SW не успевает (CPU тоже не тянет), остаёмся на SW и не прыгаем обратно. Решение «переключились» живёт до конца файла.
- Пользователь видит короткое уведомление о переходе (английский текст, `mem:app-egui/user-facing-language`), через владельца уведомлений `mem:app-egui/notifications`.
- Конфиг: миграция схемы (`mem:config/schema-store-decomposition-s23`). Старые значения не меняются, `dynamic` — новое допустимое значение. Настройки: пункт выбора + описание простыми словами.

## Тесты (результат, а не вызов)

- Fake-декодер, который отстаёт устойчиво → ровно один переход на SW, позиция сохранена, кадры дальше идут из SW.
- Короткий всплеск опоздания (seek, scrub, старт, буферизация сети) → перехода нет.
- SW тоже отстаёт → обратного прыжка нет.
- Следующий файл в Dynamic снова начинает с HW.
- `auto` / `hardware` / `software` ведут себя как раньше (регрессия выбора).
- Предупреждение: показывается при рендере GLES2 и не-Dynamic режиме, не показывается на wgpu и в Dynamic.
- Миграция конфига и сохранение выбора.

## Ручная приёмка

- T410, Dynamic, нативный Wayland и XWayland:
  - H.264 720p30 остаётся на HW (дёшево по CPU);
  - H.264 1080p60 переходит на SW и играет без потерь;
  - 1080p30/720p60 — как скажет бюджет (после 09a);
  - seek/scrub/пауза после перехода — без сбоев.
- 780M: Dynamic не переключается на обычных сценах (HW там с огромным запасом).

## Критерий выхода

- Dynamic работает по решениям владельца, тесты зелёные, приёмка на обеих машинах пройдена.
- Записаны пороги сигнала и их обоснование замером (сколько кадров/секунд отставания — переход).
