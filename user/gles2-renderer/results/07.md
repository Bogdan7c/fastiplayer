# Результат сессии 07: аппаратный zero-copy — DMA-BUF → EGLImage

## Статус

**DONE.** 25 октября 2026.

Аппаратный H.264 через VA-API доходит до экрана GLES2 без единой копии. Путь кадра такой:

1. поверхность декодера экспортируется как DMA-BUF;
2. плоскость Y импортируется в `EGLImage` как `R8`, плоскость UV — как `GR88`;
3. обе становятся обычными текстурами `sampler2D`;
4. цвет считает наш шейдер.

Доказано на обеих машинах:

| Что | Radeon 780M (radeonsi) | ThinkPad T410 (Ironlake, crocus) |
|---|---|---|
| Байт, скопированных в текстуры | **0** | **0** |
| Импортов на 600 кадров | 21 (пул декодера — 24) | 11–21 |
| Модификатор поверхности | `0x0200000010401b04` (тайловый AMD) | `0x0` (`LINEAR`) |
| Кадров вернул поток-ожидатель | 599 из 600 | все, кроме первого |
| Паритет с wgpu, NV12 (6 сцен) | max Δ **1** | — (на T410 нет Vulkan) |

Критерий выхода:
- zero-copy доказан счётчиками на обеих машинах, профиль `perf` не снят (см. «Ограничения»);
- освобождение кадра покрыто тестами, пул декодера не истощается ни на паузе, ни при спящем UI;
- ограничения драйверов записаны в таблицу совместимости ниже.

## Решения владельца (25.10.2026, в README — 32–33)

32. **Кадр возвращается декодеру потоком-ожидателем внутри GLES2-рендера.**
    - Поток спит в ядре на fence кадра показа и сразу отдаёт кадр, когда GPU его дочитал.
    - Приложение и его цикл событий не меняются. Освобождение не зависит от того, нарисует ли интерфейс следующий кадр.
    - Отклонённый вариант — «будить приложение по таймеру». Он затащил бы детали рендера в приложение и будил бы процессор на паузе.
33. **10-битный HW-декод (P010 через DMA-BUF) в GLES2 не объявляется и не делается.**
    - Довод владельца: GPU с аппаратным 10-битным декодом всегда тянет wgpu/Vulkan.
    - На GLES2 10-битное видео идёт программным декодом. Он полностью работает с сессии 06.
    - Пункт 5 плана 07 отменён вместе с вопросом, как фильтровать P010.

## Найденные дефекты и их причины

1. **На T410 перезапись памяти процессором не видна GPU** (3 теста перезаписи udmabuf).
   - Причина доказана экспериментом из 6 вариантов. У Ironlake нет общего с процессором кэша (LLC). GPU читает чужой dma-buf мимо кэша CPU, а запись процессора лежит в кэше.
   - i915 сбрасывает кэш только при первой привязке страниц, поэтому первый кадр верен.
   - `DMA_BUF_IOCTL_SYNC` на x86 у `udmabuf` кэш не сбрасывает. Помогает только `clflush` по записанному диапазону.
   - Исправление в тестах: тестовый «производитель» соблюдает протокол записи CPU в dma-buf (`SYNC` + `clflush`). Проверка не ослаблена.
   - Настоящий VA-декодер этим не страдает: он пишет силами GPU, 400 разных кадров из 400.
   - **Важно для сессии 12** (программный кадр «без копий» через udmabuf на T410): CPU-декодер обязан сбрасывать кэш по кадру, иначе со второго кадра GPU покажет старые данные. Первый кадр будет верным и замаскирует дефект.
2. **На T410 процесс падал при выходе** (`corrupted double-linked list`), если поток-ожидатель хоть раз работал.
   - Причина доказана на T410 вариантами разборки (по 10 прогонов) и gdb. Последний fence держал `EGLDisplay` живым.
   - Этот fence умирал в потоке-ожидателе (`eglDestroySync` + последний `eglTerminate`) уже после уничтожения контекста, одновременно с `exit()` и обработчиками завершения Mesa.
   - Исправление у владельца — в привязке: `renderer_detaching(grace)`.
     - Рендер зовёт его перед уничтожением `Gles2Context`.
     - Метод дожидается fence ожидающих кадров (до 250 мс), отпускает кадры ровно один раз и уничтожает все fence в потоке рендера, пока контекст жив.
     - Плюс страховка в `Drop` последнего клона.
   - На T410: 25 из 25 прогонов без падений; без исправления было 10 из 10 падений.
   - Цена: если GPU завис и fence не сработал за 250 мс, кадр возвращается декодеру без fence. Показывать его уже некуда, рендер уничтожается. Отдельный счётчик `released_at_renderer_detach_unfinished`.
3. **CI красный с сессии 06: `byte_pairs_reach_the_shader_as_exact_codes` на llvmpipe** (12-битный код терял 1/8).
   - Причина: в GLSL ES 1.00 (§4.5.3) у `sampler2D` во фрагментном шейдере точность по умолчанию `lowp`, а результат `texture2D` наследует точность сэмплера.
   - llvmpipe урезает `lowp`; radeonsi и crocus — нет, поэтому сессия 06 этого не видела.
   - Исправление: `precision highp sampler2D;` в программах 10/12 бит и HDR. Тест зелёный на трёх драйверах, паритет не изменился.
4. **Тесты отказа драйвера падали на llvmpipe** (среда CI).
   - Причина: программные драйверы Mesa не проверяют fd при `eglCreateImage` и «импортируют» даже `/dev/null` и конец pipe (проверено).
   - Эти два теста на llvmpipe/softpipe пропускаются с явной причиной. На аппаратном драйвере принятый не-dma-buf — падение теста.
5. **Паспорт буфера в первой версии требовал offset/pitch плоскостей.**
   - Путь «попадание в кэш без dup fd» был бы невозможен: дешёвый поиск у VA-API их не отдаёт.
   - Исправлено до встраивания: паспорт = только то, что даёт поиск идентичности.

## Известные ограничения

- **Встраивания в приложение нет** — это сессия 09. Что ей сделать:
  - склад импорта GLES2 за `VideoFrameImport`;
  - `set_dma_buf_import_capacity` по плану импорта;
  - `purge_dma_buf_imports` при смене декодера;
  - `publish_presented_frame_fence` после каждого кадра показа;
  - `renderer_detaching` перед уничтожением контекста;
  - перевод исходов в `FrameMaterializationOutcome`.
- **`perf` не снят** (`perf_event_paranoid = 2` на обеих машинах, без sudo). «Нет копии» доказано счётчиками: `copied_bytes = 0`, `upload_calls = 0`, импортов не больше пула, байт-в-байт картинка.
- **udmabuf бывает только `LINEAR`:** тайловый путь проверен живым VA-API на 780M, тестом — нет.
- **Поток VA-API декодера не присоединяется при уничтожении** (`VideoDecodeThread` без `join`). В сериях P6 не падал, но это тот же класс риска, что дефект 2. Записано в общий бэклог (п. 13).
- При отвязке рендера кадр, чей fence не сработал за 250 мс, возвращается без fence (дефект 2, осознанная цена).
