# Результат сессии 13b: AV1 без копии вживую на T410 и T480s

## Статус

**DONE** (28 октября 2026). Программный AV1 без CPU-копии (сессия 13) проверен на двух машинах без аппаратного AV1:
- T410 — GLES2, нативный Wayland и XWayland;
- T480s — оба рендера: Auto = wgpu (Vulkan) и принудительный GLES2.

На обеих машинах все кадры AV1 идут без копии. В каждой ячейке оба прогона без копии ниже обоих прогонов копии по главному потоку, кадры те же. Против mpv и VLC CPU процесса ниже на всех сценах, где соперник играет без потерь. На 1080p60 у T410 mpv теряет кадры, а мы нет.

| AV1, SW, окно 20 с, среднее двух прогонов (ABBA) | главный поток: копия → без копии | CPU процесса: копия → без копии |
|---|---|---|
| T410 1080p60, Wayland | 24,1 → **18,1** (−25 %) | 168,7 → **159,3** |
| T410 1080p60, XWayland | 25,0 → **18,5** (−26 %) | 171,8 → **161,8** |
| T480s 1080p60, wgpu | 8,6 → **5,8** (−33 %) | 64,5 → **62,6** |
| T480s 1080p60, GLES2 | 6,8 → **3,6** (−47 %) | 60,9 → **58,8** |

Проценты — доля одного ядра.

Попутно найдено и починено:
- GLES2 на повторном показе того же кадра заново сбрасывал кэш CPU и считал кадр ещё раз (решение 91);
- давний дефект ядра плеера: если звук в файле кончается раньше видео (или пропадает посередине), картинка застывала, и файл не заканчивался. Частный случай — seek за последний кадр AV1. Время показа теперь переходит к монотонным часам, пока звука нет (решение 92).

## Решения владельца (28.10.2026, в README — 90–92)

- **90. Метод 13b:** протокол v4 на обеих машинах параллельно, на T410 оба режима окна полностью, общий бюджет — не больше 2 часов. Главного потока в v4 нет, поэтому «копия против без копии» дополнительно снята короткими ABBA-прогонами.
- **91. Повторный показ кадра в GLES2 чинится в самой сессии** (а не в бэклог): правка маленькая, тест падает без неё, домер — короткий ABBA.
- **92. «Звук кончился раньше видео — файл не заканчивается» чинится в самой сессии**, с выходом за бюджет 2 часа.
  - Исполнитель — сабагент Opus с усилием high, по слову владельца.
  - Объём рос в два шага, на каждом владелец подтвердил «чинить сейчас»: сначала seek за последний кадр AV1, потом короткий хвост видео, потом звук, который кончается задолго до конца видео.
  - Перед последним шагом владелец остановил проверки на ноутах (отключение света): живая проверка второй части — только на основной машине.

## Метод

Скрипты и сырые логи — в scratchpad сессии, в репозиторий не входят. Обе машины: от сети, экран не заблокирован, курсор при замерах не трогали (решение 71), «Системный монитор» закрыт. Стоп-кран на рост `GPU HANG` в `journalctl -k` — за всю сессию 0 новых зависаний на обеих машинах.

Файлы (`make_matrix.py --preset t410`): AV1 Main 8 бит 720p30 3 Мбит/с, 1080p30 10 Мбит/с, 1080p60 15 Мбит/с; на T480s ещё 4K60 40 Мбит/с из `benchmark-matrix`. Для жизненного цикла — AV1 Main **10 бит** 720p30 / 1080p30 (SVT-AV1, теги BT.709), нарезка 12 с.

1. **ABBA «копия / без копии»** — скрипт по образцу `profile_run` сессии 12a.2:
   - прогрев 12 с, окно 20 с, порядок «без копии, копия, копия, без копии» в каждой ячейке;
   - CPU по потокам из `/proc/<pid>/task` (главный поток — поток с TID процесса), KWin и Xwayland, Render/3D (`intel_gpu_top`, только T410), RSS;
   - новые кадры и опоздания (интервал > 1,5 номинала) — из трассы кадра `render frame stage timings`;
   - **путь кадра** — разность `sw_frames_without_cpu_copy` / `sw_frames_cpu_copied` за окно (сессия 13a).

   T410: 3 сцены × 2 режима окна, T480s: 4 сцены × 2 рендера — 56 прогонов, ~13 / ~17 минут.
2. **Протокол v4 с соперниками** (`docs/benchmarks/tools/local`, `run_series.py`), два diagnostic-повтора на плеер (порядок по чётности), `losses: annotate_all`, quality-gate по уникальным кадрам. В плане не больше 3 плееров, поэтому когорты такие:
   - T410 Wayland: без копии, копия, mpv (`--vo=dmabuf-wayland` на 30 fps и `--vo=gpu --gpu-api=opengl --gpu-context=wayland --profile=fast` на 60 fps — лучшие режимы mpv на T410 по сессиям 00/11/12a);
   - T410 XWayland: без копии, копия, VLC (`--avcodec-hw=none --vout=gl`); отдельно без копии против mpv `--vo=xv` (единственный чистый SW 60 fps соперника под XWayland в сессии 00);
   - T480s Wayland, wgpu: без копии, копия, mpv (`--vo=gpu-next --gpu-api=vulkan`);
   - T480s XWayland: без копии wgpu, без копии GLES2, VLC.

   Все плееры — программный декод (`--hwdec=no` / `--avcodec-hw=none`). Шесть серий, ~55 минут машинного времени.
3. **Жизненный цикл** — виртуальные мышь и клавиатура через `/dev/uinput` (абсолютный «планшет»), финальная сборка с правкой 91. Координаты таймлайна для scrub — по снимку экрана с открытой панелью (91,5 % высоты на обеих машинах). На T410 оба режима окна, на T480s оба рендера.

Метод ABBA быстрый (без cgroup и quality-gate), v4 — строгий по окну и кадрам, но с двумя повторами. Строгие числа — в сессии 14.

## Находка: повторный показ кадра в GLES2 (решение 91, починено)

**Симптом.** У GLES2 счётчик «без копии» за окно больше числа новых кадров: T410 1080p30 — 677–704 при ~607, T480s 4K60 — 1203 при ~860. У копии и у wgpu счётчик совпадает с кадрами.

**Причина** (`render-gles2-shell/src/host_block_import.rs`, `show_block`). Видеослой показывает один и тот же кадр повторно, когда интерфейс перерисовался или декодер отстал. Копия на повтор отвечает `UploadOutcome::AlreadyCurrent` и ничего не делает. А путь без копии:
- сбрасывал кэш CPU видимых строк **до** проверки «кадр уже текущий» (на Ironlake это ~1,2–1,7 мс главного потока на кадр 1080p, сессия 12);
- считал повтор новым кадром.

Комментарий в коде уже говорил «на каждый новый кадр» — реализация с ним расходилась.

**Правка.** `show_block` сначала спрашивает видеослой. Ответ «этот кадр уже текущий» — внутренний исход `BlockShow::AlreadyCurrent` без сброса кэша и без счёта. Сброс и счёт — только у нового кадра (`BlockShow::NewFrame`). Граница `HostBlockZeroCopy::try_show → ZeroCopyShow` для вызывающего не меняется: кадр на экране без копии в обоих случаях.

**Тест** `host_block_import::tests::a_repeated_show_of_the_current_frame_neither_flushes_nor_counts` (настоящий EGL):
- три показа одного кадра → `Shown` все три, но 1 сброс кэша, 1 кадр в счётчике, 1 dma-buf;
- новый кадр в том же блоке → 2 сброса, 2 кадра;
- пиксели обоих кадров равны пути копии.

Мутация «старый `host_block_import.rs`» — тест падает (счётчик 3 вместо 1).

**Домер** (ABBA, окно 20 с, без правки → с правкой):

| T410 XWayland 1080p30 | 14,9 / 14,9 → **14,2 / 14,3** | 107,95 → 107,45 | 690, 700 → **607, 607** (605–607) |

- На T480s сброс не нужен (общий кэш), CPU тот же — меняется только честность счётчика.

## Жизненный цикл (финальная сборка)

Сценарий одного запуска (очередь из двух файлов: AV1 **10 бит** 12 с, затем AV1 8 бит 1080p30), по фазам считались новые кадры и путь кадра из трассы:

| продолжение 2,5 с | 68 | 67 | 68 | 69 |

| seek +60 / −10 | 2 / 80 | 2 / 78 | 80 / 81 | 81 / 81 |

| «предыдущий файл» | 164 | 164 | 164 | 166 |

### Находка: файл не заканчивается, если звук кончился раньше видео (решение 92)

**Симптом в сценарии.** На T410 seek +5 у конца 12-секундного AV1-файла: плеер встал на последнем кадре и не перешёл ко второму файлу очереди — 0 новых кадров за 6 с.

**Не регрессия сессии 13.** Отдельная проверка на T410, по одному запуску на случай:

| Случай | Сборка | Итог |
|---|---|---|
| AV1 10 бит, обычный досмотр до конца | без копии | следующий файл, 294 кадра |
| AV1 10 бит, seek за последний кадр | без копии | **встал** (1 кадр за 10 с) |
| то же | **копия** (FFmpeg без патча dav1d) | **встал** |
| AV1 8 бит, seek за последний кадр | без копии | **встал** |
| H.264, seek в конец (кадр с PTS = цели есть) | без копии | следующий файл |
| H.264, **звук 10 с, видео 12 с**, обычный досмотр без seek | без копии | **встал на 10-й секунде** |

Последняя строка показала, что AV1 и seek тут ни при чём.

**Причина** (трасса `player_core=trace`). Seek к цели 12 000 мс за последним кадром (~11 967) коммитится на fallback-кадре 11 900 (`commit_position_policy="eof-fallback-frame"`). Звук после seek начинается с цели, поэтому его отрезок 11 900–12 000 отброшен. Дальше тысячи раз подряд:

```
EOF drain waiting blocker=Some(VideoPresentQueue { queued_frames: 2 }) playback_state=Draining
current_position_ms=11900.0 audio_eof_drain_state=DrainedOutput audio_clock_now_ms=0.0
```

Время показа ведут аудиочасы (`player-core/src/session/position_clock.rs`, `presentation_clock_position_at`). Когда звук доигран, они встают, а передачи времени другим часам не было. Кадры после конца звука никогда не становились «пора показывать», EOF-drain вечно ждал очередь видео. Заплатка `queued_video_frames_unreachable_after_audio_end` покрывала только кадры **за** длительностью файла. Вторая точка той же связки — запас декода (`video_decode_ahead_lead`) тоже считался от вставших аудиочасов.

**Третья ловушка того же корня — звук кончается задолго до конца видео.** Нашлась живой проверкой первой правки: 5 с звука на 20 с видео. Сессия ещё в `Playing`, демуксер не дошёл до EOF. Трасса:

```
Demux backpressure: waiting for downstream capacity pause_reason=WaitingForDemuxAudioPriority
  pending_audio_packets=0 pending_video_packets=240 queued_video_frames=0 audio_buffer_ms=Some(0.0)
A/V sync: holding video packet to limit decode-ahead
```

Это взаимная блокировка:
- демуксер «догоняет звук» и читает видео до лимита 240 пакетов, ожидая аудио, которого в файле нет;
- декодер держит видео, потому что аудиочасы стоят;
- до EOF дело не доходит.

Пауза в звуке посреди файла (звук 0–5 и 12–20 с) без блокировки давала склейку: звук 12-й секунды звучал на позиции 5 с.

**Правка** (`player-core`, исполнитель Opus по решению владельца, проверка и приёмка — основной агент). Поведение как у mpv/VLC: пока звука нет, время ведут монотонные часы, видео играет непрерывно, звук возвращается на своём PTS.
- **Владелец времени** — `PlaybackPipeline`, новый модуль `pipeline/presentation_clock_handover.rs`:
  - источник времени `PresentationClockSource::{AudioOutput, MonotonicAfterAudioEnd, MonotonicWithoutAudio}`;
  - явные шаги `hand_over_presentation_clock_after_audio_end` (хвост видео в EOF-drain) и `hand_over_presentation_clock_for_audio_gap` (разрыв в `Playing`), возврат `resume_audio_clock_after_gap`;
  - исходы раздельные, без общего `bool`.
- **Когда время передаётся — только по доказательству, не по таймеру** (`session/audio_gap.rs`):
  - следующий аудио-пакет начинается позже конца записанного звука больше чем на 500 мс — это факт контейнера;
  - демуксер упёрся в лимит видео без единого аудио-пакета, а звук доигран. Файл читается по порядку, значит, в этом отрезке звука нет; без передачи это вечная блокировка.

  В обоих случаях звук до разрыва доигрывается полностью.
- **Пока время у монотонных часов**, догон звука в демуксере и предел запаса декода не ждут аудиочасы. Звук после разрыва ждёт своего PTS, затем перепривязывает часы к текущей позиции: позиция назад не прыгает, звук совпадает с видео.
- **Передача сбрасывается** на seek / новом поколении, при перепривязке и установке аудиочасов, при повторе после конца и при закрытии. Пауза в хвосте замораживает позицию, скорость 2× сохраняется.
- Файлы, где звук и видео кончаются вместе, ведут себя как раньше: передачи не происходит, это закреплено тестом.

**Тесты** — функциональные, через настоящий tick сессии: demux → fake-декодер → показ, модель звуковой карты в реальном темпе.
- `session/tests/eof_audio_ends_before_video.rs`, 7 тестов: хвост показан по кадрам и `Ended`; seek за последний кадр → `Ended`; пауза в хвосте; 2× в хвосте; seek назад из хвоста; повтор после конца; звук и видео кончаются вместе → передачи нет.
- `session/tests/audio_gap_clock_handover.rs`, 4 теста:
  - звук 5 с из 20 → все кадры и `Ended`;
  - пауза 5–12 с → видео непрерывно, звук возвращается на 12,0–12,1 с, записанный PCM совпадает с отрезком [возврат, 20 с) ±5 мс;
  - редкие аудио-пакеты (1 с) с отставанием 2 с → **ложной передачи нет**;
  - seek назад из паузы.
- `pipeline/tests/presentation_clock_handover.rs` — 10 focused-тестов API.
- Мутации (каждая откатывалась):
  - без передачи тесты падают ровно как вживую (`state=Draining position=10s presented=[10.25s]`, `state=Playing position=5s pending_video=40`);
  - без сброса передачи падают seek и повтор;
  - сдвиг привязки на 80 мс ловится как рассинхрон;
  - ослабленное доказательство «демуксер упёрся» ловится тестом редких пакетов.
- `cargo test -p player-core` — 1028 зелёных.

**Живьём на основной машине** (780M, wgpu, программный декод, A/B «до» = сборка с правкой 91 / «после» = итог). Ноуты к этому времени владелец отключил от проверок.

| Файл, очередь из двух файлов | до | после |
|---|---|---|
| H.264, звук 5 с / видео 20 с, досмотр | 17 новых кадров за 20 с, встал | 585 кадров: хвост 15 с + следующий файл |
| H.264, пауза в звуке 5–12 с (MKV, настоящая дыра в пакетах) | 233 кадра за 20 с, файл не закончился | весь файл + следующий. Звук вернулся на 12 127 мс при PTS первого пакета 12 121; часы непрерывны всю паузу (шаг PTS показанных кадров 33–34 мс, один пропуск на 745) |
| H.264, звук 10 с / видео 12 с | — | хвост + следующий файл |
| AV1, seek за последний кадр | — | следующий файл |
| H.264 12 с, звук и видео вместе (регрессия) | 264 / 213 кадров за 9,5 с, следующий файл | 266 / 272, следующий файл |

Раньше, до отключения ноутов, первая часть правки прошла на T410: H.264 со звуком 10/12 с и AV1 seek за последний кадр — до правки стоят, после переходят к следующему файлу; естественный EOF AV1 без изменений.

**Остаётся** (риски исполнителя, в бэклог не выносились):
- разрывы звука короче 500 мс склеиваются, как и раньше;
- если звук в файле перемежён с видео с отставанием больше лимита догона (240 пакетов), такой поздний звук будет обрезан как прошедший — раньше в этом случае была вечная блокировка;
- seek внутрь паузы в звуке отдельным тестом не проверен;
- живой проверки второй части на T410/T480s нет — ноуты отключены владельцем до его команды;
- во время паузы в звуке раз в 2 с пишется предупреждение `Audio output starvation observation` (звук намеренно удержан) — шум в логе, не ошибка.
