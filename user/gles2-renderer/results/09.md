# Результат сессии 09: встраивание в приложение и выбор рендера

## Статус

**DONE.** 25 октября 2026.

Fastiplayer впервые играет на собственном рендере OpenGL ES 2.0, и не на стенде, а как обычное приложение. Рендер сам выбирается на старте: аппаратный Vulkan → wgpu, иначе GLES2. ThinkPad T410 без Vulkan открывает видео в режиме `auto` без ручных настроек, аппаратно (H.264) и программно (HEVC, VP9, AV1).

| Что | Итог |
|---|---|
| `render-gles2-shell` за контрактом `RenderShell` | conformance из **11 / 11** проверок на настоящем GLES2 без окна (780M и llvmpipe) |
| Видео из настоящего FFmpeg-декодера через GLES2 | 12 кадров VP9: `Presented`, ожидаемый pts, каждый пиксель сверен с формулой, каждый кадр возвращён декодеру ровно один раз после fence |
| T410, `auto`, первый настоящий запуск | GLES2 «no hardware Vulkan adapter»; H.264 → `vaapi-dmabuf-gles2` + `VA-API EGL DMA-BUF`; HEVC/VP9 → FFmpeg; первый кадр через 403–518 мс после старта процесса |
| T410, только программный Vulkan (lavapipe поставлен на время) | `auto` и явный `vulkan` → GLES2, а не процессорный Vulkan за 216–280 % CPU (факт сессии 00) |
| T410, 20 выходов во время HW-видео (решение 34) | **20 / 20** чистые: 10 нативный Wayland + 10 XWayland, код 0, закрытие ≈ 0,15 с, без coredump и `GPU HANG` |
| 780M, `auto` = wgpu, замер «до/после» | в шуме: CPU, главный поток, GPU, RSS, уникальные кадры — без изменений |
| 780M, живая приёмка `profile = "opengles"` | весь сценарий UX в обоих режимах окна — PASS (ниже) |
| `scripts/ci-checks.sh all` с `GLES2_EGUI_REQUIRE_EGL=1` | exit 0 |

Критерий выхода:
- плеер стартует и играет на T410 в `auto` без ручных настроек — да;
- выход на T410 во время HW-воспроизведения чистый во всей серии — да; общий бэклог п. 13 закрыт без правки декодера;
- на основной машине `auto` = wgpu, поведение без изменений — да, замер ниже;
- memories обновлены (список в конце).

## Решения владельца (25.10.2026, в README — 35–41)

35. **Явный профиль + метка падения.** Пользователь выбрал `vulkan`, а прошлый старт этого рендера не дошёл до первого кадра. Тогда этот запуск один раз идёт на GLES2 с уведомлением «Settings still say Vulkan». Иначе человек застревает в цикле падений и не может добраться до настроек.
36. **Миграция конфига: `vulkan` → `auto` у всех.** Старый конфиг пишет профиль явно всегда, отличить выбор от умолчания нельзя. Прецедент — `stop` → `skip` в v10 → v11.
37. **Смена профиля — после перезапуска: строка «Applies after restart» и кнопка «Restart now».** Пауза после перезапуска не сохраняется, как и при обычном старте.
38. **Таблица HDR→SDR GLES2 строится в фоне** (вопрос из сессии 06).
39. **Явный `vulkan`, а Vulkan на машине негоден** (только lavapipe, нет адаптера, создание упало) → этот запуск на GLES2 с уведомлением, а не фатальное окно.
40. **Уведомление о выборе рендера — только при сбоях.** На старом железе GLES2 — нормальный режим, тост при каждом запуске надоедал бы. Обычный выбор виден в панели телеметрии и в логе.
41. **Честный сигнал «рендер не умеет показать этот аппаратный кадр»** вместо маскировки под ошибку декодера.

Мелкие решения агент принял сам и вынес в «Ограничения»:
- закрытие с ошибками владельцев не перезапускает приложение;
- бинарь, заменённый обновлением, не перезапускается по очищенному пути;
- кнопка «Restart now» скрыта, пока в других полях есть неприменённые правки;
- метка снимается после обработанной ошибки создания: процесс не упал;
- метка пишется с fsync (≈ 5,5 мс на NVMe): после намертво зависшего GPU, который на Ironlake бывает, её нужно найти на диске после выключения кнопкой.

Задачу разделили на шесть пакетов для фоновых исполнителей (Sonnet) с непересекающимися зонами файлов:
- P1 — GLES2-рендер за контрактом;
- P2 — фоновая таблица HDR;
- P3 — конфиг и перезапуск;
- P4 — каталог, пробы, метка;
- P5 — хвосты интеграции;
- P6 — исправления по ревью.

Независимый ревьюер прочитал весь diff и нашёл шесть подтверждённых дефектов; все закрыты тестами, падающими без исправления (подробности — «Причины найденных дефектов»). Живую приёмку на 780M вёл отдельный агент через `/dev/uinput`, скриншоты и логи. Серии на T410 агент гонял по ssh, окно закрывал скриптом KWin (`closeWindow`) — тем же путём, что крестик.

## Что изменилось

### `render-gles2-shell` — полный `RenderShell`

| Модуль | Что внутри |
|---|---|
| `shell/creation.rs`, `create_error.rs`, `probe.rs` | `Gles2Renderer::new(window, SurfacePresentSettings)`, стартовые цвета как у wgpu, `probe_gles2_renderer()`; таблица «ошибка EGL → стадия создания» |
| `shell/presentation.rs` | Показ по маппингу сессии 03: `Mailbox` → vsync с исходом `PresentModeFallback`, смена прозрачности → `AlphaPreferenceChangeUnsupported`, detach/reattach |
| `shell/frame.rs`, `frame_fence.rs`, `frame_outcome.rs`, `frame_layers.rs` | Кадр: видео + субтитры + интерфейс + углы; после каждого кадра, где рисование началось, — один fence для видеослоя и обёртки освобождения |
| `shell/live_settings.rs`, `gpu_idle.rs`, `video_frames.rs`, `render_shell.rs` | Живые настройки цвета/HDR без пересоздания программ, `wait_for_gpu_idle`, склад кадров, перевод контракта |
| `video_import/` | Подготовка и установка импорта, подача кадра на слой, исходы DMA-BUF, перенос импорта при пересоздании |
| `frame_release/drain.rs` | Ожидание возврата уже отпущенных кадров (без него `wait_for_gpu_idle` гонялся бы с потоком-ожидателем) |

Ключевые решения:
- **«Один текущий кадр» видеослоя.** Ключ кадра несёт рецепт (эпоха декодера, ключ на слое, источник), а не текстуры. Ключ, который уже не текущий (заморозка, скраб, повтор при `Busy`, кадр прежнего декодера), показывается заново по рецепту. Если это невозможно — типизированная ошибка, но не чужая картинка.
- **Фон не заливается под видео на всю цель.** На T410 это −2,2 мс GPU на кадр. Видеослой сам заливает чёрным всё, куда не рисует. В `gles2-egui` новый `FrameLayers::underlay_coverage()`.
- **Пересоздание внутри семейства** передаёт обёртку освобождения новому рендеру. Старый при уничтожении её не отвязывает.
- **Порядок уничтожения:** слои → `renderer_detaching` → контекст (урок падения при выходе из сессии 07).

### Приложение (`app-egui`)

- **Каталог `[WgpuVulkan, Gles2]`** (`render_backend/`):
  - Пробы ленивые: на машине с годным Vulkan проба GLES2 не запускается.
  - `start_renderer` при ошибке создания сразу пробует следующего кандидата в том же запуске.
  - `RendererStartupReport` даёт строку телеметрии и (только при сбое) уведомление.
  - Фатальное окно — только если не годен никто. Текст поправлен: «Vulkan or OpenGL ES 2.0».
- **Метка незавершённого старта** (`app_shell/renderer_startup_marker.rs`):
  - Файл `renderer-startup.marker` в каталоге конфига. Пишется до пробы и до создания рендера.
  - Снимается после первого показанного кадра или при штатной остановке.
  - Не снимается, если до закрытия были только ошибки кадра и ни одного показанного («живой, но немой» рендер).
- **Строка `Renderer:` в панели телеметрии**, например `OpenGL ES 2.0 — Auto: no hardware Vulkan adapter`.
- **Перезапуск** (`app_instance/relaunch.rs`). Штатное закрытие → замок single-instance отпускается и даёт токен → только по токену запускается новый процесс. Иначе новый процесс проиграл бы гонку за замок и просто передал бы управление старому.
- **Перерисовка, пока строится таблица HDR:** `RenderShell::needs_follow_up_frame()`. Иначе на паузе картинка застряла бы со старой таблицей.
- **Программный фолбэк декода** теперь срабатывает и на отказ рендера (`DmaBufFallbackTrigger`).

### Контракт `render-shell-api`

- `RenderShell::needs_follow_up_frame() -> FollowUpFrame::{NotNeeded, Soon}`. wgpu всегда `NotNeeded`.
- `FrameImportUnsupportedReason::RendererCannotShowHardwareFrame(HardwareFrameRefusal::{HostMemoryDescriptor, FrameFormatNotShown, DriverCannotImport})` (решение 41).

### wgpu (`render-wgpu-shell`)

- `probe_hardware_vulkan_adapter()`: instance + тот же выбор адаптера, что при создании, без устройства и окна. Годен адаптер не-CPU с NV12. Instance пробы переиспользуется при создании (−3 мс старта).
- Создание рендера отвергает CPU-адаптер (lavapipe), чтобы сработал фолбэк на GLES2. Тестовый `new_headless` (CI на lavapipe) — нет.
- На машине с аппаратным GPU поведение не меняется (замер ниже).

### Конфиг и настройки

- **Конфиг v24:**
  - по умолчанию `render.profile = "auto"`;
  - миграция `vulkan` → `auto`;
  - `[render.opengles]` (`enabled`, `simple_ui`) удалён.
  - GLES2 своих ручек показа не получил: он всегда с vsync и прозрачностью, `[render.vulkan]` его не касается.
- **Новый механизм применения `AppliesAfterRestart`.** Значение сохраняется, рантайм не трогается, исход в отчёте Apply отличим от «ничего не изменилось». Строка «Applies after restart» и кнопка «Restart now».
- `ensure_candidate_profile_supported` (прежний отказ «OpenGL ES renderer is absent») удалён: профиль до пересоздания больше не доходит.

### Декодер VA-API

- `ZeroCopyImportTarget::{VulkanDmaBuf, EglDmaBuf}`. Под GLES2 декодер пишет `backend_contract="VA-API EGL DMA-BUF"`, под wgpu — прежнее имя байт-в-байт. Гарантии одинаковые, меняется только имя. По нему `evidence.py` доказывает аппаратный путь GLES2.

### `gles2-video`

- `HdrTableBuilder`: таблица 65³ считается в фоновом потоке, на экране старая таблица до готовности новой. Первая таблица слоя — синхронно. Параметры, промелькнувшие при перетаскивании ползунка, не строятся.

## Причины найденных дефектов

1. **Отказы GLES2 при аппаратном кадре не включали программный фолбэк.**
   - Чтобы фолбэк сработал, отказ выдавали за «неправильное описание кадра от декодера». Политика фолбэка лечила только составной multi-object дескриптор, всё остальное кончалось ошибкой.
   - Исправлено отдельной причиной (решение 41): отказ рендера лечится программным декодом всегда.
2. **Упавший кадр не ставил fence** (ревью).
   - Если `eglSwapBuffers` или освобождение текстур падали после того, как видео уже нарисовано, аппаратный кадр мог вернуться декодеру, пока GPU его ещё читает.
   - Теперь fence ставится на любом кадре, где рисование началось. Если fence не вышел — `glFinish` и счётчик.
3. **«Живой, но немой» рендер обходил защиту метки** (ревью). Каждый кадр — ошибка, окно чёрное, человек закрывает его, и метка снималась как при штатной остановке.
4. **Падение драйвера внутри пробы не ловилось** (ревью): метка писалась только перед созданием, а проба уже создаёт instance или EGL-контекст.
5. **Проба wgpu оценивала «любой аппаратный адаптер», а создание брало low-power** (ревью). На машине с dGPU (NV12) и iGPU (без NV12) получился бы ложный отказ.
6. **Вечная перерисовка после ухода видео с HDR.** Отозванный запрос таблицы считался «в работе», а кадр без видео не отзывал ожидание.
7. Мелочи ревью:
   - установка импорта теперь сверяет, что декодер обёрнут текущей обёрткой освобождения рендера;
   - счётчик вытеснений таблицы HDR больше не завышается.
8. **Флейк теста FFmpeg → GLES2 на llvmpipe** (~1 из 15).
   - `Busy` кольца загрузки — честный исход контракта: llvmpipe дочитывает асинхронно, и все слоты ещё под fence. Тест требовал `Ready` с первой попытки.
   - Теперь он повторяет, как приложение, с дедлайном: утечка слота по-прежнему ловится.
   - После правки — 40 / 40 зелёных.

## T410: короткий срез плавности (`auto`, нативный Wayland, окно 20 с)

| Сцена | Путь | Уникальные кадры из 600 |
|---|---|---|
| H.264 720p30 | HW (VA-API + EGL zero-copy) | 598 |
| HEVC 720p30 | SW (FFmpeg + одна копия) | 600 |
| HEVC 1080p30 | SW | 598 |
| H.264 1080p30, принудительный программный декод | SW | ≈ 600 (≈ 30 новых кадров/с) |
| **H.264 1080p30** | **HW** | **262** |

**HW H.264 1080p30 на T410 не плавный — известное ограничение.** Причина:
- наш VA-API декодер на Ironlake не успевает (сессия 00: 72–75 % потолка кремния);
- видео стоит, а время на шкале тикает, поэтому рисуются кадры только интерфейса — 419 таких кадров за прогон;
- на GLES2 каждый такой кадр заново рисует видео, а GPU на Ironlake общий с декодером: `eglSwapBuffers` в среднем 19,5 мс, p90 50 мс.

Лечат это:
- сессия 09a (конвейер декодера);
- сессия 09b (режим `dynamic` уводит такое видео на программный декод, который на T410 тянет 1080p30);
- бэклог «частичный показ» — для кадров, где меняется только интерфейс.

Регрессией этой сессии это не является: до неё на T410 плеер не стартовал вовсе.

## Проверено вручную

**780M (агент-приёмщик, `/dev/uinput`, скриншоты, логи), нативный Wayland и XWayland:**

1. **`profile = "opengles"`.**
   - Старт на GLES2 (`chosen in Settings` в телеметрии). HW H.264 → `vaapi-dmabuf-gles2` + `VA-API EGL DMA-BUF`.
   - Работают пауза и продолжение, ←/→, скраб мышью и очередь из трёх файлов HW → SW (HEVC main10) → HW.
   - Фуллскрин: панели скрываются через ~3 с и возвращаются от мыши; выход из фуллскрина, resize.
   - Видео уходит из-под боковой панели настроек.
   - Субтитры SRT, включение по C.
   - Скругление углов: альфа 0 во всех четырёх углах скриншота окна.
   - Живая цветокоррекция и Apply.
   - HDR AV1 4K60 (BT.2020 PQ, программно): живой предпросмотр белого SDR без зависания окна, Apply.
   - Без чёрных экранов и без `Dropped`/`Failed` в трассе.
2. `auto` → wgpu, без уведомления.
3. `auto` + сломанный Vulkan ICD → GLES2 молча, причина в телеметрии.
4. Явный `vulkan` + сломанный ICD → GLES2 + уведомление «до ×», в файле по-прежнему `vulkan`.
5. **Метка `wgpu-vulkan` перед стартом:**
   - запуск идёт на GLES2 с уведомлением;
   - после первого кадра файл метки исчез;
   - следующий запуск снова на wgpu.
6. **Настройки → профиль OpenGL ES:**
   - появляется «Applies after restart»;
   - Apply сохраняет значение без живого пересоздания;
   - Restart now: приложение закрылось и открылось на GLES2 с тем же файлом и позицией (42,9 с).
7. Серия 5 + 5 выходов на GLES2 во время HW-видео — все код 0, без coredump.
8. `evidence.py` классифицирует прогоны: GLES2 HW / SW, wgpu HW.

**T410:**
- первый настоящий запуск — проигрывание в Auto;
- 20 выходов (решение 34);
- lavapipe на время: `auto` и явный `vulkan` → GLES2, затем lavapipe удалён;
- XWayland-прогоны подтверждены как X11-клиенты (`_NET_CLIENT_LIST` + `WM_CLASS`).

**Не проверено:**
- PGS-субтитры вживую на GLES2: покрыты портом 20 GPU-тестов и паритетом сессии 08;
- GUI-сценарии UX на T410 (скраб, фуллскрин, настройки): на T410 проверены старт, проигрывание и выход, остальное — сессия 11;
- потеря контекста вживую: покрыта инъекцией в тестах.

## Известные ограничения

- **HW H.264 1080p30 на T410 не плавный** (выше) — сессии 09a и 09b.
- **План декода в логе пишет только предстартовый декодер.**
  - Кандидаты strong open (следующий файл очереди, программный 10 бит, HDR) строку `plan=` не пишут — так было и у wgpu.
  - `evidence.py` поэтому не доказывает программный путь для файла, открытого не первым.
  - Реальный декодер видно по потокам (`video-decode` — VA-API, `ffmpeg-video-decoder` — FFmpeg) и по строке телеметрии `Backend:`. Если сессиям 10–11 это нужно — строка плана для кандидатов.
- На машине без Vulkan wgpu-hal сам пишет две строки `ERROR enumerate_adapters: Initialization of an object has failed`. Это шум чужой библиотеки при пробе, не сбой.
- **Последний клон fence кадра теоретически может умереть в потоке плеера** после уничтожения контекста. Окно узкое: при штатном закрытии плеер гасится раньше рендера. Найдено ревью, не исправлялось.
- Если не вышли ни fence, ни `glFinish` при живом контексте (`FrameWorkRetirement::Unprotected`), защиты от раннего возврата кадра нет: только `error!` и счётчик `frame_fence_failures`. Практически недостижимо.
- `Mailbox` у GLES2 при создании только пишет в лог (вместо vsync), а при перенастройке — честный исход `PresentModeFallback`.
- Метка старта стоит ≈ 5,5 мс главного потока на старте (fsync, NVMe) — осознанно, см. решения агента.
- Давние, не этой сессии (найдены приёмкой):
  - во вкладке Render настроек две группы «profile»: `tone_mapping` числится в группе `profile` после вложенной `hdr_to_sdr` — отложенная полировка UI;
  - `WARN Ignoring unknown button type: icon`;
  - «Frame pacing: bad» на 24-кадровом Sintel — одинаково на wgpu и GLES2.
- Шаблоны замеров `docs/benchmarks/tools/t480s/*-template.toml` (schema 12, `profile = "vulkan"`) у нового бинаря мигрируют в `auto`. На GPU с Vulkan это wgpu, но на T410 сессия 11 должна задавать профиль явно.
