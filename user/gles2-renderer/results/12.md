# Результат сессии 12: программный кадр без CPU-копии (memfd → udmabuf → EGLImage)

## Статус

**DONE, путь включён.** 27 октября 2026. Эксперимент «0 копий» удался и принят владельцем (решения 59–61). Программно декодированный кадр (8 бит) на рендере GLES2 больше не копируется на CPU. Декодер пишет кадр в блок памяти, видеокарта читает этот блок напрямую.

| Вопрос плана | Ответ |
|---|---|
| 1. Пускает ли система | Да на обеих машинах: `/dev/udmabuf` с ACL `rw` пользователя (выдаёт сессия рабочего стола), модуль загружен. Лимит udmabuf на T410 — 64 МиБ, кадру 4K хватает. Без прав путь честно недоступен, плеер права не трогает |
| 2. Принимает ли драйвер, нет ли скрытой копии | crocus (T410) и radeonsi (780M) принимают раскладку блоков декодера: линейная память, шаг строк 2304/1280, плоскости R8. Проход GPU из линейной системной памяти такой же, как из загруженной текстуры (стенд: 4,39 против 4,49 мс), лишнего CPU при рисовании нет — скрытой копии нет |
| 3. Цена импорта, кэш или импорт на кадр | Нужен кэш «один dma-buf и один импорт на блок пула». Импорт на каждый кадр стоил +0,7 мс system-времени на кадр 1080p |
| 4. Синхронизация | Кадр возвращается декодеру только после fence (решение 30). На Ironlake без сброса кэша CPU 231 из 240 кадров показывались со старыми данными. Со сбросом видимых строк (`CLFLUSH`) — 0 ошибок. На 780M сброс не нужен |
| 5. AV1 | libdav1d не умеет DR1, AV1 по-прежнему идёт одной копией. 10/12 бит тоже — решение владельца 60 |

## Решения владельца (27.10.2026, в README — 59–61)

59. **Реализовать путь и проверить коротким замером.** На стенде выигрыш выглядел умеренным: −4…−7 % ядра на 1080p60. Владелец выбрал реализацию, а не отказ и не перенос в каталог 12a. Замер — короткий, на батарее (в этот день не было электричества).
60. **Архитектура:**
    - вид памяти блоков декодера выбирает приложение по семейству рендера, как уже сделано для VA-API: GLES2 → запечатанный memfd, wgpu → анонимная память, как раньше;
    - нужен ли сброс кэша CPU, решает самопроверка рендера, а не имя видеокарты;
    - только 8 бит;
    - при любом отказе — прежняя копия.
61. **Порядок закрытия:** коммит кода → домер (XWayland, SW HEVC 1080p30, загрузка GPU) → отчёт и memories → коммит и push.

## Как шёл эксперимент

1. **Стенд без декодера** (`gles2-egui/examples/udmabuf_zero_copy_probe.rs`). Одна программа рисует три R8-плоскости кадра 1080p I420 тремя способами: `glTexSubImage2D`, импорт с кэшем по блоку, импорт на каждый кадр. Пиксели проверяются на каждом кадре. Цифры T410, CPU потока на кадр:

   | | подготовка | рисование | system | проход GPU |
   |---|---|---|---|---|
   | копия (как в плеере) | 2,42 мс | 0,18 | 0,15 | 4,49 мс |
   | импорт с кэшем + `clflush` видимых строк | 4,71 мс | 0,18 | 0,09 | 4,39 мс |
   | импорт на кадр | 4,9 мс | 0,68 | 0,87 | — |
   | `clflush` уже чистых строк | 1,43 мс | | | |
   | импорт без `clflush` | 231 из 240 кадров со старыми данными | | | |

   В стенде кадр записан прямо перед сбросом, поэтому строки «горячие» и сброс дороже копии.
2. **Сброс на настоящем декодере.** Цена `CLFLUSH` зависит только от того, где лежат строки кадра, а не от вида памяти. Поэтому её сняли на прежнем стенде сессии 05: настоящий FFmpeg, H.264 1080p60, темп 60 Гц, временный флаг `--flush-probe`, после замера убран. К моменту показа кадр почти вытеснен из кэша: сброс стоил **1,19 и 1,66 мс** против копии **2,43 и 2,42 мс** (2 круга). Отсюда оценка −0,7…−1,2 мс главного потока на кадр и решение владельца 59.
3. **Реализация** — три пакета: A — память декодера, B — `gles2-video`, C — `render-gles2-shell`. A и B делали фоновые исполнители (Sonnet) с общим брифом, C и интеграцию — главный агент. Архитектуру владелец утвердил до кода.

### Инварианты

1. Отказ на любом шаге — прежняя одна копия: нет прав, драйвер, самопроверка, 10/12 бит, кадр без memfd-блока. Ошибка импорта выключает путь до пересоздания рендера, предупреждение пишется один раз.
2. Сброс кэша CPU идёт на каждый новый кадр, если самопроверка его требует: декодер переписывает блок при каждом переиспользовании.
3. Кадр возвращается декодеру только после fence показа (решение 30). Блок не перепишется, пока GPU его читает.
4. dma-buf блоков ограничены пулом плана и закрываются при смене декодера. udmabuf держит страницы memfd, без ограничения память блоков, выброшенных декодером, не освобождалась бы.
5. Путь wgpu и VA-API не меняется: wgpu получает анонимные блоки, как в 08b. amdgpu `userptr` принимает только анонимную память.

## Тесты

- **`video-core`:** вид памяти по умолчанию, анонимный блок без memfd, memfd-блок через трейт.
- **`video-ffmpeg`:**
  - пул memfd: печати есть, `F_SEAL_WRITE` нет, страницы нулевые, запись видна через `pread`, отказ системы даёт `None`;
  - **настоящий FFmpeg** VP9/H.264/HEVC декодирует в memfd-блоки побайтно как обычное выделение;
  - вид памяти доходит от конфига до открытия декодера (настоящий поток декодера);
  - фабрика.
- **`app-egui`:** GLES2 → memfd, wgpu → анонимная; фабрика получает вид памяти своего рендера.
- **`gles2-video`** — 23 новых интеграционных теста на настоящем EGL и udmabuf, плюс 10 юнит-тестов:
  - паритет планарного импорта с копией тех же байтов: 4:2:0, 4:2:2, 4:4:4 и нечётный 31×15;
  - кэш, вытеснение (счёт живых текстур), один текущий кадр в цепочке upload → planar → NV12 → …;
  - перезапись видна, 10 бит отвергаются до импорта, отказ драйвера;
  - самопроверка: write-through, «только после сброса», «никогда», «две видимые записи — ещё не когерентность»;
  - состояние GL и число объектов до и после самопроверки совпадают.
- **`render-gles2-shell`:**
  - 12 фокусных тестов: кадр из memfd без копии, пиксели равны копии; переиспользованный блок — новая картинка без нового dma-buf и импорта; ветка сброса; кадры вне пути идут копией без самопроверки; драйвер без импорта; ёмкость и смена декодера; правило «итог самопроверки → политика»; модуль ядра (печати, udmabuf отвергает memfd без `F_SEAL_SHRINK`, паспорт `fstat`);
  - сквозной `ffmpeg_vp9_frames_in_memfd_blocks_reach_the_screen_without_a_cpu_copy`: настоящий FFmpeg → `Gles2Renderer`. 12 из 12 кадров без копии, каждый пиксель сверен с CPU-формулой цвета, возврат по fence.
- **Мутации** (каждую поймали):
  - сброс кэша выключен — **на настоящем T410** падают 2 теста, на экране старый кадр;
  - кэш dma-buf всегда промахивается;
  - U/V перепутаны в паспорте;
  - у исполнителей — 4 мутации пакета A и 11 пакета B, одну дыру пакета B закрыли новым тестом.
- **На T410** (crocus, настоящий Ironlake) гонялись тестовые бинари: 12 фокусных и 2 сквозных — зелёные. Самопроверка там сама выбрала «сбрасывать видимые строки».
- **Общий прогон:** `GLES2_EGUI_REQUIRE_EGL=1 scripts/ci-checks.sh all` — exit 0. Первый прогон упал на формате стенда-примера, исправлено. Тесты `render-gles2-shell` прошли и на llvmpipe (`LIBGL_ALWAYS_SOFTWARE=1`).

## Что проверено вручную

Прогоны выше — настоящий плеер в фуллскрине на T410 в обоих режимах окна. В логе каждого нового прогона есть строка `software frames are shown without CPU copy (udmabuf), CPU cache flush: visible rows of every frame`. Эти сценарии используют тот же механизм освобождения по fence, что и копия, и входят в переквалификацию 12a.

## Известные ограничения

- **Только Linux x86_64** с доступным `/dev/udmabuf`. Там, где самопроверка требует сброса кэша, нужен `CLFLUSH` (x86_64); на других архитектурах такой GPU получает копию.
- **8 бит.** 10/12 бит и AV1 идут копией. Для 16-битных плоскостей нужна шейдерная ветка `GR88` вместо `LUMINANCE_ALPHA`.
- **Замер короткий**, без пар протокола и без квалификации против mpv/VLC. Строгая серия — в конце 12a.
- **Стоимость `CLFLUSH`** на Westmere (1,2–1,7 мс на кадр 1080p) остаётся статьёй расхода главного потока. Её можно было бы перенести в поток декодера или освобождения — кандидат в каталог 12a.
- **Ёмкость кэша dma-buf** равна пулу плана (24). Если блоков в обороте больше, dma-buf пересоздаются, это видно по счётчику `dma_bufs_created`. В прогонах этого не мерили: счётчик пишется в лог только при смене декодера.
- Скрипт короткого замера и сырые логи — в scratchpad сессии, в репозиторий не входят.
