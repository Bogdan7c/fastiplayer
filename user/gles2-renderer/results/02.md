# Результат сессии 02: wgpu-рендер за контрактом

## Статус

**DONE.** 24 октября 2026.

`app-egui` работает с любым рендером через `Box<dyn RenderShell>` и больше не знает wgpu: импорт кадров декодера, материализаторы и освобождение после GPU живут внутри wgpu-рендера. Выбор и создание рендера идут через каталог `app-egui::render_backend`. Поведение для пользователя не изменилось: замер в шуме, уникальные кадры, RSS и GPU прежние, строки логов для инструментов байт-в-байт прежние.

Найден давний дефект — падение при Apply настроек Vulkan. Падают и сборка до сессии, и после неё. По решению владельца он вынесен в отдельную сессию [02a](../02a-renderer-recreation-crash.md).

## Решения владельца (24.10.2026, в README — 18–21)

1. **Conformance на настоящем wgpu без окна.** У рендера появилась «цель показа» двух видов: окно (как раньше) и offscreen-текстура только для тестов. Весь остальной путь кадра общий, поэтому тест проверяет настоящий код.
2. **Профиль `opengles` на старте → wgpu + предупреждение в лог**, как и раньше: приложение не перестаёт открываться у тех, у кого он уже сохранён. Apply с `opengles` в настройках — прежний отказ «OpenGL ES renderer is absent».
3. **«Подготовщик импорта» в контракте.** Кандидат нового файла (открытие, переход по очереди, смена HW↔SW) запускается в потоке плеера, а рендер живёт в потоке окна. Рендер выдаёт переносимый `VideoImportPreparer`: он оборачивает декодер и готовит импорт там же, где это делал прежний драйвер приложения. Установка остаётся на рендере в потоке окна.
4. **Падение при Apply настроек Vulkan чиним отдельной сессией 02a**, не смешивая с рефакторингом шва (правило 8).

## Что изменилось

### `render-shell-api` (контракт)

- `trait VideoImportPreparer: Send` + `RenderShell::video_import_preparer(&self)`. Метод живёт на `RenderShell` с `&self`: выдать подготовщик — это чтение, и 40 read-only цепочек приложения не пришлось переводить на `&mut`.
- Conformance-проверка №7: подготовщик работает в другом потоке, не трогает активный импорт, его импорт ставится на выдавший рендер и даёт `Ready`. Новый fake-дефект `PreparerStampsForeignOwner` ловится только ей.

### `render-wgpu-shell` (wgpu-рендер)

| Модуль | Что внутри |
|---|---|
| `shell/render_shell.rs` | `impl RenderShell for Renderer`: перевод вызовов контракта в прежние операции |
| `shell/gpu_context.rs` | instance/adapter/device/queue, подписка на потерю устройства, ожидание GPU → нейтральный `RendererGpuDrainError` (вынесено из `shell.rs`) |
| `shell/present_target.rs` | цель показа `PresentTarget::{Window, Offscreen (#[cfg(test)])}`: surface и её конфигурация, `pre_present_notify`, present. Логика получения буфера swapchain перенесена без изменений |
| `video_import.rs` | склад кадров `WgpuVideoFrameImport` и `WgpuVideoImportPreparer`: обёртка декодера, материализаторы DMA-BUF/HostPlanar, привязка освобождений. Перепривязка очереди — только для импорта, подготовленного пересозданием |
| `video_import/renderable_frame.rs` | сборка `WgpuRenderableFrame` из ключа (NV12/P010/HostPlanar), перенесена из `app-egui::frame_prepare`. Тексты ошибок прежние |
| `test_support.rs` | стенд тестов: рендер без окна, белый/чёрный HostPlanar-кадр, журнал освобождений, readback пикселя |

Удалены wgpu-версии `RenderFrameInput` / `AcquiredSurfaceFrame` / `SurfaceFrameAcquire`, публичный `GpuContext`, wgpu-шный `RendererGpuDrainError`, аксессоры `instance()/adapter()/device()/queue()` и реэкспорты нейтрального словаря. `shell.rs`: 714 → 482 строки.

### `app-egui` (приложение)

- `AppShell.renderer: Option<Box<dyn RenderShell>>`. Около 130 сигнатур переведены с `&Renderer` на `&dyn RenderShell` / `&mut dyn RenderShell`.
- **Каталог `render_backend/`:**
  - `selection.rs` — чистая `select_renderer(профиль, пробы, метка старта)` с таблицей тестов;
  - `wgpu_vulkan.rs` — проба, фабрика и **единственный** маппинг `[render.vulkan]` → настройки показа. Дубль в `render_settings.rs` и `renderer_recreation.rs` удалён;
  - `mod.rs` — `create_renderer` (старт и пересоздание) и `create_startup_renderer`.
- **`VideoPipelinePlan`** — маршрут декода (`VaapiDmaBuf`, `FfmpegHostUpload`). Метка `diagnostic_label(семейство рендера)` для wgpu прежняя (`vaapi-dmabuf-wgpu`, `ffmpeg-host-upload-wgpu`), для GLES2 своя (`*-gles2`). Есть `import_plan()`. Запуск декодера по плану — одна функция `start_decoder_backend` для обоих путей установки.
- **Прямой путь установки** (`install_video_pipeline_plan`: старт, реактивная смена backend-а, runtime-фолбэк DMA-BUF → SW, пересборка из настроек) получает «цель импорта» (семейство + `&mut dyn VideoFrameImport`) вместо четырёх wgpu-ручек.
- **Кандидаты:**
  - слот обобщён по одному «импорту рендера» (`PendingVideoImport`);
  - драйвер `RendererCandidateVideoPipelineResourceDriver` берёт подготовщик рендера;
  - безотказный коммит после `Installed` отдаёт импорт, и тот ставится в рендер;
  - склад рендера протянут во все опросы strong open: блокирующее и неблокирующее открытие, same-item, возобновление после suspend, старт, пересборка из настроек, восстановление VOD, Open.
- **Кэш кадров** (`RenderablePresentFrame`, override скраба, замороженный кадр смены backend-а) держит непрозрачный ключ рендера. Субтитры берут размер картинки из метаданных декодера в ключе.
- **Пересоздание рендера** идёт через каталог и контракт: экспорт импорта → подготовка на новом рендере → установка после ожидания старого GPU. При потере устройства — `release_after_device_lost` старого рендера.
- **Фатальная ошибка старта:** `FatalStartupError::renderer_unavailable(&RendererCreateError)` даёт прежний текст («could not initialize the renderer: <цепочка причин>»), это закреплено тестом.
- **Зависимости:** `wgpu` и `render-wgpu-video` переехали в dev-dependencies (их используют только GPU-тесты субтитров и web-media, которые рисуют напрямую). `render-wgpu-shell` остался ради фабрики каталога.

## Причины найденных дефектов

1. **Падение при Apply настроек Vulkan — давний дефект, не регрессия** (подробности и план — сессия 02a). Корни:
   - пересоздание сначала строит новый рендер с новой Vulkan-surface, пока старая жива. Mesa WSI на Wayland запрещает второй объект `wp_fifo_v1` на одном `wl_surface`;
   - новый egui-рендер получает только изменения текстур, без атласа шрифтов, и egui-wgpu 0.36 паникует.

   Эталон `27be1df1` падает так же: тот же лог, тот же код 139.
2. **Мой стенд в тестах склада** сначала ждал освобождения неотправленного кадра без ожидания GPU. В стенде освобождение аренды всегда уходит в обёртку рендера, а та ждёт GPU (у плеера неотправленный кадр идёт декодеру напрямую). Исправлено ожидание теста, а не код рендера.
3. **Clippy после переезда:**
   - `large_enum_variant` в `MainVisualOverrideAcquisition`: вариант `Ready` стал маленьким ключом, а сам enum не вырос. Оставлен `expect` с причиной, потому что `Box` дал бы аллокацию на кадр скраба;
   - лишние `&`;
   - лишнее ожидание `too_many_arguments` после удаления параметра `window`.

## Тесты

- **`render-wgpu-shell`: 65**, из них новые на настоящем wgpu без окна:

  - склад:
    - порядок проверок «контракт → декодер → provider»;
    - Busy/Missing/Fatal различимы и не освобождают кадр;
    - аппаратный кадр на программном импорте — `Unsupported`, а не `Error`;
    - чужие ключ и импорт отклоняются без изменений;
    - пересоздание: импорт переносится на новый рендер, рисует белый кадр и освобождает его ровно один раз; чужое семейство отклоняется;

Release, 780M, нативный Wayland. Каждая попытка: 15 с прогрева, 20 с окна, `run_pass.py` + трасса стадий кадра. Оба бинарника с одним изолированным конфигом, 2 круга с обратным порядком; SW AV1 4K60 — 4 пары. Значения — среднее по парам.

Вывод:
- **Качество кадров:** уникальных кадров в окне столько же, сколько показывает fps × окно, то есть потерь нет у обеих сборок. RSS и GPU не изменились.
- **CPU в шуме, но с оговоркой.** Знак разницы скачет между сценами: HW 1080p60 и SW 1080p60 — ноль или минус, HW 4K30 — плюс по CPU, но минус по времени кадра.
- **Открытый вопрос — SW AV1 4K60:** главный поток +0,16 / +0,15 / 0,00 / +0,30 п.п. в 4 парах при собственном разбросе эталона 0,25 п.п. Стадия отправки кадра +2…18 мкс при разбросе эталона 22 мкс. CPU процесса у новой сборки ниже. Новая работа на кадр — проверка контракта, вторая сборка wgpu-кадра, одна аллокация билета и одна ключа — это доли микросекунды и такую разницу не объясняет. Профиль samply не снят: на машине `perf_event_paranoid = 2`, а нужно ≤ 1. **Предложение:** снять профиль в 02a или в замере сессии 04, если сдвиг повторится.
- **Цена `Box` билета** (вопрос из сессии 01) в шуме: стадия получения буфера не изменилась.

## Проверено вручную

Приёмка проведена агентом: виртуальные клавиатура и абсолютная мышь через `/dev/uinput`, скриншоты `spectacle`, сверка по логу. Release «после», нативный Wayland, очередь H.264 1080p60 (HW) → VP8 720p30 (SW) → H.264 4K30 (HW) → Sintel с SRT.

- Старт: `plan="vaapi-dmabuf-wgpu"`, первый кадр через 135 мс после запуска процесса.
- Пауза и продолжение (Space), перемотка ←/→, скраб мышью по шкале времени: превью-кадры, финальный коммит, продолжение со звуком.
- Смена файла и переключение HW → SW → HW через очередь, то есть через подготовщик в потоке плеера: VP8 ушёл на программный путь (загрузка без CPU-копии), затем вернулся VA-API H.264.
- Субтитры SRT видны поверх видео под интерфейсом; кнопка CC включает дорожку.
- Фуллскрин (F): видео на весь экран; выход из фуллскрина; resize кнопкой «развернуть» — картинка и интерфейс корректны.
- Боковая панель настроек: видео уходит из-под неё (исключение области).
- **Apply настроек render → vulkan — ПАДЕНИЕ, давнее** (см. «Причины», сессия 02a).

**Не проверено вручную:**
- скругление углов на скриншоте не разглядеть, проверено только косвенно: маска рисуется, прозрачная surface выбрана;
- XWayland-режим;
- потеря устройства вживую.
