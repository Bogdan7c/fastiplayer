# Результат подсессии 11a: программный декод на слабом процессоре

## Статус

**DONE.** 26 октября 2026. Файл подсессии — [`../11a-weak-cpu-software-decode.md`](../11a-weak-cpu-software-decode.md).

## SHA

- База: `7b94310b` (`main`, итог сессии 10).
- Итог: коммит этой подсессии.

## Решение владельца

Точечно для слабых машин (не больше 4 логических CPU):
- AV1 до 1080p — до 2 кадров в работе;
- HEVC в авто-режиме — все логические CPU;
- H.264 и VP9, а также мощные машины — без изменений.

## Как нашли причину

Живой прогон на T410: нативный Wayland, фуллскрин, режим декода `dynamic`. Окно 25 с после 12 с прогрева. Считались уникальные кадры показа по трассе `video_render_acceptance`, CPU процесса — по `/proc`. По одному прогону на точку.

Потоки вручную (`video.sw_decode_threads`), 1080p60, программный декод:

| Сцена | 2 потока (было в авто) | 3 | 4 | 5 |
|---|---|---|---|---|
| HEVC 20 Мбит/с | 56,1 к/с, 203 % CPU | 59,2 / 221 % | 60,0 / 223 % | 60,0 / 224 % |
| AV1 15 Мбит/с | 16,4 / 129 % | 15,7 / 131 % | 14,8 / 132 % | 13,9 / 132 % |
| VP9 20 Мбит/с | 60,0 / 149 % | 60,0 / 158 % | 60,1 / 160 % | 60,0 / 163 % |
| H.264 40 Мбит/с | 60,0 / 150 % | 60,0 / 159 % | 60,0 / 160 % | 60,0 / 164 % |
| H.264 15 Мбит/с | 60,0 / 121 % | 60,0 / 128 % | 60,0 / 132 % | 60,0 / 133 % |

Выводы:
- HEVC упирается в число потоков;
- AV1 от потоков не ускоряется, даже чуть замедляется, при CPU 130 % из 400. Значит, его держит не процессор, а правило «один кадр в работе». Голый декод ffmpeg + libdav1d на T410 это подтвердил:

| `max_frame_delay` | 2 потока | 4 потока |
|---|---|---|
| 1 (наше правило для AV1 ≤ 1080p) | 29,9 к/с | 28,9 |
| 2 | 79,8 к/с | 82,7 |
| 0 (авто dav1d) | 79,6 к/с | 83,1 |

## Что изменилось

- `crates/video-ffmpeg/src/decoder_thread/send_receive/decode_threading.rs`:
  - `HostCpuProfile` (`detect`, `with_logical_cpus`, `is_constrained`);
  - `CONSTRAINED_HOST_MAX_LOGICAL_CPUS = 4`, `AV1_UP_TO_1080P_CONSTRAINED_HOST_MAX_FRAME_DELAY = 2`;
  - `SoftwareDecodeWorkload::max_frame_delay(host)`, `apply_to_request(…, host)`, `takes_all_cpus_on_constrained_host`;
  - `resolve_decode_thread_budget(…, host)`, `auto_thread_count(…, host)`.
- `crates/video-ffmpeg/src/decoder_thread/send_receive.rs` — место открытия декодера передаёт `HostCpuProfile::detect()`.

## После фикса (авто-настройки, тот же метод)

| Сцена | До | После |
|---|---|---|
| AV1 1080p60 | 16,4 к/с | 59,0 и 59,96 к/с (два прогона), 169–171 % CPU |
| AV1 1080p30 | не успевал (по голому декоду) | 30,0 к/с, 101 % CPU |
| HEVC 1080p60 | 56,1 к/с | 60,0 к/с, 222 % CPU |
| H.264 1080p60 (контроль) | 60,0 / 121 % | 60,0 / 121 % — без изменений |

AV1 1080p60 на 2 потоках — у края: в одном из двух прогонов 59,0 кадра/с. С 3 потоками — 60,0, но +20 п.п. CPU. По решению владельца потоки AV1 не трогаем, окончательно покажет лесенка сессии 11.

## Тесты

`decode_threading` — 14 тестов, из них 5 новых:
- AV1 до 1080p на слабой машине получает задержку 2, на мощной и на 5 CPU — 1;
- HEVC на 4 CPU — 4 потока, на 2 CPU — 2, на мощной — «ядра − 2»;
- H.264/VP9/VP8/AV1 на слабой — по-прежнему 2 потока;
- ручной `sw_decode_threads` не меняется;
- запрос на открытие декодера несёт правила слабой машины.

Мутации, каждую поймали:
- граница `<=` → `<`;
- HEVC-исключение выключено;
- AV1-исключение выключено.

Прогоны:
- `cargo test -p video-ffmpeg` (с FFmpeg и без) — зелёный;
- `cargo clippy -p video-ffmpeg --all-targets --all-features -D warnings` — чисто.

## Известные ограничения

- Функционального теста «AV1 играет на слабой машине» в CI нет: профиль CPU в месте открытия декодера берётся у настоящей машины. Доказательство «доходит до экрана» — живой прогон на T410 выше. Правило закреплено тестами политики.
- AV1 1080p60 на 2 потоках у края (см. выше).
- Профиль считает логические CPU. Машина с 4 простыми ядрами без HT тоже «слабая» — так и задумано: у неё тот же запас «ядра − 2» = 2 потока.
