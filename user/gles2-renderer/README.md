# Fastiplayer: свой рендер OpenGL ES 2.0 для старого железа (issue #6)

Подготовлено 23 октября 2026 в сессии планирования. Код плеера в этой сессии не менялся. Ниже задания для следующих сессий.

**Цель владельца:** дать новую жизнь старым компьютерам по принципу «софт должен уважать железо». Fastiplayer должен запускаться и играть видео плавно на машинах, где нет Vulkan (эталон — ThinkPad T410 без дискретной видеокарты). На таком железе он должен обходить лидеров рынка по производительности и крутить видео, на которых mpv и VLC уже теряют кадры.

Ссылки на строки кода — снимок на 23 октября 2026 (HEAD `cba51ace`). Перед правкой сверять с текущим кодом.

## Решения владельца (23 октября 2026, сессия планирования)

1. **Рендер полностью свой.** Рисование интерфейса egui, видео, шейдеры цвета, HDR→SDR, субтитры, скругление углов окна пишем сами. Готовый `egui_glow` не используем. Из чужого берём только два тонких «провода» к драйверу: `glow` (таблица функций OpenGL) и `khronos-egl` (контекст EGL на окне). Оба уже есть в `Cargo.lock` как зависимости `wgpu-hal` (`glow 0.17`, `khronos-egl 6.0`), то есть в проект не приходит новый непроверенный код.
2. **Переиспользуемость.** Рендер должен подключаться к любому egui-приложению (в первую очередь к редактору Fasticut) без хардкода под плеер. Переиспользуемые crate-ы живут в нашем workspace, а guardrail-скрипт запрещает им зависеть от любого crate-а плеера. Вынос в отдельный репозиторий или на crates.io — потом, когда API устоится.
3. **Шов «приложение ↔ рендер» — общий интерфейс (trait), а не переключатель на две ветки.** Требование владельца: дальше нас ждут Windows через wgpu (DX12/Vulkan) и свой рендер на DirectX 10, и рефакторинг шва повторять нельзя. Поэтому:
   - приложение знает только контракт `RenderShell` и не видит ни wgpu, ни GL;
   - **рендер сам владеет импортом кадров декодера** (DMA-BUF сегодня, DXGI shared handle завтра) и освобождением кадра после GPU. Приложение передаёт нейтральную аренду кадра и получает непрозрачный ключ;
   - выбор рендера делает **каталог рендеров платформы**: упорядоченный список кандидатов с проверкой «годен / не годен и почему». Чтобы добавить DX10, надо дописать строку каталога и crate, а не править приложение.
4. **Автовыбор (`Auto`).** wgpu, если есть аппаратный Vulkan с нужными нам расширениями. GLES2, если Vulkan нет, если есть только программный Vulkan (lavapipe/llvmpipe, `DeviceType::Cpu`) или если wgpu не смог стартовать. Если рендер упал на старте (метка «запуск рендера не завершён» осталась с прошлого раза), следующий запуск в `Auto` пропускает его и показывает уведомление.
5. **Ручной выбор** — в настройках. Смена рендера применяется после перезапуска приложения, живую смену семейства рендера не делаем. Пересоздание внутри одного семейства (режим показа и т.п.) работает как сейчас.
6. **Инварианты копий.** Аппаратный декод — строго zero-copy (VA-API → DMA-BUF → EGLImage). Программный декод — не больше одной копии (драйвер копирует кадр в текстуру). Архитектура источника плоскостей сразу допускает и 0 копий; попытка добиться 0 копий — отдельная сессия-эксперимент (`12`), решение по замеру.
7. **Строгий паритет с wgpu** по внешнему виду и по шейдерам цвета: цветокоррекция, HDR→SDR BT.2446-C, ориентация, letterbox, исключения под сайдбаром, оба слоя субтитров, скругление углов, прозрачность окна. Единственный допустимый компромисс — 10-бит **аппаратного** декода, если драйвер не даёт импортировать P010. Программный 10/12-бит обязан работать полностью. Заглушка конфига `render.opengles.simple_ui` противоречит паритету и удаляется.
8. **Критерий успеха на T410.** Соперники — mpv (в лучшем режиме, который работает на GL 2.1 / GLES 2.0: `gpu-next` там не стартует) и VLC 3 (в лучшем рабочем режиме). Критерий из трёх частей:
   - (1) на обычных видео (H.264 720p/1080p, аппаратно и программно, **обязательно включая 60 fps**) у нас 0 потерянных кадров и CPU не выше, чем у обоих соперников;
   - (2) «стресс-лесенка»: поднимаем разрешение, fps и кодек (программные HEVC/VP9/AV1, 10-бит), пока плеер не начнёт терять кадры. Наш потолок должен быть выше, чем у обоих;
   - (3) память не хуже.

   Сначала всё проверяем на основной машине (Radeon 780M, режим GLES2), потом на T410 по ssh.

   **Уточнено решениями 13–15 (сессия 00):** критерий меряется в режиме декода `dynamic`; HW 1080p60 исключён, потому что на Ironlake он физически невозможен; CPU сравнивается двумя числами.
9. **Аппаратный MPEG-2** (Ironlake его умеет, наш VA-API декодер — нет) — в бэклог, решаем по замеру программного MPEG-2 на T410 в сессии 11.
10. Работа в `main`, без веток и PR. Коммит — в конце сессии после зелёных проверок. Push — по отдельному поручению.
11. Запрет «альтернативного рендерера» из плана `user/cpu-parity/` (решение 5, issue #10) относился к поиску CPU-паритета внутри wgpu. Этот план — отдельное осознанное решение владельца по issue #6 и тот запрет не нарушает.

## Решения владельца (24 октября 2026, сессия 00 — по итогам разведки T410)

12. **CPU соперника меряем двумя числами**: CPU процесса и CPU процесса + композитора (kwin_wayland + Xwayland) за то же окно. Победа нужна **по обоим**. Причина: вывод Xv у mpv перекладывает перевод цвета на сервер Xwayland (+21–34 % CPU), и в «CPU процесса» этой работы не видно.
13. **Новый режим декода `dynamic`** рядом с `auto` / `hardware` / `software`. Он предпочитает HW, а если аппаратный декодер не успевает, переходит на SW. Тяжёлое видео остаётся плавным, лёгкое экономит батарею на GPU. Обратно на HW — только со следующим файлом. Сессия [09b](09b-dynamic-decode-mode.md).
14. **По умолчанию остаётся `auto`.** На рендере GLES2 показываем предупреждение «производительность может теряться, желательно включить Dynamic». На wgpu его нет. Та же политика потом — для legacy-рендера на Windows.
15. **Критерий 8 на T410 мерим в `dynamic`**, то есть по тому, что видит пользователь:
    - 0 потерь на всех обычных сценах, включая 1080p60 (через SW, если HW не влезает);
    - CPU — по решению 12 — не выше лучшего **чистого** режима каждого соперника.

    Вторичный критерий — принудительный `hardware`:
    - на 720p30/720p60/1080p30 цель 0 потерь, минимум — меньше потерь, чем у обоих соперников, при CPU не выше;
    - HW 1080p60 не требуем: потолок кремния ~39,6 кадра/с (`results/00.md`).
16. **Конвейер нашего VA-API декодера** — отдельная сессия [09a](09a-vaapi-decode-pipelining.md). Сейчас он даёт 72–75 % потолка кремния, и HW 1080p30 на T410 у нас не идёт в реальном времени. Сессия не должна сломать то, что работает. Обязательна тщательная проверка стабильности: воспроизведение, перетаскивание по таймлайну, seek.
17. VLC с выводом `xcb_xv` исключён из кандидатов эталона: после его старта T410 поймал неустранимое зависание GPU.

## Решения владельца (24 октября 2026, сессия 02)

18. **Conformance-набор гоняется на настоящем wgpu-рендере без окна:** цель показа рендера бывает окном или offscreen-текстурой (только в тестах), остальной путь кадра общий.
19. **Профиль `opengles` до сессии 09 стартует wgpu** с предупреждением в лог — как и раньше, приложение не перестаёт открываться.
20. **Подготовщик импорта в контракте** (`RenderShell::video_import_preparer`): кандидат нового файла запускается в потоке плеера, и обёртку декодера готовит переносимый объект рендера, без GL/GPU-объектов у GLES2.
21. **Давнее падение при Apply настроек Vulkan** (две surface на одном окне + пустые текстуры интерфейса у нового рендера) чинится отдельной сессией [02a](02a-renderer-recreation-crash.md), а не внутри рефакторинга шва.

## Решения владельца (24 октября 2026, сессия 02a)

22. **«Одно окно — одна surface» — двумя способами.** Present mode и задержка кадра (`[render.vulkan]`) применяются на месте (`RenderShell::reconfigure_presentation`), без нового device. Полное пересоздание: старый рендер отпускает окно до создания кандидата (`detach_presentation`), откат возвращает его (`reattach_presentation`). GLES2 реализует тот же контракт (EGL: одна EGLSurface на окно, `eglSwapInterval`).
23. **Полная синхронизация текстур интерфейса** (`render_shell_api::UiTextureSync`). Новый рендер получает полный набор: атлас — у egui, свои картинки — из CPU-копий. Изменения текстур — это состояние рендера: они применяются и в отклонённом кадре и не теряются, если кадр не дошёл до рендера. Рассинхронизация — это `Dropped(UiTexturesOutOfSync)`, а не паника.
24. **Давний дефект очереди «кодек прошлого файла»** (найден в приёмке 02a) — в общий бэклог (`user/general_problems/general_backlog.md`, п. 12), вернуться до 09b.

## Решения владельца (24 октября 2026, сессия 03)

25. **`wl_egl_window` — из `wayland-sys` 0.31** (уже в дереве через wgpu-hal), а не из нового crate-а `wayland-egl`. Это продолжение решения 1: в проект не приходит новый чужой код.
26. **Минимум — EGL 1.5** (вся Mesa с 2015 года, T410, 780M, llvmpipe). На EGL 1.4 — типизированная ошибка `EglVersionUnsupported`. Путь `EGL_EXT_platform_base` — в бэклоге.
27. **CI ставит Mesa EGL** (`libegl1 libegl-mesa0 libgles2 libgl1-mesa-dri`), пиксельные тесты GLES2 идут на llvmpipe в каждом прогоне. `GLES2_EGUI_REQUIRE_EGL=1` превращает пропуск без EGL в падение.

## Решения владельца (24 октября 2026, сессия 04)

28. **Тест пиксельного паритета wgpu ↔ GLES2 живёт в тестах `render-wgpu-shell`.** Там он сравнивает настоящий художник шелла (`EguiCompositor`) и настоящую маску углов с GLES2-художником, без копий кода. `gles2-egui` подключается к шеллу только как dev-зависимость. Normal-зависимость на GLES2-crate-ы guardrail по-прежнему запрещает.
29. **Дизеринг egui-wgpu повторяется в GLES2** (тот же шум `interleaved_gradient_noise`, ось Y перевёрнута под `gl_FragCoord`). Нужен `highp` во фрагментном шейдере; без него шум выключается сам (`EffectiveDithering::UnavailableWithoutHighp`).

## Решения владельца (24 октября 2026, сессия 05)

30. **Кадр программного декодера возвращается в пул только после fence** кадра показа, в котором GPU его последний раз трогал.
    - Правило одно для копии (05), HW zero-copy (07) и SW zero-copy (12).
    - Освобождение «сразу после `glTexSubImage2D`» было бы корректно по спецификации, но в 12 один и тот же кадр `HostPlanar` может прийти и копией, и импортом. Единое правило не требует помнить, как использован каждый кадр.
    - Цена — слот пула декодера освобождается примерно на кадр позже.
    - Исполняет обёртка освобождения сессии 09.

## Решения владельца (25 октября 2026, сессия 06)

31. **HDR→SDR в GLES2 — таблицей 65³ везде, и только в GLES2.** Путь wgpu не меняется.
    - Точная формула wgpu в шейдере стоила на T410 39,7 мс GPU на кадр 1440×900 — больше бюджета 30 к/с. Таблица стоит 20,5 мс.
    - Таблица считает ту же формулу на CPU в `f64`. Отличие от точной формулы: худший случай 3/255, против wgpu в паритет-тесте — 2/255.
    - Вариант «обе, с автовыбором» отклонён: два пути и критерий «слабый GPU».

## Решения владельца (25 октября 2026, сессия 07)

32. **Кадр возвращается декодеру потоком-ожидателем внутри GLES2-рендера.**
    - Поток спит на fence кадра показа и отдаёт кадр, как только GPU его дочитал.
    - Приложение и цикл событий не меняются. Освобождение не зависит от следующего кадра интерфейса.
    - Вариант «будить приложение по таймеру» отклонён: детали рендера в приложении и пустые пробуждения на паузе.
33. **10-битный HW-декод (P010 DMA-BUF) в GLES2 не объявляется.**
    - GPU с аппаратным 10-битным декодом всегда тянет wgpu/Vulkan.
    - На GLES2 10 бит идёт программным декодом (сессия 06). Пункт 5 сессии 07 отменён.
34. **Выход приложения с HW-видео на T410 проверяется обязательно (общий бэклог, п. 13).**
    - Поток VA-API декодера сейчас не присоединяется при уничтожении — риск того же класса, что падение при выходе в сессии 07.
    - Проверка входит в приёмку сессии 09: серия выходов во время воспроизведения, оба режима окна.

## Решения владельца (25 октября 2026, сессия 09)

35. **Явный профиль + метка падения.** Пользователь сам выбрал `vulkan`, а прошлый старт этого рендера не дошёл до первого кадра. Тогда этот запуск один раз идёт на следующем годном кандидате (GLES2) с уведомлением, что настройка по-прежнему Vulkan. Настройка не меняется, следующий запуск снова пробует Vulkan. Причина: без этого человек застревает в цикле падений и не может добраться до настроек.
36. **Миграция конфига v23 → v24: `vulkan` → `auto` у всех.** Старый конфиг всегда пишет профиль явно, отличить выбор от умолчания нельзя. Прецедент — миграция v10 → v11 (`stop` → `skip`). На машинах с нормальным Vulkan Auto и так выберет wgpu. Значение по умолчанию — `auto`, `[render.opengles]` удаляется.
37. **Смена профиля применяется после перезапуска: строка «Applies after restart» и кнопка «Restart now».** Перезапуск идёт после полного штатного закрытия, когда замок single-instance отпущен. Очередь и позиция восстанавливаются существующим путём, пауза не сохраняется (прежнее поведение старта).
38. **Таблица HDR→SDR в GLES2 строится в фоне** (вопрос сессии 06). Старая таблица остаётся на экране, пока не готова новая. Самая первая таблица, когда старой нет, строится синхронно, как сейчас.
39. **Явный `vulkan`, а Vulkan на машине негоден** (только программный lavapipe, нет адаптера или рендер не создался): как в решении 35, этот запуск идёт на GLES2 с уведомлением, настройка не меняется. Раньше было фатальное окно «requires a graphics card with Vulkan support», и вернуть Auto можно было только правкой `config.toml` руками.
40. **Уведомление о выборе рендера — только при сбоях.** Обычный выбор Auto (нет аппаратного Vulkan → GLES2) проходит молча: его видно в панели телеметрии и в логе. Уведомление, которое висит до ×, появляется, когда прошлый старт упал, wgpu не создался или явный выбор невыполним (решения 35, 39). Причина: на старом железе GLES2 — нормальный режим, тост при каждом запуске только надоедал бы.
41. **Честный сигнал «рендер не умеет показать этот аппаратный кадр».** Раньше программный фолбэк запускался только сигналом «декодер прислал неправильное описание кадра», и отказ рендера GLES2 (драйвер не импортирует формат и т.п.) приходилось выдавать за ошибку декодера. Теперь в общем словаре кадра есть отдельная причина. Фолбэк прежний, но в логах и диагностике видна правда. Пригодится и будущему DX10.

## Решения владельца (25 октября 2026, после сессии 09)

42. **Отдельная сессия экстремальной оптимизации [12a](12a-extreme-optimization.md): обойти mpv и VLC с запасом, а не на уровне шума.**
    - Метод — как в геймдеве: сначала бюджет кадра и профиль, потом трюки против найденных статей расхода. Каждый трюк меряется «до/после» на T410 и доказывается тестом, бесполезный откатывается.
    - Строгий паритет (решение 7) остаётся. Трюки, которые меняют пиксели или поведение (пропуск deblocking, динамическое разрешение и т.п.), — только по отдельному решению владельца.

## Решения владельца (25 октября 2026, сессия 09b)

43. **Предупреждение «включите Dynamic» на GLES2 — только строкой в настройках** под выбором режима декода (как B6). Уведомлений при запуске нет: это продолжение решения 40.
44. **Отставание декодера считается на любой скорости воспроизведения.** На 2× и 4× рывки видны так же. Цена: файл, который однажды на ускорении ушёл на SW, остаётся на SW до конца, даже когда скорость снова 1×.
45. **Давние дефекты общего бэклога п. 12 (приложение не знает требование текущего видео) и п. 15 (T410, `hardware`, переоткрытие на EOF отвергается) чинятся в этой сессии обязательно**, отдельными шагами до режима Dynamic.
    - Уточнено в ходе сессии: п. 15 оказался не дефектом. На EOF очередь переходит к соседним HEVC/VP9 из той же папки, а режим «только hardware» их честно не берёт. Владелец решил закрыть пункт с объяснением, без правки кода.
46. **09b принимается при ≈51 из 60 кадров/с на программном 60 fps на T410.** Dynamic уводит такое видео с HW (13 кадров/с) на SW (51 кадр/с). Оставшиеся потери идут в загрузке и показе GLES2, не в декоде: детектор после перехода видит 0 % пропусков. Тот же результат даёт и чистый `software`. Дотянуть до 60 — задача сессий 11 и 12a.

## Решения владельца (26 октября 2026, сессия 10)

47. **Полная серия в обоих режимах окна**: нативный Wayland и XWayland, аппаратный и программный декод.

## Решения владельца (27 октября 2026, сессия 12)

59. **Путь «0 копий» — реализовать и проверить коротким замером**, а не отклонить и не отложить в 12a. Оценка стенда была −4…−7 % ядра на 1080p60. Замер — короткий, на батарее.
60. **Архитектура пути:**
    - вид памяти блоков декодера выбирает приложение по семейству рендера, как для VA-API: GLES2 → запечатанный memfd, wgpu → анонимная память (amdgpu `userptr` принимает только её);

61. **Порядок закрытия:** коммит кода → домер (XWayland, SW HEVC 1080p30, загрузка GPU) → отчёт и memories → коммит и push. Итог T410: CPU процесса −7…−8 п.п. на SW 1080p60, −4 на HEVC 1080p30, кадры и загрузка GPU те же (`results/12.md`).

## Решения владельца (27 октября 2026, сессия 12a, по итогам профиля)

62. **Трюки 12a:**

63. **Цель отрыва — реалистичная:**

64. **Лесенка: одна ступенька тяжелее**, чтобы развести ничью с VLC. Особое внимание — 0 пропусков у нас и экономичность.
65. **Давний дефект «слоты zero-copy импорта не растут вместе с пулом VA-поверхностей» чинится в 12a** отдельным фоновым исполнителем.

66. **Пул VA-поверхностей по умолчанию — 16 только на рендере GLES2.**

## Решения владельца (27–28 октября 2026, подсессия 12a.1)

73. **«В GPU не больше двух картинок декода» — на всех GPU и для всех кодеков.**
    - Причина пропусков 12a.1: после паузы (ключевой кадр) декодер заливал в GPU пачку из 5–7 картинок, и на Ironlake проход показа стоял в общей очереди за ней. Картинки, которые H.264 держит для перестановки B-кадров, не учитывала очередь «в полёте» 09a.
    - Правка в патче cros-codecs: `BlockingMode::SyncPreviousPicture` — отправив картинку k, декодер ждёт k−1.
    - Итог T410: HW 720p60 — 1 пропуск vsync за 20 с вместо 19–27, HW 1080p30 — 30,1 кадра/с без потерь. 780M не просел.
74. **Остаток на HW 1080p30 — подсессия [12a.2](12a.2-decode-present-phase.md).** 5–10 % кадров показываются на vsync позже (не теряются). Это одиночный декод, который случайно встал перед проходом показа. Идея — отправлять декод сразу после показа.
75. **Цена правки принимается:** +1 п.п. CPU на HW 720p. Корень — сброс кэша CPU (`drm_clflush_sg`) при отображении буферов драйвером i965, его стало больше, потому что GPU теперь чаще свободен. Давний сброс кэша i965 (~26 % потока декода ещё до правки) — тоже в 12a.2.
76. **Протокол v4 для 12a.1 не снимается.** В отчёт идут ABBA-замеры по трассе кадров, строгая квалификация — в сессии 14 (публикация; до перенумерации 28.10 — 13).

## Решения владельца (28 октября 2026, подсессия 12a.2)

77. **«Декод после показа» — в аппаратном декодере VA-API, а не в плеере.**
    - Рендер даёт нейтральный сигнал «проход показа отправлен на GPU» (`video_core::PresentPassSignal`, `RenderShell::present_pass_signal`).
    - Если у декодера есть запас кадров, следующую картинку он подаёт только после этого сигнала. В очереди GPU получается «показ → декод».
    - Условие владельца: wgpu не ломать. wgpu сигнала не даёт, и декодер под ним работает как раньше.
    - Причина. Трасса T410 показала, что на HW 1080p30 декодер работает почти без пауз: GPU у Ironlake декодирует чуть быстрее 30 к/с. В очереди GPU почти всегда стоит картинка декода (~27 мс), и проход показа ждёт за ней. Временная сборка дала 0 опозданий за 20 с вместо 34–40.
78. **Такт включается везде, где рендер GLES2**, без проверки «общая ли очередь GPU»: надёжно узнать это без имени видеокарты нельзя. Одно правило, как в решении 73.
79. **Метрика каденса — колонка анализатора** (`docs/benchmarks/tools/local/cadence.py`): опоздавшие новые кадры (интервал больше 1,5 номинала). Quality-gate протокола v4 не меняется. У mpv и VLC такого потока событий нет.
80. **Сброс кэша i965 принимается, причина записана.**
    - Драйвер сам выделяет и отображает в память CPU три батч-буфера по 512 КиБ и таблицу макроблоков (~1 МиБ на 1080p) на каждую картинку.
    - Когда GPU свободен, libdrm отдаёт из кэша буфер, который GPU уже трогал, и ядро сбрасывает кэш CPU для всего объекта (на Ironlake нет общего кэша CPU и GPU).
    - Со стороны плеера уйти от этого можно, только держа GPU занятым, а это противоречит решению 77. Правка системного драйвера — не наш путь.
81. **Поиск кадра VA-API ждёт замок пула ресурсов не дольше 250 мкс**, а не сдаётся с первой попытки. Правило общее для всех рендеров, включая wgpu.
    - Причина. С тактом (решение 77) декодер просыпается ровно тогда, когда приложение выбирает следующий кадр. Его микросекундные участки под замком стали совпадать с поиском. Ответ «занято» превращался в повтор кадра и потом в пропуск: на 780M 1–3 пропуска за 20 с на 1080p60 в GLES2.
    - С ожиданием до 250 мкс — 0 ответов «занято» и 0 пропусков. Если замок занят дольше, ответ по-прежнему «занято».

## Решения владельца (28 октября 2026, после подсессии 12a.2)

82. **Новая сессия 13: программный AV1 без копии на обоих путях Linux.**
    - Обёртка dav1d в FFmpeg (`libdav1d.c`) не объявляет `DR1` и берёт память из своего пула, поэтому AV1 — единственный программный кодек, который всё ещё копируется.
    - Чиним маленьким патчем закреплённого FFmpeg. Цель владельца: на Linux все пути без копии.
    - Проверка в 13 — только на основной машине, в обоих рендерах (GLES2 и wgpu).
83. **Патч FFmpeg оформляется ради надёжной сборки и простой миграции:**
    - один маленький unified diff рядом с закреплённой версией;
    - строгое применение без fuzz, понятная ошибка сборки, если патч не лёг;
    - SHA патча в штампе сборки;
    - запись в inventory с чек-листом миграции.

    Чем накладывать (GNU `patch`, `git apply` или свой применятель) — решение владельца в начале 13.
84. **Сессия 13b — полная живая проверка AV1 на T410 и T480.** У обеих машин нет аппаратного AV1; на T480 владелец ждёт очень большую отдачу.
85. **Сессия 13a — все остальные программные кодеки без копии на wgpu** на основной машине: матрица путей, тесты, сравнения с копией и mpv.
86. **Публикация переезжает в сессию 14.** Ссылки «сессия 13» в решениях 71, 76 и отчётах до 28.10.2026 означают публикацию / строгую квалификацию, то есть теперь сессию 14.

## Решения владельца (28 октября 2026, сессия 13)

87. **Патч FFmpeg накладывает системный GNU `patch`** — строго (`--fuzz=0 --forward`), после пробного прогона.

## Решения владельца (28 октября 2026, сессия 13a)

88. **Плеер не открывает программные 12 бит и 4:2:2/4:4:4 — в глобальный бэклог, в 13a не делаем.**
    - Что не открывается: HEVC Main12 / 4:2:2 / 4:4:4, VP9 12 бит / профили 1 и 3, AV1 High 4:4:4.
    - Причина: старые ворота `codec-core` («v1 zero-copy path», «Phase 9»).
    - Декодер и рендер wgpu эти раскладки уже принимают, тесты 13a доказывают путь без копии.
    - Это новая возможность для пользователя, а не вопрос копии. Запись — `user/general_problems/general_backlog.md`, п. 18.
89. **10 бит без цветовых тегов рисуется как SDR BT.709** (как 8 бит и как mpv).
    - Раньше FFmpeg отдавал цвет кадра «unspecified», декодер считал его настоящим, запасной SDR не включался, и рендер 10/12 бит падал фатальной ошибкой.
    - Теперь «неизвестны матрица, праймериз и передача, HDR-данных нет» = цвета нет. Известный диапазон кадра сохраняется.
    - Неполный HDR по-прежнему отвергается.
    - Итог сессии: все программные раскладки, которые плеер играет, идут на wgpu без CPU-копии. Принудительная копия дороже на всех 7 сценах: процесс −2…−19 п.п., главный поток −27…−62 % (`results/13a.md`).

## Решения владельца (28 октября 2026, сессия 13b)

90. **Метод 13b: протокол v4 на T410 и T480s параллельно, на T410 оба режима окна полностью, бюджет — до 2 часов.** Главного потока в v4 нет, поэтому «копия против без копии» дополнительно снята короткими ABBA-прогонами.
91. **Повторный показ кадра в GLES2 чинится в самой сессии.**
    - Находка: путь без копии на повторе уже текущего кадра заново сбрасывал кэш CPU и считал кадр ещё раз.
    - Итог: на T410 главный поток −5 % на 1080p30, счётчик пути кадра равен числу новых кадров.
92. **«Seek за последний кадр — плеер встаёт навсегда» чинится в самой сессии**, с выходом за бюджет 2 часа.
    - Давний дефект, не связанный с путём без копии: сборка без патча dav1d ведёт себя так же.
    - Найден живым жизненным циклом 13b.
    - Корень шире AV1: время показа вели только аудиочасы. Когда звук кончался раньше видео (или пропадал посередине), картинка застывала, и файл не заканчивался.
    - Правка: пока звука нет, время ведут монотонные часы, переход только по доказательству из контейнера, звук возвращается на своём PTS. Исполнитель — Opus, по слову владельца. Живая проверка: основная машина, затем (после отключения света) финальная сборка на T410 и T480s — все случаи доходят до конца файла и следующего в очереди.

### Инварианты (нарушать нельзя)

- **HW-путь — zero-copy**: ни readback, ни CPU-конверсии, ни повторной загрузки аппаратного кадра. Если импорт DMA-BUF невозможен, GLES2 честно не объявляет контракт `HardwareZeroCopy` → `auto` уходит в программный декод, а не в тихую копию.
- **SW-путь — не больше 1 копии** (один `glTexSubImage2D` на плоскость кадра). Никакой промежуточной CPU-переупаковки. Без `GL_EXT_unpack_subimage` — загрузка «текстура шириной в stride + обрезка в шейдере», а не построчный repack.
- **Кадр декодера освобождается только после того, как GPU закончил его читать** (EGL fence), ровно один раз. Освобождение не зависит от того, нарисует ли UI следующий кадр (рендер по изменению из cpu-parity 04 может спать).
- **`RenderCapabilities` GLES2 выводятся из реально найденных возможностей драйвера.** Нет highp — нет 10-бит/HDR-контрактов. Нет импорта DMA-BUF — нет zero-copy. Честное «не поддерживается», а не чёрный экран.
- **Ограниченные пулы**: кольцо загрузки и кэш EGLImage ограничены и согласованы с пулом поверхностей декодера (как `DmaBufImportCacheCapacity::matching_surface_pool`). Без небоундед-роста.
- **Поведение wgpu-пути не меняется**. Сессии 01–02 — чистый рефакторинг шва с замером «до/после» и quality-gate.
- Переиспользуемые crate-ы (`gles2-egui`, `gles2-video`) не зависят ни от одного crate-а плеера. Это проверяет `scripts/check-refactor-guardrails.py`.
- egui-контракт: premultiplied alpha, смешивание в гамма-пространстве, текстуры не sRGB, `ONE, ONE_MINUS_SRC_ALPHA`, `CLAMP_TO_EDGE` (так делает egui-wgpu и так требует egui).

### Уровни возможностей GLES2 (определяются на старте, а не по имени GPU)

| Уровень | Требует | Даёт |
|---|---|---|
| Базовый (обязательный) | GLES 2.0, EGL 1.5 (решение 26), NPOT-текстуры с clamp без mip (ядро GLES2), `GL_LUMINANCE` | интерфейс, SW 8-бит 4:2:0/4:2:2/4:4:4, субтитры, углы |
| Точность | `GL_FRAGMENT_PRECISION_HIGH` | SW 10/12-бит, HDR→SDR BT.2446-C |
| Zero-copy | `EGL_EXT_image_dma_buf_import` + `GL_OES_EGL_image` + импорт `DRM_FORMAT_R8`/`GR88` | VA-API NV12 без копий |
| Zero-copy 10-бит | то же + импорт плоскостей P010 как `GR88`/`ABGR8888` (сборка 16 бит в шейдере) | VA-API P010 (на Ironlake не нужен: нет 10-бит декода) |
| Удобства | `GL_EXT_unpack_subimage`, `GL_OES_element_index_uint`, `GL_OES_vertex_array_object`, `EGL_KHR_fence_sync`, `EGL_EXT_buffer_age` | меньше вызовов; без них — описанные фолбэки (u16-батчи egui, `glFinish` перед освобождением с явным счётчиком) |

Проверено в сессии 00:
- **T410 (crocus):** базовый, точность, zero-copy и удобства — все есть. Zero-copy 10-бит не нужен: на Gen5 нет 10-битного декода.
- **780M (radeonsi):** все пять уровней, включая P010 через GR88 + ABGR8888.
- **Сессия 03 (`gles2-egui`, живой вывод):** на T410 и 780M доступны все пять уровней. crocus отдаёт и ABGR8888 как `sampler2D`, но на Gen5 нет 10-битного декода. Уровни выводит `Gles2Capabilities::tiers()`.
- **Важно для тестов:** radeonsi и llvmpipe на запрос «GLES 2» отдают контекст **ES 3.2**. Поэтому уровни выводятся только из ES 2.0 + строк расширений, а возможности ES3 не используются даже там, где они есть (сессия 03).

### Как не повторять рефакторинг под Windows/DX10

- Контракт `render-shell-api` не содержит ни одного типа wgpu/GL/Linux. Импорт кадров идёт через `video-present-core::VideoFrameLease` и нейтральные `video-core`-дескрипторы. Новые виды аппаратных кадров (DXGI) добавляются как новые варианты нейтрального словаря `video-frame-contract`, а рендер объявляет их в `RenderCapabilities`.
- Окно передаётся через `raw-window-handle` (работает и для HWND).
- Каталог рендеров — данные платформы (`#[cfg(target_os)]`-список кандидатов), а не `if` в приложении.
- Тесты контракта (`render-shell-api` conformance-набор с fake-рендером + одинаковые пиксельные тесты для каждого реального рендера) пишутся один раз и прогоняются для каждого семейства.

## Общие правила для всех сессий

Работай в корне checkout-а репозитория. Сначала `AGENTS.md`. Перед кодом:
- Serena `initial_instructions`, активация проекта, `mem:core`, `mem:gles2-renderer/core`, `mem:render-video/core`, `mem:task_completion`, `mem:conventions`, `mem:testing/sandbox_policy` и memories из файла сессии;
- Context7 для каждой затрагиваемой внешней библиотеки (`glow`, `khronos-egl`, `wayland-egl`, `raw-window-handle`, `egui`/`epaint`, `winit`, `wgpu`). Для EGL/GLES-расширений источник истины — спецификации Khronos (registry.khronos.org), ссылки на номера разделов в комментариях;
- широкий поиск по репозиторию — read-only субагентом (модель Sonnet), основной агент читает только точные символы;
- перед реализацией — короткое описание архитектуры: владелец состояния, boundary-методы, инварианты, тесты (правило 9 `AGENTS.md`). Если всплывает решение, меняющее ownership/lifecycle или поведение для пользователя, — **стоп, вопрос владельцу**.

Тесты (тест проверяет результат, а не вызов):
- каждый путь рендера — пиксельный тест с readback из offscreen-цели (EGL surfaceless/pbuffer на Mesa: на машине разработчика и в CI через llvmpipe). Проверяются известные цвета, позиции, смешивание. Пропуск теста без EGL — с явной причиной в выводе, не молча;
- **кросс-рендерный паритет**: один и тот же вход (egui-кадр, YUV-кадр, оверлей субтитров) рисуется wgpu и GLES2, пиксели сравниваются с допуском и с объяснением любого расхождения;
- для каждого нового boundary/API — focused-тесты: отсутствующий ресурс, активный fake, ошибка, edge-accounting, «метод не трогает чужое состояние»;
- функциональные тесты: видео из фикстуры доходит до стадии показа через GLES2 (а не «декодер открылся»);
- оптимизации — тестом, который падает без фикса (счётчик загрузок/импортов/draw-call-ов, а не «функция вызвалась»).

Замер — обязательная часть каждой сессии с кодом рендера (с 04 и дальше):
- на основной машине в режиме GLES2: `docs/benchmarks/tools/dev/run_pass.py` до и после, `agg_timing.py` по стадиям кадра; сравнивать только в один день с чередованием;
- с сессии 11 — те же сцены на T410;
- запрещено сравнивать разные сцены, окна разной длины, debug с release.

Quality-gate (ничего не сломать):
- wgpu-путь: уникальные кадры, `drops_*`, RSS/PSS, CPU — без изменений относительно базы дня (сессии 01, 02, 09 проверяют это явно);
- GLES2-путь: ≥ 99 % уникальных кадров от «fps × окно» (как протокол v2), A/V-синхрон, seek/scrub/pause/resume/смена файла/resize/фуллскрин вручную на двух файлах (HW и SW);
- `scripts/ci-checks.sh all` зелёный, существующие тесты не ослабляются, Vulkan validation layer и `KHR_debug` (где есть) без новых сообщений.

Код:
- новая логика — у владельца состояния. Файлы ≥ 700 строк не раздувать (hard limit 800, ratchet `scripts/module-size-baseline.json`). Особенно не расти `app-egui/src/frame_prepare.rs` (1467, legacy) и `app_shell/mod.rs` (798);
- boundary API самодокументирующиеся (enum/newtype/intent-method), absent / busy / fatal / no-op / unsupported не сливаются в `bool`;
- `unsafe` (EGL/GL FFI, fd) — в отдельных модулях безопасности с `// SAFETY:` и hermetic-тестами владения fd, по образцу `render-wgpu-video/src/dma_buf_import/safety.rs`;
- без `unwrap/expect/panic` в production (`mem:panic-invariant-policy`). Ошибка компиляции шейдера, отказ драйвера, потеря контекста — типизированные ошибки;
- русская документация ключевой логики и инвариантов;
- в `user/` только Markdown, без личных путей, имён хостов и логов. Сырые логи, профили, дампы `eglinfo` — в scratchpad (в отчёт — выжимка).

Отчёт сессии `results/NN.md`: статус, решения владельца, SHA базы и итога, что изменилось (файлы/символы), причина каждого найденного дефекта, тесты, замер «до/после» (если был код рендера), что проверено вручную, известные ограничения, обновлённые memories.

## Удалённая работа с T410

- Доступ: ssh-алиас `t410` в `~/.ssh/config` владельца (имя хоста и пользователь в план не пишутся). Сессия 00 проверяет `ssh t410 true`, Mesa, ядро, композитор и права на `/dev/dri/renderD128`, `/dev/udmabuf`.
- Система T410 (со слов владельца, 23.10.2026): свежая установка, графическая сессия **Wayland**.
- **Решение владельца (23.10.2026): тестируем в обоих режимах — нативный Wayland (EGL `wl_egl_window`) и XWayland (EGL X11).** Это касается ручной приёмки, пиксельных/функциональных тестов окна и квалификации против mpv/VLC на обеих машинах. Под XWayland протокол v3 уже запускает плееры. Соперники в каждом режиме тоже идут в одном и том же режиме, режимы не смешиваются.
- Сборка: на основной машине (`x86_64`, тот же дистрибутив — бинарник совместим; иначе собирать на T410), доставка `rsync` бинарника + `target/release/lib/` (свой FFmpeg, RUNPATH `$ORIGIN/lib`).
- Запуск GUI по ssh — в живой графической сессии T410 (`DISPLAY`/`WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR` пользователя), замеряющие скрипты работают **на самом T410**, артефакты забираются обратно. Удалённой оркестрации в `docs/benchmarks/tools` сейчас нет — её добавляет сессия 11 (тонкая обёртка, не переписывание протокола).
- Грабли разведки 00:
  - оболочка входа на T410 — fish, составные команды запускать через `bash -c` или скриптом;
  - `XAUTHORITY` = `/run/user/1000/xauth_*`, имя меняется после перезагрузки;
  - перед замером проверять, что экран не заблокирован (`loginctl … LockedHint`): под блокировкой окна не видны. Разблокировку и отключение автоблокировки делает владелец;
  - rc-интерфейс VLC печатает по-русски, плееры запускать с `LC_ALL=C.UTF-8`;
  - **стоп-кран обязателен**: рост числа `GPU HANG` в `journalctl -k` останавливает серию. Неустранимое зависание лечится только перезагрузкой, её делает владелец.

## Инструменты диагностики

- `docs/benchmarks/tools/dev/{thread_cpu.py,run_pass.py,agg_timing.py}` — быстрые срезы (CPU по потокам, GPU по fdinfo, стадии кадра).
- `docs/benchmarks/tools/local/` — строгий протокол v3 (cgroup, чередование, quiet/diagnostic, quality-gate). Привязан к KWin/XWayland/amdgpu: имена движков `gfx`, память `drm-memory-gtt/vram`. Адаптирует сессия 11. На Ironlake fdinfo i915 отдаёт только `drm-resident-system0` (без `drm-engine-*`), загрузку GPU даёт только `intel_gpu_top` от root (глобально).
- `docs/benchmarks/tools/local/make_matrix.py --preset t410` / `--preset t410-hdr` — фикстуры T410 (`test-assets/benchmark-t410*/`, вне git), список сцен — `results/00.md`.

## Бэклог (не в этом плане)

- **Аппаратный MPEG-2 через VA-API** (решение владельца: по замеру программного MPEG-2 на T410 в сессии 11). Это работа декодера (`video-vaapi`, в cros-codecs MPEG-2 нет), а не рендера. Данные 00: кремний Ironlake декодирует MPEG-2 1080i со скоростью 111 кадров/с; VLC через HW играет 1080i за 61 % CPU, лучший SW у соперников — 72–117 % (деинтерлейс у плееров разный).
- **Dynamic: возврат на HW внутри файла** (когда нагрузка спала) — после первой версии 09b, решение владельца.
- **Прямой показ полноэкранного буфера без копии композитора (direct scanout)** — не требование. Решать по замеру нагрузки KWin в сессиях 10/11: на HW 1080p30 после декода у GPU остаётся ~8 мс на кадр, композитор берёт ~3. Кандидат каталога сессии 12a.
- **Эксперимент: программный кадр в YUYV на sprite-плоскость Ironlake** (0 работы GPU на видео). Конфликтует со строгим паритетом (цвет, HDR, субтитры поверх). Только как идея, без сессии.
- **Windows: wgpu (DX12/Vulkan) и свой рендер DirectX 10.** Шов из сессий 01–02 спроектирован под них; сами рендеры — отдельные планы.
- **Частичный показ** (`EGL_KHR_swap_buffers_with_damage`/`EGL_KHR_partial_update`) для кадров, где меняется только интерфейс. Перенесено в каталог сессии 12a: находка 09 — на HW 1080p30 T410 ~15 кадров/с «только интерфейс» заново рисуют видео целиком.
- **Меньшие пулы по умолчанию для слабого железа** (`video.zero_copy_surface_pool_slots = 24` ≈ 75 МБ NV12 1080p в общей памяти). Решать по замеру памяти сессии 11, решение владельца; кандидат каталога сессии 12a.
- **EGL 1.4 через `EGL_EXT_platform_base`** (решение 26): только если найдётся живое железо/драйвер без EGL 1.5.
- **Общий `EGLDisplay` с другими пользователями EGL в одном процессе** (найдено в сессии 04). Mesa отдаёт один display на платформу, и `eglTerminate` одного пользователя (наш реестр после последнего контекста, GL-бэкенд wgpu при своём разрушении) гасит display под другим. В Mesa нет `EGL_KHR_display_reference`. В плеере конфликта нет: wgpu-шелл работает только через Vulkan, а GPU-тесты шелла переведены на тот же Vulkan-instance. Для встраивания в чужое приложение с EGL (Fasticut с GL-бэкендом wgpu, mpv render API) — решать до публикации crate-а: например, режим «не завершать display».
- **Linux-путь `TILING_LINEAR` в wgpu-импорте DMA-BUF** (`mem:render-video/core`, известный дефект) — не трогаем в этом плане.
